# 실험실 사전 스트레스 검증 — 확정 정책과 설계 제안

2026-09-27 KST. 사용자는 스킬 자동 취소 제거를 요청했고, 실험실에서 500–1,000 유닛을 소환해 스킬을
시험한 뒤 임계점 초과 시 스킬 빌드를 거부하는 방안을 제안했다. 자동 취소 제거는 반영했다.
아래는 사용자 확정 정책과 검토자의 설계 제안을 구분한 기록이다. 시험 profile·정식 인수 기준·상세 등록 절차 확정이나 구현 완료는 아니다.

이 문서는 확정 정책의 원본을 유지한다. 작업 범위·선행·잠정 순서는 [별도 로드맵 편입안](../../roadmaps/mod_validation_safety/ROADMAP.ko.md),
기존 R 순서와의 연결 이유는 [의존성 검토](../../roadmaps/mod_validation_safety/DEPENDENCY_REVIEW.ko.md)에서 관리한다.

후속 사용자 정정: **실험실은 모드 제작자를 위한 도구이며, 스킬 추가는 모드 추가로 취급한다.** 사용자가 제안한 첫 실행/레지스트리 변경 시
자동 검증·캐시 재사용을 상세 계획에 반영할 대상으로 삼는다. 추가/삭제 외 내용·종속 데이터·엔진·검증 규칙 변경의
캐시 무효화와 게임 시작/실게임 진입의 차이는 후속 설계에서 구체화한다.
**20분 검증은 모든 현재·후속 단계에서 제외**하며, 장기 시험은 기반 마련 뒤 사용자가 직접 수행한다.

## 판단

실험실 검증은 **모드의 본편 적용 전제**다. 실패한 모드는 본편에 적용하지 않는다.
레지스트리 전체를 일괄 거부하자는 앞선 추천은 채택되지 않았다. draft 저장·편집·진단 실행은 허용한다.
여기서 빌드 거부는 Rust 프로그램 빌드 거부가 아니다.
“정해진 지원 조건에서 검증된 콘텐츠”라고 표시한다. 유한한 시험을 모든 실제 전투의 비용 상한 증명으로 쓰지 않는다.

## 사용자 확정 정책 — 2026-09-27 후속 답변

1. **거부 단위는 모드**다. 실패 모드의 일부 스킬만 적용하거나, 무관한 정상 모드를 함께 불합격 처리하지 않는다.
2. **검증 주체는 core 실행 주체**다. 로컬 core는 로컬에서, 서버 core는 서버에서 검증하고 그 실행 주체가 관리하는 결과를 사용한다.
   별도 중앙 인증 서비스를 전제로 하지 않는다. 모드가 동봉한 PASS나 다른 실행 주체의 캐시를 그대로 승인 근거로 쓰지 않는다.
3. **저사양 예외를 두지 않는다.** 사양이 낮다는 이유로 기준을 낮추거나 실패를 통과로 바꾸지 않는다.
   저사양을 배려해 시간·실측 메모리를 항상 경고로만 쓰자는 앞선 추천은 철회한다.
   성능도 확정된 시험 기준의 차단 항목이 될 수 있다. 단, 이 답변이 구체적인 시간·메모리 숫자나 단일 표본 판정을 확정한 것은 아니다.

기존 R06의 약9MB 회귀 기준을 경고로 전환한 결정은 별개이며 되돌리지 않는다.
검증 미완료·실행 오류는 승인하지 않되, 측정된 기준 초과와 구분하여 보고한다. 저사양에 대한 통과 예외는 없다.

### 실패 시 동작 — 추가 사용자 확정

2026-09-27 현재 대화에서 아래 세 가지 추천안에 사용자가 “응.”으로 동의했다.

1. **개별 통과 모드의 조합에서만 실패하면 해당 조합의 적용을 보류한다.** 실패한 조합을 안내하고 사용자가 구성을 변경하게 한다.
   임의로 모드 하나를 선택해 제거하지 않는다. 개별 통과 기록은 유지하되 실패 조합의 승인 근거로 사용하지 않는다.
2. **불합격으로 제외된 모드가 기존 세이브에 필요하면 해당 세이브의 로드를 차단한다.** 필요한 모드를 안내하고 원본 세이브를 보존한다.
   호환되는 세이브와 새 게임은 이용할 수 있게 한다. 누락된 스킬·아이템을 자동 삭제하는 복구는 이번 범위에 포함하지 않는다.
3. **실제 전투에서 runtime 안전장치에 걸리면 해당 전투를 오류 상태로 중단하고 진단 정보를 남긴다.**
   게임 프로그램 전체 종료나 특정 스킬 자동 취소로 처리하지 않는다. 오류 전투의 결과를 정상 결과로 반영하지 않는다.

위 내용은 목표 동작의 확정이며 현재 코드의 구현 완료를 뜻하지 않는다. 전투 중단의 host 전달, 복원 지점,
결과·보상·저장 반영 차단 경계는 후속 코드 검토로 구체화한다. 이전 상태 전체 복원이나 전투 재시작 가능성을 미리 보장하지 않는다.
구체적인 성능 합격 수치는 대표 시험·측정 방식과 근거를 마련한 뒤 제안한다. 저사양 예외와 20분 시험은 추가하지 않는다.

## 모드 적용 경계 — 코드에 근거한 설계 방향

[PackManifest](../../../src/game/data/content_pack/schema.rs)는 pack_id·dependencies·Replace/Remove 정보를,
[resolver](../../../src/game/data/content_pack/resolver.rs)는 의존성·writer 선택 검증을 이미 제공한다.
이를 재사용한다. 사용자 모드 하나와 pack 여러 개의 매핑은 상세 설계에서 확인하며 pack 하나가 반드시 모드 하나라고 단정하지 않는다.

- 시험용 후보 구성을 로드하되 검증 완료 전 본편에 공개하지 않는다. 현재 load의 정적 유효성 토큰과 스트레스 승인 기록은 구분한다.
- 실패 모드를 제외하면 그 모드를 필수로 요구하는 모드도 적용 보류한다. 이는 별도 성능 불합격이 아니라 의존성 미충족이다.
- 제외 후 남은 구성의 참조·writer 선택·유효성을 다시 확인한다. 실패 모드의 교체/삭제 결과를 남겨 둔 채 계속하지 않는다.
- 검증·캐시는 실제로 적용할 구성에 결속한다. 개별 통과 기록만으로 서로 다른 조합을 승인하지 않는다.
- 조합 실패와 필수 모드가 누락된 세이브의 동작은 위 확정 정책을 따른다. 의존성·세이브 호환성 판별 방법은 상세 설계에서 확인한다.
  정상 개별 모드의 실패 기록으로 전파하거나, 저장 데이터를 자동 삭제·변환하거나, 참조가 깨진 상태로 진행하지 않는다.

현재 loader에는 스트레스 승인 게이트가 없으므로, 실행 주체 선택을 재사용할 수 있어도 시험 실행·캐시·본편 적용 연결은 구현이 필요하다.

## 재사용할 현재 코드

- [authoring CLI](../../../src/bin/author_content.rs)에 validate/describe/explain/simulate가 있다.
- [TrialSession](../../../src/authoring/trial.rs)은 prepare/advance/run_to_end, content identity, input hash,
  typed failure와 receipt를 제공한다. 같은 실제 실행 경로에서 시나리오·보고서를 재사용하는 방향이다.
- [ScenarioLimits](../../../src/authoring/scenario.rs)는 단계/clock 제한이 있다. 기본 max_steps256,
  max_clock_delta60,000ms, max_total_clock3,600,000ms지만 이 수치만으로 모든 부하 profile의 실행 가능을 주장하지 않는다.
  trial 전체 work·receipt와 실제 작업 비용도 검토해야 한다.
- 이 조사는 공개 시험 포트의 재사용 가능성을 확인한 것이다. 실험실 UI의 버튼·500/1,000 생성 adapter나
  시험 통과→실게임 등록 차단 연결은 구현되어 있다고 확인한 바 없다. 제품 private fixture만으로 완료하지 않는다.

## 권장 시험 구성

1. 스킬 catalog의 정적 검증: 수식 유한성·깊이·owner/context·참조·checked cost. 기존 검증을 재사용한다.
2. 표준 stress profile: 일반/500/1,000 유닛, 조밀/분산 배치, 단일 시전/반복 시전/다중 시전자,
   projectile·area·buff·proc·사망 연쇄 등 해당 스킬의 실제 경로가 실행되도록 한다.
3. 대표 조합 profile: 개별 스킬 통과만으로 다수 스킬 조합을 보증하지 않는다. 실제 동시 시전자 조건과
   알려진 조합을 별도로 확인한다. 무한 조합 전수검사나 장시간 실행을 등록 조건으로 요구하지 않는다.
4. 같은 seed/config의 repeat와 결과 identity로 재현성을 확보한다. 필요한 실제 시전·적중·effect count를 확인한다.
   유닛을 많이 놓았지만 스킬이 발동하지 않거나 target이 없는 실행을 PASS로 세지 않는다.

500/1,000은 시험 부하 후보이지 모든 스킬이 1,000명을 실제로 공격해야 한다는 게임 규칙이 아니다.
정식 유닛/동시 시전 지원 범위와 baseline fixture 자체의 비용을 먼저 정한다.
setup만으로 한도를 넘으면 **profile 실행 불가/환경 문제**로 분리하고 아직 실행되지 않은 스킬의 결함으로 판정하지 않는다.

## 판정과 기록

결과는 PASS / 콘텐츠 실패 / 시험 미완료·환경 실패를 구분한다. 후자의 경우 사용 승인은 보류하지만
스킬의 문제라고 단정하지 않는다. 정해진 hard safety 오류·결정론 위반은 실패다.
실측 memory/time 임계값은 representative baseline·지원 환경·정해진 반복 방식과 여유를 바탕으로 수립한다.
저사양에 따른 기준 완화는 하지 않는다. 반복·측정 구간·집계 방식은 상세 설계에 명시하여 판정을 재현할 수 있게 한다.
성능 차단 수치는 대표 측정 근거로 정하며, 기존 약9MB 회귀 기준을 새 모드 검증 한도로 복사하지 않는다.

검증 기록에는 스킬 및 종속 데이터 identity, 실제 engine/compiler 버전, effective safety profile,
시험 suite/scenario/seed·환경, 실제 경로 coverage와 raw 결과를 결속한다.
게임/데이터/한도/지원 조건이 바뀌면 영향받는 검증을 무효화·재시험한다. 변경 없는 입력은 근거가 맞는 결과를 재사용한다.
실게임 등록 시 현재 artifact와 검증 기록의 결속을 확인하며, 임의 클라이언트가 제출한 PASS 문자열을 신뢰하지 않는다.

## 실제 게임에 남길 것

기존 유한 작업량·메모리 admission·event 제한·오류/rollback은 최후 방어로 유지한다.
설계 목표는 정상 승인 콘텐츠가 그 경계에 도달하지 않는 것이다. 조합·환경 차이나 버그가 발생해도
사전 시험 PASS만으로 runtime 검사를 생략하지 않는다. 초과를 스킬 자동 취소로 바꾸는 기능은 만들지 않는다.
안전 오류의 사용자 동작은 위 확정 정책에 따라 해당 전투 중단으로 연결하며, 기존 복원 경계와 host 결과 반영 경로를 검토한다.
관측은 승인 profile과 실제 사용량 차이 및 새 문제의 재현 정보를 제공한다.

위 사용자 결정에 따라 S3의 콘텐츠 측정을 모드 승인 절차로 확장하는 상세 계획을 작성한다.
S1/S2 설정/메트릭 재사용은 유지하고, 새로운 등록 게이트를 R06에 조용히 추가하지 않는다.
