# 의존성과 작업 준비도

계획 v2.1 · 2026-09-09 · **아래 목록은 계획상 선행 후보이며, 실제 코드 의존성 전수 검토나 확정된 실행 순서가 아니다.**

이번 개정은 v2.0의 후보 edge를 추가·삭제·재배열하지 않았다. 현재 구조를 참고한 설계 판단과 실제 구현 준비를 구분한다. 모든 선행을 단순한 기능 이름으로 확정하거나, 미검토 관계를 증거 없이 불필요하다고 지우지 않는다.

## 1. 세 가지 서로 다른 판단

| 판단 | 근거와 소유자 | 이것만으로 주장할 수 없는 것 |
| --- | --- | --- |
| 계획상 순서 | 이 로드맵·CA 카드·GOALS.json의 후보 관계와 권장 구조 | 실제 호출 의존·최소 작업 경계·실행 가능성 |
| 코드 검토 기반 순서 | 선택 범위의 P2G-20 Code Review와 P2G-40의 의미 검토·Phase Plan·필수 구조 검증 | 선행 기능이 이미 구현·검증·감사되었다는 주장 |
| 실제 실행 준비 | GEX 인수의 exact Handoff·Goal, 선행 결과·current 감사·관련 코드/데이터·권한 | 다른 Topic·전체 로드맵의 준비 완료 |

이는 세 개의 새 상태나 승인 Gate가 아니라 기존 근거의 **증거 수준을 설명하는 구분**이다. 현황에는 해당 범위와 원본 링크만 요약한다. 구조 검증기의 graph/cardinality 성공과 의존 이유의 의미적 타당성도 구분한다.

## 3. 관계마다 확인할 내용

| 관계 | 실제로 답할 질문 | 기록할 근거 |
| --- | --- | --- |
| 기능상 필수 선행 | 후행의 어느 세부 작업이 선행의 어떤 API·상태·결과를 소비하는가? 기존 기능으로 충족되는가? | 생산자/소비자 파일·심볼, 현행 계약과 승인 목표 delta |
| 함께 전환해야 하는 관계 | 나누면 authority·원자성·스키마·저장·장착·결과가 불일치하는가? | reader/writer·transaction·수명, 분리 시 깨지는 경계 |
| 검증을 위한 선행 | 독립 완료를 무엇으로 관찰하며, 그 seam이 현재 존재하거나 누가 만드는가? | 실행 진입점·fixture·검사 방법·구현/검증 owner |
| 진행상 권장 순서 | 반드시 먼저일 필요는 없지만 위험·중복·통합 비용을 줄이려는 선택인가? | 선택 이유·대안·실제 필수 edge와의 구분 |

이 네 분류는 P2G-40의 기존 dependency type/reason에 사용하는 설명 관점이다. 닫힌 enum이나 별도 필수 artifact를 추가하지 않는다. 파일 충돌은 작업 조정 사유일 수 있지만 runtime 필수 선행을 자동 증명하지 않는다.

선택 범위의 관계에는 **선행 결과와 후행 소비 지점, 의존 유형, source revision·관련 dirty 근거, 무시했을 때 깨지는 상태/완료 주장, 유지·세분화·통합·대체 판단과 이유**를 남긴다. 아직 확인하지 않은 것은 unknown으로 남기고, 기존 구현이 조건을 충족하면 새 CA 전체를 중복 수행하지 않는다.

## 4. 언제 얼마나 조사할 것인가

최초 인수·CA00에서는 loader/작성 정의/행동 실행/상태·사본/보스/저장 등 주요 공유 경계에서 큰 누락·역전·과잉 선행 후보를 살핀다. 이것은 24개 작업의 모든 함수를 전수 분석하거나 후반 설계를 전부 동결하는 작업이 아니다. 다음 후보의 직접 관련 경계와 미확인 부분을 구분한 조사 결과를 남긴다.

실제 Topic을 Goal화할 때 P2G-20이 그 범위의 생산자→검증→실행→수명/결과·저장→소비자·테스트를 확인하고, P2G-40이 그 근거로 Work Package·Atomic Group·Phase와 순서를 정한다. 미래 Phase의 결과가 아직 구현되지 않았다는 사실 자체는 계획 작성 금지가 아니다. 다만 그 결과의 의미·생산자·검증 owner를 정의하고, 존재하지 않는 현재 API나 실행 증거로 취급하지 않는다.

선택한 다음 범위의 필수 근거와 실행 전제가 닫히면 그 범위를 진행할 수 있다. 관계없는 후반의 미검토 edge 때문에 전체 개발을 정지하지 않는다. 현재 범위의 유효성을 좌우하는 근거 부족은 후반 작업으로 숨기지 않는다.

## 5. 중간 상태와 실제 순서 확정

**이 Phase가 끝난 뒤 다음 Phase를 하지 않아도, 해당 범위는 유효하고 독립적으로 검증 가능한가?**

- 정상 로딩·공개 실행·거부·실패/복원과 해당 저장 reader/writer가 일치해야 한다.
- 서로 다른 버전의 owner가 경쟁하거나 아직 없는 소비자가 있어야만 완료 주장이 성립한다면 경계를 다시 나눈다.
- 실제 안정된 계약으로 분리할 수 없으면 P2G-40의 최소 Atomic Group으로 묶는다. 편의로 거대 그룹을 만들지 않는다.
- 승인된 no-legacy 정책을 지키며, 새 상태의 저장·후퇴 영향은 그 상태를 도입할 때 함께 처리한다. CA19 번호를 이유로 미루지 않는다.
- 병렬화는 graph의 경로 부재만으로 허용하지 않고 파일·authority·state·schema·독립 검증을 함께 확인한다.

순서의 원본은 해당 범위의 current Phase Plan이다. 로드맵은 후보와 그 Plan의 대응을 보여주며 이를 덮어쓰지 않는다. 이미 인수한 Phase/Goal의 scope·순서·Atomic Group을 바꿔야 하면 P2G의 해당 owner에서 successor와 영향을 처리한다. 현황표만 고쳐 우회하지 않는다.

## 6. 특별히 확인할 큰 작업 경계

| 후보 관계 | 아직 코드로 확인할 질문 |
| --- | --- |
| CA03 → CA04 | 상태 kernel 검증에 공통 CLI 전체가 필수인가, 현재 시험 seam을 재사용할 수 있는가? |
| CA08 → CA10 | 사본 보유·개화의 어느 부분이 지속 action에 실제로 의존하며, 장착·형태 적용과 분리해 유효한 상태를 만들 수 있는가? |
| CA14/CA09 → CA16 | 명시 스킬 호출·완료·취소부터 구현하려면 모든 설치물·방어 기능이 필요한가, 일부 보스 기믹에만 필요한가? |
| CA10 ↔ 지급·장착·저장 | 사본화와 reader/writer 전환을 어떻게 묶어 중간 상태를 보존할 것인가? |
| CA01/CA02/CA03 | 최소 최신 RON→검증→실행 slice와 외부 로딩·공개 포트를 어디에서 끊어 각각 검증할 것인가? |

이 표는 **조사 질문**이지 선행 관계를 제거·추가했다는 결론이 아니다. CA16.1–CA16.4 같은 하위 계약의 각 소비 지점을 확인하여 필요한 부분만 선행으로 정한다.

## 7. v2에서 이어받은 설계 판단

v2는 CA14에서 유물 연쇄 CA13 전체의 직접 선행을 제거하고 CA15에 CA13+CA14를 두었다. 생성·진화 자체와 유물 연쇄 통합의 책임을 구분하려는 권장 판단이다. v2.1은 그 후보를 보존하며, 실제 compiler/runtime 경계에 대한 검토 완료로 승격하지 않는다.

공통 K 계약 초안으로 보스·유물의 상세 설계 후보를 병행할 수 있지만, 실제 구현·시험 인수에서는 생산자/소비자·계약 revision·실행 준비를 확인한다. `권장안 존재 ≠ 코드 기반 순서 검토 ≠ 실제 선행 구현 완료`다.
