# 코드 조사·상세 설계·구현·검증 절차

계획 v2.1 · **사용자는 정책을 결정하고, 로드맵은 권장 아키텍처를 제공하며, 구현 AI는 현재 코드에 근거한 상세 설계·구현·검증을 담당한다.**

## 1. 세 종류의 결정

| 표기 | 의미 | 변경 권한 |
| --- | --- | --- |
| P — 확정 정책 | 대화에서 정한 목표·범위와 최신 원문 승인 사항 | 구현 편의로 변경하지 않음. 실제 정책 변화는 사용자 결정 |
| R — 권장 구조 | A01–A08의 아키텍처·알고리즘·포트 선택 | 실제 코드·대안·영향을 기록해 검토 후 수정 가능 |
| L — 작업 상세 설계 | 구체 Rust 타입·함수·오류·queue·자료구조·파일 변경 | 구현자가 조사 후 작성하고 인터페이스 정합성 점검 |

미확인 사실과 미정 정책은 구분한다. “현재 코드가 무엇을 하는지 모른다”는 사용자에게 정해 달라고 할 정책 질문이 아니라 구현 AI가 조사할 일이다.

## 2. 모든 작업의 진행 과정

### D0 — 범위·선행 계약 확인

선택 CA와 대상 경계, 현재 revision·관련 dirty 변경, 승인된 실행 모드, 실제 선행 artifact를 확인한다. CA 번호가 있다는 사실만으로 구현 완료로 간주하지 않는다. 아키텍처 문서의 제안 타입을 실제 API라고 import하지 않는다.

### D1 — 관련 코드의 종단 조사

입력 또는 사건의 생산자에서 파싱·검증·컴파일·실행·상태/결과·저장·테스트 소비자까지 관련 경로를 읽는다. 긴 파일은 필요한 범위를 읽고 범위를 기록한다. entry symbol만 보고 unseen 호출자·소비자를 추정하지 않는다.

조사 산출은 현재 호출/데이터 흐름, authority와 수명, 재사용할 기능, 삭제/교체할 경로, 실패·취소·재접속 경계, 현재 tests와 baseline 실패, R 설계의 확인/반증된 가정이다. 저장소 전체를 매번 처음부터 읽는 것이 아니라 변경에 필요한 경계를 누락하지 않는 것이 목표다.

### D2 — 코드 기반 상세 설계

R 설계를 current code와 대조해 채택/수정/기각한 이유를 적는다. 최소한 exact types/port payload·result, 상태 key와 생성/변경/소멸 표, 순서/원자성, 검증·오류 matrix, 파일/심볼별 변경, 최신 schema·저장 cutover, 테스트 입력/기대 결과를 포함한다.

새로운 코드를 쓴 것만 설계 증거가 아니다. 대안은 핵심 한두 가지와 비교하면 충분하며 불필요하게 거대한 문서를 만들지 않는다. 필요하면 승인된 범위 안에서 폐기 가능한 compile probe/characterization test로 가정을 시험한다. probe를 production 기능 완료로 표시하지 않는다.

### DG — 설계 준비 점검

다음 질문에 답할 수 있어야 production 구현을 시작한다.

| 점검 | 필요한 증거 |
| --- | --- |
| R 권장안을 실제로 확인했는가 | 읽은 경로와 채택·변경 근거 |
| 생산자·소비자가 같은 계약을 쓰는가 | 타입·입출력·버전·오류 표 |
| 상태·종료가 완결되는가 | owner/lifetime·cancel·failure/rollback 표 |
| 의미 미정은 무엇인가 | PG와 영향 범위·확정 또는 blocked 상태 |
| 선행 관계와 중간 상태를 코드로 확인했는가 | 실제 소비 지점·필수/권장 구분, current Phase Plan과 선행 evidence |
| 구현 순서가 최신 경로 하나를 유지하는가 | 다음 Phase 없이도 유효한 상태, 파일 전환·삭제·대체 테스트 계획 |
| 완료를 판정할 수 있는가 | 긍정·부정·stale·동시 사건 테스트 기대값 |

DG는 모든 기술 선택을 사용자에게 승인 요청하는 절차가 아니다. 내부 선택은 구현 AI와 검토자가 증거로 판단한다. 다른 작업이 의존하는 K 계약 변경은 통합 설계 검토를 먼저 거친다. 독립 검토자가 없으면 검토 주체를 솔직하게 기록하고 별도 역할 관점의 self-review를 할 수 있지만 이를 독립 AI 감사라고 위조하지 않는다.

### I — 구현과 점진적 시험

검증→compile→executor→descriptor/diagnostic→테스트/문서를 하나의 지원 기능 경계로 갱신한다. 기존 기능은 의미가 맞으면 재사용하고 구형 스키마 parser·dual runtime·content-specific callback을 남기지 않는다. 커밋 분할 때문에 임시 compile 불가 상태가 있어도 이를 통합 완료로 게시하지 않는다.

### V — 실제 검증과 설계 환류

DG에서 정한 test·release loading·실제 RON slice를 실행한다. 설계 가정이 깨지면 현상·원인·변경 대안·영향을 기록하고 D2/DG로 돌아간다. 통과하도록 기대값을 정책 근거 없이 고치지 않는다. performance 또는 refactor로 revision이 바뀌면 이전 receipt의 유효성 범위를 재평가한다.

### A — 완료 검토와 인계

현재 revision·실제 tests·남은 미정·범위 밖 diff·canonical 동기화를 대조한다. 설계 합의, compiler 성공, runtime 성공, 공식 콘텐츠 이식, 독립 제작 성공은 서로 다른 완료 항목이다.

## 3. 설계 변경 등급

| 등급 | 예 | 처리 |
| --- | --- | --- |
| L0 내부 동등 변경 | helper/컨테이너/인덱스·동일 의미 최적화 | 구현자 근거 기록·관련 테스트. 매번 사용자 질의하지 않음 |
| L1 공유 계약 변경 | ActionHandle result, EffectSite 식별·cache key·scope | DESIGN_DELTA와 영향 소비자 목록, 계약 revision 갱신·검토·회귀 후 진행 |
| L2 gameplay/제품 정책 변경 | timeout/reinput 승자·비용 환불·사본 자원 소실·호환 정책 | 관련 동작 중단·PG에 사용자 결정. 무관한 승인 작업은 진행 가능 |
| L3 범위 변경 | 외부 코드 실행, 서버·Unity 전환, 전체 재작성 | 별도 범위 승인 전 실행하지 않음 |

## 4. 기록 형태

현재 저장소 workflow를 먼저 따른다. 기존 PLAN/EXPERIMENTS/EXPERIMENT_NOTES/COMPLETION_REVIEW에 내용을 담을 수 있다. 추가 파일은 그 workflow에 맞게 선택하며 파일 개수 자체가 목표가 아니다.

권장 추가 기록은 `DESIGN.md` 또는 PLAN의 상세 설계 절, `DESIGN_REVIEW.md` 또는 검토 절, `DESIGN_DELTA.md` 또는 notes의 변경 이력이다. 템플릿은 [templates](templates/DESIGN.template.ko.md)에 있다. 아직 실행하지 않은 작업에는 가짜 active/complete/test PASS를 채우지 않는다.

## 5. 설계와 구현 의존성

전체 로드맵의 R 설계는 제안으로 읽을 수 있다. CA01에서 K01–K10의 필요한 최소 경계를 정리한 뒤 도메인별 design draft를 병행할 수 있다. 하지만 실제 코드를 참조하는 L 상세 설계와 DG는 해당 인터페이스의 현재 구현 또는 정확한 합의된 계약을 검증해야 한다. 미완료 의존 API를 실제 실행 증거로 사용할 수 없다.

병렬 구현은 파일 소유자·계약 revision·통합 담당을 정한 뒤 한다. 핵심 identity/event/resource를 여러 AI가 각각 새로 설계하게 하지 않는다. 하나의 CA가 여러 독립 계약이면 묶음별 설계·인수 증거를 나누며, 필요한 경우 실제 Goal 분할을 승인 범위 안에서 정리한다.

## 6. 후보 순서의 코드 검증과 기존 절차의 연결

[DEPENDENCIES](DEPENDENCIES.ko.md)의 기준에 따라 D1에서 선택 범위의 선행 결과·후행 소비 지점을 확인하고, D2에서 기능 필수·동시 전환·검증 선행·진행상 권장을 구분한다. DG는 실제 Phase Plan과 current 선행 결과가 맞는지 확인한다. 이 D0–A 표기는 P2G/GEX 안에 수행할 활동을 설명하며 별도 승인 단계·독립 상태 기계가 아니다.

P2G-20 이전의 범위 후보 조사와 정식 코드 검토, P2G-40의 순서 확정, GEX의 실제 준비 확인은 다른 주장이다. 기존 current 근거가 있으면 영향 없는 부분은 재사용하며, 매 작업마다 전체 graph와 모든 테스트를 처음부터 반복하지 않는다. 이미 정식으로 인수한 순서를 바꿔야 한다면 DG 자체로 그 변경을 승인하지 않고 P2G owner 절차로 연결한다.

정확한 GEX 감사 파일·권한·필수 독립 검토는 현재 저장소의 지침을 따른다. 이 로드맵에 적힌 과거 파일명이나 self-review 가능성으로 요구된 독립 감사를 대체하지 않는다.
