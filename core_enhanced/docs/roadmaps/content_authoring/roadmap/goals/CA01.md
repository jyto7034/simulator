# CA01 — 작성 단위·타입·실행 지원 계약

계획 v2.1 · 2026-09-09 · 단계 M0 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA00  
공유 계약: K01, K02, K04, K05, K06, K07, K08, K09, K10  
권장 설계: [01_SYSTEM.ko.md](../architecture/01_SYSTEM.ko.md) / [02_AUTHORING_AND_COMPILER.ko.md](../architecture/02_AUTHORING_AND_COMPILER.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

효과 단위 변경과 도구 탐색을 가능하게 하는 공통 데이터 계약을 정한다. 15축을 15개 schema 필드로 옮기지 않는다.

콘텐츠 정의/형태/효과 정의/소유 사본/시전/직접 타격/피해 segment/전달/상태/연쇄 경로 identity를 구분한다. TargetQuery, ValueExpr, Action 또는 Effect, Condition, Sequence/Branch/Parallel, ResourceRef 등의 최소 작성 단위를 설계한다. 효과별 태그와 실제 변경 가능한 property를 분리하고 consumer별 허용 조합·입출력 타입·단위·상태 필요조건을 descriptor로 정의한다. 보스 graph와 스킬 flow는 제어 책임을 분리한다. 지금 실행하는 primitive만 지원 목록에 등록한다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** 구조화된 ActionFlow와 EffectSite를 typed AST로 선언하고, 컴파일된 node index/result slot/source map으로 낮춘다. 보스는 별도 상태·작업 graph를 유지하며 작은 공통 계약만 공유한다.

**이유:** 임의 jump/string eval 대신 도구가 연결 가능한 타입과 종료·취소를 검증하고, 효과와 action carrier의 변경 범위를 분리하기 위해서다.

## 3. 실제 코드에서 확인할 질문 — D1

현재 SkillDef raw/runtime 변환, range preset, Damage/Heal consumer, Boss compiled 정의, error source 위치 보존을 추적한다. 기존 ID·target·result 타입을 재사용할 수 있는지 비교한다. 최소 typed slice와 외부 로딩·시험 포트를 어디에서 분리해 각각 유효하게 검증할 수 있는지 확인한다. 작성·컴파일·기존 kernel 소비가 후속 미구현 기능 전체를 필요로 하는지 따져, 실제 필요한 계약 부분만 선행으로 제안한다.

연결 후보: `core_enhanced/src/game/ability.rs::SkillDef, SkillStepDef, SkillEffectDef; stats.rs::TriggerType, Effect, StatId; data/skill_data.rs; data/boss_runtime_data.rs; docs/skills/run_relic_content_design_notes.ko.md:267–378`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

최소 AST·compiled shape·EffectSite/ActionSite 주소, ID 범위, descriptor↔opcode 연결, unsupported 오류, K01–K10의 필요한 최소 port sketch. 미래 op의 빈 executor는 작성하지 않는다.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

계약·source map → 실제 Damage/Heal/Instant slice → 타입/참조 부정 fixture → CA02가 사용할 최신 최소 schema.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG01, PG02의 인터페이스 영향 부분. source 식별과 lifetime key는 내부 설계로 제안하되 gameplay 변화는 분리한다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T01. 같은 효과의 태그 AND와 “서로 다른 보유 효과 존재” 조건을 혼동하지 않는다. 소비자에서 실행하지 못하는 연산은 컴파일 단계에서 이유와 위치를 가진 오류가 된다. 피해+자기 회복을 분리한 최소 계획이 작성 가능하다.

**v2 추가 기준:** E01의 두 효과가 독립 property를 갖고, carrier 수정이 공유된 다른 effect에 번질 때 진단된다. exact RON 예제를 최신 parser로 검증한 뒤 문서화한다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

문자열 property path의 임의 실행, 미지원 enum을 성공 처리, 무제한 eval/스크립트, 모든 도메인의 거대 범용 VM 강제.



## 9. 인수 산출물

작성 계약 초안, 지원 기능 descriptor, 명시적 IR/도메인 경계, 최소 긍정·부정 컴파일 fixture. 제안 타입명과 실제 구현명을 구분한다.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
