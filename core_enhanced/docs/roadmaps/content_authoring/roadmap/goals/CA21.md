# CA21 — 제3자 관점의 재조합 인수

계획 v2.1 · 2026-09-09 · 단계 M7 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA20  
공유 계약: K02, K03, K07, K09, K10  
권장 설계: [05_BOSS_AUTHORING.ko.md](../architecture/05_BOSS_AUTHORING.ko.md) / [06_PACKS_AND_TOOLS.ko.md](../architecture/06_PACKS_AND_TOOLS.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

공식 사례에 맞춘 엔진이 아니라 지원 어휘를 재사용할 수 있는 제작 기반임을 입증한다.

CA20 이후 엔진 revision을 고정한다. 다른 작성 AI/작성자는 descriptor·작성 문서·검증기만 보고 새로운 ID와 별도 팩으로 보스/장비/파편/유물을 만든다. 임의의 새 공식 유물 lore가 아니라 시험용 조합으로, 기존 두 기능군을 교차 연결한다. source·namespace를 바꾸고 다른 팩의 효과도 참조한다. 기존 팩 전체 제거/공식 교체와 진단 경로도 검증한다. 엔진 patch가 필요하면 누락 capability를 일반 기능 작업으로 되돌리고, 고정 revision부터 인수 시험을 다시 수행한다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** engine revision을 고정하고 별도 작성자는 public authoring 계약과 RON만 사용한다. 보스의 신규 상태/패턴+기믹+실패 route를 별도 필수 항목으로 둔다.

**이유:** 공식 사례 전용의 숨은 이름 분기나 wrapper code를 찾아내려면 제작 과정을 엔진 개발과 분리해야 하기 때문이다.

## 3. 실제 코드에서 확인할 질문 — D1

동결 revision·source hash·도구 사용법·기능 목록·데이터 diff를 확인한다. 첫 작성자와 검토자가 같은 경우 독립성 한계를 표시한다.

연결 후보: `CA03 describe/validate/explain/simulate; CA12 composition; CA13 chains; CA17 registration; 별도 authoring acceptance packs(제안 경로)`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

네 도메인 holdout 입력·allowed data-only paths, cross-pack 참조/교체, boss trace 기대값, 실패 진단 사용 기록, engine patch 시 재동결 절차.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

동결 → 독립 authoring → 검증/진단 수정 → 실행 → data-only diff 감사.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

새 gameplay 발명은 하지 않는다. 기존에 승인된 기능 조합과 테스트 입력만 사용한다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T22. 네 도메인별 신규 콘텐츠와 교차 조합이 엔진 소스 무변경으로 동작한다. 비확률 시험에서 source 이름 변경으로 특정 콘텐츠 실행 분기가 생기지 않는다. 동일 ID·seed·환경의 결정론은 별도 검증한다. 작성자는 private 내부 타입 생성이나 core compile 우회 없이 오류를 수정할 수 있다.

**v2 추가 기준:** ID 변경 RNG는 비확률 fixture로 비교하고 동일 seed/ID/환경 결정론을 별도로 시험한다. 새 스킬 두 개·기믹 사건을 조합한 보스를 이름 복사로 대신하지 않는다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

공식 RON 이름만 바꾼 복제를 재조합 전부로 간주, acceptance 작성자가 engine code에 특례 추가, wrapper 전용 코드가 RON을 대행.



## 9. 인수 산출물

동결 revision, 작성자가 실제 수정한 data-only diff, 재조합 팩·실행 결과·불편/진단 실패 목록.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
