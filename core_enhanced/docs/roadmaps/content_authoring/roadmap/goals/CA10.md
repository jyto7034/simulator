# CA10 — 파편 사본·개화·형태와 무기 성장 연결

계획 v2.1 · 2026-09-09 · 단계 M3 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA05, CA08  
공유 계약: K01, K03, K05, K07  
권장 설계: [03_RUNTIME.ko.md](../architecture/03_RUNTIME.ko.md) / [04_COMPOSITION.ko.md](../architecture/04_COMPOSITION.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

개화와 형태·자원이 개별 파편 instance를 따라가고 새 성장 정책과 연결되게 한다.

OwnedFragment ID와 definition ID를 분리하고 보유/장착/개화 해금/선택 형태/자원 owner를 저장한다. 같은 종류의 두 사본을 각각 개화하고 서로 다른 형태로 장착한다. 공식 파편 일반 강화는 제거하고 Maintenance 형태 선택·가루 및 추가 재료 recipe를 연결한다. 무기 성장으로 Attack/SpellPower를 구성하고 해당 식만 영향받게 한다. 파편 intrinsic/passive+active 조합을 지원하는 슬롯·공명 계약을 반영한다. grant/분쇄/사망 회수·표시·checkpoint 코드 변경을 같은 사본 경계 안에서 동반한다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** OwnedFragment aggregate가 해금·선택형태·장착·자원을 소유한다. 정의·사본·직원 참조는 별개이며 grant/분쇄/저장도 같은 경계에서 바꾼다.

**이유:** 종류별 progress를 남겨 사본 state와 이중 유지하면 독립 개화·이전·저장에서 truth가 갈라지기 때문이다.

## 3. 실제 코드에서 확인할 질문 — D1

fragment inventory/loadout/progress, grant/reward, Maintenance, death recovery, snapshot/checkpoint와 stat 조립 소비자를 확인한다. 사본 보유·개화와 장착 형태 적용이 CA08의 어느 계약에 의존하는지 확인한다. 사본화의 지급·장착·저장 전환은 유효한 중간 상태를 만드는 경계로 묶는다.

연결 후보: `core_enhanced/src/game/skill_fragment.rs::SkillFragmentInventory, SkillFragmentProgress, SkillFragmentLoadout; data/skill_fragment_data.rs; world/maintenance.rs; world/helpers.rs; reward.rs; battle/stat_pipeline.rs; world/state.rs`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

새 사본 schema, equip invariant, unlock/select command transaction, recipe·형태별 resource mapping, passive+active 계약, effective plan invalidation, 구형 삭제 목록.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

사본·grant → 장착/선택 → recipe·성장 → projection/save → 다중 사본 시험.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG05. 해금은 인스턴스별이라는 사용자 결정은 재질문하지 않는다. 형태별 자원 보존·run 진행도와 재료 수치의 미정만 남긴다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T11. A 사본을 개화해도 B는 미개화다. A의 장착 직원을 바꿔도 A identity를 유지한다. 형태 변경이 전용 유물의 활성 계산을 무효화/재계산한다. 한 사본을 둘이 장착할 수 없다.

**v2 추가 기준:** A만 개화하고 B는 미개화인 상태가 정상 공개 포트·저장 왕복에서 유지된다. 형태 변경 미정 정책을 자동 초기화로 메우지 않는다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

기존 definition→count/progress 장부와 새 사본 장부 이중 유지, 구형 파편 강화 reader, 사본별 자원을 직원별로 옮겨 버리기.



## 9. 인수 산출물

새 파편 aggregate와 성장 경로, 동일 정의 다중 사본·다중 형태·저장 round-trip 테스트.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
