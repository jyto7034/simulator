# CA22 — 실행량·결정론·회귀·성능 검증

계획상 선행 후보: CA21  
공유 계약: K02, K03, K05, K06, K08, K10  
권장 설계: [03_RUNTIME.ko.md](../architecture/03_RUNTIME.ko.md) / [06_PACKS_AND_TOOLS.ko.md](../architecture/06_PACKS_AND_TOOLS.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

자유로운 조합이 잘못된 데이터·과도한 발생량·비결정론으로 코어를 망가뜨리지 않게 한다.

parser depth/파일 수·크기/정의 수, compiled graph 크기, 동시 effect/area/projectile/object, branch fan-out, same-time microstep, retained state/history 등 예산을 계측한다. 숫자는 목표 환경·baseline으로 정하고 피해 증폭 상한과 구분한다. 검증기에서 가능한 위험은 사전 거부하고 runtime 초과는 typed failure와 원래 상태 보존을 제공한다. 정렬·pack 탐색·hash map·진단 on/off로 RNG/결과가 달라지는지 확인한다. 기존 clone/lookup/전체 검색 비용을 측정하고 필요한 지점만 인덱스·캐시로 개선한다. schema 추가마다 descriptor·validator·executor·diagnostic 일치 검사와 property/metamorphic 시험을 둔다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** 입력/정의/instance/event/microstep 예산을 초기 기능부터 구현하고, 이 작업은 통합 부하·결정론·회귀와 측정 후 최적화를 소유한다.

**이유:** 피해 상한이나 silent drop으로 런타임 폭증을 가리는 것은 자유도와 정확성을 함께 손상시키기 때문이다.

## 3. 실제 코드에서 확인할 질문 — D1

핫 경로·clone·lookup·histories·generation refs·RNG·queue order·오류 boundary를 profile로 확인한다. 기존 baseline 실패를 분리한다.

연결 후보: `core_enhanced/src/game/battle/core/boss_runtime.rs::run_boss_runtime_boundary; triggers.rs::collect_item_trigger_payload; battle/core/sim.rs; battle/event_log.rs; data/live_ron.rs; determinism.rs; Cargo.toml; tests/`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

현실/적대 workload, 측정 하드웨어·build·time step, 수치 기준, semantic trace 비교·fault/rollback 기대값, 최적화 전후 receipts.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

회귀/결정론 → peak 부하/예산 → profile → 필요한 최적화 → 재검증·holdout 유효성 확인.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG08. 측정 환경·workload·허용치가 없으면 성능 합격을 주장하지 않는다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T23. 분기/소환/틱 폭증이 조용한 효과 누락이 아니라 제어된 실패로 종료되고 rollback이 성립한다. 동일 seed·입력·resolved pack은 동일 trace/state다. 기능별·통합·release 로딩·회귀 테스트와 계측값을 기록한다.

**v2 추가 기준:** 최적화가 실행 의미나 계약을 바꾸면 CA21 evidence도 다시 획득한다. 전체 연쇄 과거를 되감는다고 주장하지 않고 공개 atomic boundary에서 fault를 처리한다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

숫자 없는 “성능 충분” 판정, 오류를 성공으로 숨김, 전체 워크스페이스 서버 통합 성공 주장, 밸런스 상한으로 안전 예산 대체.



## 9. 인수 산출물

부하 모델·결정론/예산/회귀 결과, 실제 profile 기반 수정, 남은 범위·실패·환경 제약.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
