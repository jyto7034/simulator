# CA19 — 결과·후퇴·저장·재접속의 통합 정합성

계획 v2.1 · 2026-09-09 · 단계 M6 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA15, CA17, CA18  
공유 계약: K01, K03, K05, K06  
권장 설계: [03_RUNTIME.ko.md](../architecture/03_RUNTIME.ko.md) / [06_PACKS_AND_TOOLS.ko.md](../architecture/06_PACKS_AND_TOOLS.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

각 단계에서 추가한 상태의 내구·복원 경로를 종단 간 검증하고 동일 데이터 세대만 소비하게 한다.

Run 사본 상태·선택 형태·장착·자원을 최신 checkpoint에 포함하고 compiled 정의는 저장하지 않는다. 콘텐츠 세대 fingerprint와 실행 계약 버전, id 참조·소유 양방향을 검증한다. 신규 포맷만 읽고 mismatch는 명시적으로 거부한다. 메모리 내 이전 런 세대 보존과 legacy schema 지원을 혼동하지 않는다. battle result의 run-local delta를 source copy에 정확히 한 번 commit하며 defeat/retry/retreat를 구분한다. bounded 로그를 지워도 필요한 인과·자원 상태는 유지한다. 같은 프로세스 재접속은 현재 active battle의 조회·pause/resume이지 저장 지점 load가 아니다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** 런 사본 state와 attempt overlay를 분리하고 result delta는 source copy에 정확히 한 번 commit한다. 저장은 content fingerprint를 검증해 재바인딩한다.

**이유:** compiled index를 저장하거나 ID만 같은 다른 정의를 복원하면 효과 구성·자원·진행이 달라지기 때문이다.

## 3. 실제 코드에서 확인할 질문 — D1

RunCheckpointPayload·BattleEntrySnapshot·active_run·ApplicationCheckpoint와 result/retreat/retry/reconnect 실제 경로를 확인한다.

연결 후보: `core_enhanced/src/game/world/state.rs::RunCheckpointPayload, BattleEntrySnapshot, ActiveBattleSession; world/active_run.rs; world/combat.rs; world/application.rs; world/snapshot.rs; src/application.rs::ApplicationCheckpoint`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

current save schema, stable refs·content 계약, result idempotency key, restore validation plan, lifetime matrix와 commit 원자성, mismatch 오류.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

각 CA 상태 receipt 대조 → source delta → save roundtrip → rollback/reconnect → mismatch.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG05, PG07. 다른 최신 팩으로 바뀐 저장을 자동 재바인딩하지 않는 것이 기본안이다. 임의의 기존 파일 삭제는 금지.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T20. 저장/로드 round-trip에서 사본 구분과 형태·재료·Run 자원이 보존된다. 동일 ID의 내용이 바뀌어 fingerprint가 다르면 불러오기 실패가 무변경이다. retreat는 진입 전 자원·UUID·이력을 복원하고 retry는 새 attempt다.

**v2 추가 기준:** 새 저장 포맷은 각 상태 도입 때 동반하며 이 작업까지 미루지 않는다. 기존 파일 삭제 없이 mismatch를 거부한다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

여러 구세대 reader, 자동 데이터 복구, 진행 전투 전체 durable save 확대, 저장 버전만 맞으면 다른 pack을 허용, 모든 저장 작업을 이 단계까지 미루기.



## 9. 인수 산출물

최신 저장 계약 및 수명 경계 시험. CA04 이후 각 작업은 이미 자기 상태의 저장/복원을 함께 갱신해야 하며 이 작업은 최종 합성 검증이다.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
