# CA04 — 자원·상태 소유와 수명 kernel

계획 v2.1 · 2026-09-09 · 단계 M2 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA03  
공유 계약: K01, K05, K08  
권장 설계: [03_RUNTIME.ko.md](../architecture/03_RUNTIME.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

사본 자원, 전투당 사용 기록, 배치 임시 상태, 효과 공유량을 서로 혼동하지 않게 한다.

RunCopy/Employee/Attempt/Deployment/Activation/Delivery/Chain 의미의 상태 scope를 구현한다. resource kind와 owner reference를 타입화하고 cap·grant·decay·consume·reserve/commit을 지원한다. 상태 공급자·실행자·보유자·수혜자를 별도 참조로 둔다. 살아 있는 버프뿐 아니라 사망 직전 상태 사실을 보존할 경계를 CA06에 제공한다. epoch와 종료 token으로 이전 예약 작업의 재진입을 차단한다. 연쇄 상태는 bounded presentation log에서 역추론하지 않는다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** StateOwner와 Lifetime을 별도 typed key로 저장하고 ResourceTxn·ActionLease·generation handle을 공통 기반으로 둔다.

**이유:** 직원·사본·배치·attempt를 한 ID로 통합하면 개화·재배치 사용 제한·공유 pool이 서로 오염되기 때문이다.

## 3. 실제 코드에서 확인할 질문 — D1

현재 RuntimeUnit/RuntimeItem/BuffInstanceKey, 배치 재생성, proc key, entry/checkpoint와 결과 commit을 추적한다. 어떤 상태가 이미 source별로 보존되는지 확인한다. CA03 전체 완료가 상태 kernel의 실제 필수 조건인지, 현재 시험 seam으로 독립 검증이 가능한 진행상 권장 순서인지 확인한다. 확인 전에는 edge를 확정하거나 삭제하지 않는다.

연결 후보: `core_enhanced/src/game/battle/core/types.rs::RuntimeUnit, RuntimeItem, ActiveBuff, BuffInstanceKey; battle/core/ids.rs; battle/core/build.rs; world/state.rs::ActiveBattleSession, BattleEntrySnapshot, GameCoreState`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

owner×lifetime matrix, store key, handle ABA/stale 방지, reserve/commit/abort, copy binding, overlay와 Run commit 경계, 신규 상태의 저장/복원 위치.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

키·binding → resource transaction → epoch/lease → 재배치·후퇴 최소 시험.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG05. 파편 사본 identity에 귀속되는 상태와 직원 귀속 상태를 구분한다. 미정인 재배치·형태 전환 보존 규칙은 owner만 보고 추론하지 않는다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T05. 같은 정의의 두 사본 자원이 분리된다. 재배치로 deployment 상태만 바뀌고 attempt 기록은 남는다. 거부된 소비는 자원·RNG·이벤트·revision을 바꾸지 않는다. 종료 후 stale event는 no-op이다.

**v2 추가 기준:** 사본 owner지만 배치 lifetime인 상태와 사본 owner·attempt lifetime인 기록이 같은 재배치에서 다르게 처리된다. 비용 오류에 ID·RNG·queue 누출이 없다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

모든 상태를 RuntimeUnit에 저장, definition ID로 사본을 합치기, 디버그 로그 seq만으로 RNG 또는 연쇄 권한을 결정.



## 9. 인수 산출물

타입화된 state/resource store와 수명 계약, 다중 owner·중복 소비·취소 검증.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
