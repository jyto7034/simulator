# CA02 — 최신 schema 전환·외부 다중 팩 게시

계획 v2.1 · 2026-09-09 · 단계 M1 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA01  
공유 계약: K02, K03, K10  
권장 설계: [02_AUTHORING_AND_COMPILER.ko.md](../architecture/02_AUTHORING_AND_COMPILER.ko.md) / [06_PACKS_AND_TOOLS.ko.md](../architecture/06_PACKS_AND_TOOLS.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

배포된 live_data를 읽어 하나의 검증된 데이터 세대를 만들며, 구형 문법·embedded fallback 없이 최신 경로 하나를 사용한다.

먼저 CA01의 최소 피해·회복·단계 계획을 기존 계산·전달 kernel에 연결한다. 팩 manifest, namespace, 의존성, 추가/명시적 교체/삭제 또는 비활성, 최종 선택 규칙을 구현한다. 디렉터리 우연한 탐색 순서는 권한이 아니다. source 확보→raw 구문·타입 검증→override 해석→effective graph 참조 검증→compile→generated setup 검증→immutable publication 순서를 둔다. 읽기 도중 변경은 snapshot 일관성을 확인하며 재시도 또는 실패한다. game_resources/data는 공식 authored pack 원본, live_data는 패키징 결과로 단일 원본을 유지한다. 현행 파일 목록·고정 콘텐츠 수에 묶인 검증은 의미 검증과 공식 콘텐츠 coverage 검사로 분리한다. 새 런은 새 factory/application에서 해당 세대를 잡고 기존 런은 교체하지 않는다. 새 코어 구성 시 플레이어 identity와 영구 profile의 기존 소유를 보존하고 콘텐츠 reload 때문에 초기화하지 않는다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** 팩 합성 후 최종 참조를 검증하고 immutable ValidatedGeneration을 게시한다. 새 런만 새 세대를 bind하고 기존 런은 그대로 유지한다.

**이유:** raw 참조를 먼저 전부 강제해 정상 override를 막거나, 디스크 상태를 전투 중에 섞는 문제를 피하기 위해서다.

## 3. 실제 코드에서 확인할 질문 — D1

include_str inventory→parse→local/cross→compiled boss→generated setup→Core construction과 공식 파일수 검증을 추적한다. 저장소와 live_data 패키징·root path 소유를 확인한다.

연결 후보: `core_enhanced/src/game/data/live_ron.rs::GameplayRonSourceSet, ParsedGameplayRon, LiveRonError; data/mod.rs::load_live_sources, ValidatedGameData; data/validation.rs; src/application.rs; game_resources/data/; docs/data_loading_contract.md`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

팩 manifest/selection 타입, namespace/import/replace/remove 알고리즘, raw와 effective 검증 순서, path·동시 변경·예산 정책, fingerprint·generation factory, 최소 RON 전환과 삭제 경로.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

파일 입력 묶음 → manifest/합성 → compile/게시 → 최소 최신 런 → A/B pin·실패 시험.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG07. 본 로드맵 기본안은 명시적 교체만 허용, 미해결 다중 교체 충돌 거부, 삭제 뒤 dangling reference 거부다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T02–T03. 바이너리는 그대로 두고 외부 RON 수정 후 새 런 결과가 바뀐다. 이미 시작한 런은 이전 검증 세대와 결과를 유지한다. 손상·중복·순환 의존성·지원되지 않는 schema·모호한 override에서 부분 게시가 없어야 한다. 최소 정상 런과 전투가 새 schema만으로 성립한다.

**v2 추가 기준:** 삭제된 loser의 사용하지 않는 참조와 최종 dangling 참조를 구분한다. A/B 세대별 실행과 오류 시 세션 보존을 실제 같은 바이너리에서 검증한다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

구형 parser/별칭/버전 분기 adapter, production의 include_str fallback, 공격 때마다 디스크 읽기, 요청한 새 런에 실패를 숨기고 구세대를 적용, 기존 파일 임의 삭제.



## 9. 인수 산출물

외부 loader와 generation receipt, 최신 최소 공식 pack, 패키징 경로, 최신 semantic compiler와 기존 kernel 연결, 재빌드 없는 로딩 검증. 현재 카탈로그 전체 폐기는 허용이나 필요 없는 대량 삭제가 목표는 아니다.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
