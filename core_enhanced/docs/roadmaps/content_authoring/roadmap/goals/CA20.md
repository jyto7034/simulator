# CA20 — 대표 공식 콘텐츠의 실제 RON 이식

계획 v2.1 · 2026-09-09 · 단계 M7 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA15, CA16, CA19  
공유 계약: K02, K03, K04, K05, K06, K07, K08, K09, K10  
권장 설계: [08_WORKED_EXAMPLES.ko.md](../architecture/08_WORKED_EXAMPLES.ko.md) / [05_BOSS_AUTHORING.ko.md](../architecture/05_BOSS_AUTHORING.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

합의된 공식 구조를 최신 데이터로 작성하고 실제 실행 증거를 확보한다.

C01–C07을 대상으로 작성·로딩·시전/패턴·결과·추적을 연결한다. 초기 prototype을 각 선행 CA 단계에서 이미 실행하고 이 단계는 최신 경로로 통합한다. 원문 근거와 합의/제안/미정 상태, 시험 수치·policy profile을 각 파일에 연결한다. 공식 이름으로 구형 placeholder를 유지하거나 테스트 전용 값을 공식 밸런스로 승격하지 않는다. 원문의 기본/개화·서로 다른 파편·보스와 보상을 분리한다. 세부 미정이 남은 prototype은 완성 콘텐츠로 표시하지 않는다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** C01–C07을 최신 팩에 실제 저작하고 source→compiled→runtime→result의 의미 대응표를 남긴다. 각 선행 단계의 prototype을 종단 통합한다.

**이유:** 이름만 같은 placeholder나 private builder 시험으로 공식 설계 이식을 대신하지 않기 위해서다.

## 3. 실제 코드에서 확인할 질문 — D1

선정 원문 최신 절·승인/미정 기록과 해당 새 schema/compiled consumers·fixture를 대조한다. 콘텐츠 이름별 우회 코드를 검색한다.

연결 후보: `core_enhanced/docs/skills/*.md의 선정한 원문; game_resources/data의 새 공식 pack; live_data 배포 경로; CA03 runner; tests/ron_loading.rs; tests/skill_runtime_contract.rs; tests/live_item_skill_activation.rs; tests/live_skill_catalog_audit.rs`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

콘텐츠별 authoring graph·참조 목록·기대 trace·원문 대조표, prototype 수치 라벨, 하위 미정과 통과 범위, domain E2E 설정.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

C01/02 → C03/04/05 → C06/07 → 교차 조합 → 모든 원문 coverage 재검토.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

각 C 사례의 PG blocker. 동작을 바꾸는 미정 정책이 남은 사례는 실제 통과한 하위 계약까지만 기록한다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T21. 최소 두 구조가 다른 보스와 장비·파편·유물이 외부 RON→공통 compile→runtime→결과로 실행된다. C 목록의 각 기대 결과와 로그/상태 receipt가 연결된다. 코어에 해당 콘텐츠 이름을 분기하는 코드가 없어야 한다.

**v2 추가 기준:** 두 구조가 다른 보스가 실제 pattern/task에서 실행되어야 한다. 전체 장비세트·연출 완성으로 확대하지 않는다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

RON 없이 코드 builder fixture만 성공, placeholder 결과를 정식 구조로 간주, 모든 공식 콘텐츠 전량 이식을 강제, 구조 구현 대신 과도한 특별 enum 추가.



## 9. 인수 산출물

실제 C01–C07 RON과 실행 receipt, 원문 대조표, 전체 요구 표현력 갭의 재검토.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
