# CA17 — 등록·획득·공식 규칙 교체·전투력 연결

계획 v2.1 · 2026-09-09 · 단계 M6 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA10, CA11, CA12, CA16  
공유 계약: K02, K03, K07, K09  
권장 설계: [01_SYSTEM.ko.md](../architecture/01_SYSTEM.ko.md) / [06_PACKS_AND_TOOLS.ko.md](../architecture/06_PACKS_AND_TOOLS.ko.md) / [04_COMPOSITION.ko.md](../architecture/04_COMPOSITION.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

새 콘텐츠가 카탈로그에만 존재하지 않고 테스트·런의 등장/획득 경로까지 연결되게 한다.

새 조우·장비·파편·유물의 명시적인 등록/제거/교체와 reward/shop/encounter 참조를 지원한다. 하나의 환상체가 복수 fragment identity를 제공하는 경로와 ClaimAll/선택 결과가 결정된 경우의 지원을 검토한다. 공식 policy profile과 custom profile을 구분하고 공식이라는 이유의 교체 금지는 두지 않는다. 활성 effective plan을 Certified 전투력의 입력으로 연결하되 가중·정확한 산식은 승인 규칙을 사용한다. 프로필이 바뀌면 관련 캐시·전투력 fingerprint도 갱신한다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** 콘텐츠 등록·보상 연결은 최종 catalog의 typed 참조로 관리하고 effective plan을 전투력 평가 입력으로 제공한다. 공식 정책은 rule profile이다.

**이유:** 정의는 만들 수 있지만 플레이에서 등장/획득하지 못하거나 공식 ID whitelist가 창작을 막는 것을 방지하기 위해서다.

## 3. 실제 코드에서 확인할 질문 — D1

reward source uniqueness·복수 파편 관계, grant transaction, node/shop/encounter 등록, certified 계산과 캐시·저장 버전을 조사한다.

연결 후보: `core_enhanced/src/game/reward.rs::GrantExecutor; world/grant_state.rs; encounter_progression.rs; data/pve_data.rs; data/run_policy_data.rs; world/node_flow.rs; world/shop.rs; combat_power.rs::certified_combat_power_for_roster; world/snapshot.rs`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

등록/replace/remove 의미, reward 선택·commit payload, 소유/형태 전달, effective plan→평가 요약 포트, 모델 version과 미정 weight 처리.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

등록 참조 → 정상 grant/loadout → replacement → 전투력 입력·승인 모델 → E2E.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG06 획득·선택, PG08 전투력. 공식 드롭 빈도 미정은 test-only 획득 recipe와 분리하며 임의 출시 수치로 확정하지 않는다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T18. 새 pack의 보스 등장→전투→일반 grant→보유/장착 경로가 콘텐츠 ID hardcode 없이 작동한다. 삭제한 콘텐츠의 dangling reward 참조는 진단된다. 비활성 유물은 활성 효과로 평가되지 않는다.

**v2 추가 기준:** 미정 공식 공급정책과 test-only grant를 분리한다. 신규 보스를 정상 포트로 플레이해 얻은 사본이 장착·저장에 연결된다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

신규 ID allowlist, 특정 공식 카탈로그 개수를 범용 loader 필수조건으로 유지, 모든 유물 획득안을 이번 요청의 승인으로 간주, 무관한 경제 전면 재작성.



## 9. 인수 산출물

등록·획득 확장과 core 단위 E2E, 공식/custom rule 구분, 승인 모델의 전투력 입력 검증.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
