# CA23 — 독립 완료 감사와 제작 기반 인계

계획 v2.1 · 2026-09-09 · 단계 M8 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA22  
공유 계약: K01, K02, K03, K04, K05, K06, K07, K08, K09, K10  
권장 설계: [01_SYSTEM.ko.md](../architecture/01_SYSTEM.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

목표·원문·데이터·실행 증거를 대조해 제작 기반의 완료 여부를 판단한다.

COVERAGE의 모든 고정 baseline 요구를 재검토한다. supported에는 compiler/consumer/fixture/evidence가 있어야 하고 blocked/policy-pending은 완료로 바꾸지 않는다. dependency/정책 gate/forbidden diff/legacy 경로/문서·코드 일치/외부 비범위를 독립 검토한다. 각 CA의 실제 revision·test 수·명령·artifact를 확인한다. capability를 추가할 때 필요한 descriptor/schema/validation/runtime/test/diagnostic 작성 순서를 문서화한다. 신규 작성자가 SDK 포트를 사용하는 최소 예제를 최종 인계한다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** 요구 COV와 P/R/L 결정, 현재 K revision·실행 receipt를 연결해 최종 verdict를 낸다. 문서 존재와 구현 완료를 구분한다.

**이유:** 부분 예제 성공만으로 전체 제작 기반을 완료 처리하거나 architecture와 code의 drift를 숨기지 않기 위해서다.

## 3. 실제 코드에서 확인할 질문 — D1

모든 실제 작업의 design review/delta·code/data/test receipt·남은 PG·변경 범위를 현재 revision에서 확인한다.

연결 후보: `ROADMAP, POLICY_GATES, COVERAGE, ACCEPTANCE, 각 CA 실행 기록; core_enhanced/docs의 최신 canonical; 최신 code/data; CA21 data-only diff와 CA22 receipts`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

조건별 evidence matrix, 구현 아키텍처 요약, 실제 public 작성 계약·extension 절차, 미지원·미정·비범위 구분, 독립 감사 주체.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

coverage → K 정합성 → 실제 인수/회귀 → leftover legacy/특례 → 최종 문서·verdict.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

필수 완료 조건에 필요한 미해결 PG는 complete를 막는다. 공식 획득 빈도·미승인 개별 콘텐츠 밸런스 등 범위 밖 항목은 미정으로 명시해 둘 수 있다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T24. 외부 최신 RON 다중 팩, 네 도메인 제작·교체·등록, 효과 변형·연쇄, 사본·상태 수명, 침식 예외, 공통 도구, 재조합 data-only 검증이 모두 증거를 가진다. 미해결 공통 기능이 남으면 부분 완료로 보고한다.

**v2 추가 기준:** 미해결 필수 기능·gate가 있으면 부분 완료다. 프로젝트·클라이언트 전체 완료, 실행하지 않은 feature/performance 통과를 주장하지 않는다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

코드 존재=완료, 일부 대표 사례 성공=전체 표현력 증명, 실행하지 않은 결과·감사 복사, 자동 구버전 지원 부활.



## 9. 인수 산출물

COMPLETION_REVIEW 기반 최종 verdict와 인계 문서. “엔진 제작 기반 완료”, “공식 전체 콘텐츠 이식 완료”, “조합기/클라이언트 출시 완료”를 서로 다른 주장으로 분리한다.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
