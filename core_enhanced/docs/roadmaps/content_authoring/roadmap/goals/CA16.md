# CA16 — 보스 공통 행동·패턴·전장 사건 연결

계획 v2.1 · 2026-09-09 · 단계 M5 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA07, CA08, CA09, CA14  
공유 계약: K02, K04, K05, K06, K09, K10  
권장 설계: [05_BOSS_AUTHORING.ko.md](../architecture/05_BOSS_AUTHORING.ko.md) / [03_RUNTIME.ko.md](../architecture/03_RUNTIME.ko.md) / [08_WORKED_EXAMPLES.ko.md](../architecture/08_WORKED_EXAMPLES.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

보스별 전용 코드 없이 단계·패턴·스킬·형태·작업 반응을 데이터로 구성한다.

기존 compiled phase/behavior/pattern/state/task 구조를 유지·확장한다. 명시 스킬 호출과 완료/실패/중단 결과, 조준 방향, 상태 소유 modifier/profile 교체, targetability·피해 허용 조건, field-work 완료 신호, 카운터/시간 조건을 도입한다. FixedSequence를 유지하고 필요한 Priority/Weighted selection은 구현·검증 후 공개한다. 상태 capability 충돌·결과 mapping·zero-time loop·recursive summon 검증을 재사용한다. 스킬·피해 kernel, 웨이브 진행, 전투 결과 권한을 보스 interpreter가 침범하지 않게 한다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** Encounter→Phase→Behavior→Pattern→State→Task 구조를 확장하고 Task는 typed ActionService와 handle로 연결한다. boss blackboard는 scope·writer·type이 있는 상태다.

**이유:** 보스마다 스킬 실행 의미를 따로 만들거나 스킬과 wave authority를 모두 boss에 넣지 않으면서 커뮤니티 패턴 재사용을 지원하기 위해서다.

## 3. 실제 코드에서 확인할 질문 — D1

현재 compiler·task admission·RouteCombat gate·microstep/cancel·phase timing·query·summon/wave·field-work와 trace를 종단 조사한다. 새 CastSkill을 어느 공개/내부 포트로 요청할지 확인한다. CA16.1–CA16.4 각각이 CA07/08/09/14의 어느 결과를 소비하는지 검토한다. 기본 스킬 요청·결과·취소에 설치물·공유 보호 전체를 불필요하게 선행시키지 않고, 반대로 소환·전장 기믹의 필수 소비자를 누락하지 않는다. 분할 가능성은 코드와 중간 상태 근거로 판단한다.

연결 후보: `core_enhanced/src/game/data/boss_runtime_data.rs; battle/core/boss_runtime.rs::admit_state_tasks, boss_runtime_allows_combat_action, run_boss_runtime_boundary; combat_setup/boss_runtime.rs; data/pve_data.rs::PveFieldWorkCompletionEffectData; battle/core/field_work.rs; wave_runtime.rs`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

보스 authoring/compiled/runtime shape, TaskRequest/Result closed schema, milestone/cancel/failure 표, blackboard scope·typed parameters, state/phase arbitration, selector·signal/wave 매핑.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

CA16.1 graph/descriptor → CA16.2 ActionHandle/cancel/방향 → CA16.3 forms/conditions/selection → CA16.4 signals/multi-actor/wave/trace.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG03, PG04, PG06. 여러 HP 임계치 통과 시 피해 보존, 변신 완료 시 단계 skip, 작업 결과 우선순위.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T17. 아무 것도 없는에서 임계치 초과 피해가 사라지지 않고 죽기 전에 다음 형태를 강제로 유지하지 않는다. 정지 보스도 명시 방향으로 스킬을 사용한다. 포큐버스 작업 사건이 상태·강화 행동에 연결된다. 잘못된 graph는 게시 전에 거부된다.

**v2 추가 기준:** E02의 release vs settled, t50/t150 cancel, stale completion, C03 HP skip, C07 작업 억제, failed task route와 보스 data-only holdout을 필수로 둔다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

보스 이름별 행동 분기, 모든 것을 단일 스킬 VM으로 이동, 미구현 selector를 enum 존재로 지원 처리, 단순 profile 교체에서 유닛 HP/처치 identity 재생성.



## 9. 인수 산출물

보스 작업 확장과 원문 구조 기반 RON prototype, graph·cancel·wave 통합 검증.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
