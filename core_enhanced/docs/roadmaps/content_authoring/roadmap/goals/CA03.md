# CA03 — 공통 검증·설명·headless 시험 실행 포트

계획 v2.1 · 2026-09-09 · 단계 M1 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA02  
공유 계약: K02, K03, K10  
권장 설계: [06_PACKS_AND_TOOLS.ko.md](../architecture/06_PACKS_AND_TOOLS.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

RON 조합기 없이도 같은 작성 경로로 검증·시험·결과 확인을 할 수 있게 한다.

엔진 API와 얇은 CLI에 validate, describe, explain, simulate의 동등한 기능을 제공한다. 명칭·명령 문법은 구현에서 확정하고 현재 존재하는 도구처럼 문서화하지 않는다. 파일/pack/정의/효과/필드 위치, 오류 코드, 필요한 capability를 구조화해 반환한다. seed·팩 해시·입력 시퀀스·결과 요약을 기록한다. 일반 공개 코어 포트를 사용하는 시나리오와 low-level kernel fixture를 구분한다. 재로딩 성공 후 새 시험 전투를 생성하며, 실패 시 기존 시험 세션에 섞지 않는다. 새 CLI target은 autobins=false인 Cargo에 명시적으로 등록한다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** library의 작성 포트를 공통 authority로 두고 CLI는 얇은 adapter로 만든다. describe/validate/explain/simulate는 동일 generation·compiler·runtime을 사용한다.

**이유:** 향후 조합기가 별도 검증기를 복제하거나 test builder만 통과하는 제작 경로가 생기지 않게 하기 위해서다.

## 3. 실제 코드에서 확인할 질문 — D1

공개 CoreApplication·ValidatedGameData의 실제 construction 권한, existing fixture 도구 Cargo 등록, 진단 형식과 테스트 입력 경계를 조사한다.

연결 후보: `core_enhanced/Cargo.toml; src/application.rs::CoreApplication; src/game/data/mod.rs::ValidatedGameData; data/live_ron.rs::LiveRonError; battle/core/sim.rs; tests/ron_loading.rs; tests/skill_runtime_contract.rs`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

포트 입력/출력·오류 schema, scenario/seed/input/clock 형식, release 지원, 재로딩 session swap transaction, source-span/trace receipt, 명령의 실제 등록 방법.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

라이브러리 포트 → CLI → 독립 경로 RON → 같은 입력의 API/CLI 동등 시험.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

시험용 임의 숫자는 PG00 규칙에 따라 별도 pack과 receipt에 기록한다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T04. 독립 디렉터리의 RON으로 validate→simulate→explain 경로가 성공한다. 같은 잘못된 입력에 API와 CLI가 동일 의미의 진단을 제공한다. release 빌드에서 test-fixtures의 bare builder 없이 새 로딩 경로가 작동한다.

**v2 추가 기준:** 잘못된 팩으로 reload할 때 기존 시험 session이 먼저 사라지지 않는다. explain/preview는 state·RNG·revision을 바꾸지 않는다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

RON 조합기 UI 구현, 전용 캐릭터 ID를 아는 runner, 검증 우회 입력, 서버·Unity 구현을 끌어오기.



## 9. 인수 산출물

공통 authoring API, 최소 CLI, 실행 receipt 규격, 지원 기능 설명 출력. 이후 CA 작업이 새 primitive를 추가할 때 같은 포트에 즉시 등록한다.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
