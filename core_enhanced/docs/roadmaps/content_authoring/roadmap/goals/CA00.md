# CA00 — 기준 상태·전체 요구사항·정책 추적표

계획 v2.1 · 2026-09-09 · 단계 M0 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: 없음  
공유 계약: K01, K02  
권장 설계: [01_SYSTEM.ko.md](../architecture/01_SYSTEM.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

현재 작업 트리를 보존하고, 대표 콘텐츠와 전체 설계의 표현력 요구를 구별한 구현 기준선을 만든다.

작업공간·revision·관련 dirty 파일을 기록한다. project_map은 입구로만 쓰고 세 콘텐츠 문서의 합의된 단계·분기·병행과 개별 효과를 원문에서 목록화한다. 기본/개화, 탱/딜, 보스/플레이어 보상을 별개 요구로 등록한다. 각 요구에 15축의 해당 하위 요소, 원문 상태, 담당 CA 작업, 검증 사례를 연결한다. 기존 P2G/GEX 문서 규칙과 이 로드맵의 작업 경계를 대조한다. 테스트 기준선은 실행 권한이 주어진 경우 실제 명령·test 수를 수집하며, 과거 기록은 별도 출처로 남긴다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** 원문별 COV 추적표와 “현재 사실 / P 정책 / R 권장안 / 미정” 네 열을 기준선으로 만든다. 기존 CA 작업에 실제 요구를 배정하되 목록에 안 맞는 요구를 삭제하지 않는다.

**이유:** 코드 전수 읽기를 로드맵 작성자가 미리 끝낸 것처럼 전제하지 않고, 구현 단계의 조사 범위를 근거로 결정하기 위해서다.

## 3. 실제 코드에서 확인할 질문 — D1

현재 지도·콘텐츠·승인 기록의 날짜와 dirty 상태를 비교한다. 관련 기능의 실제 entry/validation/consumer/test만 먼저 표본 확인하고, 전체 콘텐츠 요구는 원문 전체의 해당 절을 읽어 목록화한다. 주요 공유 경계(loader·작성 정의·행동·상태/사본·보스·저장)에서 순서의 큰 역전·누락·과잉 선행 후보를 1차 확인한다. 최초 다음 범위의 직접 관계는 source로 뒷받침하고, 나머지는 미검토·추가 조사 질문으로 구분한다. 24개 작업 전체의 상세 의존성 검증을 완료한 것으로 표현하지 않는다.

연결 후보: `core_enhanced/docs/project_map.ko.md; docs/skills/run_relic_content_design_notes.ko.md; docs/skills/abnormality_skill_fragments_design_notes.md; docs/skills/abnormality_design_notes.ko.md; docs/engineering_workflow.md; docs/policy_to_goal_pipeline.md; docs/goal_execution_pipeline.md; Cargo.toml; tests/`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

원문별 요구 목록, 보스 제작 능력 목록, 현재/목표 차이, K 계약 owner와 PG 상태, baseline test 계획. CA01에 넘길 unresolved assumptions를 구체적인 코드 질문으로 작성한다. 의존성 1차 조사 범위·확인한 관계·미확인 관계·다음 후보의 직접 전제와 근거를 기존 조사 기록에 포함한다. 후속 Topic의 P2G-20/40에서 확정할 검토 대상을 제시하며 별도 전역 의존성 장부를 만들지 않는다.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

기준·권한 확인 → 원문 coverage → 대표 구조와 추가 최소 fixture 배정 → 첫 K 계약 점검 목록.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG00 및 모든 PG의 최초 분류. 아직 미정인 수치를 채우는 작업은 하지 않는다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T00. 승인된 기계적 요구마다 출처·작업·검증 또는 구체적인 정책 blocker가 있어야 한다. “대표 사례에 없어서 제외”인 행은 없어야 한다. 새 코드 변경 없이 조사 기준선과 현재 실패 목록을 구분한다.

**v2 추가 기준:** “지원할 것”과 “현재 실행 확인” 표기를 분리한다. 이 단계는 모든 runtime 기능의 세부 설계·수정 단계가 아니다. 다음 후보의 계획상 순서와 코드로 확인한 관계를 분리하고, CA00 인수·조사 완료를 정식 Phase Plan 또는 구현 준비 완료로 승격하지 않는다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

사용자 dirty 변경의 삭제·덮어쓰기, 서버 문제를 선행 차단으로 지정, 전체 문서를 읽지 않고 전수 확인으로 표시, 기존 평가를 무조건 정답으로 복사.



## 9. 인수 산출물

기준 상태 기록, COVERAGE의 전체 원문별 행, 정책·선행 작업 목록. 실행된 테스트가 없다면 그 사실을 명시한다.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
