# CA12 — 효과 선택·변형·유효 효과 구성

계획 v2.1 · 2026-09-09 · 단계 M4 · **실행·DG·구현·프로젝트 검증 모두 미수행**

계획상 선행 후보: CA09, CA10, CA11  
공유 계약: K02, K07, K10  
권장 설계: [04_COMPOSITION.ko.md](../architecture/04_COMPOSITION.ko.md) / [02_AUTHORING_AND_COMPILER.ko.md](../architecture/02_AUTHORING_AND_COMPILER.ko.md)

> **순서 근거:** 위 선행은 계획상 후보다. [의존성 기준](../DEPENDENCIES.ko.md)에 따라 선택 범위의 실제 코드·중간 상태를 P2G-20/40에서 검토하고, GEX 인수에서 current 선행 결과를 확인한다. 이 카드는 정식 Goal·실행 준비 증거가 아니다.

## 1. 목표와 범위

장착 조합에서 효과별 변경 결과와 활성/휴면 이유를 결정론적으로 산출한다.

원효과 identity/역할/태그/property capability/전용 콘텐츠·형태 selector를 도입한다. Add·Scale·Replace와 typed 구조 변환의 합성 단계를 분리한다. 원본 catalog는 immutable로 유지하고 loadout별 effective plan을 만든다. 새로 부여된 효과를 활성 판정에 포함하되 의미 없는 자기 부트스트랩을 막는다. 생성/태그 변형/대상 변환/수치 변경의 dependency와 write set을 검사한다. 구조 변환은 입력·출력과 보존해야 할 source/lifetime/property를 선언한다. 공유→단일과 오라→단일은 공통 interface를 쓰되 개별 계약에 맞는 변환 recipe를 RON으로 제공한다.

## 2. 권장 구조와 선택 이유 — R

**채택안:** 긍정 grant의 최소 closure와 층화된 구조 변환·typed property 합성을 실행하고 최종 graph를 재검증한다. global 정의는 immutable이다.

**이유:** 장착 순서나 last-writer로 결정하면 공용 효과 변경·생성 태그·전용 대상 의미가 불안정해지기 때문이다.

## 3. 실제 코드에서 확인할 질문 — D1

현재 profile merge·ModifyDamage 단계 범위·compatibility tag·snapshot explain 소비자를 읽고 새 composer를 호출할 mutation 경계를 확인한다.

연결 후보: `core_enhanced/src/game/ability.rs::SkillStepDef, SkillEffectDef; battle/core/sim.rs::build_skill_step_commands; data/skill_fragment_data.rs::compatibility_report; battle/stat_pipeline.rs; world/snapshot.rs; 새 composer/descriptor 모듈(경로는 구현 시 확정)`

위 경로는 조사 입구다. 실제 선택 작업에서는 관련 호출자·검증기·소비자·상태·테스트를 모두 연결해 읽고 확인한 범위를 적는다. 새 설계 타입을 현재 API로 가정하지 않는다.

## 4. 구현 전에 작성할 상세 설계 — D2/DG

selector/patch AST, signed dependency·closure termination, effect output ID, apply-key, typed write/preserve set, conflict matrix, cache key, before/after plan.

공통 [설계 절차](../DESIGN_WORKFLOW.ko.md)의 DG 표를 충족한다. R을 변경하면 현 코드 근거·대안·영향 소비자·P 정책 보존 여부를 기록한다. exact 함수·자료구조는 구현자의 L 설계이며, K 의미 변경은 L1 검토, gameplay 변화는 L2/PG다.

## 5. 구현·시험 묶음

selector → numeric patch → finite grant/activation → 구조 recipe → 최종 검증·explain.

새 상태의 snapshot/rollback/save 영향은 이 작업에서 동반한다. CA19에 모든 저장 구현을 미루지 않는다. 작업 범위에 해당하지 않으면 “해당 없음”과 근거를 적는다.

## 6. 정책 결정 지점

PG01, PG02, PG03. 태아 상태별 교체값과 포큐버스 2S를 공통 무조건 ×2로 합치지 않는다.

이미 합의한 사본별 개화·외부 팩·레거시 없음 등의 P 정책은 재질문하지 않는다. 미확인 구현 사실은 D1 조사로 해결한다.

## 7. 필수 검증과 완료 증거

T13. 동일 장착 집합의 입력 순서를 바꿔도 같은 effective plan이다. 피해 범위만 바꾸면 자기 회복·다른 피해의 출처는 그대로다. 새 폭발을 다른 유물이 강화한다. 새 부여 태그로 전용 대상 조건을 우회하지 못한다.

**v2 추가 기준:** E01 피해 범위만 변경, E03 단일 pool, E05 교체값·channel 유지, 생성 폭발의 후속 강화·NOT cycle 거부를 검증한다.

완료 증거는 실제 revision·명령·실행 수·기대/실제 상태·semantic trace·팩 fingerprint·남은 제약을 포함한다. DG 완료와 test PASS를 혼동하지 않는다.

## 8. 금지·비범위

전역 SkillDatabase 직접 변조, 문자열 JSON patch로 임의 내부 필드 수정, effect 태그의 파편 전체 합집합 매칭, 미정 충돌을 마지막 쓰기 승리로 처리.



## 9. 인수 산출물

효과 합성 compiler, 활성/휴면·변경 이력 explain, 속성별 합성과 상충 조합 검증.

추가로 현재 코드 조사 기록, 채택한 L 상세 설계, DG 검토 근거, 발생한 설계 변경 이력, 실제 검증·완료 검토를 연결한다. 해당 파일명은 현재 저장소 workflow에 맞춘다. 이 카드 자체는 실행 기록이 아니다.
