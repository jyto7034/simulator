# 로드맵 현황 운영 규칙

v1.6 · 2026-09-12 · 진입점: [ROADMAP_STATUS.md](ROADMAP_STATUS.md)

이 문서는 사용자와 합의한 “진입 문서를 읽고 다음 작업을 수행한 뒤 기록을 갱신”하는 방식을 위한 **운영 제안**이다. 새 P2G/GEX 단계·상태 기계·승인 artifact를 만들지 않는다. P2G는 정책에서 Goal·인수까지, GEX는 실제 구현·검증·완료 감사를 담당한다.

## 1. 시작은 두 파일, 나머지는 필요할 때

| 위치 | 소유할 내용 | 넣지 않을 내용 |
| --- | --- | --- |
| ROADMAP_STATUS.md | 현재 위치, 다음 작업 하나, 원본 링크, CA별 한 줄 요약, 최근 기록 | 상세 설계·전체 정책·검증 콘솔·모든 과거 기록 |
| OPERATING_RULES.md | 읽기·재개·대상 선택·갱신·분리 기준 | 매 실행 결과와 실제 Goal 상태 |
| history/YYYY-MM.md — 필요 시 | 오래된 간결한 진행 기록 | 테스트 로그 원문과 정책·Goal의 복제 |
| 기존 Topic/Goal 문서 | 정책·검토·Freeze·Phase·Goal·상세 설계·실행·감사의 실제 근거 | 운영 문서의 새 독립 복제본 |

실행 문서 이름은 현재 GEX가 정한다. 과거 로드맵에 적힌 이름을 그대로 강제하지 않는다. 예를 들어 이번에 확인한 GEX는 `COMPLETION_AUDIT.md`를 사용한다. 필요 없는 CA별 폴더·빈 표·별도 승인 장부를 미리 만들지 않는다.

### 분리 기준 — 크기보다 책임과 읽는 시점

1. **다음 판단에 직접 필요한가?** 현재 위치·막힌 이유·다음 작업과 그 근거 링크면 진입 문서에 둔다.
2. **지금 선택한 Topic/Goal만 필요한가?** 그 원래 작업 문서에 둔다. 매번 보는 진입 문서로 끌어오지 않는다.
3. **과거 경위를 찾을 때만 필요한가?** 최근 요약을 넘으면 history로 옮긴다.
4. **여러 작업의 공통 규칙인가?** 기존 P2G/GEX/로드맵/계약에 있으면 링크만 둔다. 운영 규칙에는 재개·분리 자체만 둔다.
5. **한 곳에서 이미 소유하는가?** 같은 사실의 독립 원본을 추가하지 않는다. 요약은 원본 링크를 가진 조회용으로만 둔다.

규모 가이드: 진입 문서는 대략 150–200줄 안팎, 최근 기록은 5건 이내로 유지한다. hard limit이나 실행 중단 조건은 아니다. 기록 1건은 결과·근거·남은 일 중심으로 5–10줄 정도가 적절하다. 매 도구 호출을 기록하지 않는다.

월별 history가 대략 300줄 또는 30건 이상으로 읽기 어려워지면 `YYYY-MM-02.md`처럼 나눈다. 단 하나의 실행 기록을 숫자에 맞춰 쪼개지는 않는다. 완료된 이력을 의미 수정하지 않고 이동하며 기존 기록 표지·근거·검색 경로를 보존한다.

CA 표가 여러 Topic/Goal 매핑 때문에 실제로 비대해지면 그때만 `WORK_INDEX.md`를 분리한다. 처음부터 만들지 않는다. 그 경우 상세 매핑은 WORK_INDEX 하나가 소유하고, 진입 문서에는 현재 행과 요약 링크만 남긴다.

## 2. 짧은 요청의 해석

사용자의 “현황 문서를 읽고 다음 단계를 진행해줘”는 **요청 시작 시 확인한 다음 작업 하나**를 대상으로 한다. 실제 지침·참조·현재 근거에서 대상과 범위가 명확하면 P2G ID나 긴 프롬프트를 다시 요구하지 않는다.

실행 전 다음 작업의 표지, 요청 원문 또는 확인 가능한 요청 위치, 대상·종료점·허용 변경을 기존 실행 기록에 연결한다. 자연어로 충분하며 별도 허가 파일이나 디지털 서명을 요구하지 않는다. 요청의 권한은 사용자에게서 오며 이 문서가 스스로 생성하지 않는다.

- `상태 알려줘`, `읽어봐`, `검토만`은 실행·코드 변경 요청으로 확대하지 않는다.
- 다음 작업이 **P2G**라면 승인된 Topic과 끝점까지 r2 `bounded_pipeline`을 적용한다. 단계마다 재승인을 반복하지 않는다.
- 다음 작업이 **GEX Single/Phase Goal 실행**이라면 `(Goal Set Ref, Goal ID)`와 Handoff, 실제 scope·수정 범위·종료점을 확인해 현재 GEX의 `goal-run`으로 인수한다. 이 요청 아래 해당 Goal의 구현·검증·감사 및 허용된 기술적 교정을 수행하되 다른 Goal로 넓히지 않는다.
- 다음 작업이 **감사만**이면 해당 `stage-run`의 읽기·검사·감사 기록만 수행한다. 발견한 코드 결함은 감사 도중 고치지 않는다.
- Goal Set 전체 실행·Master 감사가 필요하면 대상과 종료점을 별도로 표시한다. 기본 Next 카드에서 Phase 하나를 지정했는데 Set 전체 실행으로 확대하지 않는다.
- Topic·Goal이 아직 없거나 대상·수정 범위·권한이 모호하면 먼저 조회·후보 식별을 수행하고, 실질적인 선택만 질문한다. 없는 exact Ref를 채워 넣지 않는다.

문서의 다음 작업이 갱신됐다고 같은 사용자 요청이 새 Topic/Goal에도 연장되지는 않는다. 선택한 작업은 끝까지 수행하고 다음 단위는 다음 요청으로 진행한다. 단, 선택한 P2G 묶음이나 GEX `goal-run` 안의 단계들은 해당 지침에 따라 이어간다.

### 사용자가 채택하는 단일 R 실행 요청

사용자가 개정 [AUTORUN_REQUEST.ko.md](AUTORUN_REQUEST.ko.md)를 채택한 실행은 단일 NEXT 기본값 대신
**요청 시작 시 선정·고정한 R 하나**를 범위로 삼는다. 그 R 안의 필요한 P2G `bounded_pipeline`과 exact
Single/Phase/Set GEX `goal-run`은 각 진입·종료 조건을 지키며 이어간다. 선택 R을 완료하거나 실제 중단
조건에 도달하면 종료하며 다음 R의 계획·초기화·구현·검증·위임은 새 사용자 요청에서만 수행한다.

과거 R00–R24 전체 연속 요청은 당시 실행 기록으로 보존하며 현재 단일 R 범위를 확대하는 근거로 쓰지 않는다.
파일 교체·현황 갱신 자체는 실행 시작이나 기존 시스템 Goal 범위 변경이 아니다. 실제 실행 요청을 인수할 때
채택한 개정·고정 R·종료점을 연결한다. 요청 문서 편집을 게임 구현 재개로 해석하지 않는다.

2026-09-12 실제 채택 요청은 **single-r-v2 / R05 — 타입화 자원·owner×lifetime·원자적 소비**로 고정했고 R05 완료로 종료했다. [원래 Topic 인수 기록](../../goals/content_authoring_resource_lifetimes/REQUEST_INTAKE_001.ko.md)은 당시 요청·범위·재개 근거로 보존한다.

2026-09-13 새 실제 채택 요청은 **single-r-v3 / R06 — ValueExpr·집계·Attack/SpellPower와 무기 성장**으로 고정했다. 종료점은 R06 완료 또는 실제 중단 조건이며 [R06 인수 기록](../../goals/content_authoring_value_expressions/REQUEST_INTAKE_001.ko.md)이 현재 요청·범위·재개 근거를 소유한다. 일반 NEXT 기본 동작과 과거 실행 기록은 유지한다.

### 통상적 정책의 결정과 기록

정의·다섯 판단 조건·예외·정식 기록의 원본은
[P2G §8.6](../../policy_to_goal_pipeline_revised_v2.md#86-blocker와-중단-조건)이다. 사용자에게 위임받은 범위에서
기존 합의 유지, 기본 동작의 도출 근거, 별도 게임 규칙을 추가하지 않음, 해당 기능 안의 영향, 기존 사용자
데이터 보존을 모두 충족하면 AI가 정책을 결정·기록하고 계속한다. AUTORUN §3은 선택 R 안에서 이 권한을 부여한다.

material 여부와 사용자 의논 필요는 구분한다. 위임 결정은 사용자 직접 답변·기술 결정과 구분하여 실제 owner에
근거와 함께 남긴다. 정식 P2G 절차와 동결된 artifact의 불변성은 유지하며, 사실이 부족하면 먼저 조사한다.
사용자 선택이 필요한 정책에만 아래 대기 규칙을 적용한다. 통상적 판단으로 R·scope·권한을 확대하지 않는다.

### 정책 의논 시 주 작업 대기와 실행 중인 독립 작업

이 규칙은 단일 NEXT와 단일 R 실행 요청 모두에 적용한다. 위 판정에서 사용자 정책 의논이 필요하면 주 작업 담당자는 추가
조사·계획·구현·검증·감사와 후속 진행을 멈춘다. 안전한 중단·기존 작업의 범위 제한 전달·상태 기록과 이미
확보한 근거로 질문을 작성하는 최소 정리만 한다.

| 대상 | 처리 |
| --- | --- |
| 주 작업 담당자 | 일반 채팅의 최종 답변으로 질문하고 응답을 끝낸 뒤 사용자 답변 대기 |
| 실행 중이며 정책에 의존하거나 의존성이 불분명한 작업·하위 agent | 안전하게 임시중단 |
| 이미 실행 중이며 독립성이 확인된 작업·하위 agent·백그라운드 작업 | 질문 전에 배정받아 실행 중이던 범위까지만 완료 가능 |
| 새 작업·위임·후속 단계·다른 Goal/Topic/로드맵으로 전환 | 독립 여부와 관계없이 답변 전 금지. 배정됐어도 미실행인 작업은 시작하지 않음 |

독립성이 확인되려면 어느 정책 답변이 선택돼도 요구사항·완료 기준·결과의 유효성이 유지되고, 보류 작업과
파일·공유 상태의 충돌이 없어야 한다. 기존 근거로 판단할 수 없으면 중단하며 새 조사를 시작하지 않는다.
계속 실행하던 작업에서 정책 의존성·충돌 또는 그 불확실성이 드러나도 중단한다.

질문은 **일반 채팅의 최종 답변 본문**에 남기고, 주 작업 대기와 계속 실행하는 기존 독립 작업의 범위를 알린다.
독립 작업이 끝날 때까지 질문 전달을 늦추거나 질문 카드만 띄운 채 주 작업을 계속하지 않는다. 기존 독립 작업은
배정 범위의 결과를 보존하고 종료한다. 주 작업 담당자는 완료 통지를 받아도 결과 보존 외의 추가 검토·통합·
후속 배정을 하지 않고 대기한다. 무응답·기본 선택·경과 시간·작업 완료 통지는 재개 근거가 아니다.
실제 답변으로 정책이 해소되면 원래 owner와 승인 범위에서 재개한다.

상세 실행 계약은 [P2G §8.6](../../policy_to_goal_pipeline_revised_v2.md#86-blocker와-중단-조건)과
[GEX §6.6](../../goal_execution_pipeline%281%29.md#66-goal-run-자동-전환과-중단)이 소유한다. 미완료를 완료로
표시하거나 실행 시스템에서 실제로 적용하지 않은 `paused` 상태를 주장하지 않는다.

### 일반 단일 NEXT의 P2G와 GEX 인계

P2G-60 완료는 구현 승인 자체가 아니다. Goal화가 현재 작업이면 Handoff까지 만든 뒤 다음 카드에 실제 GEX 대상을 적는다. 이후 사용자가 같은 짧은 요청으로 그 명확한 구현 카드를 선택하면, 그 사용자 요청을 GEX 실행 근거로 삼을 수 있다. 문서의 `실행 가능` 표시는 승인이나 완료가 아니다.

현재 상위 AGENTS·runner·GEX가 요구하는 권한 조건을 우회하지 않는다. 지침 충돌을 해결할 수정 권한이 없으면 충돌 부분만 보고한다. 운영 문서 작성 요청을 이런 지침 수정 또는 게임 구현 승인으로 간주하지 않는다.

## 3. 다음 작업을 고르는 기준

고정된 “검토 → 수정 → 감사”를 새 절차로 만들지 않는다. 현재 원본 상태와 P2G/GEX 전이를 확인하여 다음처럼 판단한다.

| 확인한 사실 | 이어갈 곳 |
| --- | --- |
| 선택 대상·근거·권한이 모호하거나 상충 | 관련 확인 또는 필요한 사용자 질문. 성공 상태를 만들지 않음 |
| 선택된 범위에 미완료 작업·미해결 감사 지적이 있음 | 원래 owner의 재개·수정·재감사. 새 기능 착수보다 우선 |
| 구현 종료 주장만 있고 current 감사가 없음 | 필요한 GEX 감사. 구현자 완료 선언을 그대로 완료로 복사하지 않음 |
| current Handoff와 eligible Goal이 있고 구현 카드의 요청이 있음 | 정확한 Goal을 GEX에 인수 |
| 요구는 있으나 정식 Goal·인수가 없음 | 관련 범위의 P2G 또는 그 범위를 결정하기 위한 제한적 조사 |
| 필요한 Goal·통합 검증이 모두 완료 | 로드맵 범위를 완료로 요약하고 다음 후보 하나를 기록 |

실제 순서·자동 correction·감사 전환은 현재 P2G/GEX가 소유한다. 동시에 여러 후보가 있으면 **해당 범위의 current Phase Plan·Goal과 실제 선행 결과**를 우선한다. 로드맵의 번호·후보 표만으로 이 조건을 충족했다고 보지 않는다. 안전한 기술적 순서만 재량으로 선택하고, 정책·결과·ownership이 달라지는 대안을 자의로 고르지 않는다.

한 CA가 여러 Goal에 걸리거나 여러 CA의 일부가 한 Goal에 포함될 수 있다. 번호 순서대로 기계적으로 새 Topic을 만들지 않는다. 나머지 Goal이나 실제 통합 검증이 남으면 `일부 완료`라고 적고 무엇이 남았는지 연결한다.

### 3.1 순서를 검토하고 실행 준비를 확인하는 기준

**계획상 순서 / 코드 검토로 뒷받침된 Phase Plan / 실제 선행 구현·감사 충족**은 별개의 판단이다. 이 구분은 기존 원본의 evidence 수준을 요약하는 것이지 신규 Gate·정식 상태·승인 장부가 아니다.

처음에는 주요 공유 경계의 큰 누락·역전·과잉 선행 후보를 살피고, 곧 수행할 범위의 직접 관련 코드를 깊게 본다. 전체 로드맵의 모든 함수·후반 세부 의존성을 다 조사해야 시작한다는 요구는 없다. 필요한 코드 조사·판단은 구현/검토 AI가 수행하고, 모른다는 이유로 기술적 사실을 사용자에게 결정해 달라고 하지 않는다.

선택 범위의 P2G-20은 선행 결과와 실제 후행 소비 지점의 코드 근거를, P2G-40은 관계 유형·Phase·최소 동시 전환·중간 상태와 검증 owner를 소유한다. GEX 인수는 이 Plan과 실제 선행 결과·감사·권한을 확인한다. 자세한 기준은 [DEPENDENCIES](roadmap/DEPENDENCIES.ko.md)를 따른다.

후보 관계를 기능 필수·동시 전환·검증 선행·진행상 권장으로 구분한다. `A 전체 → B 전체`로 쓰인 항목이라도 B의 어느 부분이 A의 어떤 계약을 소비하는지 확인한다. 단계가 나뉘어도 다음 Phase 없이 현재 상태가 유효해야 한다. 기존 기능으로 이미 충족된 조건은 중복 구현하지 않는다.

상세 근거는 기존 Code Review·Phase Plan·Goal 실행 기록 한 곳에서 소유한다. 현황에는 검토 범위와 링크, actual 준비 여부만 남긴다. 단순 DAG/JSON 일치 검사·테스트 파일 존재를 코드 의존성 검토나 실행 준비 증거로 사용하지 않는다.

초기 Next 카드가 조사라면 조사 결과까지만 만든다. 정식 Plan이 없는 상태를 `검토 완료` 한 줄로 GEX 준비에 승격하지 않는다. 이미 정식 Phase Plan이 있으면 그 원본을 우선하고, 틀린 전제가 발견되면 P2G owner에 반환한다. 현황/로드맵만 바꿔 approved Plan을 우회하지 않는다.

구현 후 예상한 선행 결과는 다음 작업의 basis로 사용한다. 실제 계약·범위·전제가 변하지 않았다면 P2G 전체를 반복하지 않는다. 관련 코드·계약·테스트가 변하면 영향받는 관계만 재확인한다.

## 4. 다음 작업 카드에 반드시 적을 내용

한 카드가 길어지면 상세 내용은 원래 작업 문서의 절을 참조한다. 초기화 전에는 임의 Ref 대신 `후보`, `미연결`, `미확인`을 쓴다.

```text
작업 표지와 제목: NEXT-xxxx / 이번 단위의 결과
분류: 조회·정리 / P2G / GEX 실행 / 감사 / 해당 owner의 교정
대상: 관련 CA·Topic 또는 실제 (Goal Set Ref, Goal ID)
근거 위치: 실제 Handoff·현재 작업 기록·관련 audit와 입력 basis
범위: 포함 / 제외 / 요청 시 허용할 변경
종료점: 완료 산출물 또는 현재 지침의 terminal result
순서 근거: 계획상 후보인지 / 해당 범위 Code Review·current Phase Plan의 실제 위치
필수 선행: 어떤 결과를 소비하는지 / 실제 구현·감사·currentness / 재개 시 확인할 변화
미검토·조정: 아직 확인할 관계 / 순서 변경이 필요한 owner와 범위
중단 조건: 필요한 정책·범위·권한·근거·독립 reviewer
```

`NEXT-xxxx`는 이 진입 문서의 로컬 표지일 뿐 P2G Exact Artifact Ref나 새 Goal ID가 아니다. 실행 중 의미가 같은 기술적 보완은 기록하고 진행할 수 있지만, 대상 Goal·허용 변경·정책 범위를 바꾸는 것은 사용자 요청을 자동 확장하는 수단이 아니다.

## 5. 새 AI·새 세션에서의 읽기

### 현재 요약 우선과 공통 근거 연결

현재 실행의 exact 요청/Goal·최신 구현 또는 교정 결과·target·검증·미해결 finding·다음 pass는 실제
PLAN/NOTES 역할 또는 허용된 현재 인수 안내 한 곳에서 찾을 수 있어야 한다. 원문과 요약이 다르면
최신 successor 관계를 확인하고 locator를 정리한다. EXPERIMENTS 전체 재독으로 요약 부재를 상시 보충하지 않는다.
동결된 요약은 당시 snapshot으로 보존하며 감사 중 덮어쓰지 않는다. 허용된 비대상 현황/안내로 최신 result를 연결한다.

감사자는 [GEX](../../goal_execution_pipeline%281%29.md) §5의 조건별 영향, §6.4의 공통 검사/검증 근거 재사용,
§6.7의 reviewer 기준을 사용한다. 이 운영 문서에 기준을 복제하거나 원래 Goal의 독립성을 완화하지 않는다.
같은 사실은 exact source/결과 ref로 연결하고, 각 문서에는 자기 역할의 판단과 남은 차이만 쓴다.
도구는 필요한 기계 검사를 완전히 수행하되 AI에게는 비교 기준·변경/누락/실패와 원문 위치를 우선 제공한다.
조건별 근거·현재성·실패 이력을 생략하거나 공통 도구 PASS를 게임/감사 완료로 승격하지 않는다.

단계 또는 reviewer가 바뀌었다는 이유만으로 불변 공통 규칙·전체 이력·전체 테스트를 반복하지 않는다.
같은 범위의 작은 명령/시험 오류는 원인·수정·재검증과 기존 범위 참조로 기록한다. 실제 정책·권한·격리·
대상 변경이 있으면 해당 영향만 다시 확인한다. 축약은 필수 기준의 삭제가 아니라 불필요한 복제의 제거다.

### 원문 확대 기준

진입 문서 → 관련 원본의 현재 상태 → 지금 수행할 지침의 관련 절 → 필요한 코드·시험 순으로 읽는다. 이 운영 규칙은 처음 인수하거나 변경됐을 때 확인하고 매번 전부 다시 읽지 않는다.

수행 전에 관련 workspace/revision·dirty 변경과 현재 대상·근거를 대조한다. 작성 시각이 최신이라는 이유만으로 현재 근거라 보지 않는다. unrelated 변경만으로 전체 이력·전체 저장소·모든 테스트를 다시 확인하지도 않는다.

원본이 더 진행됐는데 진입 문서만 뒤처졌으면 그 사실을 확인하여 요약을 고친다. 이미 끝난 작업을 다시 수행하지 않는다. 새로 드러난 다음 대상이 현재 요청의 카드와 다른 Topic/Goal이면 새 카드를 제시하고 그 새로운 실행까지 자동 승인하지 않는다. 같은 대상의 재개·감사·교정은 해당 요청 범위와 실제 지침에 따른다.

필수 링크가 끊겼으면 알려진 Topic/Goal 폴더와 실제 ID부터 제한적으로 찾는다. 찾을 수 없으면 근거 누락을 기록한다. 완료 상태·Ref·시험 결과를 추정하여 복구하지 않는다.

## 6. 실행 결과와 현황 갱신

작업 시작에는 대상·작성자/세션·worktree·원래 기록 위치를 남기고, 종료·질문 중단·도구 한계에는 다음 순서로 갱신한다.

1. 정책·실행·감사·검증의 원래 소유 문서에 실제 결과를 남긴다.
2. 확인된 경로·문서 ID·결과·basis를 진입 문서에 연결한다.
3. 수행한 일·결과·남은 일·재개 지점만 최근 기록에 추가한다.
4. 현재 요약과 다음 카드 하나를 갱신한다. 오래된 이력은 필요한 경우에만 분리한다.

기록 예시는 아래 정도로 충분하다. 실제 실행한 명령·test 수·로그 원문은 기존 실행·검증 기록에서 확인한다.

```text
기록 xxxx / 실제 날짜 / 선택 작업 표지
- 수행·결과: 검토한 경계 또는 변경·검증·감사 결과를 짧게 구분.
- 원본: 경로#절 + 해당하는 actual Goal/Ref/basis.
- 남은 일: 실패·미실행·필수 질문·감사 currentness 등.
- 다음: 재개할 대상과 이유. 완료 증거 없으면 완료라고 쓰지 않음.
```

문서 작성·코드 작성·테스트 성공·감사 완료를 한 가지 `완료`로 합치지 않는다. 감사 verdict는 실제 표현과 target을 유지한다. 예: `구현 종료 / GEX-20 미실행`, `감사 Not Complete / 교정 필요`. 초기 `미확인`을 임의로 `미착수`로 바꾸지 않는다. 서로 다른 작업의 무게를 동일하다고 가정한 완료율은 만들지 않는다.

감사 pass 중 운영 기록 변경도 현재 GEX가 허용하는 report/audit evidence 범위에서만 한다. 진입 문서가 감사 target에 포함돼 있으면 감사에서 직접 수정하지 않고 허용된 별도 기록 작업으로 처리한다. 감사 중 코드 수정은 금지하며, 결함 교정은 별도 구현 pass로 수행한다.

실행 중단 전에 가능한 범위에서 마지막 유효 결과를 기록한다. 비정상 종료로 원본만 갱신됐으면 다음 인수가 원본을 기준으로 요약을 회복한다. 이 문서 체계를 위한 별도 DB·분산 lock·복잡한 transaction 프로토콜은 만들지 않는다.

여러 AI가 작업할 때 진입 문서는 한 명의 통합 담당자가 갱신한다. 이미 다른 실행이 같은 대상·dirty 경계를 사용 중이면 범위를 확인하고 충돌을 피한다. 단지 오래된 `진행 중` 문구가 있다는 이유로 작업을 영구 잠그지 말고 실제 실행 기록을 확인한다.

## 7. 배치와 기존 문서의 관계

권장 위치는 저장소의 `core_enhanced/docs/roadmaps/content_authoring/`다. 이는 제안 경로이며 이번에 저장소에 생성한 경로가 아니다. 기존 파일이 있으면 먼저 identity와 내용을 비교하고 임의 덮어쓰기·이동을 하지 않는다. 두 파일은 같은 폴더에 둔다.

최종 묶음은 개정한 로드맵 v2.1 분할본과 P2G r2 배포 사본을 포함한다. 이는 새 정책 authority가 아니라 사용자에게 전달할 동일 원문의 사본이다. 저장소 적용 후에는 실제 소유 경로를 진입 문서에 연결하고 이중 편집하지 않는다. GEX는 묶음에 복제하지 않고 현재 저장소 원문을 사용한다. 파일명이 바뀌어도 선택한 revision·내용을 확인한다. 특히 최초 P2G 문서의 한 요청당 한 단계 규칙과 r2의 bounded_pipeline을 혼합하지 않는다.

[사용 안내 v2.1](guides/policy_to_goal_pipeline_roadmap_usage_v2_1.ko.md)은 배경 설명·적용 예시다. 그 문서를 매번 읽는 필수 단계로 만들거나 여기의 기록과 중복 관리하지 않는다. 향후 두 운영 안내가 충돌하면 실제 P2G/GEX와 사용자 요청을 기준으로 정리하되, 불변 artifact를 수정하거나 운영 문서가 정책 authority가 되지 않게 한다.
