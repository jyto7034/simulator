# Simulator 콘텐츠 제작 기반 — ROADMAP 순서에 따른 단일 R 계획 요청

최초 작성일: 2026-09-09 · 개정일: 2026-09-13 · 요청문 개정: single-r-v5-plan-only
배치: `core_enhanced/docs/roadmaps/content_authoring/AUTORUN_REQUEST.ko.md`

이 개정은 선택 R·통상적 정책 위임·정책 질문 대기·필수 감사 기준을 유지하며, 이번 요청의 종료점을
P2G-60 검증·계획 인계 완료로 제한한다. 고성능 모델로 검토·계획을 마친 뒤 사용자가 모델을 바꿔
별도로 구현을 요청하는 경계다. [이전 single-r-v3 원문](records/plan_handoff_boundary_20260913/before/AUTORUN_REQUEST.ko.md)은 과거 실행 근거로 보존한다.
문서 편집 자체는 P2G/GEX 재개가 아니다. 실제 사용자 요청과 적용 revision을 현재 인수 기록에 연결한다.

이 파일은 사용자가 검토한 뒤 Codex에 “이 요청을 채택하고 수행하라”는 메시지 또는 `/goal`을 제출할 때 사용하는 실행 요청문이다. 파일의 존재·교체·검색 결과·AI의 자체 작성만으로 권한이 발생하지 않는다. 정식 P2G Artifact, GEX Goal Set, 완료 증거 또는 새로운 파이프라인 규격이 아니다. 사용자 채택 전에는 검토용 수정안이다.

사용자가 이 개정본을 채택하면 **요청 시작 시 선정·고정한 R 하나의 계획**만 수행한다. `AUTORUN`은 승인된 P2G 끝점까지의 자동 진행을 뜻한다. 기존 요청의 R 전체 완료·연속 구현 위임은 현재 사용자 지시와 새 인수 기록에서 계획 전용 종료점으로 대체한다. 과거 요청·산출물은 보존하며 파일 교체만으로 실행 중인 다른 세션이나 시스템 Goal이 변경됐다고 가정하지 않는다.

## 1. 프로젝트 목적과 이번 요청의 종료점

Simulator 콘텐츠 제작 기반의 개정 로드맵 `2.2-review.1`의 `ROADMAP.ko.md` 순서에 따라 R 하나를 선정·고정하고, 필요한 P2G 코드 검토·정책 동결·Phase Plan·Goal Set 작성과 P2G-60 Handoff 검증까지 수행하라. **P2G-60의 필수 종료 조건과 §6의 계획 인계 요건을 충족하면 이번 계획 요청을 정상 완료하고 즉시 종료한다. GEX-00 인수·Goal activation·구현·감사는 새 사용자 요청이 있어야 시작한다.** 실제 중단 조건이면 마지막 유효 결과와 미완료를 보고하고 종료한다.

최종 목적은 제3자가 엔진의 공통 명령·행동·조건·효과·규칙을 RON으로 조합하여 보스·장비·무기·파편·유물을 제작하고, 기존 콘텐츠 변형·교체·등장·획득까지 연결하는 것이다. 지원 조합 안에 콘텐츠 이름별 전용 실행 코드를 추가하지 않는다. 실제 부족한 표현력은 승인 범위의 공통 기능으로 확장한다.

프로젝트의 조사 대상 영역은 `core_enhanced`, `game_resources/data`, 해당 기능의 테스트·headless 제작 도구·코어 계약·P2G/GEX 작업 기록이다. **이번 수정 권한은 선택 R의 P2G 계획·검토·문서 검증·인계 기록에 한정**된다. 필요한 비변경 진단과 기존 검증 근거 확인은 가능하나 production source·게임 테스트 소스·RON·저장 데이터 구현 변경은 수행하지 않는다. 서버·Unity/클라이언트·외부 서비스 배포·RON 조합기 UI는 제외한다.

‘한 단계’는 R 하나이며 P2G 단계 하나나 정식 Single Goal 하나와 같지 않다. 선택 R에 여러 Topic/Goal/Phase가 필요하면 그 R의 승인된 계획 범위 안에서 인계 coverage를 대조한다. 선행 구현이 필요한 후속 상세는 의존성과 다음 owner를 명시하고 준비 완료로 꾸미지 않는다. 계획 완료와 R 전체 완료를 구분한다.

프로젝트 전체 완료 기준은 각 R의 applicable 요구·직접 검증·증거의 현재성과 대표 RON 이식·전체 합의 요구의 표현력 대조·독립 제작·최종 감사다. 이 기준은 유지하지만 **이번 종료점은 계획·인계 완료**다. R 구현·감사나 프로젝트 전체의 미완료를 이유로 이 요청을 계속하지 않는다.

기존 연구 ZIP의 `input_package/`와 그 안의 HANDOFF_PROMPT는 당시 조사 요청의 보존 자료다. 당시의 “구현 금지”를 이번 사용자 실행 요청의 종료 조건으로 재사용하지 않는다. 동시에 과거 연구 자료를 새 gameplay 승인으로도 사용하지 않는다. 과거 전체 자동 실행 요청도 이번 단일 R 범위를 확대하는 근거가 아니다.

## 3. 선택 R 안에서 사용자가 위임하는 실행 범위

사용자가 이 요청을 채택하여 제출하면 **선택 R의 계획 권한만** 부여한다.

**계획 권한:** 선택 R에 기재된 기능 범위 안에서 승인된 정책을 추적하고, 현재 코드에 맞는 최소 Topic·Work Package·Atomic Group·Phase·Goal·Handoff를 필요한 시점에 작성·검증할 수 있다. 기존 exact artifact는 재사용하고, 필요한 기술적 수정은 해당 P2G owner에서 불변 successor와 영향 검증으로 처리한다. 같은 R 범위의 단순 P2G owner 전환을 매번 사용자에게 되묻지 않는다. 다른 R의 신규 Topic·Goal·Handoff를 미리 작성하지 않는다.

**구현 권한:** 이번 요청에는 없다. 아래 조건은 계획에 기록할 후속 GEX 인수 요건이다. 모두 충족돼도 P2G-60에서 종료하며, 사용자가 모델을 선택하고 별도 구현 요청을 제출해야 한다. 이전 single-r-v3의 연속 구현 위임을 재사용하지 않는다.

별도 구현 요청에서 확인할 선택 R 안의 정식 Goal 자격 조건:

1. 선택 R 카드와 요구·승인 정책의 대응, 허용 코드/데이터 경계와 완료 조건이 추적되고 다른 R의 신규 기능이 포함되지 않는다.
2. material policy는 사용자 직접 결정 또는 [P2G §8.6](../../policy_to_goal_pipeline_revised_v2.md#86-blocker와-중단-조건)의 통상적 정책 위임·조건 충족 근거로 확정했으며, 사용자 선택이 필요한 미결 정책이 없고 승인 범위·위험·외부 권한을 확대하지 않았다.
3. 해당 P2G의 필수 검토·구조 검증·current Goal/Handoff가 실제로 존재한다.
4. 현재 필요한 선행 계약·검증·감사와 작업 격리가 충족된다.
5. `(Goal Set Ref, Goal ID)` 및 Handoff·Phase Plan·R 대응을 실행 기록에 실제 값으로 명시한 뒤에만 GEX를 시작한다.

존재하지 않는 Ref를 만들어 적지 않는다. 미래 Goal 전부가 현재 생성·활성화된 것처럼 기록하지 않는다. 이번 계획 요청은 GEX root나 Goal을 실행 대상으로 선택하지 않는다. 후속 구현 대상·범위·종료점은 새 사용자 요청과 실제 GEX가 정한다.

**선택 R의 승인된 기능 범위 안에서 [P2G §8.6](../../policy_to_goal_pipeline_revised_v2.md#86-blocker와-중단-조건)의 다섯 조건을 모두 만족하는 통상적 정책의 결정·기록을 AI에 위임한다.** 기존 합의 유지, 확인된 소유·정체성·수명 등의 도출 근거, 별도 게임 규칙을 추가하지 않음, 해당 기능 안의 영향, 기존 사용자 데이터 보존을 모두 확인한다. gameplay·수명에 관한 결정이라는 이유만으로 질문하지 않는다. 조건을 만족하지 못해 사용자가 원하는 게임 경험을 선택해야 하는 정책, 명시된 정책·예외의 변경, 범위·위험·외부 권한 확대는 위임하지 않는다.

위임 판단·exact 결정·영향은 기존 owner 기록에 남기고 사용자 직접 답변과 구분한다. 정식 정책은 P2G-10의 Decision/Policy Element에 반영하며, 통상적이라는 이유로 동결된 artifact를 직접 고치거나 필수 검토·동결·인계를 생략하지 않는다. 같은 선택 R 안의 필요한 P2G owner 처리는 위 계획 권한으로 수행한다. 보고서의 권고·관행·기존 placeholder 자체는 승인 근거가 아니다. 승인 의미를 보존하는 자료구조·함수·파일·테스트 설계와 기술적 계획 분할은 기술 결정으로 처리한다. 분류에 필요한 사실은 먼저 조사하고 사용자 선택이 필요한 경우에만 질문한다.

기존 정식 Goal·Phase·Atomic Group이 다른 R까지 걸쳐 있어 선택 R만으로 유효하게 수행할 수 없다면, 임의로 잘라 실행하거나 전체를 승인된 것으로 취급하지 않는다. 실제 충돌·최소 동시 전환·조정 owner를 확인하여 필요한 최소 범위를 사용자에게 제시한다. 정식 계획의 범위 안에서 기술 상세를 구체화하는 것과 실행 범위를 확대하는 것은 다르다.

## 4. 운영 문서와 이번 실행 범위의 연결

이 요청은 **선택 R 하나의 P2G 계획·인계를 완료하는 연속 요청**이다. 같은 R 안의 필요한 P2G owner 전환은 이어가되 P2G-60에서 종료한다. 같은 R이라는 이유로 GEX 경계를 넘지 않는다. 다른 R 착수는 승인하지 않는다.

최초 인수에서 `OPERATING_RULES.md`와 `ROADMAP_STATUS.md`에 이번 단일 R 요청의 원본 위치·개정·선정 R·범위·종료점을 필요한 만큼만 연결할 수 있다. 과거 전체 자동 진행 기록은 당시 기록으로 보존하고 현재 적용 중인 실행 범위와 구별한다. 일반 단일 NEXT 요청의 기본 동작과 최근 기록 보관 규칙을 바꾸지 않는다.

`ROADMAP_STATUS.md`의 다음 카드가 갱신되어도 이번 대상을 다시 선정하지 않는다. 계획 완료 후 다음 카드는 같은 R의 `구현 요청 대기`이며 exact Handoff·Goal 후보·재개 조건을 연결한다. 일반적인 “계속”, 자동 재개·컨텍스트 압축·현황 갱신·모델 변경만으로 구현 승인을 추정하지 않는다. 사용자의 “이 계획으로 구현해줘”처럼 구현을 명시하는 새 요청이 필요하다. 다음 R은 후보·근거만 안내한다.

P2G/GEX 본문·검증기·AGENTS·상위 runner·전역 Codex 설정은 이 요청으로 수정하지 않는다. 정식 artifact의 의미·진입/종료 조건을 우회하지 않는다. 실제 상위 지침과 이 요청의 범위를 양립시킬 수 없으면 정확한 충돌 절과 필요한 최소 변경 권한을 보고한다.

새 Campaign 시스템, 전용 승인 artifact, 중복 상태 기계나 25개 빈 Goal 폴더를 먼저 만들지 않는다. 기존 현황과 원래 Topic/Goal 기록을 이용한다. 이 요청 원문을 AI가 수정하여 자기 권한이나 완료 기준을 넓히지 않는다.

## 5. ROADMAP 순서에 따른 R 선정·고정

순서 원본은 `core_enhanced/docs/roadmaps/content_authoring/reviews/2026-09-09-dependency-review-v2.2/roadmap_v2.2-review/ROADMAP.ko.md`다. 이 개정안의 기본 순서는 R00 → R01 → … → R24다. 과거 CA 번호·NEXT 번호를 R 순서와 동일시하지 않는다.

1. **같은 요청의 재개라면:** 기존 기록에 고정한 R과 마지막 유효 P2G pass부터 이어간다. 계획 인계가 이미 완료됐다면 그 근거와 구현 요청 대기를 보고하고 종료한다. R 전체가 완료된 경우도 재실행하거나 다음 R을 새로 선정하지 않는다.
2. **새 단일 단계 요청이라면:** ROADMAP의 기본 순서와 최신 현황·실제 증거를 대조하여 완료 근거가 유효하지 않은 첫 R 하나를 선정한다. 구현 중·교정 중·감사 대기·보류도 미완료다. 선택을 위해 이미 유효하게 완료된 R을 건너보는 것과, 미완료 R을 우회해 다른 작업을 시작하는 것은 다르다. 모든 R이 유효하게 완료됐다면 근거만 보고한다.
3. 사용자가 특정 R을 명시했다면 그 대상을 확인하되, 실제 선행·현재 진행·정식 계획과 충돌할 때 임의로 순서를 바꾸거나 실행 범위를 넓히지 않는다. 자료로 해결할 수 없는 선택만 질문한다.
4. 선정한 R의 ID·제목·선정 근거·요구 범위·포함/제외·종료점을 시작 보고와 기존 실행 기록에 고정한다. 이후 자동 재개·턴 전환·컨텍스트 압축·현황 갱신은 새로운 R 선정 기회가 아니다.
5. ROADMAP의 권장 순서와 기능상 필수·동시 전환·검증 선행·조건부 관계는 구별한다. 번호만으로 정식 Phase Plan이나 실제 선행 충족을 대신하지 않는다. 순서·현황·진행 중 작업·정식 범위가 충돌하면 직접 근거를 확인하고 최소 질문을 남긴다. 이전 작업을 되돌리거나 완료 상태를 추정하지 않는다.

R00은 기존 M0·CA00·최소 계약 P2G·배포본 인수 성과를 재사용하는 단계다. 전체를 재작성하지 않는다. 최초 구현의 기존 대응은 `GS-CAMEC-P2G50-001 / GOAL-CAMEC-01`과 R01이며, current basis와 후속 진행을 확인한다. 이미 완료된 R01을 매 요청마다 다시 실행하거나 기존 Single Goal을 전체 로드맵 Master로 바꾸지 않는다.

선택 R의 지금 필요한 최소 유효 작업만 상세 계획으로 닫는다. 한 R이 반드시 Single Goal 하나라는 가정은 하지 않는다. 필요한 경우 해당 범위의 Master/Phase Goal Set을 사용하되 최소 동시 전환을 깨지 않는다. 미래 전체의 상세 타입·Phase·Goal을 미리 동결하지 않는다.

## 6. 선택 R 내부의 계획 반복과 인계 종료

선정·고정한 R에 대해서만 다음을 진행한다.

1. 관련 source·정식 artifact·선행 구현/감사의 현재성을 확인한다. 이미 유효한 계획 인계가 있으면 부족한 이번 인계 요건만 확인하고 종료한다. 구현/감사만 남은 경우에도 그 작업을 자동 재개하지 않는다.
2. 필요한 P2G-00→10→20→30→40→50→60을 실제 entry/exit에 따라 수행한다. 이미 유효한 결과는 재사용하고, 통상적 정책 결정과 허용된 기술 수리는 해당 owner에서 기록·검증한다.
3. P2G-20에서 producer·consumer·상태·저장·시험까지 조사하고 P2G-40/50의 기존 필드에 구현 순서와 책임을 연결한다. 구현자가 소비할 설계에는 변경 파일/symbol, 주요 타입·입출력, 처리 순서, 상태 key·수명·저장·복원·취소·오류 처리, 전환 범위, 시험 입력·기대 결과·실행 수단을 위험에 비례해 구체화한다.
4. 핵심 알고리즘·공유 계약·시험 oracle을 “구현자가 결정”으로 일괄 넘기지 않는다. 미완료 설계는 위치·이유·담당 owner·필요 선행과 구현 전 준비 조건을 명시한다. 안전하게 정할 수 있는 내용은 이번 계획에서 닫고, 필요한 선행 구현이 아직 없으면 조건부로 인계한다. P2G-60 complete와 구현 준비 완료를 동일시하지 않는다. 기술적 내부 조정은 후속 GEX의 설계·준비 점검을 따르고 정책/계약 변경은 실제 P2G owner에 반환한다.
5. R 요구→Review→Freeze→Phase Plan→Goal Set→Handoff의 연결·coverage와 구조 검증·설계 의미 검토를 확인한다. 여러 Topic이 필요한 경우 이번 계획 범위의 필수 인계를 대조하며 첫 Handoff만으로 전체 계획 완료를 선언하지 않는다.
6. P2G-60에서 exact current Freeze·Phase Plan·Goal Set·Handoff와 남은 gap·blocker·제약을 연결한다. Goal Set은 `Authored`, `Not Activated`, `Implementation Authorized: No`로 유지한다.
7. §9의 계획 종료 기준선과 원본 복원 위치, §10의 인계 보고를 기존 Topic 기록에 남긴다. 실제 검증을 통과한 결과만 current로 선택하고 구현 전 baseline이나 감사 target을 미리 발행한 것처럼 기록하지 않는다.
8. **필수 P2G-60 종료 조건과 이번 계획 인계 요건을 충족하면 `P2G 계획·인계 완료 / 구현 요청 대기`로 기록하고 최종 응답으로 종료한다.** 이는 요청한 결과를 달성한 정상 종료이며 R 구현 미완료를 blocker로 만들어 계속하지 않는다. GEX-00·activation·production mutation·감사를 시작하거나 위임하지 않는다.

R00 인수·R22 제작·R24 감사처럼 역할이 다른 카드도 이번 요청에서는 필요한 검토·계획 범위만 따른다. 불필요한 구현 Goal을 만들지 않으며 적용되는 계획 결과와 종료점을 분명히 보고한다.

## 7. 질문·보류·중단

다음은 사용자에게 재승인을 요청할 이유가 아니다: 기존 결정의 재확인, 보통의 타입/함수 설계 선택, 허용된 비변경 진단·문서 검사, 같은 R 계획 범위의 문서 수정·P2G owner 전환, 정책 의미를 보존하는 허용된 P2G 기술적 successor. 이 조항은 P2G-60 종료 경계를 넘는 GEX 실행에 적용하지 않는다.

정책을 발견하면 먼저 [P2G §8.6](../../policy_to_goal_pipeline_revised_v2.md#86-blocker와-중단-조건)의 통상적 정책 기준과 §3의 위임을 적용한다. 조건을 모두 만족하면 AI가 결정·기록하고 같은 R 안에서 계속한다. `material_policy`는 의미의 영향 분류이며 그 자체가 사용자 질문 사유는 아니다. 코드·기존 규칙의 사실이 부족하면 허용 범위에서 먼저 조사하고, 기술적 불확실성을 사용자 선호 질문으로 넘기지 않는다.

질문이 필요한 것은 통상적 기준으로 정할 수 없는 gameplay/밸런스/UX/수명/저장손실/호환 선택, 기존 합의의 변경, 범위 확대, 외부 배포·비밀·결제·권한 확대다. 해소할 수 없는 필수 근거 문제는 unknown과 필요한 자료를 보고한다. 이미 원문이나 실제 사용자 답변에서 결정된 내용을 다시 묻지 않는다.

사용자 정책 의논이 필요하면 질문을 **일반 채팅의 최종 답변 본문**에 남기고 응답을 끝내 대기한다. 질문에는 해당 원본 위치, 통상적 기준으로 정할 수 없는 이유·상충 의미, 선택지, 권고와 이유, 영향받는 R/Goal, 마지막 유효 결과와 답변 후 재개 지점을 붙인다. 질문 카드만 띄운 채 주 작업을 계속하지 않는다. 미정 동작을 0·무제한·관행·기존 placeholder 값으로 메우지 않는다. 시험 수치는 승인된 prototype 규칙 안에서만 분리 사용하고 공식 밸런스로 승격하지 않는다.

대기 중 주 작업과 정책에 의존하거나 의존성이 불분명한 작업은 안전하게 중단한다. 이미 실행 중이며 어느 답변에서도 요구사항·완료 기준·결과 유효성이 유지되고 보류 작업과 파일·공유 상태 충돌이 없는 작업만 기존 배정 범위까지 완료할 수 있다. 새 작업·위임·후속 전환은 시작하지 않는다. 기존 독립 작업의 결과는 보존하고, 완료 통지를 받아도 추가 검토·통합·후속 배정 없이 대기한다. 상세 조건은 P2G §8.6과 [GEX §6.6](../../goal_execution_pipeline%281%29.md#66-goal-run-자동-전환과-중단)을 따른다. 이 예외가 선택 R 밖의 작업을 허용하지는 않는다.

**선택 R이 사용자 선택이 필요한 정책 또는 해소할 수 없는 필수 근거/검증/reviewer 요건으로 막히면 보류 상태를 기록하고 종료한다. 다른 R이 독립적으로 가능하더라도 이번 요청에서는 건너뛰어 실행하지 않는다.** 해당 후보의 안내는 가능하지만 계획·초기화·구현·검증·위임은 하지 않는다.

공유 파일이나 기존 함수의 변경 계획만으로 다른 R 착수라고 보지는 않는다. 현재 R에 필요한 소비자 동시 전환과 영향 검증 계획은 포함한다. 실제 source 교정이나 다른 owner 실행이 계획 완료에 필수라면 구현을 시작하지 않고 필요한 선행·최소 조정안을 기록한다. 승인된 계획 범위에서 해결할 수 없는 조건은 직접 근거와 함께 보고한다.

안전·권한·격리 문제, 현재 환경에서 필수 증거를 얻을 수 없는 경우, 사용자 중단 요청, 실제 budget/사용량/도구/세션 제한, 의미 있는 진전 없는 반복도 중단 사유다. 같은 blocked 명령·같은 질문을 무한 재시도하지 않는다. 사용자 pause·budget·안전 정지를 무시하거나 스스로 제한을 늘리지 않는다. Goal을 complete로 바꾸어 중단을 숨기지 않는다.

사용자 답변이 오면 실제 정책 owner에 반영하고 영향받는 최소 계획/검증만 갱신하여 **같은 선택 R**을 재개한다. 답변이 다른 R이나 새 범위까지 승인한 것으로 추정하지 않는다. Codex Goal이 paused 상태라면 사용자/시스템의 정상 resume 절차를 따른다.

## 8. 후속 구현과 감사·독립 제작에 인계할 기준

아래는 별도 사용자 요청 아래 수행할 GEX의 기준이며 이번 계획 요청의 실행 권한이 아니다. [GEX Reader Contract](../../goal_execution_pipeline%281%29.md#기본-구현-인계와-선택적-단계검토)의 기본값은 exact Goal의 내부 구현·자체 검증을 마친 뒤 **GEX-10 Audit Target Record 고정 직후, GEX-20 진입 전 종료**하는 것이다. `구현·자체 검증 종료 / 감사 요청 대기`를 보고하며 Goal 전체 완료로 표시하지 않는다. GEX-20은 사용자가 고성능 모델로 별도 요청한다. “감사까지 끝까지 수행해줘”처럼 감사도 명시 위임한 경우에만 기본 최종 인계 경계를 해제한다. 여러 Phase의 필수 선행 감사는 건너뛰지 않는다.

“단계검토 과정을 포함해줘”처럼 실제 요청한 경우에만 빌드 가능한 중간 checkpoint를 추가한다. 계획 중 요청됐다면 [P2G §8.8](../../policy_to_goal_pipeline_revised_v2.md#명시적-단계검토-요청의-인계)에 따라 기존 설계·Goal 필드에 후보와 검증 방법을 연결한다. 뒤늦은 요청은 frozen Goal을 고치지 않고 GEX 실행 PLAN에 반영한다. WP/Atomic Group/Phase를 임의로 독립화하지 않는다. 중간 지점마다 구현 전/후 Git·해시·복원 자료·검증·잔여 범위를 고정하고 종료하며, 검토·교정·다음 구현은 별도 요청을 기다린다. 단순 언급·모델 변경·검토 PASS는 진행 승인이 아니다. 상세 기준은 [GEX §6.4](../../goal_execution_pipeline%281%29.md#명시적으로-요청한-단계검토)가 소유한다. 이 요청문 채택만으로 중간 단계검토가 활성화되거나 구현이 승인되지는 않는다.

구현 writer는 공유 작업 트리에 기본 한 명으로 유지한다. 선택 R 밖의 신규 작업을 다른 agent에 위임하지 않는다. 선택 R의 읽기 조사와 제한된 검증 보조는 작업 경계를 정하여 위임할 수 있다. 기존 동시 작업과의 충돌·격리도 확인한다.

감사는 구현을 멈춘 안정된 대상에서 [GEX §5·§6.4·§6.7](../../goal_execution_pipeline%281%29.md)에 따라 수행한다. 완료 조건은 전부 추적하되 영향 조건의 직접 검토와 무영향 조건의 검증된 증거 재사용을 구별한다. 원문 의미·source·oracle·환경을 확인하지 않고 과거 PASS를 옮기지 않는다.

필수 독립성은 해당 Goal/사용자 요구대로 유지한다. 그 요구에 어긋나지 않으면 동일한 구현 비참여 reviewer가 관련 Goal과 재감사를 맡고 불변 공통 문맥을 재사용할 수 있다. 매번 새 agent를 만들거나 모든 과거 이력을 다시 읽히지 않는다. 각 pass의 exact 대상·권한·판정은 분리하고 구현 조사/설계/교정 보조를 독립 reviewer로 재사용하지 않는다. 같은 모델·문맥 재사용·분리 관계를 사실대로 기록하며 사람/다른 모델 감사로 과장하지 않는다.

감사 인계에는 원문 요구의 locator, 아직 평가하지 않은 누적 변경, 조건별 영향, 최신 검증과 미해결 finding을 연결한다. 공통 해시·건수·출력 검사는 검증 가능한 도구 결과로 공유하고 AI에는 불일치와 필요한 근거를 중심으로 전달한다. 요약만 보고 승인하거나 추가 원문 접근을 막지 않는다. 감사 시작·종료의 현재성 확인은 유지한다.

현재 GEX 또는 해당 Goal이 별도 reviewer를 요구하지 않는 경우에만 허용된 fresh 자기 검토를 사용할 수 있다. 독립 reviewer가 필수인데 사용할 수 없으면 해당 감사는 보류한다. 독립 요구를 없애거나 자기 구현 요약을 독립 감사로 바꾸지 않는다. 감사자는 source를 고치지 않고 findings/증거를 반환하며 구현자는 별도 pass에서 교정한다.

R22가 선택됐을 때 독립 제작을, R24가 선택됐을 때 독립 최종 감사를 실제 요구를 충족하는 별도 작성자/reviewer로 수행한다. R22에서는 엔진 revision을 고정하고 승인된 지원 어휘를 data-only로 조합한다. R24 감사자는 source를 수정하지 않는다. engine patch나 다른 R의 교정이 필요하면 해당 owner·실패·재동결/재검증 필요 범위를 기록하고 중단한다. 이번 R 요청으로 다른 R의 수리까지 자동 시작하지 않는다. 자동으로 위임했다고 독립성이 저절로 증명되는 것은 아니다.

## 9. 증거·저장·안전·변경 보존

선택 R의 각 단계 검증은 실제 명령·환경·source revision 및 관련 dirty 식별·fixture·실행 건수·기대/실제 결과를 남긴다. 과거 PASS는 재사용 근거와 이번 재실행을 구별한다. 0 tests, skip, 미실행, 검증기 통과를 게임 실행 성공으로 쓰지 않는다.

계획에는 상태가 생기는 구현 단계가 그 상태의 소유·수명·저장·복원·실패·취소를 함께 소유하도록 배치한다. R20에서 처음 저장을 붙이지 않는다. 각 기능 도입 때 예산·결정론 검사를 배치하며 R23에서 처음 안전장치를 도입하지 않는다. 유물 개인별 실행 계획은 지연 step/projectile/area/preview까지 같은 계획을 소비하는 전환으로 묶는다.

전체 테스트를 매 작은 수정마다 무의미하게 반복하지 않는다. 변경 input→소비자→검증 범위로 focused 시험을 선택하고, 필수 baseline/통합/release/독립 인수는 해당 owner 단계에서 수행한다. 테스트를 삭제·완화하여 실패를 숨기지 않는다. 승인된 정책 전환 때문에 기대값이 바뀔 때는 기존 의미의 처분과 대체 coverage를 기록한다.

기존 사용자 dirty·미추적 파일·정식 artifact·검토 배포본과 그 해시/과거 receipt를 보존한다. dirty 보존은 해당 파일의 모든 추가 수정을 금지한다는 뜻이 아니다. 선택 R에 필요한 수정은 기존 변경의 내용과 의미를 보존하고 이번 변경을 구별하는 조건으로 수행하며, 다른 작업자의 충돌하는 동시 변경이나 보존 불가능한 부분은 질문한다. reset/clean/stash/강제 checkout·대량 재포맷·개인 저장 삭제/자동 변환을 하지 않는다. 별도 worktree/사본을 쓸 경우 현재 dirty가 빠진 clean HEAD를 같은 기준선으로 오인하지 않는다.

배포, remote push/merge, 전역 설치·환경 설정·Codex 권한/예산·검증기·P2G/GEX·AGENTS 수정은 별도 승인 없이 수행하지 않는다. repository sandbox 안의 승인된 계획 문서·검증·인계 기록만 변경한다. 필수 외부 접근은 허용된 경로를 사용하거나 필요한 좁은 승인을 요청한다. 안전장치를 비활성화해서 질문을 줄이지 않는다.

### 계획 종료 기준선과 후속 구현 전·후 비교

계획 종료 시 기존 Topic의 인계 기록 한 곳에서 다음을 연결한다. 이는 요청의 인계 요건이며 새 P2G schema/enum이나 별도 승인 artifact가 아니다.

- 저장소 위치·branch·HEAD·관찰 시점, `git status` 목록과 관련 staged/unstaged/untracked 구분.
- 검토한 source·직접 의존·계획 산출물의 명시적 경로·파일별 SHA-256, 삭제/부재와 예정 신규 파일의 `absent` 표시. 범위·제외 기준과 manifest 자체의 SHA-256을 별도 인계 기록에 남겨 자기 해시 순환을 피한다.
- 실제 이전 내용을 읽고 비교할 수 있는 원본 위치. clean tracked는 보존된 Git object, dirty/staged/untracked는 사본 또는 재구성 가능한 binary patch와 필요한 신규 파일 원문을 보존한다. 해시나 status 목록만으로 원본이 복원된다고 보지 않는다. 임시 `/tmp` 사본만을 durable 인계 원본으로 사용하지 않는다.
- exact Freeze·Phase Plan·Goal Set·Handoff 참조와 실제 검증 결과, 미결 설계·선행·다음 owner. 기존 근거를 링크로 재사용하며 전체 저장소 복제를 의무화하지 않는다.

계획 종료 기준선은 관찰 당시 코드다. 별도 구현 요청을 받은 실행자는 mutation 직전에 current source와 대조하고 영향 없는 차이·계획 전제 변경을 구분한 뒤 구현 직전 baseline을 연결한다. 구현 후에는 그 baseline 대비 추가·수정·삭제, before/after 해시, 복원 가능한 diff·원문, 실제 테스트와 exact Audit Target Record를 고정한다. 감사에서 교정이 필요하면 별도 구현 pass와 successor target으로 연결한다. 해시 일치는 내용 정체성 근거이며 구현 정확성·테스트·감사 판정을 대신하지 않는다.

## 10. 기록·재개와 최종 종료 보고

진행 상황은 `ROADMAP_STATUS.md`와 기존 Topic/Goal 실행 문서에 남긴다. R↔정식 Goal 대응이 실제로 커질 때만 운영 규칙이 허용하는 `WORK_INDEX.md` 등으로 분리한다. 새로운 전체 복제 장부를 의무적으로 만들지 않는다. 현재 구현/교정 결과·target·검증·미해결 finding·다음 pass의 정확한 locator는 한 곳에서 갱신하고 다른 문서는 참조한다. 사소한 실패마다 전체 권한·이력·감사 순서를 재서술하지 않는다. 동결 전 현재 요약을 맞추고, 이미 동결된 요약은 원본 보존 후 허용된 비대상 안내로 최신 결과를 연결한다.

의미 있는 단위 종료·정책 질문·교정/감사 전환·세션 한계 전에 다음을 저장한다: 이번 요청 위치와 개정, 선정·고정한 R과 종료점, exact Topic/Goal/Handoff·pass, 마지막 유효 결과, 자신의 변경과 기존 dirty 구분, 실제 test/감사 evidence, 보류 이유와 영향 범위, 같은 R 안의 다음 안전한 작업. 요청 원문·자식 증거·현황 요약의 책임을 분리한다.

컨텍스트 압축 뒤에는 현재 checkpoint와 관련 변경만 대조해 **선정한 R의 미완료 P2G 계획 범위**를 이어간다. 계획 종료점에 도달했다면 완료 결과만 보고하고 멈춘다. 새 세션의 일반적인 재개·“계속”·모델 교체는 구현 승인으로 해석하지 않는다. 사용자가 구현을 명시하는 별도 요청을 하면 그때 exact Handoff·Goal·종료점을 확인한다. 프로세스 종료·연결 상실 뒤 실제 실행하지 않은 작업을 백그라운드에서 계속한 것처럼 보고하지 않는다.

진행 보고는 현재 R/P2G 단계·방금 검증한 결과·남은 핵심 사항을 짧게 제시하되 같은 P2G 범위의 계속 진행 승인을 매번 묻지 않는다. 종료 보고에는 계획 완료/부분 완료, exact 계획·Handoff 경로와 Ref, 상세 설계·검증 결과, Git·manifest 해시·원본 위치, 남은 설계·선행·제약, 같은 R의 후속 구현 요청 예문을 남긴다. 예문의 실제 Ref는 생성된 값만 사용한다. R 구현·감사는 별도 미완료로 보고한다.

감사 대상에 속하는 현황·계획 문서를 감사 중에 수정하지 않는다. 허용된 감사 evidence를 먼저 남기고, 현황 요약 갱신은 별도 허용된 기록 작업으로 수행하여 증거의 현재성 영향을 확인한다. 과거 실행·정책 결정·감사 verdict·실패 기록을 개정 요청에 맞추어 소급 변경하지 않는다.

**P2G-60 검증과 이번 계획 인계 요건을 충족하면 계획 요청을 완료하고 최종 응답으로 종료한다. 필수 계획 요건이 미완료이면 부분 완료/보류로 보고한다. R 구현·감사 미완료는 계획 요청을 계속할 이유가 아니다. 같은 R의 GEX 진입과 다른 R 착수에는 각각 새 사용자 요청이 필요하다.** 실행 시스템의 목표가 아직 옛 R 전체 완료로 남아 있으면 이번 사용자 변경 요청과 새 종료점을 연결하고 시스템이 제공하는 정상 절차를 따른다. 문서 편집만으로 시스템 Goal이나 모델을 자동 변경했다고 주장하지 않는다.
