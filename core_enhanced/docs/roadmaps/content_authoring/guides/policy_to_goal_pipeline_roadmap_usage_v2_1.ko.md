# 로드맵을 Policy-To-Goal Pipeline으로 점진적으로 실행하는 방법

개정일: 2026-10-04 · 운영안 v2.1.3 (품질 유지와 재작업 감소; 초기 본문은 P2G r2 기준)
성격: 개선 지침의 사용 제안. 새로운 승인 기록·Policy Topic·Freeze·Goal Set·실행 상태가 아니다.
기준 자료: [현행 P2G](policy_to_goal_pipeline_revised_v2.md), [로드맵 v2.1](../roadmap/ROADMAP.ko.md). 실행의 첫 진입점은 [ROADMAP_STATUS.md](../ROADMAP_STATUS.md), 재개·분리 규칙은 [OPERATING_RULES.md](../OPERATING_RULES.md)다.

## 1. 결론

이 방식은 적합하다. 로드맵은 전체 방향·공통 설계와 의존성의 지도이고, P2G는 선택한 범위를 코드에 근거한 정책·Phase·Goal로 바꾸는 절차다. GEX는 그 Goal을 실제로 구현·검증·감사하는 절차다.

다만 **“CA 하나 = P2G 한 번 = Goal 하나”로 고정하지 않는다.** 실제로 함께 변경해야 유효한 중간 상태를 만드는 계약 경계를 선택하고, 그 안에서 P2G로 Goal을 작성한 뒤 GEX로 구현한다. 번호는 추적용이며 작업을 나누는 근거가 아니다.

## 2. 세 문서의 책임

| 자료 | 질문 | 산출·책임 |
| --- | --- | --- |
| 로드맵 v2.1 | 무엇을 왜 어떤 방향으로 만들 것인가? | 전체 요구, 권장 구조, 선행 작업 후보, 검증 사례 |
| P2G | 지금 선택한 정책과 구현 경계를 어떤 Goal로 닫을 것인가? | 정책 결정, 코드 기반 검토, Freeze, Phase Plan, Goal Set, Handoff |
| GEX | 이 Goal을 현재 코드에서 어떻게 구현하고 완료를 증명할 것인가? | 실행 기준·권한, 상세 설계·구현, 실제 검증, 완료 감사 |

로드맵의 권장 아키텍처를 그대로 현재 코드라고 보지 않는다. P2G-20에서 해당 경계의 실제 코드를 읽고 재사용·교체·인터페이스·상태 수명과 검증 가능성을 확인한다. 구현 단계에서는 현재 선행 결과에 맞는 정확한 타입·함수·패치·시험을 상세화한다. 두 수준의 조사를 구분하며, 이미 유효한 근거는 관련 변경이 없을 때 재사용한다.

## 3. 권장 진행 순서

### 3.1 다음 후보를 선택한다

로드맵 전체와 관련 공유 계약에서 다음 작업 후보를 고른다. 정식 Topic이 아직 없으면 먼저 `inspect` 또는 범위 논의로 후보 경계를 설명할 수 있다. 이 활동만으로 Policy Topic이나 Goal이 생성·승인된 것은 아니다.

선택 질문은 세 가지다. 첫째, 지금 승인·검토할 의미와 완료 기준을 닫을 수 있는가? 둘째, 함께 바꿔야 하는 생산자·소비자·저장 경계가 무엇인가? 셋째, 완료 이후 후속 작업이 멈춰도 현재 상태가 유효한가?

이미 대화에서 확정한 최신 규격·외부 RON·사본별 개화 등을 다시 묻지 않는다. 원문과 exact approval을 연결하고 현재 선택 범위에 적용되는지만 확인한다. 반면 미정인 보호막 소비 순서나 형태 전환 자원 처리까지 승인됐다고 추정하지 않는다.

### 3.1.1 계획상 순서를 실행 순서로 승격하지 않는다

로드맵의 CA/M 순서·선행 표·GOALS.json은 코드 검토를 참고한 **후보**이며 모든 관계를 실제 코드로 검증한 스케줄이 아니다. 문서 graph의 정합성 검사와 실제 순서 타당성을 구분한다.

최초 인수·CA00에서 공유 경계의 큰 누락·역전·과잉 선행을 1차 확인하고, 선택할 범위의 직접 전제를 특정한다. 이후 P2G-20이 실제 생산자·소비자·상태·스키마·저장·테스트를 대조하고 P2G-40이 관계 유형·최소 동시 전환·독립 중간 상태를 근거로 Phase를 정한다. 이 초기 조사가 정식 P2G 검토를 대신하지 않는다.

필수 기능·동시 전환·검증 선행·진행상 권장을 구분하고, 실제 선행 결과·소비 지점·source·순서를 무시할 때 깨지는 상태를 owning 문서에 기록한다. 미래 전체 설계가 끝날 때까지 기다리지 않고, 지금 수행할 경계의 required 근거를 닫는다. 자세한 기준은 [DEPENDENCIES](../roadmap/DEPENDENCIES.ko.md)에 있다.

현황에는 `계획상 후보 / 코드 검토된 범위와 Plan / 실제 선행 구현·감사 준비`를 분리해 요약한다. current Phase Plan의 변경은 해당 P2G owner가 처리하며 번호나 JSON만 고쳐 강행하지 않는다.

### 3.2 선택한 Topic을 P2G로 Goal화한다

사용자가 선택한 Topic과 끝점을 지정하면 그 범위에서 `bounded_pipeline`으로 진행한다. Goal 작성까지면 필요한 P2G-00 → 10 → 20 → 30 → 40 → 50, handoff까지면 60도 포함한다. 이미 current인 prerequisite는 재사용하며 매번 다시 만들지 않는다.

단계별 확인을 원하는 경우 `P2G-20만`처럼 `single_stage`로 요청할 수 있다. 두 방식 모두 같은 entry/exit·불변 revision·참조·coverage 검증을 수행한다. 차이는 검증 경계마다 사용자에게 진행 허락을 다시 받는가이다.

| 단계 | 이 프로젝트에서의 의미 |
| --- | --- |
| P2G-00 | 승인한 좁은 scope와 원문을 보존해 Working Policy Document 초기화 |
| P2G-10 | 관련 정책·미정 질문·판정 기준을 정리. 필요한 좁은 사실 확인은 가능하나 정식 코드 검토를 대신하지 않음 |
| P2G-20 | 현재 실행 경계와 로드맵의 권장 구조를 대조. 공유 계약·원자적 전환·검증 수단을 검토 |
| P2G-30 | 해당 in-scope 의미와 코드 검토가 닫힌 정책 basis를 동결 |
| P2G-40 | Work Package·Atomic Group·Phase를 실제 유효 상태에 맞게 분해. 로드맵 CA 수를 강제하지 않음 |
| P2G-50 | current Plan의 모든 Phase를 Goal로 작성하고 코드 기반 상세 설계 인계를 포함 |
| P2G-60 | exact basis와 아직 수행하지 않은 상세 설계·구현·검증 조건을 GEX에 인계 |

r2는 **범위가 확인된 최종 산출물 요청을 단계별 재승인 없이 완성할 수 있도록** 진행 권한을 바꿨다. 단계 자체는 합치거나 건너뛰지 않는다. 각 owner가 완전한 결과를 낸 뒤 다음 단계가 이를 소비한다.

새 정책이 필요하면 질문에서 멈춘다. 기존 요청의 질문에 답을 받으면 그 범위에서 이어갈 수 있으며, 단순 문서·참조·구조 오류는 해당 owner에서 교정·재검증한다. Topic 선택이 불명확하거나 범위·비용·위험·권한이 늘어나면 필요한 입력을 요청한다. “Goal까지”가 다른 Topic이나 게임 구현까지 허용하는 뜻은 아니다.

### 3.3 Goal을 GEX로 구현한다

P2G는 production 코드를 수정하는 파이프라인이 아니다. GEX의 현재 절차에 맞춰 exact Handoff와 선택 Goal을 인수하고 별도 실행 권한을 부여한다.

계획 요청은 P2G-60 검증·상세 계획 인계 후 종료하고 별도 구현 요청을 기다린다. 구현자는 관련 코드 종단 조사 → 상세 설계·준비 점검 → 전체 내부 구현·자체 테스트·허용된 교정 → 구현 후 target 고정까지 진행한 뒤, 기본적으로 감사 요청 대기로 종료한다. 감사까지 명시 위임한 경우의 예외는 [GEX Reader Contract](../../../goal_execution_pipeline%281%29.md#기본-구현-인계와-선택적-단계검토)를 따른다.

사용자가 “단계검토 과정을 포함해줘”라고 실제 지시한 경우에만 중간 검토 중단을 추가한다. 사전 중단 조건·검증 기준은 연결하되 실제 지점은 구현자가 의미 있는 부분 진전·빌드·해당 변경의 관련 검증 결과를 보고 다음 큰 작업 전에 선택한다. 사전 후보·전체 checkpoint 일정은 필수가 아니며 WP별 독립 컴파일이나 Goal 전체 기능의 완료를 요구하지 않는다. 구간 시작 전 baseline은 먼저 고정하고, 실제 지점을 선택할 때 범위·근거·구현 후 target·관련 검증·미완료 범위를 고정한 뒤 종료한다. 읽기 전용 검토, 필요한 교정·재검토, 다음 구현은 별도 요청을 기다린다. PASS나 모델 변경은 진행 승인이 아니고 부분 검토는 최종 GEX 감사를 대신하지 않는다. 세부 규칙은 [GEX §6.4](../../../goal_execution_pipeline%281%29.md#명시적으로-요청한-단계검토)가 소유한다.

이 운영안은 GEX 본문이나 구현 권한을 바꾸지 않는다. GEX/상위 AGENTS/runner가 더 좁은 승인을 요구하면 실제 계약과 대조하고 필요한 지침 변경을 별도로 처리한다. P2G 파일 하나를 교체했다고 모든 구현 에이전트가 자동으로 연속 실행하게 됐다고 가정하지 않는다.

같은 Topic이 여러 Phase Goal을 만들었다면 각 Phase마다 P2G-00부터 다시 시작하지 않는다. 같은 accepted Handoff와 실제 선행 Phase evidence를 사용한다. 예상된 코드 변경은 정상적인 구현 결과다. 정책·검토 전제·Phase 경계가 실제로 틀렸다는 사실이 나타났을 때만 필요한 owner 단계로 반환한다.

### 3.4 실제 결과를 로드맵에 환류한다

작업별 완료 evidence, 채택하거나 수정한 권장 구조, 새 공통 기능, 남은 정책과 후속 의존을 상위 문서에서 참조한다. 코드가 존재하거나 Goal이 작성됐다는 이유로 로드맵 항목을 완료로 표시하지 않는다.

최종 통합 검증은 선택한 모든 계약이 함께 성립하는지 확인한다. 대표 RON 사례뿐 아니라 고정 엔진에서의 제3자 재조합, 정확한 상태 수명과 실패 진단도 증거가 필요하다.

## 4. 이 프로젝트에서의 경계 예시

아래는 범위 선택을 설명하는 **후보 예시**이며 정식 승인된 Topic·Phase·Goal 배정이 아니다. 구체적인 결합·분할은 P2G-20/40에서 현재 코드를 확인해 정한다.

| 후보 | 함께 확인할 경계 | 피해야 할 잘못된 분할 |
| --- | --- | --- |
| 외부 데이터 묶음의 검증·게시와 새 런 고정 | 로더, 최소 최신 작성/컴파일 계약, 최종 참조 검증, 공개 생성 포트, 정상 실행 fixture | 파일 읽기만 구현하고 검증 없이 authoritative Core를 만들거나, 미래 CA가 있어야만 정상 런을 구성할 수 있는 상태를 완료로 취급 |
| 파편 사본별 identity와 개화 | 지급·보유·장착·Maintenance·형태·자원·저장 reader/writer | 인벤토리만 사본화하고 장착·성장·저장에 종류별 장부를 남기는 분할 |
| 보스 작업의 스킬 실행과 결과·취소 | 보스 상태, 스킬 실행 핸들, 완료 지점, 작업 epoch, 방출 효과 수명, 오류·trace | 요청만 보내고 완료·취소·늦은 결과 처리는 다음 Phase로 미루는 분할 |
| 유물 선택·부여·변형·활성 판정 | effect identity, property capability, 불변 정의, 최종 계획, 휴면·충돌, 관련 ownership | 태그 검색만 만들고 실제 변경 가능한 속성과 실행 결과는 일치하지 않는 상태 |

외부 로딩 후보에는 CA01/02/03/19의 일부 관심사가 함께 등장할 수 있다. 그렇다고 그 CA 전체를 무조건 한 Topic으로 합치는 것은 아니다. 현재 경계에서 최소한의 정상 실행·저장 또는 명시적 거부를 성립시키는 데 필요한 범위만 묶는다.

## 5. 장기 로드맵을 한 번에 동결하지 않는 이유

전체 제작 기반을 하나의 거대한 Policy Topic으로 잡으면 후반 콘텐츠의 미정 판정 하나가 초반 기반의 Goal 작성까지 막을 수 있다. 모든 함수를 먼저 설계하고 동결하면 앞 단계 구현에서 드러난 사실을 반영하기도 어렵다.

반대로 지나치게 작은 항목은 생산자·소비자·저장 전환을 갈라 부분적으로 고장 난 상태를 만들 수 있다. 따라서 **상위 공통 계약은 공유하고, 실행은 의미·수명·원자성으로 닫히는 경계 단위**로 진행한다.

공유 계약 역시 그 내용이 아직 권장안인지, 정책 동결인지, 실제 구현 완료인지 구분한다. 선행 계약의 구체적인 완료 기준과 구현 owner가 있어야 후속 작업이 기대할 수 있다. 근거가 필요한 현재 경계를 “나중에 구현하면 된다”로 바꾸어 동결하지 않는다.

## 6. 작은 조회용 진행표

새 전역 관리 시스템은 필요하지 않다. 이미 있는 로드맵/프로젝트 문서에 아래 연결을 조회용으로 두는 것으로 시작할 수 있다.

| 로드맵 범위 | 정책 owner / current basis | Phase·Goal·Handoff | 실제 GEX evidence | 남은 의존·정책 |
| --- | --- | --- | --- | --- |
| 선택한 실제 경계 | exact source 또는 아직 미작성 | exact refs 또는 아직 미작성 | 실행 안 함 / 실제 기록 위치 | 구체적인 미정·제약 |

표는 근거에서 계산하는 view이며 새로운 권위 있는 상태 장부가 아니다. 중복으로 작성된 정책 문구보다 원래 결정·코드 검토·Goal·실행 기록의 exact 관계를 유지한다.

## 8. 읽기·검증을 반복 의식으로 만들지 않는 방법

AGENTS.md에는 모든 문서 내용을 복사하지 않고 짧은 적용 조건과 경로만 둔다. 정책을 Goal로 만드는 작업이면 P2G, 승인된 Goal 구현이면 GEX를 읽도록 안내한다. 일반 오타 수정이나 설명 편집에 새 Topic·Freeze·Goal을 자동 생성하지 않는다.

현재 단계와 실제로 사용하는 artifact의 계약·template부터 읽고, 정보가 부족할 때 관련 source로 확장한다. 이미 읽은 내용과 유효한 검증 근거는 재사용하되, 관련 코드·데이터·설정·의존성·환경이 바뀌면 영향받은 부분을 다시 확인한다. shared schema·harness처럼 영향 분리가 어렵거나 최종 통합 계약이 요구하면 넓은 검증을 수행한다.

새 evidence envelope가 필요하다는 사실과 원문 전체를 다시 읽거나 같은 테스트를 다시 실행해야 한다는 것은 다르다. 변경 영향을 평가하여 근거의 재사용 가능성을 확인하고, 이번에 재실행한 것으로 꾸미지 않는다.

## 9. 이번 개정의 적용 한계

v2.1.3은 P2G r8/GEX gex-r8의 운영 방법을 연결한다. 공통 생성기·fixture·검사기가 새로 구현됐다는 결과가 아니며
정식 artifact schema·validator·Goal의 완료 조건은 바꾸지 않는다. 진행 중 적용과 변경 전후 근거는
[2026-10-04 운영 개정 인수 기록](../../core_first/execution/workflow_efficiency_update_20261004_001/RECORD.ko.md)을 따른다.


v2.1.2는 사전 checkpoint 확정을 요구하지 않고 구현 중 선택하도록 안내한다. [후속 변경 기록](../records/adaptive_stage_review_20260913/README.ko.md)이 이번 검증을 소유하며 아래 v2.1/v2.1.1 기록은 보존한다.

v2.1.1은 §3.3에 현재 P2G r6/GEX gex-r6의 중단·검토 경계를 연결한 안내 개정이다. 다음 문단의 v2.1 작성 범위는 당시 이력이다. 이번 공통 지침 변경·구형 요청문 제거·검증의 실제 범위는 [변경 기록](../records/optional_stage_review_20260913/README.ko.md)이 소유한다.

이번 v2.1 묶음에서는 로드맵·현황·운영 문서를 개정했고 P2G r2는 bytes 변경 없이 포함했다. 정식 Goal·동결 artifact·프로젝트 코드·validator·GEX 본문은 수정하지 않았다. 실제 전체 의존성 검토·Phase Plan 작성 또는 실행 준비 확인을 수행한 결과가 아니다. 현재 저장소에 적용할 때는 실제 파일과 diff를 비교하고, Working Revision 저장/검증 도구가 있다면 새 applicable Decision Repartition Member를 소비할 수 있는지 확인한다.

P2G-50의 기존 quality-contract 2 field와 명령은 유지했다. r2의 Progression Mode·종료/재개 값은 요청을 기록하는 작업 view이며 새 정책 payload가 아니다. 이 view나 요청당 단일 단계 가정을 외부 도구가 해석한다면 그 consumer도 대조해야 한다.

문서 수준 검사와 실제 P2G-40/50 validator 실행·GEX 실행·게임 테스트는 별개다. 이 운영안의 예시는 실행 결과가 아니다. 저장소에 적용할 때 원래 요구한 artifact 검증과 의미 검토를 수행해야 한다.
