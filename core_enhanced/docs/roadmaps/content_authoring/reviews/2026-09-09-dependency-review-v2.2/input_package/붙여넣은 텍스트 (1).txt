# 1. 핵심 목적과 검토 대상

최종 목표는 제3자 제작자가 엔진의 공통 명령·행동·조건·효과·규칙을
RON으로 조합하여 보스·장비·무기·스킬 파편·유물을 제작하고,
기존 콘텐츠를 변형·교체할 수 있는 기반을 만드는 것입니다.

지원하는 조합 안의 새 콘텐츠마다 전용 실행 코드를 추가하지 않는
구조를 원합니다. 표현 수단이 부족할 때 엔진 공통 기능을 확장하는 것은
허용하지만, 모든 미래 기믹을 엔진 업데이트 없이 표현해야 하는 것은 아닙니다.

기존 로드맵의 순서는 권장안이며, 모든 작업 사이의 실제 코드 의존성이
검증된 확정 실행 순서는 아닙니다.

이번에는 당신이 실제 코드를 읽고 다음을 판단해 주세요.

- 무엇이 반드시 먼저 구현되어야 하는가?
- 어떤 변경은 함께 전환해야 하는가?
- 기존 선행 관계 중 불필요하거나 지나치게 넓은 것은 무엇인가?
- 어떤 작업은 나누거나 앞당길 수 있는가?
- 각 단계가 끝난 직후, 다음 단계를 수행하지 않아도
  그 단계가 약속한 기능과 데이터·상태·검증 경로가 유효한가?
- 현재 작성된 GOAL-CAMEC-01은 전체 개발의 첫 구현 단위로 적절한가?

“구현 AI가 나중에 의존성을 확인해야 한다”는 문구를 추가하거나,
기존 화살표를 정리하는 것만으로 끝내지 마세요.
실제 코드에 근거한 관계와 구현 순서를 이번 작업에서 제시해야 합니다.

기존 M0~M8·CA00~CA23은 누락 방지와 변경 추적 기준입니다.
기존 번호·단계 수·작업 개수·순서를 보존하는 것을 목표로 삼지 마세요.
분할·병합·재배치가 필요하면 근거와 기존 요구의 대응 관계를 남기세요.

# 4. 유지할 확정 방향

기존 합의와 최신 승인 원문을 기준으로 다음 방향을 유지하세요.

- RON 조합기 프로그램 자체는 범위 밖입니다.
  엔진 측 작성 정보·검증·진단·설명·시험 실행 기반은 포함합니다.
- 대표 공식 콘텐츠를 실제 최신 RON으로 이식하고,
  전체 합의된 콘텐츠 구조의 표현력은 별도로 대조합니다.
- 기존 RON 전량 교체를 허용합니다.
  레거시 parser·alias·shim·구형/신형 이중 실행 경로를
  새 전환 방식의 기본 해법으로 삼지 않습니다.
- 외부 live_data와 다중 콘텐츠 팩, 명시적 교체·의존성·충돌 검증을
  최종 목표에 포함합니다.
- 일반 플레이는 새 런에서 검증된 데이터 묶음을 고정하고,
  시험 전투는 재로딩 성공 후 초기화합니다.
  진행 중 전투의 정의를 즉시 바꾸는 기능은 범위 밖입니다.
- 제작자의 콘텐츠 추가·변형·교체·등장 및 획득 연결을 허용합니다.
  외부 스크립트·플러그인 코드 실행은 제외합니다.
- 파편 개화는 개별 인스턴스가 독립적으로 소유합니다.
- 유물·성장·침식의 승인된 의미를 보존하고,
  미정 수치·판정은 임의로 확정하지 않습니다.
- “침식된 유물”과 “파편 침식형”을 구분합니다.

기존 RON 폐기 허용은 이번 조사에서 파일을 삭제하라는 권한이 아닙니다.
또한 최신 규격 목표가 모든 기존 저장 reader를 이번 최소 Goal에서
즉시 제거하라는 뜻인지 임의로 해석하지 마세요.
현재 Goal의 명시적 범위, 실제 저장 영향, 후속 전환 목표를 구분하세요.

15개 공통 분해 축은 표현력과 변경 지점을 검토하는 설계 틀입니다.
그대로 15개 schema 필드나 독립 기능으로 환원하지 마세요.

단계·분기·병행 관계 → 개별 효과 → 각 효과의 해당 하위 축 순서로
요구를 읽고, 소환물·변신·공유 자원 등 별도 책임도 확인하세요.


# 5. 실제 코드 조사 방법과 깊이

workspace 기준 상대 경로로 read_file, search_workspace,
list_directory를 사용하세요.

지도·기존 검토·로드맵의 파일 목록은 탐색 입구입니다.
중요한 결론은 현재 코드·RON·정책 원문에서 확인하세요.

각 작업의 변경에 영향을 받는 경로를 연결해서 읽으세요.

입력·참조·호출자
→ 파싱·검증
→ 변환·컴파일
→ 실제 실행 소비자
→ 상태 변경·결과
→ 취소·종료·실패·복원
→ 저장·로드·관련 테스트

특히 다음 경계를 빠뜨리지 마세요.

- 로딩·검증·정의 게시와 런별 데이터 선택
- 효과 작성·식별·계산·대상·전달·실행 흐름
- 사건·피해 결과·출처·자원·상태 수명
- 장비·파편 사본·개화·형태·장착·성장
- 유물 소유·활성 판정·효과 변형·연쇄
- 보스 상태·패턴·작업·스킬 호출·이동·소환·전장 사건
- 웨이브·결과·후퇴·재시도·재배치·저장·재접속
- 실제 RON 이식·등록·headless 검증·독립 제작·성능 검증의 소비 경로

전체 저장소의 모든 줄을 읽는 것이 목표는 아닙니다.
하지만 필수 호출자·소비자·상태·저장·검증 경계를 읽지 않고
확인했다고 표현해서는 안 됩니다.
긴 파일은 필요한 연속 구간으로 나누고 읽은 범위를 기록하세요.

enum·타입·함수·테스트가 있다는 이유만으로 실행 지원을 인정하지 마세요.
기존 RON 사례가 없다는 이유만으로 기능이 없다고 판단하지도 마세요.
검색 결과가 없으면 탐색 범위와 다른 연결 경로를 먼저 확인하세요.

다음 세 관계를 구분하세요.
- 현재 코드의 실제 호출·데이터 의존성
- 목표 구조로 전환할 때 필요한 구현 의존성
- 불필요한 재작업을 줄이기 위한 진행상 권장 순서

아직 없는 제안 API는 현재 코드처럼 취급하지 마세요.
필요한 목표 계약, 기존 코드와의 연결, 생산자·소비자·구현 책임으로
설명하고 그 부분은 설계 판단임을 표시하세요.

이번 조사에서 읽지 않은 코드나 미실행 시험이 어떤 결론을 제한하는지
구체적으로 남기세요.


# 6. 의존성 분류와 구현 순서 재설계

기존 CA 작업을 실제 변경 경계로 분해하고,
기존 선행 관계와 새로 발견한 관계를 다음처럼 분류하세요.

1) 기능상 필수 선행
   후행 작업의 어떤 부분이 선행 작업의 어떤 계약·상태·동작을
   실제로 소비하는가?

2) 동시 전환
   나누면 상태 소유·트랜잭션·reader/writer·저장·장착·데이터 참조·
   실행 의미가 서로 어긋나는가?

3) 검증 선행
   후행 결과를 독립적으로 증명하려면 어떤 데이터·도구·검증 경로가
   먼저 필요하며, 누가 그것을 구현하는가?

4) 진행상 권장
   필수는 아니지만 재작업·위험·파일 충돌을 줄이는 순서인가?

5) 조건부 관계
   어떤 미정 정책이나 미확인 사실에 따라 순서·범위가 달라지는가?

주요 관계마다 다음을 남기세요.

- 선행 결과와 실제 후행 소비 지점
- 파일·심볼·RON 참조 등 확인 가능한 근거
- 관계가 필요한 이유
- 무시하면 깨지는 동작·중간 상태·완료 조건
- 기존 기능으로 이미 충족되는 부분
- 코드 관찰 / 목표 설계 판단 / 실행 관찰 중 근거의 종류
- 남은 가정·한계

“A 전체 → B 전체”를 그대로 받아들이지 마세요.
후행 작업 일부가 선행 작업의 특정 계약만 필요로 하면 그 경계를
드러내고, 독립적으로 구현·검증할 수 있는지 판단하세요.

반대로 나누면 유효하지 않은 변경을 CA 번호가 다르다는 이유로
분리하지 마세요. 새 상태를 도입하는 작업은 필요한 저장·복원·검증을
함께 소유해야 하며, 저장 관련 작업이 뒤에 있다는 이유로 미루지 마세요.

순환 의존은 다음 중 무엇인지 판단하세요.
- 함께 전환해야 하는 최소 묶음
- 실제 안정된 계약으로 분리할 수 있는 관계
- 잘못된 작업 분해
- 정책 결정 또는 추가 근거가 필요한 관계

순환을 없애기 위해 근거 없이 edge를 삭제하거나,
빈 executor·임시 성공 처리·미승인 fallback을 제안하지 마세요.

각 구현 단계 직후 다음 질문에 답하세요.

“다음 단계를 수행하지 않더라도, 이 단계가 약속한 기능·상태·
최신 데이터 경로·검증이 유효한가?”

후속 기능이 아직 없는 것은 허용됩니다.
하지만 현재 단계의 완료 조건을 만족시키려면 후속 단계가 반드시
필요한데도 현재 단계를 독립 완료로 나누면 안 됩니다.

병렬화는 화살표가 없다는 이유만으로 허용하지 마세요.
공유 상태·스키마·파일·테스트 환경·병합·통합 검증의 독립성을
확인하고, 근거가 부족하면 순차 진행으로 제안하세요.

최종적으로 하나의 권장 기본 순서를 제시하세요.
정책에 따라 갈리는 일부 관계는 조건과 대안 경로로 별도 표시하고,
전체 순서를 막연한 선택지 목록으로만 남기지 마세요.


# 7. 현재 GOAL-CAMEC-01의 영향 판정

정식 Plan이 있다는 이유로 무조건 정답으로 고정하지 말고,
전체 후속 요구와 실제 코드에 대조하세요.

  후속 유물 합성·출처·사본·보스 기능과 연결 가능한가?

실제 연결 비용이나 구조 충돌을 덮지 마세요.

결과에는 다음 중 어떤 방향이 적절한지 명시하세요.

A. 현재 Plan을 유지하고 GEX 인수에서 현재성을 확인한 뒤 진행
B. 구현 전 특정 코드 근거·상세 계약을 추가 확인한 뒤 진행
C. 실제 전제·범위·의존성 문제가 있어 해당 P2G owner의 수정이 선행

이 판정은 이번 검토의 권고입니다.
GEX 실행 자격·구현 승인·정식 artifact의 current/stale 판정을
대신하지 않습니다.

기존 Decision·Review·Freeze·Phase Plan·Goal Set·Handoff·감사 원본은
수정하지 마세요. 문제가 발견되면 별도 기록에 실제 근거, 영향받는 참조,
필요한 변경, 가장 이른 책임 owner를 적으세요.

# 8. 조사 중 점진적 기록과 재개

중요한 발견을 최종 답변 때까지 기억에만 보관하지 마세요.

매 도구 호출이나 내부 사고 과정을 기록할 필요는 없습니다.
후속 판단을 재현하고 작업을 재개하는 데 필요한 사실·결정·근거를
남기세요.

진행·상세 근거·최종 보고서는 읽는 시점과 책임에 따라 필요한 만큼만

대화 압축·세션 변경 후에는 저장된 기록과 관련 현재 source를 확인해
재개하세요. 대화 요약이나 기억만으로 승인·완료·시험 결과를 복원하지 마세요.

현재 조사 요약에서 누락하지 마세요.

플러그인이 저장소 읽기만 제공하면 로컬 작업 파일에 점진적으로 기록하고
최종 첨부 파일로 제공하세요. 저장소에 기록했다고 표현하지 마세요.

초기본으로 덮어쓰지 마세요. 현황 반영안에는 이번 조사의 요약·근거와
