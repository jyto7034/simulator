# Simulator 콘텐츠 제작 기반 — 전체 의존성 검토·로드맵 재설계 인수인계

당신은 simulator 프로젝트의 콘텐츠 제작 기반을 검토하는 후속 AI다. 기존 M0의 조사·정책·코드 검토·Phase·Goal·Handoff를 인수한 뒤, M0~M8 전체 로드맵을 현재 코드·RON·계약에 대조하고 안전한 구현 순서로 재설계하라.

이번에 완성할 것은 **실제 코드에 근거한 조사 보고서와 개정 로드맵 배포본**이다. 게임 기능 구현이나 Goal 실행이 아니다. 단순 요약, 첫 작업 추천, “나중에 구현자가 의존성을 확인해야 한다”는 안내로 끝내지 마라.

## 1. 작업 목적과 권한

최종 제작 목표는 제3자가 공통 명령·행동·조건·효과·규칙을 RON으로 조합해 보스·장비·무기·스킬 파편·유물을 만들고, 기존 콘텐츠의 변형·교체·등장·획득까지 연결할 수 있게 하는 것이다. 지원 조합 안의 콘텐츠마다 전용 실행 코드를 추가하지 않는다. 표현력이 부족하면 엔진 공통 기능을 확장할 수 있으며, 모든 미래 기믹을 엔진 업데이트 없이 표현해야 하는 것은 아니다.

이번 요청에서 허용하는 것은 관련 자료 읽기·검색, 안전한 비파괴 진단, 조사 기록·새 로드맵 문서·배포 파일 작성, 문서와 후보 의존 그래프의 정합성 검사다.

다음은 승인하지 않는다.
- production 코드·RON·저장 데이터의 수정, 게임 기능 구현, Goal activation, 배포·외부 서비스 변경.
- 사용자 dirty 변경의 삭제·reset·stash·재포맷, 기존 산출물의 초기화·개명·덮어쓰기.
- 기존 Decision·Review·Freeze·정식 Phase Plan·Goal Set·Handoff·감사 원본의 변경.
- AGENTS·P2G·GEX·검증기 소스의 수정·이동·교체, 새 게임 정책·밸런스의 대리 결정.

**ROADMAP_STATUS.md의 ‘다음 작업’을 실행하라는 요청이 아니다. NEXT-0009 또는 다른 GEX 실행 카드가 보이더라도 실행하지 마라.** 정식 P2G-00~60이나 GEX goal-run으로 자동 전환하지 말고, 조사·설계 검토와 문서 개정 범위를 유지하라. 필요한 정식 수정은 근거와 책임 owner를 권고하는 데 그친다.

검토 대상은 core_enhanced와 game_resources/data다. game_server·Unity 계약·클라이언트 구현은 제외한다. 코어 측 소비 경계의 실제 영향은 기록하되, 외부 영역의 문제를 코어 전체 재작성이나 선행 장애의 단독 근거로 삼지 마라.

## 2. 이전 작업의 상태와 인수 원칙

이전 AI의 **전체 의존성 검토·새 구현 순서·개정 배포본은 완료되지 않았다.** 함께 제공되는 RESUME_CHECKPOINT.ko.md는 재개용 탐색 메모이지, 검증된 의존성 보고서나 정식 P2G/GEX 산출물이 아니다. 그 파일에 없는 조사 결과·시험 결과를 추정해 복원하지 마라.

## 3. 접근 확인과 첫 인수

“Codex with ChatGPT · simulator” 연결을 사용할 수 있으면 먼저 workspace_info로 대상을 확인하고 read_file·search_workspace·list_directory로 조사하라. 로컬 저장소를 직접 제공받은 환경이면 동등한 읽기 도구를 사용할 수 있지만, 그 사본의 출처와 현재 dirty 작업 트리 반영 여부를 기록하라. 깨끗한 HEAD 사본을 현재 dirty 작업공간과 같은 것으로 취급하지 마라.

첫 진입점:
`core_enhanced/docs/roadmaps/content_authoring/ROADMAP_STATUS.md`

대상 식별, 실제 본문 읽기, 쓰기 가능 범위, 명령 실행 가능 여부를 각각 구분하라. 이전 세션의 도구 오류 설명을 현재 환경의 접근 불가 판정으로 재사용하지 마라. 도구 호출 성공이나 메타데이터 반환만으로 본문 확인을 주장하지 말고, 응답이 잘렸거나 별도 리소스에 있으면 실제 도구 계약에 맞춰 필요한 본문을 확보하라. 스키마 재조회나 같은 실패 호출을 의미 없이 반복하지 마라.

현재 브랜치·HEAD·관련 미커밋 변경·읽은 범위를 기록한다. 가능한 도구로 관련 파일의 해시 또는 다시 비교 가능한 내용 식별자를 확보하되, HEAD·파일 크기·줄 수만으로 dirty 전체를 식별했다고 하지 마라. 해시를 계산할 수 없으면 그 한계를 명시한다. 읽는 동안 변경된 source는 영향받는 판단만 다시 확인한다.

먼저 아래를 읽고 현재 선택된 원본과 직접 참조를 인수하라.
- ROADMAP_STATUS.md, OPERATING_RULES.md.
- 같은 로드맵 폴더의 records/CA00_NEXT-0001_INTAKE.ko.md, records/CA00_NEXT-0002_REQUIREMENTS.ko.md, records/CA00_NEXT-0002_COVERAGE.json.
- 기존 Topic의 WORKING_POLICY.ko.md, CODE_REVIEW_001.ko.md, current Freeze·Phase Plan·Receipt·Goal Set·Handoff와 직접 의존하는 검증·감사 기록.

이전 파일명 단서: P2G_30_FREEZE_001.json, P2G_40_PHASE_PLAN_002.json, P2G_40_PHASE_PLAN_VALIDATION_RECEIPT_002.json, P2G_50_GOAL_SET_001.ko.md, P2G_60_HANDOFF_001.json. 후속 원본이 current로 선택돼 있으면 그 선택을 따른다.

## 4. 조사 자료와 보존할 제작 방향

로드맵 위치:
`core_enhanced/docs/roadmaps/content_authoring/`

roadmap/ROADMAP.ko.md, DEPENDENCIES.ko.md, CONTRACTS.ko.md, COVERAGE.ko.md, ACCEPTANCE.ko.md, GOALS.json 및 architecture/·goals/를 검토하라. 이전 v2.1은 출발 단서일 뿐이며 최신 개정이 있으면 실제 내용을 사용한다. 기존 M0~M8·CA00~CA23은 누락 방지 기준이지 보존해야 할 단계 수나 순서가 아니다.

콘텐츠·정책 원문:
- core_enhanced/docs/project_map.ko.md
- core_enhanced/docs/skills/run_relic_content_design_notes.ko.md
- core_enhanced/docs/skills/abnormality_skill_fragments_design_notes.md
- core_enhanced/docs/skills/abnormality_design_notes.ko.md
- 위 원문에 연결된 성장·유물·침식 정책과 gameplay/runtime/data 계약.

현재 P2G/GEX의 관련 기준도 확인한다. 이전 관찰 경로는 core_enhanced/docs/policy_to_goal_pipeline_revised_v2.md의 2026-09-09-r2와 core_enhanced/docs/goal_execution_pipeline(1).md의 2026-09-09-gex-r1이다. 첨부된 구판·archive·현재 배치를 혼합하지 말고, 파일명 표준화를 위해 이동하지 마라. 이번 조사에 필요한 코드 근거·동시 전환·중간 상태·검증 소유 기준을 참고하되 정식 단계를 실행하지 않는다.

유지할 목표:
1. RON 조합기 UI는 제외하지만 엔진의 작성 정보·검증·진단·설명·headless 시험 기반은 포함한다.
2. 대표 공식 콘텐츠의 실제 최신 RON 이식과 전체 합의 구조의 표현력 대조를 구별한다. 둘 중 하나로 다른 하나를 대체하지 않는다.
3. 미래 전환에서는 기존 RON 전량 교체가 가능하다. 레거시 parser·alias·shim·구형/신형 이중 실행을 기본 해법으로 삼지 않는다. 이것은 이번 파일 삭제 권한이나 현재 최소 Goal에서 모든 저장 reader를 제거하라는 뜻이 아니다.
4. 외부 live_data·다중 팩·명시적 교체·의존성·충돌 검증을 지원한다. 일반 플레이는 새 런에 검증된 데이터 묶음을 고정하고, 시험 전투는 재로딩 성공 후 초기화한다. 진행 중 전투의 정의를 즉시 교체하지 않는다.
5. 콘텐츠 등록·교체·등장·획득 연결은 허용하고 외부 스크립트·플러그인 코드 실행은 제외한다.
6. 개화는 개별 파편 인스턴스가 독립 소유한다. 유물·성장·침식의 승인 의미를 보존하고 미정 수치·판정을 임의로 채우지 않는다. ‘침식된 유물’과 ‘파편 침식형’을 구분한다.

15개 분해 축은 검토 틀이다. 단계·분기·병행 → 개별 효과 → 해당 하위 축 순서로 읽고, 이를 15개 schema 필드나 독립 기능으로 기계적으로 옮기지 마라. 소환물·변신·공유 자원의 별도 책임도 추적하라.

## 5. 실제 코드 조사 범위와 방법

지도·이전 Review·로드맵은 입구다. 주요 결론은 현재 source·RON·정책의 실제 연결에서 확인하라.

각 변경 경계를 다음 흐름으로 추적한다.
`입력·참조·호출자 → 파싱·검증 → 변환·컴파일 → 실행 소비자 → 상태·결과 → 취소·종료·실패·복원 → 저장·로드·관련 테스트`

최소한 아래 영역 전체를 다뤄라. 경로는 탐색 입구이며, 존재나 이름 자체가 실행 지원의 증거는 아니다. 코드 경로는 별도 표기가 없으면 core_enhanced/src/ 기준이다.

전체 저장소의 모든 줄을 읽는 것이 목적은 아니다. 각 결론을 지지하는 필수 호출자·소비자·상태·저장·검증 경계를 확보하면 다음 영역으로 진행하라. 큰 JSON과 긴 파일은 구조를 보고 필요한 연속 구간으로 나눠 읽어라. 검색 hit만으로 문맥을 복원하거나 타입·enum·테스트 존재를 실행 지원으로 인정하지 마라. 검색 0건이나 공식 RON 예제 부재만으로 기능 부재를 확정하지 마라.

다음은 **확정 finding이 아니라 꼭 판정할 조사 질문**이다. 특정 순서를 미리 정답으로 삼지 마라.
- CA01 최소 metadata 계약과 CA02 외부 팩 사이에 실제 필수 선행이 있는가? embedded 최소 단계가 독립적으로 유효한가?
- CA03 도구 전체 완료가 상태·계산 kernel의 기능상 선행인가, 검증 선행인가, 진행상 권장인가? 기존 시험 경로로 분리 가능한가?
- 파편 사본화와 유물 관리 중 무엇을 독립시킬 수 있고, 지급·장착·선택 형태·회수·저장 중 무엇은 반드시 함께 바꿔야 하는가?
- 사건·결과 계약, 자원 수명, Flow 실행, 가역 modifier, 공유 보호막 중 후행 기능 전체가 아니라 어떤 최소 계약만 필요한가?
- 보스의 스킬 요청·완료·실패·취소·방향 지원을 설치물·공유 보호막·전장 기믹 전체와 분리할 수 있는가? 현재 소환 경로의 공용 기반과 보스 결속은 어디인가?
- 유물 합성과 비동기 전달이 만날 때 실제 executor·preview·출처·연쇄 경로를 함께 바꿔야 하는 범위는 무엇인가?
- 침식의 처치 부가 효과 억제와 필수 웨이브 bookkeeping, 직원 대가·결과 확정·시계 정지를 어떻게 연결해야 하는가?
- 저장·실제 RON fixture·등록·검증 도구·결정론·실행 예산 중 뒤로 미루면 중간 단계가 무효가 되는 것은 무엇인가? 최종 통합·부하 검증과 구별하라.

## 6. 의존성 판정과 하나의 권장 순서

현재 코드의 호출·데이터 의존성, 목표 구조로 전환할 때 필요한 의존성, 재작업을 줄이기 위한 권장 순서를 분리하라.

각 주요 관계를 다음 다섯 종류로 분류한다.
- 기능상 필수 선행: 후행의 실제 소비 지점이 선행의 특정 계약·상태·결과를 요구한다.
- 동시 전환: 분리하면 authority·transaction·schema·reader/writer·장착·저장·실행 의미가 어긋난다.
- 검증 선행: 후행의 완료 주장을 증명할 도구·데이터·관찰 경로가 먼저 필요하다.
- 진행상 권장: 필수는 아니지만 재작업·위험·파일 충돌을 줄인다.
- 조건부 관계: 특정 미정 정책·미확인 사실에 따라 순서나 범위가 달라진다.

각 관계에는 다음 정보를 남겨라.
`선행 결과 → 후행의 구체 소비 지점 / 관계 종류 / 경로·심볼·읽은 범위 / 필요 이유 / 무시하면 깨지는 상태·완료 조건 / 기존 기능으로 충족된 부분 / 관찰 사실·설계 판단·실행 결과의 구분 / 남은 조건·한계`

기존 CA 선행 목록을 빠짐없이 disposition하라. 유지·제거·세분화·동시 전환·권장으로 재분류·조건부·미검토 중 무엇인지 보이게 하고, 새 관계도 근거에 연결하라. 근거 없이 화살표를 삭제하지 마라.

“A 전체 → B 전체”를 그대로 유지하지 말고, 필요한 계약만 분리할 수 있는지 판단한다. 반대로 분리하면 무효가 되는 변경은 CA 번호가 달라도 최소 동시 전환 묶음으로 잡는다. 새 상태를 도입하는 단위가 필요한 저장·복원·시험도 함께 소유해야 한다.

순환은 최소 동시 전환 묶음, 실제 안정된 계약으로 분리 가능한 관계, 잘못된 작업 분해, 정책·근거 부족으로 구분하라. 빈 executor·임시 성공·미승인 fallback으로 해소하지 마라.

새 구현 단위마다 다음 내용을 작성하라.
`목적·기존 CA 대응 / 먼저 필요한 설계 계약 / 실제 구현 선행 / 함께 바꿀 코드·RON·계약·테스트·저장 / 재사용·교체·제거 경로 / 직후 유효 상태 / 검증 owner·입력·기대 결과 / 조건부·미정`

각 단위는 “다음 단계를 전혀 하지 않아도 지금 약속한 기능·상태·데이터 경로·검증이 유효한가?”에 답해야 한다. 후속 기능 미지원은 허용하지만 후속 변경 없이는 현재 완료 조건도 충족하지 못하는 분할은 고쳐라.

최종적으로 **하나의 권장 기본 순서**를 제시하라. 조건부 대안은 해당 분기만 별도로 적는다. 병렬화는 화살표 부재가 아니라 공유 상태·스키마·파일·시험 환경·병합·통합 검증의 독립성으로 판단하며, 근거가 부족하면 순차 진행을 권고하라.

## 7. GOAL-CAMEC-01의 영향 판정

정식 Plan이 있다는 이유로 현재 최소 Goal을 정답으로 고정하지 말고, 전체 후속 요구와 실제 코드에 대조하라.

효과 작성 주소·태그·typed property·SourceMap의 경계가 유물 합성·출처·사본·보스 확장에 연결되는지 검토한다. 정의 identity, compiled index, 소유 사본, 시전·효과 실행 identity를 구분하고, 기존 executor 재사용이 유효한 최소 전환인지 곧 폐기할 구조를 고정하는지 판단하라.

metadata 연결로 기존 피해·회복 계산, 효과 순서·타격 수, step의 공유 target/delivery, 취소 뒤 이미 release된 전달체의 처리 의미가 바뀌지 않는지 확인하라. 현재 동작 보존과 후속 기능의 새 의미 설계를 혼동하지 마라.

compiler/metadata·최신 RON/catalog·직접 runtime consumer의 Atomic Group이 필요한 최소 범위인지 확인하라. 현재 Goal 전에 반드시 필요한 계약과 구현을 나누고, 미래 기능 전체를 불필요한 선행으로 만들지 마라. embedded 경로만으로 외부 팩 목표와 모순이라고 하지 말고, 반대로 “나중에 확장”이라는 말로 실제 연결 비용을 숨기지 마라.

다음 중 하나를 근거와 함께 권고하라.
A. 현재 Plan을 유지하고 후속 GEX 인수에서 현재성을 확인한 뒤 진행.
B. 특정 코드 근거·상세 계약을 추가 확인한 뒤 진행.
C. 실제 전제·범위·의존성 문제가 있어 해당 P2G owner의 수정이 선행.

B라면 추가 확인할 질문·파일·소비 지점·충족 기준을 특정하라. C라면 영향받는 exact artifact, 최초 문제 지점, 필요한 최소 수정과 가장 이른 owner를 특정하라. 이번 전체 조사에서 할 수 있는 확인을 막연히 후속 구현자에게 넘기지 마라.

이는 권고이며 GEX 실행 자격·구현 승인·정식 current/stale 판정을 대신하지 않는다. 기존 원본 수정, successor·Change Declaration 발행, 정식 재실행을 하지 마라. 기존 성과 중 그대로 재사용할 부분과 불필요하게 다시 하지 않아도 되는 작업도 명시하라.

## 8. 점진적 기록·검증·중단 처리

중요한 발견을 최종 답변까지 기억에만 보관하지 마라. 의미 있는 조사 묶음마다 읽은 source·범위·내용 식별자, 확인 사실, 설계 판단·가설, 관계의 채택·수정·기각 이유, 미해결 finding과 다음 조사 위치를 파일에 남겨라. 모든 도구 호출이나 내부 사고 과정의 기록은 필요 없다.

기존에 적합한 기록이 있으면 재사용하고, 중복 원본이나 거대한 새 관리 체계를 만들지 마라. 새 조사 문서는 정식 GEX 실행 기록으로 만들지 않는다. 컨텍스트 압축·세션 변경 뒤에는 저장한 기록과 관련 현재 source를 확인해 이어가라.

저장소 쓰기 도구가 없으면 로컬 작업 파일을 작성해 최종 첨부하라. 로컬 파일을 저장소에 기록했다고 표현하지 마라. 이전 대화의 sandbox 경로·도구 응답 ID가 새 환경에서도 유효하다고 가정하지 마라.

명령 실행 도구가 실제로 있고 명령·fixture·출력 위치·부작용이 안전한 경우에만 필요한 focused 진단을 수행하라. 전체 빌드·테스트 반복을 의무화하지 말고, 실행할 수 없어도 정적 조사는 계속하라. 실행 불가·0건·skip·과거 PASS를 이번 성공으로 세지 마라. 실패를 고치려고 production 코드나 검증기를 수정하지 마라.

일부 미정 정책·접근 실패가 일부 관계만 제한하면 그 범위만 조건부로 남기고 나머지는 진행하라. 필수 source를 확보하지 못하면 무한 재시도하거나 내용을 발명하지 말고, 영향받는 결론·부족한 자료·정확한 재개 위치를 남겨라. 도구·세션 한계로 중단될 때도 부분 보고서·현재 대응표·미검토 목록을 저장하라.

## 9. 필수 산출물과 최종 확인

한국어 보고서와 새 버전 개정 파일을 제공하라. 문서 개수는 내용에 맞게 정하되 다음 여섯 결과를 빠뜨리지 마라.

A. 핵심 결론·하나의 새 권장 순서: 유지·변경 이유, 새 구현 단위, 필수 선행·권장·동시 전환, 순차·병렬과 설계 선행/구현 선행의 구분.
B. M0~M8·CA00~CA23 전체 대응표: 실제 검토 범위, 기존 성과·재사용 근거, 새 단위 대응, 유지·분할·병합·재배치·기존 기능 충족, 미검토·조건부·정책 대기·누락.
C. 의존성 근거: 기존 관계별 disposition, 새 필수 관계, 파일·심볼·소비 지점·필요 이유와 관찰/설계/실행/가정 구분.
D. 단계별 전환·검증 계획: 선행 결과, 동시 변경 경계, 직후 유효 상태, 검증의 구현 owner·방법·기대 결과, 이번 확인과 향후 시험의 구분.
E. 기존 M0·GOAL-CAMEC-01 영향 보고: A/B/C 권고, exact artifact 영향, 최소 재검토 owner와 범위, 보존·재사용할 성과.
F. 개정 로드맵 배포본: ROADMAP·DEPENDENCIES·관련 작업 카드·로드맵 GOALS.json·인수 안내의 실제 개정본, 필요한 관련 문서 정합성, 변경 요약과 가능하면 diff, ROADMAP_STATUS 반영안 및 적용 안내.

F를 보고서의 “향후 수정할 파일 목록”으로 대체하지 마라. 실제 개정 파일을 제공하되 기존 원본은 보존하고 새 버전 또는 별도 배포 경로를 사용하라. 로드맵 GOALS.json과 정식 GS-CAMEC-P2G50-001은 다른 산출물이므로 혼동하지 마라. 기존 목표·정책·권장 설계·검증 기준을 불필요하게 누락하지 말고, 범위 변경은 이유와 승인 필요 여부를 밝혀라.

ROADMAP_STATUS 반영안은 기존 진행·완료 이력과 NEXT-0009를 보존한 추가 기록/차이로 제시하라. 이번 조사 요약·근거·다음 조치 권고와 실제 적용 여부만 구분해 연결한다. 새 로드맵 권고와 기존 정식 Plan이 다르면 둘을 동시에 확정 실행 순서로 표시하지 마라. 적용을 위해 필요한 후속 절차를 명시하되 실행하지 않는다.

제출 전에 다음을 대조하라.
- 모든 M/CA 요구와 기존 관계에 대응 또는 명시적 미검토·조건부 disposition이 있는가?
- 핵심 의존성·동시 전환·중간 상태가 실제 source 또는 명확한 목표 계약에 근거하는가?
- 권장 순서를 기능상 필수로 과장하거나 순환을 근거 없이 제거하지 않았는가?
- 검증 경로가 필요한 시점에 존재하도록 구현 owner가 배정됐는가?
- 표·JSON·카드·본문의 단위·순서·의존성이 일치하고 기존 M0 성과가 보존됐는가?
- 정적 검토·문서 검사·실제 실행·미실행 계획이 구별되며 미검토를 완료로 표시하지 않았는가?

이 최종 확인은 로드맵 정합성 검토이지 게임 구현의 GEX 완료 감사가 아니다. 별도 독립 검토자가 참여하지 않았다면 독립 감사라고 하지 마라.

마지막으로 두 질문에 직접 답하라.
1. 현재 simulator와 최신 제작 목표를 기준으로 무엇을 어떤 순서로, 어느 범위까지 함께 바꿔야 중간 단계가 유효하고 재작업이 적은가?
2. GOAL-CAMEC-01을 첫 구현 단위로 유지해도 되는가? 아니라면 무엇을 확인하거나 어느 owner에서 무엇을 수정해야 하는가?

승인된 조사·개정 범위 안에서는 내부 작업 묶음마다 재승인을 요구하지 말고 전체 검토·재설계·문서 정합성 확인까지 진행하라. 실제로 완료하지 못한 부분은 범위와 근거를 명시하라. **보고서와 개정 파일을 제공한 뒤 종료하고, NEXT-0009나 다른 Goal의 구현을 시작하지 마라.**
