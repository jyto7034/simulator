# 모드 검증 및 실행 안전성 — 로드맵 편입안

2026-09-27 · v0.2 · **의존성 검토 및 잠정 배치 완료 / 상세 설계·제품 구현 미실행**.

사용자 요청: 기존 의존성 순서를 고려하여 로드맵 편입안을 먼저 작성하고, 먼저 수행할 단계부터 상세 계획을 수립한다.
현재 대화는 검토·계획, 구현은 별도 대화다. MS01–MS06은 이 문서의 작업 표지이며 정식 Goal·Phase ID가 아니다.
편입안은 기존 현황에서 찾아갈 수 있도록 연결하되, 기존 R 카드·GOALS.json·동결 Phase Plan의 실행 순서를 덮어쓰지 않는다.

## 1. 범위와 원본

목표는 모드 제작자가 실제 실행 경로로 기능별 부하를 시험하고, core 실행 주체가 검증된 구성만 본편에 적용하며,
실행 중 안전 오류도 해당 전투 안에서 처리하는 것이다. 기존 한도의 RON 분리와 메트릭은 이를 위한 공통 기반이다.

- [확정 정책](../../plans/runtime_safety_observability/LAB_STRESS_PROPOSAL.ko.md): 모드 단위 거부, 조합 보류, 필수 모드 누락 세이브 차단,
  해당 전투 오류 중단, 로컬/서버 core별 검증, 저사양 예외 없음. 정책은 이 원본 하나에서 관리한다.
- [설정·관측 설계](../../plans/runtime_safety_observability/PLAN.ko.md): S1/S2는 MS01/MS02에 재사용한다. S3 측정은 MS03/MS05/MS06으로 나눈다.
  S4 처리 분할·host 총량 제어는 필요성 관측 후 검토할 후보이며 이번 필수 단계가 아니다.
- [기존 R00–R24 권장 순서](../content_authoring/reviews/2026-09-09-dependency-review-v2.2/roadmap_v2.2-review/ROADMAP.ko.md),
  [실제 현재 상태](../content_authoring/ROADMAP_STATUS.md), [편입 의존성 검토](DEPENDENCY_REVIEW.ko.md)를 함께 읽는다.

20분 시험은 현재·후속 자동 검증 및 완료 조건에서 제외한다. 안전 초과에 따른 스킬 자동 취소, 저사양 통과 예외,
전투당 임의 3MB 한도, 기존 약9MB 회귀 cap을 새 모드 승인 한도로 복사하는 일도 포함하지 않는다.
범용 모드 스크립트 실행기·제작 UI 전면 구현·Unity 통합은 이번 편입안에 추가하지 않는다.
기존 계획에 있던 host 설정·exporter, 로컬 embedding/서버 적용·오류 전달은 포함하되 해당 adapter의 실제 수정 범위는 상세 설계에서 확인한다.

## 2. 전체 로드맵과의 관계

프로젝트의 현재 작업과 잠정 삽입 위치는 [단일 개발 현황](../content_authoring/ROADMAP_STATUS.md#후속-편입-후보)에서 확인한다.
이 문서는 후속 계획의 내부 범위·완료 조건만 소유한다. 현재 개발 주작업은 R06이며 이 문서 열람으로 MS01을 착수하지 않는다.
기존 배치안의 이유와 조건은 [의존성 검토](DEPENDENCY_REVIEW.ko.md)에 보존했다.

R19 이전에 사용자 모드의 본편 적용 기능을 제공하려면 해당 지원 범위의 MS04/MS05가 먼저 유효해야 한다.
후보 로딩·편집·시험 성공을 스트레스 승인된 본편 사용이라고 표시하지 않는다. 정확한 삽입 위치는 잠정이다.
R06 뒤 기반 작업 배치는 공용 source 충돌과 expression profile 재작업을 줄이려는 권장이다.
MS01을 먼저 선택하는 경우에도 R06 구현과 같은 파일을 동시에 변경하지 않는다.

## 3. 단계별 범위와 완료 조건

| 표지 | 범위·필요한 입력 | 해당 단계만 끝났을 때 유효한 상태 / 완료 증거 |
| --- | --- | --- |
| MS01 | 기존 한도의 host RON 이관. 현재 typed limits와 public 생성/실행 경로 | 기본값·기존 거부/복원 의미 일치, 잘못된 설정 거부, 실제 host/CLI/embedding 전달, 동일 profile identity 확인. 새 한도 상향 없음 |
| MS02 | 내부 장부의 bounded 관측, 표준 metrics/exporter·외부 그래프 | 실제 지표/그래프와 관측 on/off·수집 중단 시 gameplay 동등성. exporter가 안전 판정 권한을 갖지 않음 |
| MS03 | R02 후보 세대·R03 공개 trial 재사용, 대규모 배치 adapter, 현재 기능별 profile/coverage·측정 | 외부 데이터로 실제 스킬 경로 실행, seed/input/설정 결속, setup 실패·미발동 구별, 측정·정리 증거. 실험실 완료가 모드 사용 승인 완료는 아님 |
| MS04 | 기존 runtime fault·application transaction·결과/저장·host tick 경계 재사용 | 오류 전투의 추가 진행과 정상 결과/보상 반영 차단, 진단 반환, 다른 전투 격리, 원본 저장 보호. 스킬 취소나 전체 프로세스 종료 없음. 기존 복원 범위를 넘어선 전체 되감기 보장 없음 |
| MS05 | MS01 profile, MS03 시험·측정, MS04 오류 경계, R02 구성/의존성/저장 identity | 첫 실행/변경 감지→검증 또는 유효 캐시→실제 구성 적용의 공개 경로. 실패 모드·필수 종속 제외, 조합 실패 보류, 필요한 모드가 빠진 세이브 차단. 현재 지원 범위의 수치/반복 기준을 측정 근거로 정한 뒤에만 PASS 발행 |
| MS06-A | R19 등록 통합, R20 교차 검증, R21 대표 데이터, 누적 기능 profile | 모든 지원 기능의 시험/기준/누락표와 승인·캐시 버전을 정리해 R22 입력으로 고정. 미래 미구현 기능은 PASS로 표시하지 않음 |
| MS06-B | R22 독립 재조합, R23 측정·결정론·회귀, R24 독립 감사 | 같은 revision에 귀속한 증거를 기존 인수/감사에서 대조. 중복 부하 도구·새 최종 감사 단계 없이 실제 미완료를 남김 |

MS04 상세 조사(오류 분류·복원/commit 범위·host 진입점)는 MS01 상세 계획 때 함께 경계만 확인할 수 있다.
이는 MS01 구현에 전투 중단 기능을 섞는다는 뜻이 아니다. MS04 본 구현 전까지 기존 guard와 rollback을 유지한다.

MS03의 500/1,000 유닛은 부하 후보다. 공개 setup으로 실제 생성·발동 가능해야 하며 gameplay 인원 상한으로 선언하지 않는다.
새 소환 능력 R13은 유닛을 많이 배치하는 시험 도구 자체의 필수 선행이 아니다. 소환 능력 시험에는 R13이 필요하다.
MS02의 그래프 서비스 전체는 headless 시험 실행의 필수 선행이 아니다. MS03/MS05 판정에는 신뢰할 직접 측정·receipt를 사용한다.

## 4. 후속 기능과 중복 책임

| 기능 owner | 실험실에 보완할 항목 | 주의할 구분 |
| --- | --- | --- |
| R06 | 실제 대상 집계, Snapshot/Live, 식 비용 | 현재 WP02 부분 결과를 R06 전체 지원으로 승격하지 않음 |
| R07–R09 | 사본·형태 입력, 보스 스킬 요청/종료, 침식·강제 시계 | 실패·저장/수명은 각 기능 owner가 도입 시 닫음. R09 정책 대기 시 미지원 표기와 기존 분기 유지 |
| R10–R12 | Flow/반복·전달, 지속 modifier/channel, 공유 보호·제어 | 기본 projectile/area 시험과 새 Flow·shared pool 시험 구분 |
| R13–R15 | 생성/정리·field, 유물 합성·활성 closure | 시험 대상 유닛 생성 adapter와 콘텐츠의 소환 opcode를 구분 |
| R16–R18 | 연쇄·branch 방문, 전파/감염·공간 집계, 보스 다중 actor | 기존 ByBuffStacks를 전파 구현으로 대신하지 않음 |
| R19 | 승인 구성의 등록·획득/평가 소비, 조합 시험 보완 | 전투력 점수 통과를 안전 승인으로 재사용하지 않음 |

확정된 기능 owner의 기존 schema→compiler→consumer·오류/저장 의무는 유지한다.
새 실험실과 연결하는 delta는 후속 계획에서 명시하며 기존 동결된 R06 Phase/인수 기준은 직접 수정하지 않는다.
MS05 이후 capability·의존 데이터·엔진·시험·정책이 바뀌면 필요한 캐시를 무효화한다. 시험 미정인 기능을 조용히 승인하지 않는다.

## 5. 상세 계획의 다음 작업과 남은 결정

**이 후속 계획을 명시적으로 착수할 때 첫 단계는 MS01 상세 계획의 현재성·전달 경로 검토**다. 프로젝트의 다음 개발 작업은 단일 현황에서만 지정한다. 기존 S1 설계를 재사용하여 실제 host/CLI/embedding별 생산자·소비자,
R06과 공유하는 변경 파일, 초기화/오류·profile 전달, 단계 종료 증거를 확인하고 별도 구현 지시서를 만든다.
그때 MS04를 위해 runtime fault와 일반 입력 거부/수집 실패를 구분하는 경계도 기록한다. 이 문서는 구현 자동 시작의 근거가 아니다.

전체 후반 상세 설계를 선행 요구하지 않는다. 이후 각 단계 직전에 다음을 닫는다.

- MS03: 기능별 실제 시험표, 공개 대규모 setup, 지원 부하와 반복/집계 방식. 임의 메모리·시간 수치를 지금 확정하지 않는다.
- MS04: commit 이전 오류와 이후 전달 오류 구분, 오류 전투 재진입/재접속 제어, 안전 오류 분류, 진단 실패 시 중단 유지.
- MS05: 모드↔pack 매핑, 최초 적용 시점, 캐시 원자적 기록·정확한 무효화 단위, 세이브 필요 모드 안내 방식.
  현재 full content identity 검사를 자동 모드 제거/세이브 migration으로 완화하지 않는다.
- MS06: 지원 기능 누락/측정 결과 및 기존 R22–R24 증거 대응. 장시간 시험이나 독립 인증 서버를 추가하지 않는다.

현재 편입안 작성에 답이 필요한 새 정책 질문은 없다. 상세 설계에서 게임 동작이나 사용자 선택이 달라지는 문제가 발견되면
근거와 대안을 제시한다. 구현 기술 선택이나 기존 답변을 재확인하는 질문은 반복하지 않는다.
