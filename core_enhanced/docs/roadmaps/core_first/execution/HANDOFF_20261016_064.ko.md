## 권장 착수·구현 순서

1. 현재 코드와 실제 dirty 변경, 관련 기존 결과의 적용 범위를 확인하고 후속 기준본과 계획을 마련한다. 이전 source hash에 맞추려고 되돌리지 않는다. 이 인수 작업에서 시작한 build/host 세션은 없다. 다른 실행자의 프로세스는 별도로 확인한다.
2. 상태별 소유자·수명·저장 대상·Continue/SavePoint/거래 rollback/후퇴 처리 표를 작성한다. 자산, 창고 debit, 영구 지식, 후퇴/로드 횟수, UUID, 선택권, 결과, preview/session을 포함하고 공유할 도메인 검증 경계를 정한다.
3. 기존 공개 시나리오/runner를 재사용해 정상 생성→실제 저장 경계→fresh 복원→후속 명령 비교의 공통 검증부터 연결한다. 미완료 Continue는 현재 live 상태가 아니라 정책상 입장 전 상태와 비교한다. 제품 코드를 복제한 기대값으로 통과시키지 않는다.
4. 생성/복원 규칙 공유, 영속/임시 상태 분리와 수명 정리, 복원 비용 계량 정리를 영향 범위별로 구현한다. 기존 정책을 보존하면서 실제 문제를 줄이는 변경을 선택하고, 구체 타입 분리나 저장 형식 변경을 미리 확정하지 않는다.
5. 변경 영향 검증과 대표 정상/확장 fresh-process·IO·비용 비교를 완료한다. 기존 증거의 재사용/재실행을 구분하고 필요한 successor source/증거를 고정한 뒤 자체 검토와 감사 인계를 정리한다. U18 이후로 자동 진행하지 않는다.

- 기본 한도에서 대표 정상·확장 복원이 성공하고 임시 상태가 회수되는지 확인한다. decode/clone/reencode 계량과 실제 allocator·RSS를 구분한다. 한도 상향만으로 기존 실패를 숨기거나 매 저장마다 전체 복원을 실행하는 방식을 기본 해법으로 삼지 않는다.
- 로드맵 §1.9의 지원 경로 범위를 지킨다. 실제 구writer 원본·지원 명령/작성 오류·IO 장애는 검증하되 임의 save/checksum/메모리 변조 전용 방어를 추가하지 않는다.

인수 문서 갱신으로 기존 U17 target/PLAN/시험/공식 입력은 변경하지 않았다. 후속 구현은 별도 변경이며,
그 뒤에도 기존 target을 현재 제품 결과로 자동 승계하지 않는다. 정식 완료 판정은 해당 검증·감사 조건을 충족한 근거로만 갱신한다.
