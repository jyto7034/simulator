# Core 우선 로드맵 구현 시작 지시서

**기본 실행자는 `gpt-6-astra` / `high` 한 명이며 구현·테스트·실행·교정·검토를 직접 수행한다. 서브에이전트를 생성하거나 다른 에이전트에 작업을 위임하지 않는다.** U29의 독립 외부 제작과 U33/U31 등 별도 비참여 감사가 필수인 조건은 §8에 따라 준비·인계하며, 같은 실행자의 자체 검토로 대체하지 않는다.

이 지시서로 구현을 시작하거나 재개하라는 요청을 받으면 아래 순서로 현재 승인된 작업을 수행한다. 문서 조회·검토·수정 요청만으로 제품 구현을 시작하지 않는다. 현재 상태는 [최신 인수인계](HANDOFF_LATEST.ko.md), 과거 요청은 [이력 안내](EXECUTION_HISTORY.ko.md)를 따른다. [변경 전 지시서](history/20261013_single_astra_default/CONTINUOUS_EXECUTION_INSTRUCTIONS_REVISED.ko.md)는 참고용 원본이며 현재 실행 규칙이 아니다.

## 1 시작할 작업과 승인 범위 확인

최신 인수인계에서 현재 Goal, 승인 근거, 다음 행동, 관련 PLAN과 실행 기록의 위치를 확인한다. HANDOFF가 현재 실행의 유일한 진입점이며 [ROADMAP_STATUS](../../content_authoring/ROADMAP_STATUS.md)는 단계별 진행 근거 색인이다. 최신본이 없거나 실제 상태와 다르면 관련 소스·기록·증거를 대조해 재개 위치를 복구한다. 사용자의 최신 지시를 과거 인계의 중지·계속 문구나 당시 문서 작성 한정 권한으로 덮어쓰지 않는다. 로드맵의 날짜별 이력·초기 코드 스냅샷을 현재 작업 상태로 읽지 않는다.

- Core 우선, Unity 후속, 개별 최종보스 고유 구현 제외를 유지한다. 현재 기능을 구현하면서 관련 기반 코드의 구조적 문제를 함께 점검하고, 필요한 개선은 로드맵 범위에서 병행한다.
- 책임·상태 소유권의 혼재, 규칙 중복, 과도한 결합 등으로 정확성·변경 용이성·검증 가능성이 저하되는 경우에는 관련 기반 코드를 리팩토링한다. 당장 기능을 덧붙일 수 있다는 이유만으로 필요한 구조 개선을 미루지 않는다. 변경 범위는 문제를 해결하는 데 필요한 경계로 제한하고, 기존 동작과 공개 계약을 보존하며 영향에 맞게 검증한다. 현재 승인된 기능 변경은 해당 정책·계약을 따르며, 리팩토링을 이유로 별도의 동작 변경을 끼워 넣지 않는다. 현재 작업에 필요한 범위를 넘는 구조 문제는 근거와 함께 후속 작업으로 남긴다.
- 승인된 범위의 구현·검증·오류 교정을 끝까지 수행한다. 이미 승인된 감사·다음 작업은 필수 선행과 독립 역할 조건을 확인한 뒤 이어간다. 카드 순서·PASS 자체로 미승인 범위를 확대하지 않으며, 무관한 정리·분할·추상화를 추가하지 않는다.
- 내부 구현 선택과 일반 오류 교정은 자율 수행한다. 정책·공개 계약·완료 기준의 변경은 해당 owner 절차와 기존 권한에 따라 처리한다.
- 사용자 지정 checkpoint·중지·시간/비용 한계는 유지한다. 단순한 테스트 실패나 명령 대기를 재승인 사유로 만들지 않는다.

## 2 필요한 근거와 작업 상태 인수

이미 유효하게 읽은 자료는 변경이나 판단 공백이 있을 때만 다시 읽는다. 처음부터 전체 이력이나 모든 문서를 읽지 않고 현재 작업에 필요한 부분을 확인한다.

| 확인할 내용 | 근거 |
| --- | --- |
| 현재 범위·수용 조건·잔여 작업 | HANDOFF가 가리키는 현재 PLAN, EXPERIMENTS의 마지막 관련 실행과 실패·재사용 근거 |
| 단계별 진행 근거·과거 비교 | ROADMAP_STATUS와 필요한 과거 기록. 로드맵 §2·부록 C의 초기 상태/인수 이력은 현재 실행 위치를 대체하지 않음 |
| 구현 대상·의존성·선행 조건 | [로드맵](../ROADMAP.ko.md)의 해당 카드, 실제 코드와 사용 예 |
| 정책·공개 계약·Goal 생성 또는 변경 | [P2G](../../../policy_to_goal_pipeline_revised_v2.md)의 Reader Contract와 해당 owner 절차 |
| 구현·검증·교정·최종화 | [GEX](../../../goal_execution_pipeline%281%29.md)의 Reader Contract와 현재 단계의 진입·종료 조건 |
| 로드맵과 P2G/GEX의 연결 | 필요한 경우 [사용 가이드](../../content_authoring/guides/policy_to_goal_pipeline_roadmap_usage_v2_1.ko.md) |
| 게임 기대 동작 | 최신 사용자 합의와 [룰북](../../../game_rulebook.md)·[game_rules](../../../game_rules/)의 해당 기능 |
| 상태·수명·저장·기술 판단 | 현재 Goal의 STATE_INVENTORY·EXPERIMENT_NOTES 중 관련 계약·판단 |

실제 소스와 dirty 변경, 적용·미적용 변경, 마지막 유효 실행·감사, 남은 검증, 입력 고정과 실행 세션을 한 번에 대조한다. 과거 단계 번호나 소스 해시에 맞추려고 작업을 되돌리지 않는다. 과거 기록에 실행 중이라고 적혀 있다는 이유로 검사를 중복 시작하지 않는다. 차이는 기존 기록에 간단히 남기며 전체 테스트부터 실행하지 않는다.

## 3 구현 순서 결정과 착수

기존 계획을 현재 잔여 작업에 맞게 보완하고 바로 구현에 들어간다. 새 계획 문서는 기존 계획으로 범위·완료 조건을 설명할 수 없을 때만 추가한다.

- 수용 조건, 변경 대상과 중요한 계약, 구현 순서, 필요한 검사와 재사용 증거를 정한다.
- 기능·의존성·편집 충돌·실행 환경을 기준으로 의미 있는 작업 묶음을 만든다. 파일 수·시험 수·보고 횟수를 맞추기 위해 쪼개지 않는다.
- 핵심 API와 실제 사용 예를 읽고 공개 계약·상태 소유권·수명·저장·권한·자원 경계를 확인한다.
- 제품 코드와 테스트를 직접 작성하고 교정한다. 같은 실행자의 pass 전환마다 자신에게 인계 문서를 만들거나 별도 담당자를 만들지 않는다. §8의 필수 독립 역할을 위한 실제 인계는 기존 PLAN·실행 기록·HANDOFF에 준비한다.
- 실행 중인 검사의 제품·시험·fixture·설정·판정 도구 입력은 고정한다. 관련 수정은 실행 종료·정리 뒤 수행한다.

## 4 테스트 설계와 실행

**검증 범위의 상위 제한은 [로드맵 §1.9 — 외부 임의 변조 방어 제외](../ROADMAP.ko.md#19-검증-범위-제한--외부-임의-변조-방어-제외)를 따른다.** 정상 플레이·지원 도구·실제 저장/장애 경로에서 발생할 수 없고 파일·checksum·메모리·내부 상태를 임의 변조해야만 성립하는 사례는 보호·경계 검증 대상에서 제외한다. 이를 위해 방어 코드·시험·복구 기능을 추가하거나 감사 finding·GEX 교정·완료 차단을 만들지 않는다. 아래 부정 입력·경계·원본 보호 요구도 이 범위 안에서만 적용한다. 지원 제작 입력의 작성 오류·지원 명령의 오용·실제 도달 가능한 오류를 재현하는 fixture와 실제 IO 장애 주입은 계속 검증할 수 있다.

발생 근거는 `범위 안 — 지원 경로`, `범위 밖 — 외부 임의 변조`, `발생 근거 미확인`으로 구분한다. 아직 경로를 확인하지 못했다는 이유만으로 변조 전용이라고 단정하지 않으며, 근거 없는 의심만으로 제품 finding·새 필수 시험·완료 차단을 만들지 않는다. 관련 코드·계약·유효한 증거로 필요한 판정을 하되 전체 경로 부재 증명·별도 대규모 조사를 의무화하지 않는다. 기존 필수 수용 조건의 미검증이나 지원 경로의 실제 실패를 이 구분으로 면제하지 않는다.

기대값은 요구사항·정책·독립 계산과 외부 관찰에서 도출한다. 제품 알고리즘이나 helper를 복제하지 않고 작은 수작업 예제·대조 입력·불변 조건을 활용한다. 시험 개수보다 중요한 결함의 검출력을 기준으로 삼는다.

테스트 설계·실행자는 해당 시나리오의 결과를 좌우하는 도메인 규칙을 이해한 뒤 준비 전략을 정한다. 관련 규칙 문서·실제 구현·공개 조회를 대조하여 목표 상태의 진입·종료 조건, 행동·대상 자격, 자원과 상쇄 효과, 이벤트 순서·시간·복원 조건 중 필요한 항목을 확인한다. 게임에서는 승패 조건·사거리·피해와 회복·배치 자격 등이 이에 해당한다. API 호출 성공만으로 목표 상태에 도달할 수 있다고 가정하지 않는다. 전체 규칙을 매번 다시 읽지 않고 이번 시나리오에 필요한 부분과 미확인 가정에 집중한다. 문서와 실제 동작이 다르면 차이를 기록하고 요구사항·정책에 따라 원인을 판정하며, 현재 구현에 맞춰 기대값을 자동 변경하지 않는다.

테스트·fixture·진행기를 작성하거나 수정하기 전에, 관련 규칙을 근거로 초기 상태, 목표 연산까지의 행동 순서, 중간 선택·자동 전이·자원 임계점, 관측 지점과 기대 결과를 구체화한다. 최초 실행과 반복·재시작·복원 경로의 선행 조건이 같다고 가정하지 않는다. 중요한 가정과 미확인 사항은 기존 PLAN 또는 테스트 설계 기록에 간결히 남긴다. 계획의 상세도는 경로의 복잡도와 위험에 맞추며, 단순 테스트를 위해 별도 계획 문서나 승인 절차를 추가하지 않는다.

변경에 관련된 사례를 선택한다. 아래 항목을 모든 기능의 의무 행렬로 만들지는 않는다.

- 정상·부정 입력, 빈 값·0·최솟값·최댓값·한도 경계와 허용/거부 대조.
- 반복·중복·재시도·재진입, 이벤트 순서·동시 시각과 상태 전이.
- 객체·대상·사본·generation의 정체성, 오래된 참조, 취소·제거·만료·저장·복원 수명.
- 부분 실패·자원 부족의 원자성·rollback, 대상·출처·반복 사이 격리.
- 기존 기능과의 상호작용, 공개 경로와 내부 준비 경로의 차이, 관측·설정의 결과 영향.

정상 사례의 입력·상태·자원 한도·대상 자격·기본값·이벤트 시점이 실제 계약을 만족하는지 확인한다. 시나리오의 각 주요 행동 뒤에는 예상 상태와 다음 행동의 자격을 확인한다. 예상 밖 상태를 진행기가 임의로 건너뛰거나 자동 처리하여 실패를 숨기지 않으며, 지원해야 하는 분기는 규칙에 따라 명시적으로 처리한다. assertion은 잘못된 대상·누락·순서 오류·실패 후 잔여 변경을 구별해야 한다.

준비 상태에서 목표 연산·관측 지점에 도달하는 이유를 관련 규칙과 실제 입력으로 설명할 수 있어야 한다. 부정 사례도 의도한 거절 지점까지 도달하는 데 필요한 선행 조건을 만족하는지 확인한다. 다른 자격 오류나 초기 거절이 목표 경계의 검증을 대신하지 않도록 한다.

검증할 제품 계약과 그 상태를 만들기 위한 진행 전략을 구분한다. 테스트가 선택한 배치·탐색·조작 순서 등의 편의적 제약을 제품의 필수 규칙으로 추가하지 않는다. 준비 전략을 바꿀 때는 요구된 경로·입력 규모·관측 지점·판정 조건을 유지한다. 특정 전략이나 순서 자체가 요구사항이면 그 조건도 검증 대상이다.

수용 조건·변경 코드·직간접 호출·공유 계약·선행 회귀를 기준으로 유닛·통합·공개 경로·성능 검사를 선정한다. 개발 중에는 실패 재현과 변경 영향에 집중하고, 최종 통합 입력에서 필요한 검증의 누락을 닫는다. 유효한 기존 결과는 입력 동일성 또는 비영향 근거로 재사용한다.

기존 테스트를 재사용할 때는 fixture·공유 helper가 전제한 기본 콘텐츠, 시작 상태, 진행 구조와 저장 버전을 변경 내용과 대조한다. 과거 계약을 검증하는 입력과 현재 공식 경로를 검증하는 입력의 목적을 명시하며, 과거 입력의 통과를 현재 경로의 검증으로 대신하지 않는다. 실패를 없애기 위해 현재 경로 시험을 과거 입력으로 바꾸지 않으며, 입력을 변경할 때는 원래 검증 목적이 유지되는지 확인한다.

같은 입력·환경의 관련 사례는 기존 runner와 선택 목록으로 묶는다. 시험마다 Cargo 호출·동일 설정 빌드를 반복하지 않는다. 기능 옵션·외부 CLI/서버·재시작·전역 상태·성능 환경에 필요한 분리는 유지하며 단일 all-features 실행으로 모두를 대신하지 않는다. 명령 병렬 실행은 입력과 공유 자원이 격리될 때만 사용한다.

예상 밖 회귀나 공유 기반·공개 계약·저장 형식 변경으로 영향이 불확실하면 관련 경로의 검증을 확대한다. 필요한 전체 검사와 사용자 지정 검사는 수행하되, 한 번의 전체 실행을 이후 모든 수정에 반복하지 않는다. 고비용 검사 전에는 공통 준비와 목표 연산 도달을 작은 실제 실행 또는 유효한 증거로 확인한다. 미확인 전략은 목표 전이에 필요한 효과가 실제 발생하는지, 상쇄·차단 조건이 있는지를 구별할 수 있는 짧고 유한한 관측으로 먼저 검증한다. 지연 이벤트·주기·확률 조건을 고려하며 짧은 무변화만으로 불가능을 단정하지 않는다. 전략의 전제가 깨졌다는 증거가 나오면 §6의 소유 실행 중단·정리 규칙에 따라 원문을 보존하고 교정한다. 사전 관측 통과는 전체 시나리오 통과를 대신하지 않는다.

실행·재사용·미실행을 구분하고 종료 코드와 실제 선택/실행/통과/실패/skip 수를 확인한다. 0시험·skip·중단·환경 실패·빌드만 성공한 결과를 기능 PASS로 기록하지 않는다. 집중 검사 몇 개의 통과를 Goal 전체 검증으로 확대하지 않는다.

## 5 실패 진단과 교정

제품·테스트·fixture·기대값·판정 도구·실행 환경의 원인을 구분하고 직접 교정한다. 확정 계약에서 올바른 동작을 도출할 수 있으면 assertion이나 fixture 변경 자체로 새 승인을 요구하지 않는다.

원인이 불명확할 때 기대값·한도·workload를 완화하거나 계량을 누락해 실패를 숨기지 않는다. 테스트 편의를 위해 제품 API·권한·실행 의미를 바꾸지 않고 정상 adapter·준비 경로를 사용한다. 내부 fixture 검증과 공개 경로 검증을 구분한다.

새 가설·증거·유효 교정 없이 같은 수정·실행을 반복하지 않는다. 실패 시 예상한 전이·관측과 실제 결과의 차이, 깨진 가정 또는 아직 미확인인 가정, 교정 근거·배제한 원인·남은 불확실성을 기존 기록에 간결히 남긴다. 전제 오류가 확인되면 같은 가정을 사용하는 관련 시나리오·공유 fixture/helper·진행기도 함께 점검한다. 교정된 전략이 목표 조건에 도달할 근거를 확인한 뒤 영향 범위를 재실행하며, 원인이 미확인인 실패를 일괄적으로 테스트 탓이나 제품 결함으로 분류하지 않는다.

교정 중에도 원래 검증 목표와 성공 판정의 의미를 유지한다. 자동 종료와 명시적 중단, 실패 복구와 새 실행, 동일 프로세스 복원과 새 프로세스 복원처럼 서로 다른 경로를 대체 증거로 취급하지 않는다. 실제로 도달한 경로와 검증 범위만 기록하고, 대체 경로만 확인했다면 원래 목표는 미검증으로 남긴다.

실패 원본을 보존하고 교정의 영향 범위만 재검증한다. 계약·소유권·수명·저장·완료 기준이나 승인된 기대 동작의 변경이 필요하면 근거·영향·대안을 정리해 정식 owner 절차를 따른다. 기존 권한으로 해결할 수 없는 사용자 판단만 질문한다.

## 6 장시간 검사와 자원 한도

장시간 검사는 기존 시간·입력 규모·환경에 근거한 예상 소요와 진단·중단 조건을 기존 기록에 남긴다. 근거가 부족하면 예상 미확정과 첫 진단 시점·신호를 정한다. 출력 부재만으로 정체를 단정하지 않고 기존 세션의 진행·CPU·메모리·로그로 판단한다.

소규모 사전 실행부터 예상보다 오래 걸리면 제품 연산과 준비·승인·저장·로그 수집 시간을 구분하여 지연 원인을 확인한다. 기록·수집 병목은 검증할 동작·실패 조건·관측 정보를 유지하면서 개선하고, 개선 전후 측정 범위를 명시한다.

합의된 조건 안에서 자신이 소유한 실행만 안전하게 중단할 수 있다. 입력·명령·경과 시간·원시 출력·중단 이유를 보존하고 종료·정리를 확인한 뒤 수정한다. 운영 시간 초과는 제품 성능 합격선과 구분한다.

자원 한도는 기능·콘텐츠 단계에서 필요한 측정으로 검토하며 최종 성능 단계까지 미루지 않는다.

- 대표 정상 콘텐츠·예상 확장·지원 경로의 비정상 입력을 구분하고 입력·seed·profile·toolchain·관측 환경을 식별한다. 임의 변조 전용 사례의 제외는 로드맵 §1.9를 따른다.
- 실제 시간·지연·메모리 peak·종료 후 회수와 내부 작업량을 함께 확인한다. 내부 work/retained 회계를 CPU 시간이나 실제 heap/RSS로 간주하지 않는다.
- 오프라인 검증·실시간 실행·개발 측정·배포 기본값을 구분한다. 구조적 유한성·overflow 방지와 조정 가능한 비용 예산을 분리한다.
- 전체 비용을 관측하기 어려우면 trusted host가 선택한 유한 상한의 측정 profile을 사용하고 조건을 기록한다. 실행 중 자동 상향·무제한 실행·mod의 자기 제한 완화는 허용하지 않는다. 중도 한도 도달을 전체 성공 측정으로 기록하지 않는다.
- 동일 workload의 전후 결과, 정상 여유, 비정상 입력 거부 영향으로 한도 유지·상향·하향을 판단한다. 필요한 한도 조정을 모든 최적화 이후로 미루지 않으며, 임의 증가율로 실패를 면제하거나 조정 자체를 최적화 성과로 보고하지 않는다.
- 변경한 한도의 경계·초과 거부·실패 원자성·취소/복원·재시도·profile/캐시 분리를 영향 범위에 맞춰 검증한다.

## 7 완료 전 검토와 증거 정리

감사 finding은 먼저 로드맵 §1.9와 이 지시서 §4의 발생 근거 판정을 거친다. 지원 경로에서는 발생할 수 없고 임의 변조로만 성립하는 사례는 `범위 밖 — 외부 임의 변조`로 기록하며 제품 교정·재동결·재감사나 `Not Complete`/`Blocked` 사유로 사용하지 않는다. 발생 근거 미확인은 별도로 구분한다. 기존 포괄 계약 문구와 과거 finding이 최신 사용자 범위 결정에 우선하지 않는다.

범위 재분류는 현재 판단 기록에 사용자 결정·발생 경로 근거·제외 항목·남은 검증을 연결한다. 과거 동결 계약·증거·당시 판정은 보존하고, 정식 계약의 변경이 필요할 때 로드맵 §8.1에 따라 필요한 successor를 작성한다. 이 기록 갱신만으로 제품 수정·전체 재동결·시험 재실행·전체 재감사를 요구하지 않는다. 동일하거나 비영향인 증거는 재사용하며, 과거 감사를 새 기준에서 다시 수행했다고 표기하지 않는다. 제외 항목을 닫는 것으로 다른 필수 검증이나 Goal 전체 완료를 대신하지 않는다.

완료 보고 전에 실제 코드·중요 호출·상태 경계·시험 기대값·원시 실행 결과를 확인한다. 요구사항 충족, 계획 차이, 실패·취소·복원·재시도, 기존 동작 영향과 잔여 검증을 점검한다. 테스트 통과나 자신이 작성한 요약만으로 이 확인을 대신하지 않는다.

기존 PLAN·실행·판단 기록을 갱신하고, 새 판단이나 필수 절차에 필요한 경우에만 문서를 추가한다. 명령·입력·환경·종료 상태·시험 수·원시 결과·실패 위치·재사용 근거와 중요한 미검증 항목을 연결한다. 코드·입력이 바뀌지 않은 결과를 문서 정리나 재개만을 이유로 다시 실행하지 않는다.

기존 runner·수집·판정 도구를 우선 사용한다. 새 도구는 구체적인 미해결 문제에 필요할 때만 만든다. 작은 수정마다 전체 hash/archive/receipt를 만들지 않는다. 재개·중요 인계·최종 동결이라는 단계 이름만으로 전체 입력 대조를 반복하지 않고, 마지막 유효 확인 이후의 실제 변경과 확인되지 않은 범위를 기준으로 필요한 검사를 정한다.

소스 변경 확인과 보관·복원 무결성 검증을 구분한다. 단독 실행에서 다른 writer·입력을 바꾸는 자동 작업이 없고 자신도 마지막 확인 이후 대상 입력을 수정하지 않았다면, 단계 전환이나 시간 경과만을 이유로 같은 소스를 다시 전수 해시하지 않는다. 실제 수정, 외부 변경 징후, 입력 고정 실패 등 구체적인 근거가 있을 때 영향 범위를 재확인하며, 영향 범위를 신뢰할 수 없을 때만 전체 대조로 넓힌다. 파일 누락·보관 오류·잘못된 원본·패치 오류를 검출하는 필수 보관·복원 검증은 유지한다.

사용자의 dirty 작업과 과거 실패·출력·감사·동결 target을 보존한다. 전체 저장소 reset/clean/stash, 기록용 patch 재적용, 과거 artifact 생성 스크립트 재실행으로 원본을 바꾸지 않는다. 동결 기록은 기존 successor/currentness 절차를 따르며 재구성한 preimage를 원본으로 표기하지 않는다.

## 8 정식 Goal의 최종화

일반 변경은 승인 범위의 구현·검증·코드 검토를 끝내고 실제 상태를 보고한다. 정식 Goal은 현재 PLAN과 GEX가 요구하는 coverage·증거 결속·target 동결·복원 검증·감사 경계를 해당 범위에서 처리한다. 모든 작은 작업에 이 절차를 새로 붙이지 않는다.

최종 동결이 필요한 경우에는 대상 편집을 끝내고 최종 스냅샷을 한 번 생성한 뒤, 그 고정 입력으로 증거 결속과 정역 복원 검증을 수행하고 결과를 기록한다. 수집한 파일 목록·해시를 후속 단계에서 재사용하고, 목록 준비·복사·압축·동결 종료마다 작업 트리 전체를 다시 읽는 중복 검사를 쌓지 않는다. 보관본과 복원 결과의 정확성은 고정 스냅샷을 기준으로 확인한다. 이후 대상 입력을 수정하면 해당 스냅샷을 현재 결과로 주장하지 않고 변경 범위와 필요한 successor를 갱신한다. 최종화 도구를 교정한 경우에도 영향받은 산출물과 검사를 다시 수행하며, 변경되지 않은 제품 입력의 기능 시험까지 자동 반복하지 않는다. 별도 감사가 명시적으로 요구하는 입구·출구 확인은 해당 감사 경계에서 수행하고, 구현 최종화의 각 하위 단계에 중복 적용하지 않는다.

같은 실행자의 감사를 허용하는 경우에는 Astra가 구현 pass와 시간·작업 문맥·산출물을 분리한 fresh review를 수행한다. 감사 중 대상 입력과 기존 증거를 고정하고 감사 기록은 target과 분리한다. finding은 기록을 보존한 별도 교정 pass에서 수정하고 영향 범위를 재검증한다.

독립 제작·감사의 역할 구분은 [로드맵 §8.5](../ROADMAP.ko.md#85-단일-진입점과-p2g-상세화)를 따른다.

- **U29 독립 외부 제작:** 단독 실행자는 고정 엔진·공개 문서/API/CLI·지원 범위·실행 환경을 준비하고 사전 점검한다. 검증 대상 엔진 구현에 참여하지 않은 별도 제작자가 새 pack을 직접 작성·실행한 증거를 인수해야 한다. 같은 구현자가 역할명·세션을 바꾸거나 완성 pack을 대신 제공한 것으로 이 조건을 충족하지 않는다.
- **U33/U31 및 비참여 감사가 필수인 Goal:** 가능한 구현·검증·증거 정리·필요한 target 고정과 복원을 마친 뒤 구현에 참여하지 않은 별도 감사자의 판정을 인수한다. 자기 검토를 비참여 감사로 표기하지 않는다.
- **실제 인계:** 별도 역할이 필요해도 서브에이전트를 소환하거나 자동 위임하지 않는다. 기존 PLAN·실행 기록과 HANDOFF에 고정 입력·공개 도구·필요한 검증·충족된 조건·남은 독립 조건을 연결하고 미충족과 근거를 보고한다. 사용자가 별도 실행으로 담당자를 지정할 수 있다. 필수 독립 판정 전에는 그 조건을 완료로 표시하거나 그 완료에 의존하는 후속 작업을 시작하지 않는다. 독립성 조건에 의존하지 않는 기존 승인 작업은 지정된 중지 조건 안에서 계속할 수 있다.

## 9 실행 대기와 종료 보고

명령 대기는 기존 실행 세션의 완료 알림·출력 수집을 사용한다. 짧은 주기의 시간/status/프로세스 조회나 중복 실행을 피한다. 결과·실패·사용자 입력·진단 조건처럼 조치할 정보가 생기면 확인한다. 대기 응답마다 원문 재조회·전체 계획 재검토·보고서 갱신을 반복하지 않는다.

사용자 중지·checkpoint·승인 범위 완료·시간/비용/도구 한계에 도달했거나 현재 권한으로 해소할 수 없는 장애가 있을 때 상태를 보존하고 제어권을 반환한다. 필수 독립 역할의 인계 경계는 §8을 따른다. 사용자 판단을 기다릴 때 답변에 의존하는 작업은 진행하지 않는다. 답변과 무관하게 유효한 기존 승인 작업은 명시적 중지·checkpoint를 넘지 않는 범위에서 수행할 수 있다. 무응답·경과 시간·명령 완료를 새 승인이나 중지 해제로 간주하지 않는다.

최종 보고에는 구현한 동작, 실행하거나 재사용한 검증, 남은 문제·필수 미실행, 재현 명령과 결과 위치를 간결히 남긴다. 미완료를 완료로 표시하지 않는다. 비용을 비교할 때는 실제 입력·캐시 입력·출력과 적용 단가·측정 범위를 구분하며 총 토큰 비율을 요금 비율로 간주하지 않는다. 별도 필수 추적 도구나 보고서를 만들지는 않는다.

실제 인계·중지·장애 또는 재개 위치의 중요한 변경 때 [HANDOFF_LATEST](HANDOFF_LATEST.ko.md)를 갱신한다. 이전 최신본은 충돌하지 않는 `HANDOFF_YYYYMMDD_NNN.ko.md`에 원문 보존하고 [이력 안내](EXECUTION_HISTORY.ko.md)에 연결한다. 현재 단계·권한·다음 행동·마지막 실행·잔여·소스와 증거 위치를 남기며 문서 정리 시각을 제품 실행 확인 시각으로 바꾸지 않는다.

## 지금 시작할 일

구현 실행을 요청받았다면 최신 인수인계와 현재 작업 상태를 확인하고, 필요한 계획·계약을 인수한 뒤 Astra 한 명이 승인된 다음 행동부터 직접 수행한다. 구현·테스트·교정·완료 검토를 이어가며 서브에이전트는 사용하지 않는다. 이미 완료된 구현을 반복하거나 필수 독립 제작·감사를 자체 검토로 대체하지 않으며, 해당 경계에서는 §8의 준비·인계를 수행한다.
