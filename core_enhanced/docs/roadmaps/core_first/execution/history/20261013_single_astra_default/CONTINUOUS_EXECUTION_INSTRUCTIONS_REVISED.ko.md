# Core 우선 로드맵 연속 실행 지시서

이 문서는 상시 실행 규칙이다. 현재 단계·진행 상태·다음 행동은 [최신 인수인계](HANDOFF_LATEST.ko.md), 과거 요청·중지·재개 발화는 [이력 안내](EXECUTION_HISTORY.ko.md)로 분리한다. 문서의 조회·검토·수정 요청만으로 제품 실행을 시작하지 않는다.

## 1 목표와 권한

이 지시서에 따른 실행을 요청받으면 최신 인수인계와 실제 작업 상태를 대조하여 남은 승인 작업을 재개한다. 필요한 P2G 정리·인계, GEX 구현·검증·독립 감사·finding 교정·재감사와 다음 승인 로드맵 작업까지 포함하며, 기본 감사 인계마다 재승인을 요청하지 않는다. 사용자 중지·checkpoint와 실제 판단 대기는 [9]를 따른다.

- Core 우선, Unity 후속, 개별 최종보스 고유 구현 제외를 유지한다. 현재 기능에 필요한 기반 개선은 로드맵에 따라 병행하되 실적을 위한 분할·추상화·무관한 정리는 하지 않는다.
- 기존 계획·코드·테스트·증거를 인수한다. 인수인계 이후 변경은 영향을 검토하며, 과거 단계 번호나 소스 해시에 맞추려고 되돌리지 않는다.
- 합의된 범위의 내부 선택과 일반 오류 교정은 담당자가 자율 수행한다. 정책·공개 계약·완료 기준의 정식 변경은 해당 P2G/GEX owner에서 처리하며, 기존 위임으로 판단할 수 있는 일을 사용자 승인 대기로 바꾸지 않는다.
- 테스트 작성·테스트 측 문제 교정에는 필요한 토큰을 사용한다. 잘못된 실패·통과로 생기는 후속 재작업을 줄이기 위해 [3]의 Astra 직접 수행과 [5]의 검증 강도를 유지한다.

## 2 재개 자료와 최초 점검

메인은 [HANDOFF_LATEST](HANDOFF_LATEST.ko.md)에서 현재 Goal·권한 근거·다음 행동·관련 PLAN과 실행 기록의 위치를 확인한다. 최신본이 없으면 실제 최신 인계와 증거를 찾아 복구한다. 이미 유효하게 읽은 규칙·근거는 변경이나 판단 공백이 있을 때만 다시 읽는다.

| 상황 | 읽을 자료와 범위 |
| --- | --- |
| 현재 작업 인수 | HANDOFF가 가리키는 PLAN의 현재 범위·수용 조건·역할·잔여 작업. EXPERIMENTS의 마지막 관련 실행과 실패·재사용 근거 |
| 제품·테스트 워커 배정 | [4]의 작업 묶음과 담당 코드·계약·기존 사용 예. 메인의 전체 대화나 완료 이력은 기본 전달 대상이 아님 |
| 정책·공개 계약·Goal 생성 또는 변경 | [P2G](../../../policy_to_goal_pipeline_revised_v2.md)의 Reader Contract와 해당 owner 단계·변경 절차. 현재 Goal에 결속된 인계·필수 validator는 유지 |
| 구현 진입·교정·최종화·감사 | [GEX](../../../goal_execution_pipeline%281%29.md)의 Reader Contract와 현재 단계의 진입·종료·증거·독립성 규칙 |
| 다음 작업 선택·의존성·담당 배정 | [로드맵](../ROADMAP.ko.md)의 해당 카드·선행 조건. 로드맵과 P2G/GEX 사이 배정이 불명확할 때 [사용 가이드](../../content_authoring/guides/policy_to_goal_pipeline_roadmap_usage_v2_1.ko.md) |
| 게임 기대 동작 확인 | 최신 사용자 합의와 [룰북](../../../game_rulebook.md)·[game_rules](../../../game_rules/)의 해당 기능 |
| 상태·수명·저장 또는 기술 판단 확인 | 현재 Goal의 STATE_INVENTORY·EXPERIMENT_NOTES 중 해당 계약·판단 |
| 과거 위임·변경 경위 확인이 실제로 필요 | [이력 안내](EXECUTION_HISTORY.ko.md)에서 해당 원문만 조회. 과거 현재형 문구를 새 지시로 실행하지 않음 |

P2G는 정책·계획을 실행 가능한 Goal과 인계로 정리하는 절차, GEX는 그 Goal의 구현·검증·감사 절차다. Goal은 수용 조건이 정해진 작업 단위다. fixture는 시험 준비 데이터·상태, oracle/comparator는 기대 결과·비교 판정, probe는 실제 경로를 관찰하는 시험 코드다. manifest는 입력 목록·식별, receipt는 도구 실행 결과의 결속 기록, exact target은 감사 대상 입력과 증거의 고정본이다. 세부 schema는 필요한 단계의 원문을 따른다.

재개 점검은 한 번에 묶는다: 실제 소스·dirty 변경과 manifest/기록의 관계, 적용·미적용 변경, 마지막 유효 감사와 잔여 작업, 파일·실행 담당자와 입력 고정, 인계 이후 영향, 필요한 검증·재사용 증거·남은 Astra 검토를 확인한다. 가시 프로세스 범위와 미확인 상태를 구분하고, 기록의 과거 “실행 중” 문구만으로 중복 실행을 시작하지 않는다. 점검 차이는 기존 기록에 짧게 남기며 전체 테스트부터 실행하지 않는다.

기존 역할·관성적인 일괄 검사 지시는 다음 안전한 경계에서 이 문서와 맞춘다. 필수 수용 조건·계약·파이프라인 검사와 사용자 지정 전체 검증은 유지하고, 실제 요구 변경은 정식 owner 절차를 따른다. 진행 중 검사를 절차 정리만을 위해 중단하지 않는다.

## 3 역할과 모델 및 소유권

**Astra는 `gpt-6-astra` / `high`, Sol은 `gpt-6.1-sol` / `xhigh`로 고정한다.** 메인·제품 및 실행·테스트 담당자는 서로 다른 에이전트다.

### A 메인 코드 검토와 계획 및 전체 조정

메인 Astra는 요구사항·계약·계획·설계·순서·검증 범위와 품질 수용을 판단하고 파일·실행 소유를 조정한다. 실제 코드의 공개 계약·상태 소유권·수명·저장·권한·자원 경계를 읽고 [4-B]를 수행한다. 제품·테스트 코드를 대신 작성하지 않으며, 일반 교정의 매회 승인자나 반복 실행·로그 집계 담당자가 되지 않는다.

### B 제품 구현과 테스트 실행 워커

Sol은 계획 안에서 제품 코드·데이터·필요한 구현 문서, 제품 측 포맷·디버깅·교정을 맡는다. 준비된 제품·테스트 빌드와 검사 명령·순서·환경 복구·원시 결과 수집·기존 도구 집계를 자율 수행한다. 실제 변경·계획 차이·실행 결과·남은 문제를 전달한다. 테스트 코드·fixture·기대값·oracle·comparator·시험 판정 도구는 작성하거나 수정하지 않는다.

### C 독립 테스트 설계와 작성 담당

테스트 담당 Astra는 확정된 계약과 실제 코드 경계에서 입력·기대 결과·검증 방법을 독립 설계하고, 테스트·fixture·공개 경로 probe·판정 도구를 직접 작성·교정한다. 타입·import·등록·fixture 등 사소한 오류도 Sol에게 위임하지 않는다. 필요한 검사를 선정·보완하여 실행 기준과 함께 Sol에게 넘기고 결과의 타당성·누락·잘못된 기대값을 검토한다. 실제 교정과 판단 반환의 구분은 [6]을 따른다.

### D 최종 독립 감사

감사자는 해당 Goal의 계획·설계·제품 구현·테스트 작성·교정 및 [4-B]의 수용 전 검토에 참여하지 않은 별도 Astra다. Goal 전체의 구현·시험·검증 범위·원시 결과·요구 충족을 독립 판정하며 직접 교정하지 않는다. 본래 감사의 finding·재검증 요구만 제시했다면 같은 감사자가 재감사할 수 있다.

### E 담당자 배정

최초 배정·담당자 변경 때 실제 모델·추론 강도·참여 이력을 확인하고 기록을 재사용한다. 지정 모델을 쓸 수 없거나 배정을 확인할 수 없으면 제약을 보고하며 임의 대체하지 않는다. 기존 담당자를 재사용하고 감사자는 감사 시점에 배정한다. 추가 에이전트는 독립 산출물의 이익이 조정 비용보다 명확할 때만 쓰며 단순 실행 전용 담당자를 기본 추가하지 않는다. 기존 Sol 작성 테스트도 보존·검토·필요 보강하며 작성 이력을 바꾸지 않는다.

### F 편집과 실행 소유

- 서로 다른 파일의 독립 작업만 병행한다. 같은 파일은 영역이 달라도 순차 편집하며 embedded 테스트·등록부도 파일 전체 소유를 이관한다. 파일 소유를 받아도 자신의 역할에 해당하는 내용만 수정하고 포맷·자동 수정에도 같은 경계를 적용한다.
- helper·fixture·등록부까지 필요한 소유를 시작 시 정하고, 이관은 기존 기록에 짧게 남긴다.
- 실행 묶음의 담당자는 한 명이다. 실행 중 관련 제품·시험·fixture·설정·판정 도구 입력을 고정하고, 같은 입력·공유 자원에 영향을 주는 실행을 중복하지 않는다. 성능 측정은 기능 검사와 분리한다.
- 실행과 입력·파일·공유 자원에 영향이 없는 작업만 병행하고, 분리할 일이 없으면 [9]에 따라 대기한다.

## 4 계획과 작업 묶음 및 Astra 검토

기존 유효 계획을 남은 작업만큼 보완한다. 기능·의존성·편집 충돌·실행 환경을 기준으로 묶고, 파일 수·시험 수나 검토 횟수에 맞춘 분할·전체 로드맵의 선행 상세 설계는 하지 않는다.

인계에는 목적·수용 조건·범위, 관련 파일·심볼·중요 계약, 재사용 helper/adapter/예제, 확인 사실·정책상 기대·미검증 가정, 검사 범위·이유·재사용 증거, 편집·실행 소유·자율권·반환 조건을 전달한다. 기존 원문 위치와 차이를 우선 사용하며 전체 대화·과거 이력·무관한 로그를 복제하지 않는다. 요약은 탐색 입구이고, 테스트 담당자와 감사자의 직접 원문 확인에 필요한 근거를 생략하는 수단이 아니다.

담당자는 핵심 API·실제 사용 예를 확인한 뒤 계약 안에서 진행한다. 메인은 중요한 경계를 명확히 하되 Sol의 내부 구현 선택까지 고정하지 않는다.

### A 테스트 작성과 실행의 연결

테스트 담당 Astra는 검증 목적·선택 범위·입력·기대값·판정 기준을 정한다. 최초 실행 인계에는 runner/선택 사례, 입력·환경·순서·격리, 실행 수와 0시험/skip/중단/실패 기준, 판정 도구·원시 결과 위치, 재사용·제외·알려진 실패와 반환 대상을 남긴다. 장시간 검사는 [5-H]도 포함한다. 인계 전에 이미 모든 시험이 통과할 필요는 없다.

Sol은 의미를 보존하는 명령 구성·묶음 실행·실패 항목 우선 재실행을 자율 수행한다. 시험 측 코드·fixture나 합의된 검증 범위·판정 의미 변경은 테스트 담당 Astra에게 반환한다. 같은 묶음의 교정·재실행은 기존 지시와 변경된 입력·영향 범위를 재사용하며 새 계획·인계 문서·승인 단계를 만들지 않는다.

### B Astra의 구현 및 결과 검토

Sol의 모든 제품 변경과 검증·완료 주장은 최종 수용 전에 메인 또는 지정 Astra 검토자가 실제 코드·중요 호출·상태 경계와 증거로 확인한다.

- 요구사항·계획 충족, 계획 차이의 정당성, 공개 계약·소유권·수명·저장·권한·자원 경계.
- 실패·취소·복원·재시도와 기존 동작 영향·필요 회귀.
- 시험 입력·기대값·판정의 타당성, 실제 선택·실행·집계와 원시 결과, 재사용 근거의 현재 유효성.
- 미검증 변경·남은 위험과 완료 주장의 일치.

구현자 요약이나 테스트 통과로 이 검토를 대신하지 않는다. 의미 있는 묶음·중요 변경 경계에서 검토하며 교정 후에는 변경과 영향 부분을 확인하고 비영향 근거를 재사용한다. 기계적 사실은 기존 도구로 확인하고 모든 로그·생성 파일을 매번 처음부터 재집계하지 않는다.

검토 전에는 “구현·실행 완료”로만 기록한다. 미결정 계약·중요 finding에 의존하지 않는 승인 작업은 계속할 수 있지만, 선행 Goal의 독립 완료가 필요한 종속 구현은 해당 감사 통과 뒤 시작한다. 정식 Goal 최종화는 [8]의 경계에서 수행한다.

## 5 테스트 설계와 선정 및 실행 범위

### A 결함을 적극적으로 드러내는 테스트 설계

현재 계약과 변경 영향에 연결되는 실패 경로를 깊게 검증한다. 다음을 모든 기능의 의무 행렬로 만들지 말고 관련 사례를 선택한다.

- 정상/부정 입력, 빈 값·0·최솟값·최댓값·한도 경계와 허용/거부 대조.
- 반복·중복·재시도·재진입, 이벤트 순서·동시 시각·발생 시점에 따른 상태 전이.
- 객체·제공자·대상·사본·generation의 정체성과 오래된 참조, 취소·철수·제거·만료·교체·저장·복원 수명.
- 부분 실패·자원 부족의 원자성·rollback·재시도, 대상·출처·효과·반복 사이 격리.
- 새 기능과 기존 기능의 상호작용, 공개 경로와 내부 준비 경로의 차이, 관측·로그·설정이 게임 결과·필수 계량에 미치는 영향.

기대값은 요구사항·정책·독립 계산과 외부 관찰에서 도출한다. 제품 알고리즘·helper를 복제하지 않고 작은 수작업 예제·대조 입력·불변 조건을 활용한다. assertion은 잘못된 대상·누락된 효과·잘못된 순서·무변이 실패를 구별해야 한다. 필요한 부정 대조는 추가하되 이를 위한 대규모 도구를 기본 만들지 않는다.

정상 성공 사례는 입력 문법·허용 상태·자원/배치 한도·대상 자격·기본값·이벤트 시점이 해당 공개 경로의 실제 계약을 만족하는지 확인한다. 신규 작성과 교정 모두에 적용하며 중요한 미확인 가정은 기존 기록에 남긴다. 시험 개수·커버리지 수치보다 중요한 결함의 검출력이 기준이다.

### B 범위 선정

수용 조건·변경 코드·직간접 호출·공유 계약·선행 회귀를 기준으로 유닛·통합·공개/외부 경로·성능 검사를 선정하고 이유를 기존 기록에 남긴다. 시험 이름·파일 위치·속도만으로 범위를 정하지 않는다. 관련 검증과 명시적 필수 검사는 유지하고 무관한 검사를 관성적으로 추가하지 않는다.

### C 개발 중 실행

API/fixture 연결·실패 재현·교정·변경 영향에 집중하고 준비된 사례를 묶는다. 고비용 검사 전에는 공통 준비·참여자·대상·이벤트와 목표 연산 도달을 작은 실제 실행 또는 유효한 기존 증거로 확인한다. 공개 경로 검증은 그 경로에서 확인한다. 고장이 재현되지 않으면 연산별/누적 한도의 적용 위치와 실제 전제를 먼저 점검하며 시간·한도를 임의로 늘리지 않는다. 작은 준비 확인은 필요한 전체 workload·실패 경계 검증을 대체하지 않는다.

### D 최종 통합 검증

최종 통합 입력에서 수용 조건과 변경 영향에 필요한 검증을 닫고 누락을 보완한다. 동일 입력 또는 명시적 비영향 근거의 유효 결과는 재사용한다. 집중 검사 몇 개를 Goal 전체 검증으로 확대하지 않으며, 최종화·담당자·모델 변경 자체를 전체 재실행 근거로 삼지 않는다.

### E 범위 확대

예상 밖 회귀·공유 기반/공개 계약/저장 형식 변경·영향 범위의 구체적 불확실성이 있으면 의존성을 확인하여 위험 경로에 맞춰 확대한다. 그래도 전체 검사가 필요하거나 사용자가 명시적으로 요청하면 수행한다. 메인은 기존 권한 안에서 이유를 기록하며, 한 번의 전체 실행을 이후 모든 수정에 반복 적용하지 않는다.

### F 묶음 실행과 격리

같은 입력·환경의 관련 사례는 기존 runner·선택 목록·집계 도구로 묶고, 시험마다 Cargo 호출·동일 설정 빌드를 반복하지 않는다. 하나의 결과를 여러 수용 조건에 연결할 수 있다. 병렬 실행은 실제 공유 자원·격리 근거로 정한다. 기본/기능 옵션·외부 CLI/서버·종료/재시작·전역 상태·성능 환경의 필요한 분리는 유지한다. 단일 cargo test/all-features가 모든 설정·외부 검증을 대신하지 않는다. 빌드·캐시·환경 변경은 결과 비교 가능성과 설정 차이를 기록한다.

### G 판정

실행·재사용·미실행을 구분하고 종료 코드와 실제 선택/실행/통과/실패/skip 수를 확인한다. 0시험·skip·중단·환경 실패·빌드만 성공한 결과는 기능 PASS가 아니다. 결과 수집 미완료는 원시 결과와 복구 여부를 남긴다. 필수 누락·잘못된 기대값·미지원 경로는 통과와 별도로 확인한다. 무관한 전체 시험 미실행 자체는 완료 실패가 아니며, 실행·기능 통과·Astra 검토·독립 완료는 서로 다른 상태다.

### H 장시간 실행의 진단과 중단 기준

장시간 검사는 기존 시간·입력 규모·환경에 근거한 예상 소요와 진단·중단 조건을 기존 기록에 남긴다. 근거가 부족하면 예상 미확정과 첫 진단 시점·신호를 정한다. 출력이 없다는 이유만으로 정체를 단정하지 않고 기존 세션의 단계 진행·CPU·메모리·로그로 판단한다.

Sol은 합의된 조건 안에서 자신이 소유한 실행을 안전하게 중단할 수 있다. 입력·명령·경과 시간·진행/자원·원시 출력·이유를 보존하고 종료·정리를 확인한 뒤 관련 입력을 수정한다. 다른 실행을 함께 종료하거나 중복 시작하지 않는다. 기준 밖의 중요한 판단은 메인에게 반환한다. 운영 시간 초과는 제품 성능/자원 합격선과 구분하고, 개별 실행 중단 뒤 원인 교정·관련 재검증을 이어간다.

### I 자원 한도의 실측과 조정

초기 작업량·메모리 예산은 측정으로 재검토할 기준이다. 각 기능·콘텐츠 단계에서 필요한 측정·조정을 수행하며 최종 성능 단계까지 미루지 않는다. 정상 콘텐츠가 한도에 걸리면 불필요한 비용과 예산 적정성을 함께 검토하고, 모든 최적화가 끝나야만 조정할 수 있다고 해석하지 않는다.

- 대표 정상 콘텐츠·예상 확장·비정상/폭주 입력을 구분한다. 입력·seed·source·profile, CPU·메모리·동시 실행 규모·toolchain·관측 설정을 식별한다.
- 실제 경과 시간·지연, 메모리 peak·종료 후 회수와 내부 작업량을 함께 본다. work 단위는 CPU 명령/시간이 아니고 retained/admission 회계는 실제 heap/RSS와 다르다. 평균 외 집중 부하·분포·최댓값·필요 여유를 검토한다.
- 오프라인 authoring/검증·실시간 전투·trusted 개발 측정·배포 기본값을 구분한다. 구조적 유한성·입력 검증·overflow 방지와 조정 가능한 비용 예산을 분리하며 engine ceiling 변경은 근거·구현 영향을 재검토한다.
- 전체 비용을 관측하기 어렵다면 trusted host가 명시적으로 선택하는 유한 상한의 측정 profile을 사용할 수 있다. profile·상한·중단 조건을 기록하고 배포 기본값과 구분한다. 실행 중 자동 상향·무제한 실행·mod의 자기 제한 완화는 허용하지 않는다. 중도 한도 도달은 전체 성공 비용의 측정이 아니다.
- 기존/제안 한도, 동일 workload의 전후 결과, 정상 여유와 비정상 입력 거부 영향으로 상향·하향·유지를 판단한다. 확장 입력은 기존 비교 입력에 추가하고 과거 실패를 보존한다. 작은 초과 폭·최신 PC·임의 공통 증가율로 실패를 면제하거나 한도 조정 자체를 최적화 성과로 보고하지 않는다.
- 판단은 [6]의 권한을 따르며 한도 경계·초과 거부·실패 원자성·취소/복원·재시도·profile 식별/캐시 분리를 변경 영향에 맞춰 검증한다.

## 6 실패 교정과 판단 반환

제품 결함은 Sol, 테스트·fixture·기대값·판정 도구 결함은 테스트 담당 Astra, 실행 환경·명령 연결은 Sol이 교정한다. 시험 측 오류는 확정 계약에서 올바른 입력·기대값·판정을 도출할 수 있으면 Astra가 직접 자율 교정한다. assertion 값이나 fixture 변경 자체로 새 승인을 요구하지 않는다.

다음은 근거·영향·대안과 함께 메인에게 반환한다: 정책·공개 계약·소유권·수명·저장·완료 기준, 승인된 기대 동작·한도·workload·회귀 oracle 의미의 변경/불명확성, 파일 소유·입력 고정 충돌, 합의된 범위를 넘는 변경. 실행 환경 복구도 manifest·lock·toolchain·판정 의미를 보존하며 이 기준의 변경은 숨기지 않는다.

어렵거나 원인이 처음에 불명확하다는 이유만으로 즉시 반환하지 않는다. 다만 새 가설·증거·유효 교정 없이 같은 수정·실행을 반복하게 되면 시도·관측·배제한 원인·남은 불확실성을 메인에게 전달한다. 시험 측 원인이 확인되면 테스트 담당자에게 직접 연결한다. 반복되는 시험 전제 오류는 공유 fixture/helper의 관련 가정을 함께 점검·묶음 교정한 뒤 고비용 재검사를 진행한다.

원인이 불명확할 때 기대값·한도·workload를 완화하거나 계량을 누락해 실패를 숨기지 않는다. 테스트 편의를 위해 제품 API·실행 의미·권한을 바꾸지 않고 정상 adapter·준비 경로를 사용한다. 내부 fixture 검증은 공개 경로 검증과 구분한다. 정당한 비용 변화는 원인·전후 측정을 남기고 예산 재검토에는 [5-I]를 적용한다.

수정 전 관련 실행을 종료하거나 안전하게 정리하고 파일 소유를 넘긴다. 실패에 의존하는 후속 검사는 보류하되 독립 검사는 계속할 수 있다. 실패 원본을 보존하며 교정의 영향만 재검증하고 [4-B]의 변경 검토를 적용한다. 메인은 기존 권한 안에서 판단·연결하고 실제 사용자 판단이 필요한 경우에만 [9]로 전환한다.

## 7 증거 재사용과 보고

기존 PLAN·실행·판단 기록을 우선 사용하며 필수 절차나 새 판단 근거가 있을 때만 문서를 추가한다. 변경 가능한 기록을 갱신하고 동결 기록·감사 target은 원본을 유지한 채 기존 successor/currentness 절차를 따른다.

실행 기록은 대상 코드·시험·설정 식별, 선택 범위·이유, 실제 명령·영향 환경, 담당자·수집/판정 도구, 종료 상태·시험 수, 원시 출력·실패 위치, 변경·재사용 근거, 중요한 제외·미검증 위험을 연결한다. 고정 입력은 공통 목록과 명령별 결과를 공유할 수 있다. 모든 미실행 시험이나 동일 모델/참여 이력을 매번 열거하지 않는다.

Astra 검토는 [4-B]의 범위·중요 계약·계획 차이·finding/교정·남은 검토·코드와 증거 참조를 간결히 남긴다. 실제 실행과 증거 재사용을 구분하고, 문서·담당자·역할 변경만으로 유효 결과를 무효화하지 않는다. 새 변경은 무관한 과거 PASS로 검증했다고 하지 않는다.

기존 runner·수집·판정 도구를 우선 사용한다. 새 도구는 구체적인 미해결 문제에 필요할 때만 만들며 시험 입력·선택·기대값·판정에 영향을 주는 작성·교정은 [3-C]가 맡는다. 원시 전체 대신 요약·실패·원문 위치를 전달하고 의미 판단에 필요한 원문은 직접 확인한다.

일반 보존 확인은 diff·관련 검사, 전체 입력 대조·복원 보관은 재개·중요 인계·최종 동결의 필요한 경계에서 수행한다. 작은 수정마다 전체 hash/archive/receipt를 만들지 않는다. 사용자 dirty 작업·과거 실패·출력·감사·동결 target을 보존하고 전체 저장소 reset/clean/stash·기록용 patch 재적용·과거 artifact 생성 스크립트 재실행은 하지 않는다. successor evidence는 소비 도구와 함께 연결하고 archive 재귀 중첩·재구성 preimage의 원본 표기를 피한다.

보고는 새 결과·판단·중요 실패·방향 변경, 확인된 동작과 남은 필수 검증을 중심으로 한다. 명령·문서 수나 추정 완료율로 진척을 대신하지 않는다. 장시간 비용은 준비·빌드·시험·증거 처리의 측정 구간과 포함/제외를 구분하며 기록 공백을 작업 시간으로 추정하지 않는다. 비용 효율은 재작업·독립 감사까지 포함해 보고, 기존 모델별 사용량이 있을 때만 실제 진척과 비교한다. 별도 필수 추적 도구나 보고서는 만들지 않는다.

## 8 Goal 최종화와 독립 감사

정식 Goal 완료 경계에서 최종 통합 검증과 [4-B]를 닫은 뒤 현재 source·결과를 기준으로 다음을 처리한다.

1. 증거 선택, 선행 영향, 구현 적응(adaptation)의 현재 결속과 수용 조건별 coverage 확인.
2. 자체검증·Astra 검토와 PLAN/NOTES의 현재 상태 정렬.
3. exact target 동결, 필요한 정·역 복원 검증.
4. [3-D]의 별도 감사자가 Goal 전체를 독립 감사.

준비는 기존 도구·기록으로 묶고 항목별 새 승인·전체 재검사를 만들지 않는다. 정해진 실행·수집·기계적 집계는 Sol이 수행한다. coverage는 필수 요구·변경 영향·선행 회귀와 실제 증거를 연결하여 판정한다.

감사자는 마지막 수정 파일만 보거나 앞선 검토를 추인하지 않는다. 감사 중 대상 소스·요구·입력·기존 증거를 고정하고 새 감사 기록은 target과 분리한다. finding 교정은 감사 결과를 남긴 별도 교정 pass에서 [6]의 담당자가 수행한다. 변경 영향에 맞는 증거·target으로 재감사하고 비영향 근거는 재사용한다. 필요한 독립 완료 판정과 열린 finding 0 뒤 다음 승인 작업으로 진행한다.

## 9 비동기 대기와 종료 및 인계

위임 뒤 메인은 필요한 독립 작업을 수행하고, 분리할 일이 없거나 다음 판단에 결과가 필요하면 알림·대기 기능을 사용한다. Sol도 명령 대기 중 기존 세션의 완료 알림·출력 수집을 사용한다. 결과·실패·도움 요청·사용자 입력이나 합의된 진단 조건처럼 조치할 정보가 생기면 확인하고 다음 작업을 연결한다. 짧은 주기의 시간/status/프로세스 조회, 동일 지시 반복, 대기를 채우기 위한 문서·시험·에이전트 생성은 하지 않는다.

내부 Astra 검토는 사용자 단계검토 checkpoint와 다르다. 역할·모델 변경이나 PASS만으로 사용자 checkpoint가 추가·해제되지 않는다. 다음 경우에는 사용자에게 제어권을 반환하고 미완료·재개 조건을 남긴다.

- 사용자 중지, 승인 범위 완료, 사용자 지정 checkpoint·종료점·시간/비용/도구 한계.
- P2G/GEX 기준상 실제 사용자 선택·추가 권한이 필요한 경우 또는 현재 권한·환경에서 해소할 수 없는 장애.

사용자 정책 판단 대기는 P2G/GEX의 규칙을 따른다. 주 작업은 상태 보존·질문 뒤 멈추고, 답변 의존성이 있거나 불명확한 실행은 안전하게 정리한다. 이미 실행 중이며 어느 답변에서도 요구·완료 기준·결과가 유효하고 파일·공유 상태 충돌이 없는 작업만 기존 배정 범위까지 마칠 수 있다. 새 작업·위임·후속 단계는 시작하지 않는다. 사용자 checkpoint는 해당 GEX 정지 규칙을 따른다. 무응답·경과 시간·담당자 완료 통지는 재개 승인이 아니다.

단순 담당자 결과 대기·일반 교정·무관한 시험 미실행은 전체 종료 사유가 아니다. 사용자의 최신 명시 지시를 과거 인계의 “중지/계속” 문구로 덮어쓰지 않는다.

실제 인계·중지·장애 또는 재개 위치의 중요한 변경 때 메인이 [HANDOFF_LATEST](HANDOFF_LATEST.ko.md)를 현재 상태로 갱신한다. 이전 최신본은 충돌하지 않는 `HANDOFF_YYYYMMDD_NNN.ko.md`에 원문 보존하고 [이력 안내](EXECUTION_HISTORY.ko.md)에 연결한다. 별도 STATE 장부는 만들지 않는다.

현재 상태에는 확인 시각·단계·실행 권한/중지·정확한 다음 행동, 완료/부분/미검증/실패, 실제 역할·모델·감사 독립성, 소스·변경·마지막 실행·재사용 근거, 소유·입력 고정·실행 세션과 가시성, 중요한 계약/가정·제약·필수 원문 위치를 담는다. 장시간 실행 중이면 진단·중단 기준도 연결한다. 상세 사실은 해당 PLAN·실행 기록이 소유하고 현재 상태는 그 위치와 마지막 확인 시점을 안내한다. 문서 정리 시각을 제품 실행 확인 시각으로 바꾸지 않는다.
