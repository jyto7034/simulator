# Core 우선 로드맵 연속 실행 지시서

문서의 조회·검토·수정만 요청받은 경우에는 아래 실행을 시작하지 않는다.
이 지시서에 따른 실행을 요청받았을 때 다음 지시를 적용한다.

Core 우선 로드맵의 작업을 최신 인수인계에서 이어서 진행해줘.
이 요청은 기존 중지 상태를 해제하고, 승인된 범위의 계획·구현·테스트·검증·교정·후속 작업을 재개하는 지시다.

## 1 목표와 권한

- 최신 인수인계와 현재 작업 트리·실행 기록·감사 결과를 대조하여 실제 남은 작업부터 진행한다.
- 특정 단계 번호나 과거 소스 해시를 재개 위치로 고정하지 않는다.
- 인수인계 이후 변경은 검토하여 인수하며, 불일치한다는 이유로 과거 상태로 되돌리지 않는다.
- Core 우선, Unity 후속, 개별 최종보스 고유 구현 제외를 유지한다.
- 기존의 유효한 계획·코드·테스트·검증 증거를 재사용한다.
- 역할 변경·모델 변경·세션 재개·단계 전환 자체는 재작성이나 재실행의 근거가 아니다.
- 수용 조건·기대 동작·실패 판정·감사 독립성을 유지하면서 절차를 간소화한다.
- 현재 기능에 필요한 기반 개선은 로드맵의 리팩토링 지침에 따라 병행한다. 실적을 위한 분할·추상화·무관한 정리는 하지 않는다.
- 승인된 범위의 내부 선택과 일반 오류 교정은 자율 수행한다. 메인에게 판단을 반환하는 것은 자동 사용자 승인 대기가 아니다.
- 정책·공개 계약·완료 기준의 정식 변경은 해당 P2G/GEX 절차에서 처리한다. 기존 위임 범위 안에서 처리할 수 있으면 메인이 판단하여 진행한다.
- 단계 완료 보고만으로 종료하지 않고 다음 승인된 작업으로 이어간다.

이 실행 요청은 필요한 P2G 정리·인계와 GEX 구현·검증·독립 감사·finding 교정·재감사까지 포함한다.
따라서 GEX의 기본 감사 인계에서 재승인을 기다리지 않는다. 다만 사용자가 별도로 지정한 중간 정지·단계검토·범위 제한은 실제 후속 지시로 해제된 경우에만 넘어간다.
이 문서의 Astra 검토는 내부 품질 검토이며, 모델 분리나 검토 PASS만으로 사용자 단계검토 checkpoint가 추가되거나 해제되지 않는다.

사용 모델과 역할은 다음으로 고정한다.

- GPT-6 Astra high: 코드 검토, 계획·설계, 독립 테스트 작성, 품질 판단과 감사.
- GPT-6.1 Sol xhigh: 계획에 따른 제품 구현·교정, 준비된 테스트 실행과 결과 수집·집계.

Sol은 합의된 계획 안에서 자율적으로 구현하고 실행한다.
다만 Sol이 만든 모든 제품 변경과 검증·완료 주장은 최종적으로 Astra의 검토를 받아야 한다.
Sol의 자체 보고나 테스트 통과만으로 품질 검토를 완료했다고 간주하지 않는다.

Astra는 정상 사례의 통과만 확인하지 않고, 구현의 잘못된 가정·경계·수명·실패 경로를 적극적으로 드러내는 테스트를 작성한다.
테스트 작성과 테스트 측 문제 교정은 필요한 토큰을 사용하더라도 테스트 담당 Astra가 직접 수행한다.
잘못된 실패·잘못된 통과로 인한 후속 디버깅·재검토·재감사를 줄이는 것이 목적이다. 비용 절감을 이유로 이 책임을 Sol에게 넘기거나 관련 검증의 강도를 낮추지 않는다.

현재 목표와 변경 영향에 필요한 테스트만 실행한다.
개발 중 검사와 최종 통합 검증 모두 [5]의 같은 범위 선정 원칙을 적용한다.
공격적인 테스트 설계는 관련 실패 경로를 깊게 검증한다는 뜻이며, 무관한 전체 테스트를 관성적으로 실행한다는 뜻이 아니다.

활동량보다 실제 진척을 우선한다.
필요 없는 조회·문서·인계·검사·승인 단계를 추가하지 않는다.

1. 현재 작업 트리·manifest·실행 기록·가시적인 프로세스의 관계.
2. 이미 적용된 변경과 미적용 제안.
3. 최신 유효 완료 판정과 실제 남은 작업.
4. 현재 편집·실행 담당자와 실행 입력의 고정 여부.
5. 인수인계 이후 변경의 영향.
6. 현재 목표에 필요한 검증과 재사용 가능한 결과.
7. 구현·실행은 끝났지만 Astra 검토가 남은 변경이나 주장.

프로세스 조회의 가시성 한계는 명시한다.
확인되지 않은 상태를 추측하여 제품 변경이나 중복 실행을 시작하지 않는다.
기록용 patch를 다시 적용하거나 완료된 단계를 재시작하지 않는다.
재개 상태 확인을 위해 전체 테스트부터 실행하지 않는다.

확인한 역할·남은 작업·중요한 차이는 기존 실행 기록에 간결하게 남긴다.
새 변화나 판단 필요가 없으면 재개 점검을 반복하지 않는다.

기존 지침이나 PLAN의 관성적인 일괄 전체 테스트 요구는 다음 안전한 경계에서 [5]에 맞게 정비한다.
수용 조건·공개 계약·적용 파이프라인이 요구하는 필수 검사와 명시적으로 요청된 전체 검증은 유지한다. 실제 필수 요구를 바꾸어야 하면 해당 owner의 정식 변경 절차를 따른다.
기존 역할 배정도 진행 중 작업을 중단하지 않는 안전한 경계에서 [3]에 맞게 정비한다.
요구사항·기대 동작·실패 판정은 완화하지 않는다.
과거 요청·실행 결과·감사·동결 target은 소급 수정하지 않는다.

## 3 역할과 모델 및 소유권

사용 모델은 다음 두 종류로 고정한다.

- `gpt-6-astra` / reasoning effort: `high`
- `gpt-6.1-sol` / reasoning effort: `xhigh`

다른 모델이나 추론 강도로 임의 변경하지 않는다.
실행 전용 모델이나 별도 추론 강도 선택 절차를 추가하지 않는다.

### A 메인 코드 검토와 계획 및 전체 조정

- `gpt-6-astra` / reasoning effort: `high`.
- 요구사항·수용 조건·구현 계획·설계·작업 순서·검증 범위를 정한다.
- 실제 코드를 읽고 제품·테스트 담당자의 인터페이스와 기대 동작을 맞춘다.
- 정책·공개 계약·상태 소유권·수명·저장 의미 등 중요한 전제를 검토한다.
- Sol의 구현이 계획과 요구사항에 맞는지 실제 코드와 변경 영향으로 검토한다.
- 검증 범위의 충분성, 증거 재사용 근거와 중요한 품질 문제를 판단한다.
- 파일 소유와 실행 담당자를 정하고 결과에 따라 다음 작업을 연결한다.
- 제품 코드나 테스트 코드를 대신 작성하지 않는다.
- 테스트 담당 Astra의 독립 설계·결과 해석을 바탕으로 검증 범위와 품질 수용을 판단하고, 교정은 [6]의 해당 담당자에게 연결한다.
- 최종 독립 감사자를 겸하지 않는다.
- 일반적인 구현·테스트 교정을 매번 승인하는 병목이 되지 않는다.
- 단순 테스트 실행·원시 로그 수집·기계적인 집계를 반복 수행하지 않는다.

### B 제품 구현과 테스트 실행 워커

- 별도 에이전트: `gpt-6.1-sol` / reasoning effort: `xhigh`.
- Astra의 구현 계획과 계약을 인계받아 제품을 구현한다.
- 제품 코드·제품 데이터·필요한 구현 문서를 작성하고 제품 결함을 교정한다.
- 합의된 설계와 기대 동작 안의 내부 구현 선택·제품 디버깅·제품 측 일반 컴파일 오류는 자율 해결한다.
- 문제가 어렵다는 이유만으로 즉시 Astra에게 반환하지 않는다.
- 제품 범위의 포맷과 제품·테스트의 빌드·실행을 담당한다. 빌드 오류의 교정은 [6]의 역할 구분을 따른다.
- Astra가 정한 검증 목적·범위·입력·기대값·판정 기준에 따라 테스트를 실행한다.
- 기존 runner 확인, 실행 명령 구성, 빌드·실행 순서, 로그 수집과 환경 복구는 검증 의미와 범위를 보존하는 한 자율 수행한다.
- 실제 명령·환경·종료 상태·시험 수·원시 결과를 수집하고 기존 도구로 집계한다.
- 테스트 코드·fixture·기대값·oracle·comparator·시험 판정 도구는 작성하거나 수정하지 않는다.
- 시험 측 변경이 필요하면 실패 근거와 함께 테스트 담당 Astra에게 반환한다.
- 요구사항 해석이나 중요한 설계·계약·상태 의미 변경이 필요하면 메인 Astra에게 반환한다.
- 실제 변경, 계획과의 차이, 실행 결과, 남은 문제를 Astra가 검토할 수 있게 전달한다.
- 자신의 구현 설명이나 테스트 통과를 Astra 검토의 대체물로 사용하지 않는다.

### C 독립 테스트 설계와 작성 담당

- 제품 담당자와 별도 에이전트: `gpt-6-astra` / reasoning effort: `high`.
- 수용 조건과 실제 코드 경계를 읽고 입력·기대 결과·검증 방법을 독립적으로 설계한다.
- 테스트 코드·fixture·공개 경로 probe·판정 도구·comparator를 직접 작성하고 교정한다.
- 제품 구현이 잘못되었을 때 실패하도록 테스트를 설계한다.
- 정상 경로뿐 아니라 관련 경계값·부정 입력·상태 전이·수명·실패 복원·기존 동작 회귀를 적극적으로 검증한다.
- 외부 관찰 결과와 요구사항을 검증하며 제품 구현을 그대로 복제한 기대값을 만들지 않는다.
- 메인이 정한 수용 조건과 계약 안에서 필요한 검사를 독립적으로 선정·보완하고 기존 증거의 재사용 가능성을 검토한다.
- 준비된 관련 테스트와 실행 기준을 묶어서 Sol에게 전달한다.
- 실행 결과를 해석하고 시험의 타당성·검증 누락·잘못된 기대값을 검토한다.
- 테스트 측 일반 타입·import·fixture·등록 오류도 승인 범위 안에서 직접 자율 교정하며, 기계적인 수정이라는 이유로 Sol에게 위임하지 않는다.
- 제품 변경이 필요하면 근거와 함께 제품 담당자에게 반환한다.
- 중요한 요구사항·기대 동작·판정 기준 변경은 메인에게 반환한다.
- 최종 독립 감사자를 겸하지 않는다.

### D 최종 독립 감사

- 해당 Goal의 계획·설계·제품 구현·테스트 작성·교정 및 [4-B]의 수용 전 검토에 참여하지 않은 별도 에이전트.
- `gpt-6-astra` / reasoning effort: `high`.
- 현재 Goal 전체의 구현·테스트 타당성·검증 범위·원시 결과·요구사항 충족을 검토한다.
- 테스트 통과나 앞선 Astra 검토만으로 설계·구현의 적절성을 인정하지 않는다.
- 전체 테스트 미실행 자체를 완료 실패 사유로 삼지 않는다.
- 필요한 검증이 빠졌으면 구체적인 누락과 보완 범위를 finding으로 반환한다.
- 직접 교정하지 않는다.
- finding과 필요한 재검증 범위를 제시한 본래 감사 활동만으로 독립성을 잃지는 않는다. 직접 설계·교정에 참여하지 않았다면 같은 감사자가 재감사할 수 있다.

### E 담당자 배정

- 기존 담당자는 사용 가능 여부·실제 모델·참여 이력을 확인한 뒤 재사용한다.
- 없으면 위 역할에 지정된 모델로 새로 배정한다.
- 지정 모델을 사용할 수 없거나 실제 배정을 확인할 수 없으면 임의 대체하지 말고 제약을 보고한다.
- 모델·참여 이력 확인은 최초 배정이나 담당자 변경 때 수행하고 이후에는 기록을 재사용한다.
- 기본적으로 메인 Astra·제품 및 실행 Sol·테스트 작성 Astra를 서로 다른 에이전트로 배정한다. 같은 Astra 모델이라는 이유로 메인과 테스트 담당자의 역할을 합치지 않는다.
- 최종 감사자는 감사 시점에 배정한다.
- 별도의 단순 실행 전용 에이전트를 기본으로 추가하지 않는다.
- 추가 에이전트는 독립된 산출물이 있고 조정 비용보다 이익이 명확할 때만 사용한다.

기존 6.1 작성 테스트도 보존하며 필요한 타당성 검토와 보강만 수행한다.
작성자와 실행자가 달라도 작성 이력과 증거의 귀속을 유지한다.
과거 테스트의 작성자를 재표기하지 않는다.

### F 편집과 실행 소유

- 서로 다른 파일에서 독립적으로 가능한 작업만 병행한다.
- 같은 파일은 영역이 달라도 동시에 수정하지 않는다.
- 제품 파일 안의 테스트 모듈·등록부도 파일 소유를 넘겨 순차 편집한다. 파일 소유를 받았어도 각 담당자는 자신의 역할에 해당하는 내용만 수정한다.
- 포맷·자동 수정도 같은 편집 소유와 역할 경계를 지킨다. 제품 범위 작업으로 테스트 측 변경을 함께 적용하지 않는다.
- 예상되는 helper·fixture·등록부의 소유를 가능한 한 시작 시 함께 정한다.
- 통상적인 소유 이관은 기존 기록에 짧게 남기고 별도 승인 문서를 만들지 않는다.
- 각 실행 묶음의 실행 담당자는 한 명으로 정한다.
- 실행 중 제품·테스트·fixture·설정·판정 도구 등 관련 입력을 수정하지 않는다.
- 같은 입력이나 공유 자원에 영향을 주는 검사를 중복·동시 실행하지 않는다.
- 성능 측정은 다른 기능 검사와 분리한다.
- 실행 중 다른 독립 작업을 하려면 해당 실행의 입력·파일·공유 자원에 영향이 없음을 확인한다.
- 안전하게 분리할 작업이 없으면 대기한다.

## 4 계획과 작업 묶음 및 Astra 검토

유효한 기존 계획을 재사용하고 실제 남은 변경에 필요한 만큼만 보완한다.
전체 로드맵을 미리 상세 설계하거나 일괄 승인 단계를 추가하지 않는다.

작업은 의미 있는 기능·실제 의존성·편집 충돌·실행 환경을 기준으로 묶는다.
파일 수나 테스트 개수를 기준으로 임의 분할하지 않는다.
함께 구현·검증할 수 있는 작업은 같은 묶음에서 처리한다.
새 API의 최초 연결 확인을 자동으로 별도 인계 단계로 만들지 않는다.

각 묶음에는 다음을 전달한다.

- 목적·수용 조건·이번에 구현하거나 검증할 범위.
- 관련 파일·심볼·API와 중요한 상태·소유권·수명·저장·권한·자원 경계.
- 재사용할 helper·adapter·준비 경로·테스트 예제.
- 확인된 사실·정책상 기대 동작·미검증 가정.
- 선택한 검사 범위와 이유·재사용할 증거.
- 편집·실행 소유·자율 판단 범위·메인에게 반환할 조건.

기존 문서와 코드 참조로 충분하면 링크하고 차이만 설명한다.
매번 새로운 장문 계획·인계 문서를 만들지 않는다.
새 담당자에게는 현재 작업에 필요한 위 항목, 관련 역할·공통 규칙과 원문 위치를 전달한다. 전체 대화·완료 이력·무관한 로그를 기본으로 복제하지 않는다.
요약은 원문을 찾는 입구로 사용한다. 테스트 담당자와 감사자가 요구사항·계약·코드·증거를 직접 확인하는 데 필요한 문맥은 생략하지 않는다.

담당자는 핵심 API와 기존 사용 예를 직접 확인한 뒤 작업을 시작한다.
중요한 불일치가 없으면 추가 승인을 기다리지 않고 진행한다.

Astra는 구현 계획과 품질 판단에 필요한 경계를 명확히 하되, Sol이 자율적으로 처리할 내부 구현까지 불필요하게 고정하지 않는다.
Sol은 계획 안의 구현·빌드·디버깅·일반 교정을 계속하고 중요한 불일치만 반환한다.

### A 테스트 작성과 실행의 연결

테스트 담당 Astra는 검증 목적·선택 범위·입력·기대값·판정 기준을 정한다.
Sol은 이를 보존하는 실행 방법을 구성하고 준비된 관련 사례를 묶어서 실행한다.
합의된 검증 범위·판정 의미의 변경이나 시험 측 코드·fixture의 수정이 필요하면 테스트 담당 Astra에게 반환한다. 기존 실행 지시 안의 묶음 구성과 실패 항목 우선 재실행은 Sol이 자율 수행한다.
모든 테스트가 이미 통과해야 실행을 넘길 수 있는 것은 아니다.

최초 실행 지시에는 기존 기록을 이용해 다음을 전달한다.

- 선택한 테스트 또는 기존 runner.
- 입력 식별·필요 환경·실행 순서·격리 조건.
- 기대한 실행 범위와 0시험·skip·중단·실패 판정 기준.
- 기존 판정 도구와 원시 결과 저장 위치.
- 재사용할 결과와 중요한 제외 범위.
- 알려진 실패·환경 제약·실패 시 반환 대상.

장시간 실행이 예상되면 [5-H]의 예상 소요와 진단·중단 기준도 같은 기록에 포함한다.

같은 검증 묶음의 교정·재실행은 이 지시를 재사용한다.
변경된 입력과 필요한 재실행 범위만 전달한다.
Astra가 시험을 교정하고 Sol이 재실행할 때마다 새 계획·새 인계 문서·메인 승인·사용자 승인을 요구하지 않는다.

### B Astra의 구현 및 결과 검토

이 절을 Astra의 구현 및 결과 검토 기준으로 사용한다.
Sol이 만든 모든 제품 변경과 검증·완료 주장은 검토 범위에 포함한다.
최종 수용 전에 메인 Astra 또는 명시적으로 배정된 Astra 검토자가 다음을 확인한다.

- 구현 계획과 요구사항을 실제로 충족하는가.
- 계획과 달라진 부분이 있으며 그 차이가 정당한가.
- 공개 계약·소유권·수명·저장·권한·자원 경계를 지켰는가.
- 정상 경로뿐 아니라 실패·취소·복원·재시도 경로가 적절한가.
- 기존 동작에 대한 영향과 필요한 회귀 검증을 빠뜨리지 않았는가.
- 테스트 입력·기대값·판정 방법이 타당하고, 원시 결과가 실제 변경과 완료 주장을 뒷받침하는가.
- 실제 실행 범위·결과 집계·재사용 증거의 현재 유효성이 정확한가.
- 미검증 변경이나 남은 위험이 정확히 표시됐는가.

구현자의 요약만 읽고 검토 완료로 처리하지 않는다.
실제 변경 코드와 중요한 호출·상태 경계를 직접 확인한다.
테스트 통과가 설계·구현 검토를 대신하지 않는다.

검토는 의미 있는 구현 묶음과 중요한 변경 경계에서 수행한다.
모든 작은 수정마다 전체 코드를 다시 검토하지 않는다.
교정 후에는 변경 부분과 영향을 받는 경계를 검토하고, 이미 검토한 비영향 부분은 근거를 유지해 재사용한다.

검토 범위의 누락이 없어야 한다는 뜻이지, 모든 로그·생성 파일을 매번 사람이 처음부터 수작업으로 읽어야 한다는 뜻은 아니다.
기존 도구로 확인할 수 있는 기계적 사실과 코드·계약에 대한 의미 판단을 구분한다.

Sol은 검토 대기 중에도 승인된 계획 안의 독립 작업을 계속할 수 있다.
다만 미결정 계약이나 검토에서 드러난 중요한 문제를 확정 사실로 삼아 후속 작업을 진행하지 않는다.
선행 Goal의 독립 완료가 필요한 종속 구현은 해당 감사 통과 뒤 시작한다. 사용자 판단이나 명시적 checkpoint로 대기 중이면 [9]의 제한을 따른다.
검토 전 결과는 구현·실행 완료로 기록할 수 있지만 Astra 검토 완료로 승격하지 않는다.

작은 수정이나 검사 성공마다 정식 Goal 최종화 절차를 반복하지 않는다.
정식 Goal 완료 시에는 [8]을 수행한다.

## 5 테스트 설계와 선정 및 실행 범위

현재 목표의 수용 조건과 변경 영향에 필요한 테스트만 실행한다.
관련 범위는 깊게 검증하되 무관한 범위를 관성적으로 추가하지 않는다.

### A 결함을 적극적으로 드러내는 테스트 설계

Astra는 제품이 올바르게 보이는 사례만 작성하지 않는다.
현재 기능과 관련된 범위에서 다음을 검토하고 필요한 사례를 작성한다.

- 정상 입력과 부정 입력, 빈 값·0·최솟값·최댓값·한도 경계.
- 허용되어야 하는 조건과 거부되어야 하는 조건의 대조.
- 같은 입력의 반복 처리, 중복 요청, 재시도와 재진입.
- 순서·동시 시각·이벤트 발생 시점이 달라질 때의 상태 전이.
- 객체·제공자·대상·사본·generation 등 정체성의 혼동과 오래된 참조.
- 취소·철수·제거·만료·재배치·교체·저장·복원 등 관련 수명 경계.
- 부분 실패와 자원 부족에서의 원자성·rollback·실패 후 재시도.
- 서로 다른 대상·출처·효과·반복 사이의 상태와 결과 격리.
- 새 기능과 영향을 받는 기존 기능의 상호작용.
- 공개 경로와 내부 준비 경로의 차이.
- 관측·로그·설정 차이가 게임 결과나 필수 계량에 미치는 영향.

위 목록을 모든 기능에 기계적으로 적용하거나 별도 의무 실행 행렬로 만들지 않는다.
실제 계약과 변경 영향에 연결되는 실패 경로를 선택한다.

기대값은 요구사항·정책·독립적인 계산과 관찰 가능한 결과에서 도출한다.
제품 코드의 알고리즘이나 helper를 그대로 복제하여 같은 오류를 공유하지 않는다.
필요하면 작은 수작업 예제, 대조 입력, 독립 계산, 불변 조건을 사용한다.

정상 성공을 기대하는 사례는 입력 문법·허용 상태·자원과 배치 한도·대상 자격·기본값·이벤트 발생 시점 등 성공에 필요한 전제가 실제 계약을 만족하는지 확인한다.
유사한 경로나 모드의 계약을 그대로 적용하지 않고, 해당 공개 경로의 정책과 기존 사용 예를 확인한다.
테스트 담당 Astra는 신규 작성과 오류 교정 모두에서 이 기준을 적용한다.
중요한 미검증 가정은 기존 계획이나 실행 기록에 짧게 표시하며, 별도 전제 점검 문서나 승인 단계는 만들지 않는다.

중요한 판정은 잘못된 대상·누락된 효과·잘못된 순서·무변이 실패 등을 실제로 구분할 수 있는 assertions를 둔다.
검출력을 높이는 데 필요하면 작은 부정 대조를 추가하되, 이를 위해 별도의 대규모 검증 도구를 기본으로 만들지 않는다.

테스트 개수나 코드 커버리지 수치만으로 충분성을 판단하지 않는다.
현재 구현에서 발생할 수 있는 중요한 결함을 검출하는지가 기준이다.

### B 범위 선정

- 수정한 코드, 직접·간접 호출 경로, 공유 계약, 영향받는 기존 동작을 기준으로 선정한다.
- 테스트 이름이나 파일 위치만으로 관련성을 판단하지 않는다.
- 유닛·통합·공개 경로·외부 실행·성능 검사 중 필요한 종류를 선택한다.
- 빠르다는 이유로 무관한 테스트를 추가하거나, 유닛 테스트라는 이유로 관련 검증을 제외하지 않는다.
- 현재 목표와 관련된 선행 계약의 회귀 검증을 포함한다.
- 선택 범위와 이유를 기존 PLAN 또는 실행 기록에 간결하게 남긴다.
- 범위 선정 자체를 별도 승인·인계 단계로 만들지 않는다.

### C 개발 중 실행

- 최초 API·fixture 연결, 실패 재현, 교정 확인, 변경 영향 확인에 집중한다.
- Astra가 테스트를 작성·교정하고 Sol이 준비된 검사를 실행한다.
- 연결이 확인되면 준비된 관련 사례를 묶어서 실행한다.
- 실패한 항목을 우선 재검증하고 교정의 영향이 있는 범위만 추가 실행한다.
- 테스트 몇 개가 통과할 때마다 새 작업·인계·승인을 만들지 않는다.
- 사소한 수정마다 전체 검사를 반복하지 않는다.

고비용 측정이나 긴 검증 묶음을 시작하기 전에, 공통 준비 경로와 필요한 참여자·대상·이벤트가 실제로 동작하는지 작은 실행 또는 유효한 기존 증거로 확인한다.
공개 경로를 검증할 때는 해당 공개 경로에서 확인하며, 공통 전제가 확인된 뒤에는 사례마다 같은 준비 검사를 반복하지 않는다.
고장 재현에서는 목표 연산에 도달하는 상태·참여·발생 시점과 연산별 한도·누적 한도의 적용 위치를 확인한다.
예상한 고장이 발생하지 않으면 이 전제와 실제 진행을 먼저 진단하고, 근거 없이 실행 시간이나 한도를 늘려 탐색하지 않는다.
작은 실행은 준비 전제의 확인이며, 필요한 전체 workload 측정이나 실패 경계 검증을 대신하지 않는다.

### D 최종 통합 검증

- 의미 있는 구현 묶음이 끝나면 최종 통합 상태에서 필요한 관련 검증을 완료한다.
- Sol이 실행·원시 결과 수집·기계적인 집계를 담당한다.
- Astra가 선택 범위의 충분성과 결과의 의미를 검토한다.
- 동일 입력 또는 명시적인 비영향 근거가 있는 유효한 결과는 재사용한다.
- 작성자·실행자·역할 변경만으로 유효한 검사를 반복하지 않는다.
- 누락된 검증은 해당 범위만 보완한다.
- 집중 검사 몇 개의 통과만으로 Goal 전체가 검증됐다고 간주하지 않는다.
- 최종화·단계 완료·감사 준비라는 이유만으로 전체 테스트를 실행하지 않는다.

### E 범위 확대

예상 밖 회귀, 공유 기반·공개 계약·저장 형식의 변경, 또는 영향 범위에 대한 구체적인 불확실성이 있으면 다음 순서로 판단한다.

1. 관련 코드와 실제 의존성을 확인한다.
2. 확인된 위험과 영향 경로에 맞춰 검사 범위를 확대한다.
3. 그래도 전체 검사가 필요한 구체적인 근거가 있으면 전체 테스트를 실행한다.

사용자가 전체 검증을 명시적으로 요청한 경우에도 전체 테스트를 수행한다.

메인은 기존 권한 안에서 확대 범위와 이유를 짧게 기록하고 진행한다.
막연한 불안이나 단순한 정보 부족을 관성적인 전체 실행의 근거로 삼지 않는다.
한 번 전체 실행이 필요했다고 이후 모든 수정에 같은 범위를 반복하지 않는다.

### F 묶음 실행과 격리

- 하나의 실행 결과를 여러 수용 조건에 연결할 수 있다.
- 같은 입력과 환경의 관련 테스트는 가능한 한 묶어서 실행한다.
- 기존 runner·결과 수집·분류 자료를 우선 재사용한다.
- 가능한 경우 선택 목록을 테스트 바이너리나 하네스에 묶어서 전달한다.
- 테스트마다 Cargo를 반복 호출하거나 같은 설정을 불필요하게 다시 빌드하지 않는다.
- 기존 자동 집계·판정 도구가 있으면 사용한다.
- 원시 로그 전체를 여러 담당자가 반복해서 재집계하지 않는다.
- 실행 요약·실패 항목·원시 참조를 우선 전달하고, 의미 판단과 검증에 필요한 원시 내용은 직접 확인한다.
- 병렬 실행은 기존 검증과 공유 자원 제약을 근거로 적용한다.
- 분류상 병렬 후보라는 사실만으로 안전성이 검증됐다고 간주하지 않는다.

다음은 필요한 만큼 분리한다.

- 기본 구성과 기능 옵션처럼 실제 설정이 다른 검사.
- 외부 CLI·서버 통신·프로세스 종료와 재시작.
- 공유 자원·전역 상태 때문에 격리가 필요한 검사.
- 시간·메모리·성능 측정처럼 동시 실행의 영향을 받는 검사.

별도 프로세스가 필요해도 하나의 검증 묶음과 결과 보고로 관리할 수 있다.
프로세스 분리를 매번 사람이나 에이전트의 인계 단계로 만들지 않는다.
단일 cargo test나 all-features 실행이 필요한 모든 설정·외부 검증을 대신한다고 가정하지 않는다.

필요한 공개 경로·설정·격리 검사를 범위 축소를 이유로 생략하지 않는다.
빌드 구성·캐시·환경을 조정하면 결과 비교 가능성과 설정 차이를 명시한다.
진행 중 검사를 단순한 지침 정리·절차 통합·역할 변경 때문에 중단하지 않는다.
장시간 실행의 진단과 근거 있는 중단에는 [5-H]를 적용한다.

### G 판정

- 실제 실행, 기존 증거 재사용, 미실행을 구분한다.
- 종료 코드뿐 아니라 실제 선택·실행된 시험 수와 실패·skip 여부를 확인한다.
- 0시험·skip·중단·환경 실패를 기능 PASS로 기록하지 않는다.
- 실행 완료와 결과 수집 완료를 구분한다.
- 수집 기록이 미완성이면 원시 결과를 보존하고 복구 여부를 명시한다.
- 관련 검사 통과를 전체 회귀 통과로 표현하지 않는다.
- 전체 테스트 미실행 자체는 완료 실패 사유가 아니다.
- 필수 요구사항이나 영향받는 계약의 검증 누락은 보완해야 한다.
- 요구사항 누락·잘못된 기대값·미지원 경로는 테스트 통과와 별도로 확인한다.
- 실행자의 집계를 Astra 검토나 독립 완료 판정으로 확대하지 않는다.

### H 장시간 실행의 진단과 중단 기준

장시간 실행이 예상되는 검사는 시작 전에 예상 소요와 진단·중단 기준을 기존 실행 기록에 간결하게 남긴다.
기존 실행 시간·입력 규모·환경 차이를 근거로 정하며, 근거가 부족하면 예상 소요가 미확정임을 표시하고 첫 진단 시점과 확인할 신호를 정한다.
모든 짧은 검사에 별도 시간 행렬이나 승인 절차를 만들지 않는다.

예상 범위를 크게 벗어나거나 진행 정체·비정상 자원 사용이 확인되면, 실행 담당 Sol이 기존 프로세스나 세션에서 필요한 상태만 확인한다.
일정 시간 출력이 없다는 사실만으로 정체를 단정하지 않는다.
단계 진행·CPU 사용·메모리·기존 로그 등 현재 실행에서 확인 가능한 근거로 계속 대기, 원인 진단, 안전한 중단을 구분한다.

합의된 기준에 따른 중단은 절차 정리나 역할 변경을 위한 중단과 구분한다.
Sol은 승인된 기준 안에서 자신이 소유한 실행을 안전하게 중단할 수 있으며, 일반적인 진단·중단마다 새 사용자 승인을 요구하지 않는다.
기준 밖의 중요한 판단이나 요구사항·판정 의미 변경이 필요하면 근거와 함께 메인 Astra에게 반환한다.

중단할 때는 입력 식별·실제 명령·경과 시간·관측된 진행과 자원 상태·원시 출력·중단 이유를 보존한다.
해당 실행의 종료와 정리 상태를 확인한 뒤 관련 입력을 수정하거나 재실행한다.
다른 담당자의 실행을 중복 시작하거나 함께 종료하지 않는다.

운영상의 진단 시점이나 중단 기준을 제품의 자원 한도 또는 성능 합격 기준과 혼동하지 않는다.
시간 초과·중단을 자동으로 제품 결함이나 기능 PASS로 판정하지 않고 원인과 미검증 범위를 구분한다.
기존 성능·자원 기준에 대한 실제 실패는 그대로 보존한다.
한도 상향·workload 축소·기대값 완화·계량 누락으로 실패를 숨기지 않는다.
재검증은 원인과 변경 영향에 따라 필요한 범위를 선택한다.

### I 자원 한도의 실측과 조정

초기 작업량·메모리 예산은 영구 고정값이 아니라 측정으로 재검토할 기준이다.
이 원칙은 이후 모든 기능·콘텐츠 단계에 적용하며, 해당 단계에서 필요한 측정과 조정을 최종 통합·성능 단계까지 미루지 않는다.
정상 콘텐츠가 한도에 걸리면 불필요한 비용과 한도의 적정성을 함께 검토한다. 모든 최적화를 끝내야만 한도를 조정할 수 있는 것은 아니다.
단순히 초과 폭이 작거나 최신 PC라는 이유로 기존 실패를 허용하지는 않는다.

- 대표 정상 콘텐츠, 예상 확장 규모, 비정상·폭주 입력을 구분해 측정한다. 입력·seed·source·profile 식별과 CPU·메모리·동시 실행 규모·toolchain·관측 설정을 남긴다.
- 실제 경과 시간·처리 지연, 메모리 peak·종료 후 회수, 내부 작업량을 함께 본다. 내부 work 단위는 CPU 명령 수나 실행 시간이 아니며, retained/admission 회계와 실제 heap/RSS도 구분한다.
- 평균뿐 아니라 집중 부하·분포·최댓값과 필요한 여유를 검토한다. 근거 없는 고정 증가율이나 임의의 공통 숫자를 새 합격선으로 만들지 않는다.
- 오프라인 authoring/검증, 실시간 전투, trusted 개발 측정, 배포 기본값의 목적을 구분한다. 구조적 유한성·입력 검증·overflow 방지와 조정 가능한 비용 예산을 혼동하지 않는다. engine ceiling 변경은 그 근거와 구현 영향까지 재검토한다.

기존 한도 때문에 전체 비용을 측정하지 못하면, trusted host가 명시적으로 선택하는 유한한 상한의 측정 profile을 사용할 수 있다.
대상 profile·상한·중단 기준을 기록하고 배포 기본값과 구분한다. 실행 중 자동 상향·무제한 실행·mod의 자기 제한 완화는 허용하지 않는다.
중간에 한도에 걸린 측정은 그 시점까지의 관측이며 전체 성공 비용으로 해석하지 않는다.

변경 판단에는 기존/제안 한도, 동일 workload의 전후 측정, 정상 콘텐츠의 여유, 비정상 입력의 거부 영향과 변경 이유를 남긴다.
확장 입력은 기존 비교 입력에 추가하며, 기존 profile의 실패 기록을 덮어쓰거나 새 profile의 성공으로 소급해 PASS로 바꾸지 않는다.
증거에 따라 상향·하향·유지를 결정한다. 한도 조정 자체를 최적화 성과로 보고하지 않는다.
메인은 [6]의 기존 권한 안에서 판단하며 매번 새 사용자 승인이나 별도 Goal을 만들지 않는다. 실제 게임 정책·공개 계약·인수 의미가 바뀌는 경우에는 기존 정책 변경 절차를 따른다.
변경 영향에 맞춰 한도 경계·초과 거부·실패 원자성·취소/복원·재시도와 profile 식별/캐시 분리를 검증하고, 관련 없는 전체 시험을 반복하지 않는다.

## 6 실패 교정과 판단 반환

실패 원인을 먼저 구분한다.

- 제품 결함: Sol 제품 담당자가 분석하고 교정.
- 테스트·fixture·기대값·판정 도구 결함: Astra 테스트 담당자가 교정.
- 실행 환경·명령 연결 문제: 승인 범위에서 Sol 실행 담당자가 복구.
- 요구사항 해석·설계 전제·공개 계약·상태 의미 문제: 근거·영향·대안을 메인 Astra에게 반환.

원인이 처음에 불명확하다는 이유만으로 즉시 반환하지 않는다.
Sol은 합의된 설계와 기대 동작 안에서 제품 원인 분석·디버깅을 진행한다.
설계나 기대 동작 자체의 판단이 필요하면 분석 근거를 갖춰 메인 Astra에게 반환한다.
같은 실패에 대해 새 가설·새 증거·유효한 교정 없이 동일한 수정과 실행을 반복하게 되면, 시도·관측 결과·배제한 원인·남은 불확실성을 메인에게 반환한다. 테스트 측 원인이 확인되면 테스트 담당 Astra에게 직접 연결한다.

Sol은 테스트·fixture·기대값·판정 도구를 직접 수정하지 않고, 필요한 실패 근거와 분석 결과를 테스트 담당 Astra에게 전달한다.
테스트 담당 Astra는 확정된 계약에서 올바른 입력·기대값·판정을 도출할 수 있는 시험 측 오류를 직접 자율 교정한다. assertion의 값이나 fixture가 바뀐다는 사실만으로 새 승인을 요구하지 않는다.
승인된 기대 동작·한도·회귀 oracle의 의미를 바꾸어야 하거나 계약 자체가 불명확하면 메인 판단을 받는다. 메인은 판단과 작업 연결을 맡고, 실제 시험 측 교정은 테스트 담당 Astra가 수행한다.

같은 종류의 테스트 전제 오류가 반복되면 Astra 테스트 담당자는 관련 fixture·helper와 이를 공유하는 사례의 공통 가정을 함께 점검한다.
확인된 관련 오류는 가능한 한 묶어서 교정한 뒤 고비용 재빌드·재측정을 진행하고, 변경 영향에 맞춰 재검증한다.
이 점검을 관련 없는 전체 테스트 재작성이나 새 승인 절차로 확대하지 않는다.

실행 환경 복구는 기존 manifest·lock·toolchain·판정 의미를 유지하는 범위에서 수행한다.
이 기준의 변경이 필요하면 일반 환경 교정으로 숨기지 않고 메인에게 반환한다.

실행 중 제품이나 테스트 변경이 필요하면 다음 순서로 진행한다.

- 현재 실행과 입력의 상태를 확인한다.
- 해당 입력을 사용하는 실행이 끝나거나 안전하게 정리된 뒤 편집한다.
- 관련 파일 소유를 명확히 넘긴다.
- 변경 후 영향 범위만 재검증한다.

실패한 경로에 의존하는 후속 검사는 중지하거나 보류한다.
입력과 선행 조건이 독립적인 나머지 검사는 합의된 범위에서 계속할 수 있다.
실패한 필수 검사를 건너뛰어 완료로 처리하지 않는다.

담당자 전환이 필요하면 현재 입력을 고정하고, 짧은 재현·기대 결과·관련 파일과 소유 범위를 전달한다.
관련 없는 작업까지 다시 인수하거나 전체 계획을 재발행하지 않는다.

다음은 메인의 판단을 받는다.

- 정책·공개 계약·상태 소유권·수명·저장 의미·완료 기준 변경.
- 기존 기대값·한도·workload·회귀 oracle의 의미 변경.
- 파일 소유 충돌이나 입력 고정 문제.
- 기존 전제로 해결되지 않는 반복 오류 또는 합의된 기능·계약·검증 목적을 넘어서는 범위 확대.

메인은 기존 권한 안에서 판단할 수 있으면 사용자 승인 대기 없이 다음 작업을 연결한다.
적용 P2G/GEX 기준상 실제 사용자 선택이 필요하거나 기존 권한을 넘어서는 경우에만 필요한 결정과 근거를 질문하고 [9]에 따라 대기한다.

원인이 불명확하면 성공 기대값부터 바꾸지 않는다.
한도 상향·workload 축소·기대값 완화·계량 누락으로 회귀를 숨기지 않는다.
정당한 비용 변화는 전후 측정값과 원인을 남긴다.
이 원칙은 근거 있는 한도 조정을 금지하지 않는다. 자원 예산 재검토에는 [5-I](#i-자원-한도의-실측과-조정)를 적용한다.

제품 공개 API·실행 의미·권한을 테스트 편의를 위해 임의 변경하지 않는다.
정상 adapter와 준비 경로를 우선 사용한다.
내부 fixture 검증을 정상 공개 경로 검증으로 표시하지 않는다.

실패 원본은 보존하고 교정 후 재검증 범위는 [5]에 따라 정한다.
교정된 제품 변경과 갱신된 완료 주장에도 [4-B]의 Astra 검토를 적용한다.

## 7 증거 재사용과 보고

재현성과 추적 가능성을 유지하되 같은 사실을 여러 문서로 반복 증명하지 않는다.
기존 PLAN·실행 기록·판단 기록을 우선 사용한다.
필수 절차나 새로운 판단 근거가 있을 때만 문서를 추가한다.
기록 갱신은 변경 가능한 현재 기록에 수행한다. 이미 동결된 기록·감사 대상의 수정이 필요하면 기존 successor·currentness 절차를 따르며 원본을 덮어쓰지 않는다.

실행 기록에는 필요한 범위에서 다음을 남긴다.

- 대상 코드·테스트·설정의 식별.
- 선택한 검사 범위와 이유.
- 실제 명령과 결과에 영향을 주는 환경.
- 실행 담당자와 사용한 수집·판정 도구.
- 종료 상태와 실행·통과·실패·건너뜀 건수.
- 원시 출력과 실패 원본의 위치.
- 관련 변경·재사용한 증거·재사용 근거.
- 중요한 제외 범위·미검증 위험·남은 한계.
- 장시간 실행을 진단하거나 중단했다면 [5-H]에 따른 근거와 정리 상태.

작성자·실행자·검토자·최종 감사자의 역할을 구분한다.
모델과 참여 이력은 배정 기록을 참조하고 같은 사실을 모든 문서에 반복하지 않는다.

Astra 검토에는 [4-B]를 적용하고, 기존 기록에 검토 범위·주요 계약·계획과의 중요한 차이·발견한 문제와 교정·남은 검토 사항·코드 및 증거 참조를 간결하게 남긴다.
검토 기준 전체를 매번 다시 쓰거나 별도의 거대한 보고서를 만들지 않는다.
작성·실행 완료, Astra 검토 완료, 독립 Goal 완료를 구분한다.

실행하지 않은 모든 테스트를 열거하지 않는다.
현재 판단에 중요한 제외와 남은 위험만 명시한다.

고정 입력의 여러 명령은 공통 입력 목록과 명령별 결과를 공유할 수 있다.
수용 조건마다 별도 기록·소스 아카이브·인계 문서를 만들지 않는다.
입력이 바뀌면 시점과 영향을 식별하며 이전 결과를 덮어쓰지 않는다.

증거 재사용:

- 동일 입력 또는 명시적인 비영향 근거가 있는 유효한 결과를 재사용한다.
- 새 source 변경을 무관한 과거 결과로 검증했다고 하지 않는다.
- 재사용한 결과를 이번에 새로 실행한 것처럼 기록하지 않는다.
- 작성자·실행자·모델 변경만으로 유효한 결과를 무효화하지 않는다.
- 문서 변경이 실행 입력에 영향을 주지 않으면 이유를 기록하고 기존 결과를 유지한다.
- 형식상 참조 갱신만으로 제품 검사를 다시 실행하지 않는다.

보존과 도구:

- 기존 runner·수집·판정 도구를 우선 사용한다.
- 새 도구는 기존 수단으로 해결하기 어려운 구체적인 문제에 필요할 때만 추가한다.
- 시험 입력·선택·기대값·합격 판정에 영향을 주는 도구의 작성·교정은 Astra 테스트 담당자가 맡는다.
- Sol은 준비된 도구의 실행과 결과 수집을 맡는다.
- 일반적인 보존 확인은 diff와 관련 검사를 우선 사용한다.
- 전체 입력 대조와 복원용 보관은 재개·중요 인계·최종 동결 등 필요한 경계에서 수행한다.
- 작은 수정마다 전체 hash·archive·receipt를 다시 생성하지 않는다.
- 과거 실패·출력·감사·동결 target을 삭제하거나 덮어쓰지 않는다.
- 과거 artifact 생성 스크립트를 그대로 재실행하지 않는다.
- successor evidence를 만들면 소비 도구도 새 결속을 읽게 한다.
- archive는 필요한 참조만 보존하고 재귀 중첩하지 않는다.
- 재구성한 preimage를 당시 원본으로 표시하지 않는다.
- 전체 저장소 reset/clean/stash로 상태를 정리하지 않는다.

준비·컴파일·실행 완료·기능 통과·Astra 검토·독립 완료 판정을 구분한다.
성능 환경과 프로세스 가시성 한계를 명시한다.

장시간 실행이나 지연을 설명할 때는 준비·빌드·실제 시험·증거 수집 및 보관 시간을 가능한 범위에서 구분하고, 측정 구간에 포함되거나 제외된 비용을 명시한다.
기존 타임스탬프와 실행 기록을 우선 사용하며, 측정하지 않은 구간이나 기록 사이의 공백을 연속 작업 시간으로 추정하지 않는다.
지연 원인은 제품 결함·테스트 전제 오류·실행 환경·증거 처리 등 확인된 근거에 따라 구분하고, 불명확한 부분은 그대로 표시한다.

비용 효율은 초기 구현뿐 아니라 필요한 테스트 작성·교정·검증·검토·독립 감사와 재작업까지 포함해 판단한다.
기존 사용량 정보가 있으면 모델별 사용량과 해당 범위의 실제 진척·재작업을 함께 본다. 측정되지 않은 절감률을 추정하거나 이를 위해 별도 필수 추적 도구·보고서를 만들지 않는다.
절감은 불필요한 문맥 복제·중복 읽기·조회·인계·재실행을 줄이는 데서 구하며, 테스트 담당과 검증 강도에는 [1]을 적용한다.

진행 보고는 새로운 결과·판단·중요한 실패·방향 변경을 중심으로 한다.
작업 묶음 결과는 실제 변경·검사 결과·교정·검토 상태·남은 한계를 간결하게 남긴다.
사용자 관점에서 확인된 동작과 남은 필수 검증·완료 조건을 함께 설명한다.
명령·로그·receipt 개수를 기능 진척으로 대신하거나 근거 없는 완료율을 제시하지 않는다.
해시·긴 이력·금지 사항을 반복하지 않고 기록 경로를 연결한다.
보고를 위해 불필요한 조회나 문서를 만들지 않는다.

## 8 Goal 최종화와 독립 감사

이 절은 정식 Goal 완료 경계에 적용한다.
일반적인 작성·교정·검사 성공이나 실행권 이관마다 반복하는 절차가 아니다.

현재 Goal의 최종 통합 상태에서 [5]에 따른 필요한 검증을 완료한다.
Sol의 제품 변경과 완료 주장에 대한 [4-B]의 Astra 검토가 누락되지 않았는지 확인한다.

현재 source와 실제 결과에 맞춰 다음을 연속해서 처리한다.

1. evidence selection
2. predecessor impact
3. adaptation의 현재 결속
4. coverage
5. 자체검증 및 Astra 검토 완료
6. PLAN/NOTES 최신화
7. exact target 동결과 필요한 정·역 복원 검증
8. 독립 감사

1–7의 내부 준비는 기존 도구와 기록으로 묶고, 항목마다 별도 에이전트 작업·사용자 승인·전체 재검사 단계를 만들지 않는다.
8의 독립 감사는 [3-D]의 별도 감사자가 수행한다. 준비 작업의 통합으로 감사자의 독립성을 없애지 않는다.

정해진 도구의 실행·원시 결과 수집·기계적인 집계는 Sol이 맡는다.
메인 및 테스트 담당 Astra의 검토 결과는 기존 기록을 참조하고 같은 자료를 역할별로 중복 작성하지 않는다.

현재 Goal의 수용 조건·필수 검증 차원·관련 선행 회귀 조건을 실제 증거에 연결한다.
coverage는 요구사항과 변경 영향을 기준으로 확인한다.
저장소의 모든 테스트 실행 여부를 coverage의 대체 기준으로 삼지 않는다.

최종 감사자는 [3-D]의 독립성을 지키고, [4-B]의 코드·계약·시험·증거 검토 기준을 현재 Goal 전체에 독립적으로 적용한다.
마지막 수정 파일만 감사하거나 앞선 Astra 검토를 그대로 추인하지 않는다.
앞선 Astra 검토와 테스트 결과를 최종 독립 완료 판정으로 대신하지 않는다.
감사 중 대상 소스·요구·입력·기존 증거를 변경하지 않는다. 감사 기록과 새 감사 evidence는 동결 target과 분리해 작성한다.

finding의 교정이 필요하면 감사 결과를 남기고 별도 교정 pass에서 [6]의 해당 담당자가 수정한다. 감사자는 직접 제품이나 테스트를 고치지 않는다.
변경 영향에 맞는 새 증거와 target으로 재감사하고 유효한 비영향 증거는 유지한다.
필요한 독립 완료 판정과 열린 finding 0을 충족하면 다음 승인된 로드맵 작업으로 진행한다.

## 9 비동기 대기와 종료 및 인계

서브에이전트는 비동기로 운영한다.
메인이 계속 명령을 실행해야 담당자가 진행되는 것으로 취급하지 않는다.
아래의 독립 작업·후속 진행 규칙은 현재 실행 권한이 유효하고 사용자 판단·명시적 checkpoint 대기 중이 아닐 때 적용한다.

위임 후 메인은 다음과 같이 진행한다.

1. 현재 필요한 독립 작업이 있으면 수행한다.
2. 독립 작업이 끝났거나 다음 판단에 결과가 필요하면 알림·대기 기능으로 기다린다.
3. 결과·실패·도움 요청·사용자 입력이 도착하면 판단하고 다음 작업을 연결한다.

Sol은 명령 실행을 기다리는 동안 반복적인 추론·조회·로그 재집계를 하지 않는다.
도구가 제공하는 완료 알림·대기·출력 수집 기능을 우선 사용한다.
상태 확인이 필요하면 기존 프로세스나 세션을 이어서 확인하고 같은 명령을 중복 시작하지 않는다.
장시간 실행의 진단 시점이나 중단 조건에 도달하면 [5-H]를 적용한다.

Astra는 Sol의 실행 중 현재 입력과 충돌하지 않는 필요한 독립 작업이 있을 때만 진행한다.
안전하게 분리할 일이 없으면 결과를 기다린다.
Sol도 실행 입력에 영향을 주는 제품 편집을 병행하지 않는다.

이미 끝낸 검토를 반복하거나 담당자의 작업을 중복 수행하지 않는다.
대기 시간을 채우기 위해 새 문서·검사·에이전트를 만들지 않는다.
새 정보나 이상 징후가 없으면 다시 대기한다.

시간·파일·git status·프로세스·에이전트 상태를 짧은 주기로 반복 조회하지 않는다.
같은 지시나 상태 요청을 반복해서 보내지 않는다.
실행 중 산출물을 계속 열어보며 진행을 추측하지 않는다.

중간 조회는 도움 요청·오류·소유 충돌 의심·사용자 상태 요청·합의된 진단 조건 도달처럼 결과에 따라 취할 조치가 있을 때 수행한다.
필요한 진행 안내는 짧게 하고 같은 대기 설명이나 긴 이력을 반복하지 않는다.
메인과 담당자의 대기는 정상 상태이며 종료나 장애가 아니다.

전체 작업의 종료 또는 사용자에게 제어권을 반환하는 경우는 다음과 같다.

- 사용자 중지 요청.
- 승인된 범위 완료.
- 사용자가 지정한 checkpoint·종료점·시간/비용/도구 한계 도달.
- [6]과 적용 P2G/GEX 기준상 실제 사용자 판단 또는 추가 권한이 필요한 경우.
- 현재 권한·환경에서 해결할 수 없는 실제 장애.

사용자 정책 판단이 필요한 경우에는 P2G/GEX의 대기 규칙을 따른다. 주 작업은 필요한 상태 보존과 질문 뒤 멈추며, 정책 답변에 의존하거나 의존성이 불명확한 실행은 안전하게 정리한다.
이미 실행 중이며 어느 답변에서도 요구사항·완료 기준·결과가 유효하고 파일·공유 상태 충돌이 없는 작업만 기존 배정 범위까지 마칠 수 있다. 새 작업·위임·후속 단계는 시작하지 않는다.
사용자 checkpoint에서는 해당 GEX 정지 규칙을 적용한다. 이런 대기에서는 무응답·시간 경과·검토 PASS·담당자 완료 통지를 재개 승인으로 삼지 않는다.
대기·미완료와 승인 범위 완료를 구분하며, 단순 담당자 판단 반환을 사용자 대기로 확대하지 않는다.

담당자 결과 대기나 무관한 테스트 미실행은 종료 사유가 아니다.
개별 검사를 [5-H]에 따라 중단한 경우에도 원인 진단·교정·관련 재검증은 승인 범위 안에서 계속한다.
개별 실행의 중단을 전체 작업의 자동 종료 사유로 삼지 않는다.

실제 중지·세션 인계·장애로 작업을 넘길 때 다음을 갱신한다.

최신 인수인계를 확인하고 실제 남은 작업을 인수해줘.

GPT-6 Astra high가 코드 검토·구현 계획·설계·독립 테스트 작성·품질 판단을 맡고,
