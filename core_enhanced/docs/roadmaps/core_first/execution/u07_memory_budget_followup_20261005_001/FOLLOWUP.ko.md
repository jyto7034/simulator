# U07-M — 실측 기반 실행 예산 조정 준비 / 후속 구현 인계

2026-10-05 · 상태: **후속 작업 등록·구현 대기**. 정식 P2G Freeze/Goal, GEX 실행 결과 또는 제품 완료 문서가 아니다.

## 1. 사용자 요청과 현재 작업의 경계

사용자는 8MiB 내부 예산의 의미, 개발 중 제한 완화와 실제 플레이 집계, 평균/피크에 따른 수치 조정을 논의한 뒤 다음을 요청했다.

> 일단 지금은 구현이 진행중이라서, u07 의 후속 구현으로 남겨야겠다. 내용을 준비한 뒤, 문서를 한 번에 변경해줄래?

이에 따라 [로드맵](../../ROADMAP.ko.md)의 순서를 **U07 → U07-M → U08**로 보완한다. U07-M의 명칭·단계 분리는 이 요청을 실현하기 위한 계획상 선택이며 새 게임 규칙이나 구체적 예산 수치를 사용자 결정으로 표시하지 않는다.
U07-M은 U07의 독립 Complete / High·열린 finding0 이후 별도 후속 작업으로 상세화한다. 현재 진행 중인 U07의 목표·8MiB 기준·교정·검증·감사 범위를 바꾸지 않는다. 기존 실패를 향후 한도 조정으로 소급 PASS 처리하지 않는다.

지금은 문서만 등록한다. 현재 실행·재개 위치는 [U07 PLAN](../../../../goals/core_independent_objects/execution/single_goal/PLAN.md), 과거 중지 기준은 [두 번째 인계](../HANDOFF_20261005_002.ko.md)가 소유한다. 이 문서의 작성 시점으로 현재 제품이나 테스트 상태를 고정해 추정하지 않는다.

## 2. 확인된 기반과 아직 없는 완료 증거

- [trusted 설정](../../../../../../config/runtime_safety.ron)의 `native_runtime.max_retained_bytes`는 8,388,608 bytes다. 설정 주석도 RSS가 아니라 operation admission/extent임을 명시한다.
- [RuntimeFactLimits/계량](../../../../../src/game/battle/runtime_control.rs)은 코드의 `ENGINE_MAX`에도8MiB를 두고, operation 시작 보유 extent에 양의 growth를 누적한다. 중첩/rollback이 allowance를 초기화하지 않고 해제도 같은 operation의 allowance를 환급하지 않는다.
- [RuntimeSafetySettings](../../../../../src/runtime_safety.rs)는 trusted 설정 검증과 raw/effective profile hash를 제공한다. 따라서 현 상태에서 설정 숫자만 높이는 것은 유효한 제한 완화 경로가 아니다.
- [기존 public guard 측정](../../../../../tools/runtime_architecture_final_validation/src/public_guards.rs)은 allocator 관측의 live/peak/retained delta·할당 횟수를 가진다. PC의 누적 requested bytes·native admission은 heap peak나 process RSS와 같지 않다. 기존 R05 수치 guard도 별도 측정 범위/기준을 가진다.
- 이 기반의 존재는 정상 플레이 경로 수집·완전한 플랫폼 계측·최종 배포 예산 산정이 이미 끝났다는 뜻이 아니다. 구현자가 당시 코드를 확인하고 재사용할 부분과 실제 연결 부족분을 구분한다.

## 4. 구현 방향 — 실제 코드 조사 뒤 상세화

### 4.1 배포 기본과 개발용 측정 경로

배포 기본 profile과 현재 기본 거절 의미를 보존하고 trusted host가 명시 선택하는 개발용 측정 profile을 제공한다. 콘텐츠 팩·저장·일반 게임 명령이 제한을 올리거나 측정 모드를 켜지 못한다.

개발 측정에서는 기존 정상 예산 초과를 bounded 경고/수치로 남기며 **별도로 정한 유한 비상 상한까지** 진행할 수 있게 한다. `ENGINE_MAX`와 설정 검증의 정합, 경고 기준·실제 enforce cap·허용 가능한 코드 상한을 설계에서 구분한다. 정확한 임시 상한과 타입/API 분리는 지금 고정하지 않고 개발 환경·최대 실험 범위·계량 정확성에 근거해 기록한다. 비상 상한은 배포 권장값이 아니다.

work·clone·객체 수·입력 크기·overflow 등 관련 없는 보호를 일괄 해제하지 않는다. 오류를 무시하고 fault가 걸린 상태를 계속 실행하거나 rollback으로 예산을 되찾는 우회를 만들지 않는다. warning-only 기준과 실제 hard fault 경로를 입장 검사 단계부터 분리한다. 비상 상한 초과는 기존 typed fault·원자 복원·세션/저장 보호를 따른다.

profile은 세션/실행 경계에서 명시 선택하고 identity를 기록한다. 플레이 중 평균에 따라 자동 변경하거나 프로세스 RSS·수집기 속도를 게임의 성공/실패 판단에 직접 사용하지 않는다. 같은 profile/seed/input의 결정론을 보존하고 다른 profile의 허용 범위 변화는 의도된 차이로 명시한다. profile mismatch·저장/재현/승인 해시 소비자는 기존 owner와 함께 검토한다.

### 4.2 지표와 수집

각 수치에 측정 범위·단위·방법을 붙인다. 지표를 서로 대체하거나 합산해 하나의 가짜 메모리 피크를 만들지 않는다.

| 지표 | 최소 설명/연결 |
| --- | --- |
| operation 시작/current/최대 retained extent | 실제로 계량한 owner 범위·capacity·공유 저장소의 중복 취급과 한계를 명시 |
| operation 누적 retained admission | 시작값·누적 증가·최대 요청·초과 site, rollback/중첩/해제 의미 |
| allocator live/peak·종료 후 delta | 추적 구간·baseline·공유/다른 스레드 포함 여부, 관측 overhead. process 전체 RSS로 부르지 않음 |
| process RSS/peak(지원 환경) | OS·측정법·프로세스/동시 세션 범위. 미지원이면 명시하며 allocator 값으로 대체하지 않음 |
| work·clone·할당·queue/object 수 | 실제 부하를 설명하고 과도한 반복/해제 누락과 정상 최대 부하를 구분 |
| 실행 시간·정상 결과 | 빌드/관측 모드별 측정 분리, 성공/typed 거절/중단과 실행된 시나리오 범위 |

가능한 기존 런타임 관측과 도구를 확장한다. 정상 CoreApplication/host의 선택된 실제 경로에서 샘플을 만들어 명령/입력·seed·콘텐츠/엔진/profile hash·빌드/기기·전투 규모·조합·동시 세션 수·측정 창과 연결한다. Unity 화면 연결은 U26/U30-P에서 수행한다. 임시 direct-private 호출만으로 실제 플레이 연결 완료를 주장하지 않는다.

수집 버퍼/파일/샘플 수와 출력 크기를 제한하고 드롭·누락·표본 수를 표시한다. 수집기 부재/포화/비활성화가 gameplay나 영속 결과를 바꾸지 않게 한다. 새 원격 수집 서비스나 dashboard를 필수화하지 않는다. 요약은 평균·상위 구간·최대·조건별 분포를 제공하되 적은 표본에서 분위수를 확정적 최대치로 해석하지 않는다.

### 4.3 대표 시나리오와 수치 결정

현재 지원되는 정상 전투, 설계상 지원할 최대 부하, 소환/함정/광역 연쇄, 반복 생성·해제, Pause·재접속·저장/복원, 동시 전투를 구분한다. U07 PC 실패 원본과 같은 입력도 재현 비교에 남긴다. 기존500/1000 유닛 fixture 자체를 모든 콘텐츠의 gameplay 상한으로 승격하지 않는다.

U07-M에서는 실제 수집과 경계 시험에 필요한 최소 현재 시나리오를 닫는다. 콘텐츠가 확장되면 도입 owner가 표본을 추가하고 U30-C/U30-P에서 목표 플랫폼·정상 최대 규모·동시성·다른 시스템 메모리·여유분을 근거로 값을 정한다. 평균은 평소 비용 설명에, 피크/정상 최대와 환경 예산은 상한 결정에 사용한다. 표본 최대가 이론적 최악의 상한을 증명한다고 쓰지 않는다.

값 변경은 새 profile/revision과 전후 원시 측정·이유·영향에 결속한다. 이전 실패나 기존 숫자 oracle을 덮어쓰지 않는다. 실제 구현 버그/이중 계량/누락은 수정하고, 정상 부하에 비해 낮은 예산은 별도의 근거 있는 정책 변경으로 처리한다. 메모리 peak를 그대로 누적 admission 설정값에 대입하지 않는다.

## 6. 진행 중 구현 담당자의 인수

현재 U07 runner·교정·감사를 이 문서 때문에 중단하지 않는다. 다음 안전한 pass 경계에서 [발행 기록](RECORD.ko.md)과 로드맵의 다음 선택을 인수한다. U07의 active PLAN/실험 기록·불변 정책/Goal·실패/감사/target은 이번 문서 작업에서 수정하지 않는다.

문서 hash가 감사/검증 입력에 들어가면 실제 delta를 확인하고 현행 GEX currentness에 따라 필요한 결속을 갱신한다. 후속 범위 등록만으로 전체 P2G/제품 테스트/감사 재실행 또는 자동 PASS를 선언하지 않는다. 독립 감사가 이미 진행 중이면 고정 target을 보존하고 이 후속 등록은 차기 선택 시점의 입력으로 처리한다.

U07 독립 완료 후 당시 최신 사용자 실행 권한·모델/역할 지시를 인수해 U07-M을 시작한다. 계획자는 실제 코드에 근거한 구현 방향을 작성하고 구현자와 독립 감사자를 분리한다. 이번 문서는 새로운 agent 소환·제품 구현·실측 실행 자체를 수행하지 않았다.
