# 시스템별 리팩토링 실행 지침

작성일: 2026-10-16

큰 코드베이스를 **전체 경계 파악 → 선택 시스템의 흐름 조사 → 책임 단위 설계 → 구현과 검증 → 완료 검토 → 시스템 간 통합 확인**으로 다룬다.
모든 시스템의 상세 설계를 한꺼번에 확정하지 않고, 공통 경계와 의존성을 파악한 뒤 선택한 영역을 깊게 검토한다.
시스템을 나누는 목적은 조사·변경·검증 범위를 통제하는 것이며, 폴더나 crate를 먼저 분리하라는 뜻은 아니다.

[리팩토링 판단과 실행 기준](refactoring_criteria.ko.md)은 무엇을 왜 개선할지 판단한다.
이 지침은 그 판단을 큰 프로젝트에 순차 적용하는 방법, 작업 인계와 완료 조건을 정한다.

이번 프로젝트 리팩토링의 목적·범위·현재 위치·다음 행동은
[Core 리팩토링 목적과 진행 현황](refactoring/README.md)에서 확인한다.

§2의 지도를 먼저 만들고, 승인된 각 시스템·작업에 §3~6을 적용한다. 새로 확인한 경계만 지도에 반영하며,
여러 시스템을 마친 뒤 §7에서 최종 연결 상태를 확인한다. 재개 시에는 §8~9의 현재 기록에서 해당 단계로 돌아간다.

## 1 요청 범위와 적용 절차

처음에 현재 요청의 대상, 원하는 결과, 허용 행동과 종료점을 확인한다. 이전에 확인된 권한·결정을 재사용하고,
문서 작성이나 조사 요청을 제품 구현 시작으로 해석하지 않는다.

| 요청 | 수행할 범위와 종료점 |
| --- | --- |
| 지침 작성·수정 | 지침과 관련 탐색 링크를 정리하고 종료 |
| 전체 시스템 지도 작성 | §2의 경계 지도와 상세 조사 후보·순서를 정리하고 종료 |
| 특정 시스템 조사·계획 | 실제 흐름과 구조 문제를 확인하고, 필요한 작업 묶음·검증·의존성을 정리한 뒤 종료 |
| 선택 작업 구현 | 승인 범위의 상세 설계·구현·자체 검증을 끝내고 완료 검토에 필요한 대상을 고정하여 인계 |
| 완료 검토·감사 | 고정된 대상과 근거를 읽고 판정. 구현 수정은 별도 교정 작업으로 분리 |
| 정해진 범위를 감사까지 연속 수행 | 포함된 시스템·작업·감사와 종료점 안에서 단계를 구분해 진행. 명시적 중지와 필수 독립성 조건은 유지 |

일반 구현 요청의 기본 종료점은 구현·자체 검증 후 검토 인계다. 감사까지 명시 위임받은 경우에는 그 범위에서
별도 검토 pass로 이어갈 수 있다. 중간 단계마다 사용자 검토를 기다리는 방식은 사용자가 요청했을 때만 적용한다.
단계 번호 변경, 계획 작성 완료나 검토 통과만으로 새 작업 범위가 승인되지는 않는다.

### P2G와 GEX의 적용 관계

이 지침은 P2G/GEX의 유용한 원칙을 리팩토링에 맞춰 선별한 실행 안내다. 정식 Goal이 아닌 내부 변경에
Policy Topic·Freeze·Goal Set·Exact Ref 등록표를 일률적으로 만들지 않는다.

이미 정식 P2G/GEX로 관리되는 작업이면 해당 원문의 인수·산출물·동결·감사·완료 조건을 유지하고,
이 지침은 시스템 조사와 작업 분할 방법으로 사용한다. 간소화된 기록을 정식 산출물이나 `Complete / High` 판정으로 대신하지 않는다.
새 정책·공개 계약 변경으로 정식 절차가 필요하면 해당 owner 절차로 연결한다. 내부 타입·함수·파일 배치 선택은
승인 의미와 공유 계약을 보존하는 범위에서 실행자가 결정한다.

## 2 전체 시스템 지도를 만든다

### 2.1 첫 조사의 깊이

공개 진입점, 상위 모듈, 주요 상태 소유자와 실제 실행 경로를 읽어 다음 관계를 파악한다.

```text
외부 입력 → 애플리케이션 실행 경계 → 도메인 규칙과 상태 변경 → 결과·이벤트·조회
                      ↕                         ↕
                콘텐츠 게시 데이터          저장·복원과 상태 수명
```

모든 함수의 호출 그래프나 전체 리팩토링 후보를 이 단계에서 작성하지 않는다. 어떤 시스템이 어떤 사실을 소유하고,
어디에서 다른 시스템과 연결되는지 설명할 수 있는 깊이까지 조사한다. 다음 내용을 한 표에 모은다.

| 시스템 | 주요 진입점·소스 | 소유 상태·규칙 | 생산자·소비자·공유 경계 | 조사 상태·다음 행동 |
| --- | --- | --- | --- | --- |
| 시스템 이름 | 실제 위치와 선택된 실행 경로 | 원본과 파생 상태 구분 | 의존 방향과 외부 경계 | 미조사·조사 중·조사 완료·재확인 필요 |

상위 모듈과 공개 기능을 지도에 대조해 빠진 영역을 확인한다. 아직 배정하지 못한 영역은 미분류로 남기고,
지도에 없는 기능을 조사 완료로 간주하지 않는다. 테스트·설정·생성 경로는 그것이 검증하거나 선택하는 시스템에 연결한다.

### 2.2 초기 분할안

다음은 현재 모듈과 주요 실행 루트를 바탕으로 한 조사 출발점이다. 확정된 의존성 그래프나 리팩토링 필요 판정이 아니다.
모든 경로는 `core_enhanced/src` 기준이며, 실행 시 관련 경로의 현재성을 확인한다.

| 조사 영역 | 시작할 소스 | 주요 조사 질문 |
| --- | --- | --- |
| 애플리케이션 실행 | `application.rs`, `game/behavior.rs`, `game/world/application.rs` | 명령 자격·처리 경로·commit·결과의 책임이 일관되는가? |
| 콘텐츠 로딩·검증 | `game/data/`, `game/data/content_pack/` | 작성 입력에서 검증·게시까지 원본과 데이터 세대가 명확한가? |
| 원정·지도 진행 | `game/map/`, `game/expedition_lifecycle.rs`, `game/world/node_flow.rs`와 원정 관련 모듈 | 출발·이동·노드 진입·종료가 유효한 상태 전이를 만드는가? |
| 영구 상태·저장·복원 | `game/encounter_compendium.rs`, `game/world/active_run/`, `game/world/expedition_recovery.rs` | 영구 profile과 진행 중 원정의 수명·저장·재시작 경계가 일치하는가? |
| 직원·장비·성장·경제 | `game/employee.rs`, `game/resources/`, `game/skill_fragment/`, `game/relic/`, 관련 `world` 처리 | 사본·장착·성장·재화의 소유와 소비·지급 책임이 명확한가? |
| 노드 활동·이벤트·VN | `game/world/`의 shop·reward·maintenance·event·VN 처리, `game/visual_novel.rs` | 세션별 선택·취소·종료와 노드 진행을 어떻게 연결하는가? |
| 전투 진입·결과 정산 | `game/combat_preview/`, `game/combat_setup/`, `game/world/combat.rs`와 전투 상호작용 | 원정 상태 전달과 전투 결과의 반영·종료가 완결되는가? |
| 전투 실행 기반 | `game/battle/core/mod.rs`, `game/battle/core/sim.rs`, `game/battle/core/queue.rs`, 생성·사망·종료 관련 모듈 | 시간·순서·유닛 수명·전투 종료의 권위가 어디에 있는가? |
| 전장·이동·저지 | `game/battle/battlefield/`, `game/battle/core/movement/`, 공간·전술 관련 모듈 | 위치·점유·경로·충돌·저지가 같은 상태 의미를 사용하는가? |
| 공격·스킬·효과 | `game/battle/core/skill_runtime/`, 타겟팅·평타·투사체·피해·효과 관련 모듈 | 시전·전달·해결·취소·후속 효과의 책임과 순서가 분명한가? |
| 콘텐츠 제작·실험·모드 검증 | `authoring/`, `mod_validation.rs`, `mod_validation/`, 관련 CLI | 제작·미리보기·실험·검증 결과가 실제 실행 계약과 연결되는가? |

직원·경제, 노드 활동, 공격·효과처럼 큰 영역은 상세 조사에서 다시 나눈다. 분할 기준은 상태 소유권, 수명,
transaction과 검증 가능한 흐름이다. 줄 수나 파일 수로 고정 크기를 맞추지 않는다.

유물·보스·소환처럼 여러 영역을 관통하는 기능은 각 규칙·상태의 주 소유 영역을 정하고 연결 검증을 따로 배정한다.
공통 타입·결정론·자원 제한·관측·공유 테스트 도구도 사용하는 시스템과 연결한다. 모든 시스템이 같은 공통 코드를
독립적으로 재설계하거나, 어느 시스템도 책임지지 않는 공통 경계를 만들지 않는다.

### 2.3 상세 조사 순서

우선 애플리케이션 실행 루트와 상태 소유 관계를 파악한다. 그 뒤 현재 실패·개발 차단·반복 변경 부담과 의존성을
기준으로 첫 시스템을 선택한다. 초기 후보로 전투 진입·결과 정산처럼 여러 시스템을 연결하는 경계를 검토할 수 있지만,
관련 전제가 부족하거나 더 시급한 문제가 확인되면 순서를 조정한다.

조사 순서와 구현 순서는 같을 필요가 없다. 넓은 연결 경계를 먼저 조사하더라도 실제 구현은 확인된 작은 책임 단위부터 시작한다.
전체 범위를 위임받았다면 근거에 따라 다음 시스템을 선택하고 기록한다. 특정 시스템만 요청받았다면 인접 시스템으로
자동 확대하지 않고 필요한 경계 확인과 후속 제안까지만 수행한다.

## 3 선택 시스템의 실제 흐름을 조사한다

### 3.1 조사 단위

한 번에 설명·검증할 수 있는 사용자 행동이나 실행 흐름을 선택한다. 예를 들어 장비 시스템은
“장착 요청 → 자격 확인 → 사본·슬롯 변경 → 스탯 반영 → 결과 반환”으로 추적한다.
진입점만 읽거나 내부 함수만 고립시켜 판단하지 않는다.

선택 흐름에서 다음을 확인한다.

1. 실제 생산 입력, 지원 조건, 선택되는 구현·설정·feature.
2. 원본 상태와 변경 주체, 조회용 사본·캐시·파생값.
3. 검증·변경·후속 사건·결과 반환의 순서와 실패 의미.
4. 관련 생성·취소·종료·재시도·복원 경로와 상태 수명.
5. 실제 소비자, 공유 타입·데이터·저장·외부 계약.
6. 기존 테스트가 보호하는 불변조건과 중요한 검증 공백.
7. 대표 변경을 대입했을 때 함께 수정할 표현·소유자·동기화 지점.

모든 흐름에 모든 기법을 적용하지 않는다. 호출·역참조·상태 흐름·실행 관측 중 주장에 필요한 방법을 선택한다.
검색 결과나 타입·테스트의 존재만으로 실제 도달 가능성이나 소비자 부재를 확정하지 않는다.
접근하지 못한 외부 소비자는 미확인으로 남기고 해당 계약 보존 주장의 한계를 표시한다.

### 3.2 조사 결과와 종료 조건

후보는 [리팩토링 기준](refactoring_criteria.ko.md)의 문제·영향·개선·검증 조건으로 판정한다.
같은 원인을 여러 증상으로 부풀리지 않으며, 각 후보에 주 소유 시스템을 하나 정하고 관련 시스템을 연결한다.

| 분류 | 다음 행동 |
| --- | --- |
| 유지 | 현재 구조가 적절한 근거를 기록 |
| 동작 보존 리팩토링·정리 | 보존 계약과 목표 구조를 정해 작업 설계로 이동 |
| 오류 교정 | 확정 계약 위반과 올바른 기대값을 구분하여 교정 범위를 정함 |
| 정책·공개 계약 판단 필요 | 기존 승인·위임으로 결정 가능한지 확인하고 실제 미결정만 해당 owner로 전달 |
| 근거 부족 | 부족한 사실과 영향받는 결론, 필요한 좁은 조사를 기록 |
| 범위 밖 | 근거와 후속 위치를 남기되 현재 작업을 확대하지 않음 |

조사 완료는 선택한 흐름·평가 항목의 적용 여부와 근거, 미확인·보류가 모두 설명되는 상태다.
시스템이 무결점이거나 모든 후보를 구현했다는 뜻은 아니다. 핵심 경로가 미확인이면 일부 조사 완료로 표시하고
그 경로를 포함하는 전체 조사 완료를 주장하지 않는다. 개선 후보가 없어도 조사 자체는 완료할 수 있다.

## 4 책임 단위의 작업과 순서를 설계한다

### 4.1 하나의 작업에 담을 내용

작업마다 식별 가능한 이름 또는 간단한 ID를 두고 다음을 기존 조사 기록에 연결한다.

- 해결할 후보와 구조적 목표, 작업 유형, 포함·제외 범위.
- 현재 소유자·생산자·소비자와 목표 소유 관계.
- 보존할 동작·불변조건·공개 계약과 별도로 승인된 교정 사항.
- 재사용·변경·제거할 경계, 선택한 대안과 이유.
- 선행 작업·공유 계약, 구현 후 유효해야 할 중간 상태.
- 동작 보존과 구조 개선의 수용 조건, 검증 경로와 실행 책임.
- 미확인·정책 질문, 구현자에게 남기는 내부 설계 선택.

승인된 의미, 권장 구조, 실제 타입·함수 수준의 상세 설계를 구분한다. 구현자는 의미와 공유 계약을 보존하면서
더 나은 내부 구조를 선택할 수 있다. 반대로 상태 수명·소비자 의미·실패·저장 전환처럼 작업 분할의 전제를
바꾸는 선택을 “구현 때 결정”으로 미루지 않는다.

### 4.2 의존성과 함께 구현할 경계

의존 관계에는 선행 작업, 후행 작업, 필요한 계약과 이를 무시했을 때 깨지는 조건을 적는다.
같은 파일을 수정한다는 사실과 실행 의존성을 구분한다.

작업을 분리했을 때 다음 문제가 생기면 경계를 다시 설계한다.

- 원본 상태를 둘이 소유하거나 아무도 소유하지 않음.
- 한 동작의 검증·commit·정리가 다른 작업에 남아 정상 경로가 완결되지 않음.
- 생산자·소비자, 저장 writer·reader가 서로 다른 의미나 형식을 사용함.
- 다음 작업 전에는 현재 결과를 정상 실행·검증할 수 없음.

해결 방법은 실제로 유효한 안정된 계약을 사이에 두거나, 함께 바뀌어야 하는 최소 작업을 한 묶음으로 구현하는 것이다.
순환 의존성이 있으면 그 원인부터 확인하고 위 방법으로 해소한다. 근거 부족이나 정책 질문을 가짜 선행 작업으로 숨기지 않는다.
여러 파일·시스템을 건드려도 하나의 불변조건을 함께 지켜야 한다면 같은 작업에 포함할 수 있다.

각 구현 묶음의 종료 시점에는 다음 작업이 시작되지 않아도 현재 상태가 실행·검증 가능해야 한다.
임시 전환 경로가 필요하면 기존 승인에 따른 권위 상태, 소비자, 유지·제거 조건을 명시한다.
여러 시스템으로 나눴다는 이유로 자동 병렬화하지 않는다. 기본은 단독 순차 진행이며, 별도로 병렬 작업을
위임받은 경우에도 상태·계약·파일·검증 자원의 독립성을 확인한다.

### 4.3 통합 검증을 미리 배정한다

시스템 사이의 필수 조건마다 검증 방법과 책임 작업을 정한다. 마지막 감사에서 새 테스트나 제품 API를
급히 만들어야 하는 상태를 남기지 않는다.

| 검증 방법 | 계획에 남길 내용 |
| --- | --- |
| 기존 테스트·공개 실행 경로 | 실제 위치, 입력·실행 방법, 관측 결과와 보호하는 조건 |
| 대상 수정 없는 임시 관측 | 관측할 현재 동작, 재현 방법, 임시 출력 위치와 한계 |
| 새 테스트·fixture·제품 경계 필요 | 이를 구현할 작업, 완료 조건, 통합 검토자가 사용할 방법 |

조사·계획만 요청받았다면 여기서 구현 가능한 계획과 남은 질문을 인계한다. 계획 완료를 구현 승인으로 쓰지 않는다.
정식 P2G 대상이면 P2G-20의 코드 검토, P2G-40의 작업 분할, P2G-50/60의 Goal·인계 조건을 원문대로 충족한다.

## 5 선택 작업을 구현하고 자체 검증한다

### 5.1 인수와 기준선

구현 시작 시 선택 작업·권한·종료점, 선행 결과와 현재 소스·데이터·테스트를 대조한다.
선행 결과가 문서 제안인지 실제 구현인지 구분하며, 기존 사용자 변경을 이번 작업의 성과로 귀속하거나 되돌리지 않는다.
변경이 겹쳐 안전하게 분리할 수 없으면 그 부분의 편집을 멈추고 상황을 정리한다.

변경 전 관련 상태를 다시 식별·복구할 수 있게 남긴다. 깨끗한 commit, 관련 diff·파일 사본 등 작업에 맞는 방법을 쓰고,
dirty 상태를 commit ID 하나로 표현하지 않는다. 정식 동결·복원 검증이 요구되는 작업은 그 절차를 따른다.
초기 실패·미실행을 구분하고, 필수 사전 검증은 변경 전에 수행하거나 유효한 기존 증거로 확인한다.
변경 후 결과를 변경 전 성공 기록으로 소급하지 않는다.

### 5.2 구현 순서

1. 인계된 구조를 현재 코드에 맞춰 상세화한다. 타입·입출력·상태 key·수명·순서·실패·정리와 시험 기대값을 필요한 만큼 정한다.
2. 기존 테스트가 보존 계약을 보호하는지 확인하고 중요한 공백을 먼저 보강한다. 단순 내부 이동에 구현을 복제한 새 테스트를 추가하지 않는다.
3. 설계한 최소 책임 묶음을 구현하고 생산자·소비자·관련 설명을 함께 맞춘다.
4. 위험한 경계의 작은 실제 검증부터 수행한다. 상태 소유·실패·저장·공유 형식 변경은 비싼 전체 실행 전에 주요 가정을 확인한다.
5. 관련 집중 검사와 필요한 통합 검사를 수행하고, 예상 밖 영향이 있으면 검증 범위를 넓힌다.
6. 최초 구조 문제를 다시 대입해 소유권·의존·수동 동기화가 실제로 개선됐는지 확인한다.
7. 전체 수용 조건과 최종 변경을 대조하고 완료 검토에 필요한 대상·diff·근거·잔여를 고정한다.

필요한 내부 교정은 승인 범위에서 계속한다. test 전용 제품 분기, 조용한 오류 보정, 근거 없는 재시도·delay,
소비자 측 규칙 재구현, 무조건적인 snapshot 갱신이나 assertion 삭제로 실패를 숨기지 않는다.
검토 대상 고정 후의 변경은 기존 결과를 덮어쓰지 않고 새 변경과 영향받는 검증을 식별한다.

### 5.3 검증 범위와 근거 재사용

검증은 보존 조건과 실제 위험에서 선택한다. 정상·거절·경계, 실패 후 상태, 반복·재시도, 순서·결정론,
생성·취소·종료, 저장 후 계속 실행, 실제 생산자·소비자, 이전 경로 제거, 성능·자원 중 적용되는 항목을 연결한다.
모든 항목을 별도 테스트 명령으로 만들지 않으며 비적용 이유를 설명할 수 있어야 한다.

[현재 로드맵의 검증 범위](roadmaps/core_first/ROADMAP.ko.md#19-검증-범위-제한--외부-임의-변조-방어-제외)를 유지한다.
지원 경로·실제 장애로 발생 가능한 오류를 확인하고, 임의 변조로만 가능한 상태를 새 방어·필수 시험·완료 차단으로 만들지 않는다.

기존 결과는 명령·선택 조건, 입력·fixture, 관련 제품·테스트·설정·의존성·환경과 결과의 유효 범위를 확인해 재사용한다.
제품 코드가 바뀌었으면 테스트 파일이 같아도 영향받는 검증을 다시 한다. 테스트·fixture·판정 도구가 바뀌면 해당 결과를 다시 확보한다.
공유 경계의 영향을 분리할 수 없을 때는 필요한 넓은 검사를 수행한다. 단계 이동·날짜 변경·새 검토자만으로 전체 검사를 반복하지 않는다.

기존 테스트·공유 helper를 재사용할 때는 전제한 기본 콘텐츠, 시작 상태, 진행 구조와 저장 버전이 현재 검증 목적에 맞는지 확인한다.
과거 계약을 보호하는 fixture와 현재 공식 경로를 확인하는 입력을 구분한다. 과거 입력의 통과로 현재 경로의 검증을 대신하거나,
실패를 없애기 위해 현재 경로 시험을 과거 입력으로 바꾸지 않는다. 입력을 바꿀 때도 원래 검증 목적을 유지한다.

전체 초기·최종 검사가 필요한 범위라면 실행할 명령·시점·책임 작업을 계획에서 정한다. 마지막 통합 검토는 필요한 실행 근거를
확인하며, 검증 준비나 제품 수정을 대신 떠맡지 않는다. 초기 1회·최종 1회 계획을 실패 교정과 입력 변경 후 재검증의 상한으로 삼지 않는다.
0시험·skip·중단·환경 실패를 통과로 기록하지 않으며 기존 실패와 새 회귀를 구분한다.

### 5.4 테스트 준비와 기대값

테스트·fixture·진행기를 작성하거나 수정하기 전에 해당 시나리오의 규칙과 실제 입력을 확인한다. 초기 상태에서 목표 연산까지의
행동 순서, 중간 선택·자동 전이·자원 임계점, 관측 지점과 기대 결과를 구체화한다. 첫 실행과 반복·재시작·복원의 선행 조건이
같다고 가정하지 않는다. 중요한 가정과 미확인은 기존 계획이나 테스트 설계 기록에 경로의 복잡도에 맞게 간결히 남긴다.
단순 테스트를 위해 별도 계획 문서나 승인 절차를 추가하지 않는다.

주요 행동 뒤에는 예상 상태와 다음 행동의 자격을 확인한다. API 호출 성공만으로 목표 상태 도달을 판단하거나,
진행기가 예상 밖 상태를 임의로 건너뛰어 실패를 숨기지 않는다. 부정 사례도 의도한 거절 지점까지의 선행 조건을 만족해야 하며,
다른 자격 오류나 초기 거절을 목표 경계의 검증으로 기록하지 않는다.

기대값은 요구사항·정책, 독립 계산과 외부 관찰에서 도출한다. 제품 알고리즘이나 helper를 복제하지 않고 작은 수작업 예제,
대조 입력과 불변조건을 활용한다. 문서와 실제 동작이 다르면 원인을 확인하며 현재 구현에 맞춰 기대값을 자동 변경하지 않는다.

검증할 제품 계약과 목표 상태를 만들기 위한 준비 전략을 구분한다. 테스트가 편의상 선택한 배치·탐색·조작 순서를 제품의
필수 규칙으로 추가하지 않는다. 준비 전략을 바꾸더라도 요구된 경로·입력 규모·관측 지점·판정 조건은 유지한다.
고비용 실행 전에는 작은 실제 실행이나 유효한 기존 근거로 목표 연산 도달을 확인하되, 이를 전체 시나리오 통과로 대신하지 않는다.

성능 기준 초과는 [판단 기준 §7.4](refactoring_criteria.ko.md#74-성능과-자원)에 따라 실제 사용 영향을 먼저 평가한다.
기존 측정과 호출·소비 경로를 재사용해 목표 PC, 빈도·규모, 절대 비용과 전체 비용의 비중을 확인하고,
영향이 작으면 유지·후순위로 종료할 수 있다. 영향이 미확인이면 필요한 좁은 확인을 선택하며,
기준 초과나 특정 함수의 비용 순위만으로 세부 계측·최적화·벤치마크 반복을 다음 필수 작업으로 만들지 않는다.

### 5.5 실행 입력과 장시간 검사

실행 중인 검사의 관련 제품·테스트·fixture·설정·판정 도구 입력은 고정한다. 해당 입력 수정은 실행 종료·정리를 확인한 뒤 수행한다.
같은 입력·환경의 관련 사례는 기존 runner와 선택 목록으로 묶어 동일 설정 빌드를 반복하지 않는다. 기능 옵션·서버·재시작·전역 상태·
성능 환경에 필요한 분리는 유지하며, 명령 병렬 실행은 입력과 공유 자원이 격리될 때만 사용한다.

장시간 검사는 기존 실행 시간·입력 규모·환경을 근거로 예상 소요와 진단·중단 조건을 기존 기록에 남긴다.
예상 근거가 부족하면 미확정으로 표시하고 첫 진단 시점과 확인할 신호를 정한다. 출력 부재만으로 정체를 단정하지 않고
기존 세션의 진행·CPU·메모리·로그를 확인한다. 예상보다 느리면 제품 연산과 준비·저장·로그 수집의 지연을 구분한다.

대기는 기존 실행 세션의 완료 알림·출력 수집을 이용하며, 짧은 주기의 상태 조회나 중복 실행을 피한다.
합의된 조건 안에서 자신이 소유한 실행만 안전하게 중단한다. 입력·명령·경과 시간·원시 출력·중단 이유를 보존하고
종료·정리 뒤 교정한다. 운영상 대기 한도 초과를 제품의 성능 기준 위반과 동일하게 판정하지 않는다.

## 6 구현과 분리해 완료를 검토한다

완료 검토는 구현자의 요약을 결론으로 받아들이지 않고, 요구사항·현재 소스·변경·원시 검증 근거를 대조하는 별도 pass다.
검토 중에는 대상 코드를 고치지 않는다. 필요한 비파괴 실행과 검토 기록 작성은 가능하며, 결함 교정은 검토 결과를 남긴 뒤
권한이 있는 구현 pass에서 수행한다.

별도 비참여 검토자가 요구되면 그 조건을 충족해야 한다. 같은 실행자의 검토가 허용되는 작업에서도 구현과 검토의
대상·작업 문맥·산출물을 구분하며 자기 검토를 비참여 감사로 표기하지 않는다. 필요한 독립 역할이 없으면 인계 준비와
잔여 조건을 보고한다. 이 지침 자체는 서브에이전트 소환이나 역할 위임을 지시하지 않는다.

검토자는 다음을 확인한다.

- 구현 전제·선행 계약과 검토 대상이 현재도 유효한가?
- 모든 수용 조건이 실제 코드·실행 근거와 연결되는가?
- 원래 구조 문제가 해소됐으며 무관한 동작 변경이나 새 중복 소유권이 없는가?
- 실패·수명·저장·소비자·성능 등 적용 조건의 검증이 충분한가?
- 기존 결과의 재사용 근거, 비적용과 미실행 판단이 타당한가?
- 임시 경로·대체 구현·과거 책임의 제거 또는 승인된 전환 조건이 충족됐는가?
- 관련 문서와 데이터가 일치하고 사용자 변경이 보존됐는가?

일반 작업의 결과는 `완료`, `미완료`, `판정 보류`와 근거로 기록한다. 완료는 모든 필수 조건이 현재 근거로 충족되고
완료를 막는 미확인이 없음을 뜻한다. 필수 실패는 미완료, 필요한 사실·권한이 없어 판단할 수 없으면 판정 보류다.
정식 GEX 작업은 원문의 `Complete / High`, `Not Complete`, `Blocked` 의미를 그대로 사용한다.
검토 결과는 구현·다음 시스템 선택·배포 권한을 새로 만들지 않는다.

## 7 시스템 사이의 연결과 전체 결과를 확인한다

개별 작업이 끝날 때 영향받는 연결 조건을 확인하고, 승인된 여러 시스템의 개선이 끝나면 최종 상태에서 통합 검토한다.
각 작업이 통과했다는 사실만으로 시스템 사이의 계약까지 통과한 것으로 보지 않는다.

초기 통합 흐름 후보는 다음과 같으며 실제 범위에 해당하는 것을 선택·보완한다.

| 흐름 | 확인할 연결 조건 |
| --- | --- |
| 콘텐츠 로딩 → 실행 데이터 → 스킬 실행 | 같은 데이터 세대·정의 의미가 실제 실행까지 전달됨 |
| 장비·유물 변경 → 전투 진입 → 스탯·효과 적용 | 사본 소유·장착 결과가 전달되며 서로 다른 규칙으로 재해석되거나 누락되지 않음 |
| 전투 종료 → 보상·노드 정산 → 원정·영구 상태 반영 | 완료와 지급이 계약대로 한 번 반영되고 종료 상태가 일치함 |
| 저장 → 재시작·복원 → 다음 행동 | 저장 수명·identity·진행 상태와 계속 실행 결과가 보존됨 |
| 제작·미리보기·검증 → 실제 실행 | 도구가 확인한 계약과 실제 제품 경로의 의미가 일치함 |

후속 변경이 앞선 결과에 미친 영향을 판정한다. 예상된 선행 구현의 실현이나 내부 이동은 그 자체로 전체 계획 재작성을
요구하지 않는다. 공유 의미·수명·순서가 달라지거나 회귀가 생겼으면 영향받는 검증·완료 판단을 갱신한다.
오래된 대상에서 얻은 통과를 현재 통과로 표시하지 않는다.

전체 완료에는 승인된 시스템 조사 범위, 선택한 필수 개선 작업, 시스템 간 수용 조건과 현재 근거가 모두 연결되어야 한다.
일부 시스템만 수행했다면 그 범위의 완료로 보고한다. 비필수 후속 후보는 남길 수 있으나 현재 필수 조건을 후속으로 숨길 수 없다.
정식 다중 Phase 작업이면 이 단계는 GEX-30의 전체 통합 감사와 연결하고 그 진입 조건을 따른다.

## 8 발견 사항의 처리와 재개

| 발견 내용 | 돌아갈 위치와 처리 |
| --- | --- |
| 승인 의미 안의 내부 구현 오류 | 해당 변경을 소유한 구현 작업에서 교정하고 영향 검증·검토 |
| 코드 사실·소유자·소비자에 관한 전제가 틀림 | 선택 시스템 조사로 돌아가 영향을 받은 설계만 보완 |
| 작업 분할 뒤 유효한 중간 상태를 만들 수 없음 | 작업 경계·의존성 설계로 돌아가 재분할·결합 |
| 정책·공개 결과·저장 수명·호환 의미 변경 필요 | 기존 결정·위임 여부를 확인하고 해당 정책·계약 owner로 연결 |
| 검증 도구·fixture·기대값 문제 | 제품 결함과 구분해 원인을 고치고 해당 검증을 다시 확보 |
| 후속 작업이 선행 시스템에 회귀를 만듦 | 회귀를 만든 변경의 책임 작업을 찾아 교정하고 영향받은 선행·통합 판단 복원 |
| 무관한 새 개선 후보 | 후속으로 기록하고 현재 범위는 유지 |

실패 원인이 미확인이면 제품·테스트·fixture·기대값·판정 도구·환경 중 하나로 성급히 확정하지 않는다.
새 가설·증거·유효한 교정 없이 같은 수정과 실행을 반복하지 않는다. 예상 전이·관측과 실제 결과의 차이, 깨진 가정과 미확인 가정,
교정 근거·배제한 원인·남은 불확실성을 기존 기록에 간결히 남긴다. 전제 오류를 확인하면 같은 가정을 쓰는 관련 시나리오와
공유 fixture·helper·진행기도 확인하고, 교정된 전략이 목표 조건에 도달할 근거를 확보한 뒤 영향 범위를 재실행한다.

실패 원본과 원래 성공 판정의 의미를 보존한다. 원인을 모른 채 기대값·한도·입력 규모를 완화하거나 관측을 생략하지 않는다.
자동 종료와 명시적 중단, 실패 복구와 새 실행, 동일 프로세스 복원과 새 프로세스 복원은 서로 다른 경로다.
대체 경로만 확인했다면 실제 검증 범위를 기록하고 원래 목표는 미검증으로 남긴다.

정식 파이프라인에서는 코드 전제는 P2G-20, 작업·의존성은 P2G-40, Goal 매핑은 P2G-50,
정책 의미는 P2G-10, 기술 교정은 실제 owner의 GEX-10으로 연결한다. 이 안내만으로 해당 단계의 실행 권한이 생기지는 않는다.

사용자 판단이 필요한 경우에는 질문·추천·영향·답변이 필요한 이유를 정리하고 해당 결정을 가정한 작업을 진행하지 않는다.
기존 승인 안의 해결 가능한 실패를 매번 재승인 사유로 만들지 않는다. 명시적 checkpoint·예산·범위 한계와
적용 중인 P2G/GEX의 대기 규칙을 지킨다.

재개할 때는 현재 시스템·선택 작업·권한·종료점, 마지막 유효 결과, 미해결 문제, 다음 행동에서 시작한다.
관련 소스·입력·환경이 달라진 부분만 확인하고 전체 이력·저장소를 다시 읽지 않는다. 이미 끝난 구현은 반복하지 않으며,
구현 종료·검토 대기·교정 필요·근거 재확인 필요를 구분해 필요한 위치부터 이어간다.

## 9 최소 기록과 인계 양식

기존 실행 기록이 있으면 역할을 연결해 재사용한다. 신규 일반 작업은 `docs/refactoring/<작업명>/`처럼
`goals` 밖의 한 작업 위치를 사용할 수 있다. 이 지침 작성만으로 실행 폴더나 실제 작업 목록을 초기화하지 않는다.
정식 P2G/GEX가 지정한 문서 위치와 산출물은 해당 계약을 따른다.

| 기록 역할 | 최소 내용 |
| --- | --- |
| 전체 현황 | 승인 범위·끝점, 시스템 지도, 조사 상태, 선택 작업과 다음 행동 |
| 시스템 조사·작업 계획 | 조사 흐름·근거·후보, 목표 소유권, 보존 조건, 작업·의존성·통합 검증 책임 |
| 실행·검증 기록 | 관련 기준선, 실제 변경, 기술 결정, 실행·재사용·실패·교정·미실행과 원시 결과 위치 |
| 완료 검토 | 고정 대상, 조건별 판정·근거, finding과 책임 작업, 결과와 잔여 |

일반 작업에서는 한 문서의 절로 합쳐도 된다. 다만 검토 대상과 검토 기록, 과거 실패와 후속 교정은 식별 가능해야 한다.
기존 runner·수집·판정 도구를 우선 사용하고, 새 도구는 구체적인 미해결 문제에 필요할 때만 만든다.
작은 수정이나 단계 전환마다 전체 해시·보관본·입력 대조를 반복하지 않는다. 마지막 유효 확인 이후의 실제 변경과
미확인 범위를 기준으로 필요한 확인을 정한다. 다른 writer나 입력을 바꾸는 자동 작업이 없고 자신도 입력을 수정하지 않았다면
시간 경과나 재개만으로 같은 소스를 전수 해시하지 않는다. 외부 변경 징후나 입력 고정 실패가 있으면 영향 범위를 재확인하고,
그 범위를 신뢰할 수 없을 때 전체 대조로 넓힌다. 소스 변경 확인과 보관·복원 무결성 검증을 구분하며,
필수 보관·복원 검증과 별도 감사에서 요구하는 대상 확인은 유지한다.

현재 요약은 탐색 입구이며 원시 근거를 대신하지 않는다. 인계·중단·재개 위치가 바뀔 때 다음 내용을 갱신한다.

```text
현재 요청과 허용 범위 / 종료점:
선택 시스템·흐름 / 선택 작업:
적용 기준과 관련 계약:
현재 기준선·변경 / 사용자 소유 변경:
마지막 유효 결과와 원시 근거:
조사 상태 / 구현 상태 / 검토 상태:
미해결 문제·영향받는 의존성:
다음 행동·필요한 권한 또는 사용자 판단:
```

새 실행을 시작하는 요청 예시는 다음과 같다. 예시 자체는 실행 지시가 아니다.

> 시스템별 리팩토링 실행 지침에 따라 `core_enhanced`의 전체 시스템 지도와 상세 조사 순서를 작성해줘.
> 현재 코드와 관련 계약을 근거로 책임·상태 소유자·공유 경계·미분류 영역을 정리해줘.
> 제품 코드는 수정하지 말고 지도와 첫 상세 조사 대상 제안까지 완료해줘.
