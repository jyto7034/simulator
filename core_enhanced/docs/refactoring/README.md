# Core 리팩토링 목적과 진행 현황

작성·갱신일: 2026-10-18

**현재 코드베이스를 시스템별로 검토하고, 명확한 근거와 기준에 따라 필요한 구조를 개선한다.**
기존의 유효한 동작과 계약을 보존하면서 책임·상태 소유권·의존 관계를 명확하게 하여,
후속 기능을 이해하고 변경하고 검증하는 비용을 줄이는 것이 목적이다.

이 문서는 이번 리팩토링의 출발점이다. 목적과 범위, 현재 진행 위치, 다음 행동을 여기서 확인한다.
상세 기준·절차·실행 근거는 연결된 문서가 소유하며, 이 현황을 별도의 정책이나 완료 증거로 사용하지 않는다.

이번 결론은 **측정 기준 초과와 제품 영향의 구분, 개선 우선순위 결정**이다. 영향이 없다는 보장이나 기존 guard의 통과가 아니다.
기존 수치와 실패는 보존하며 성능 기준 충족만을 위한 추가 계측·최적화를 자동으로 이어가지 않는다.
이후 사용자가 Unity 구현이 구형 기준임을 확인했으므로 S01-C2 조사를 다음 작업에서 제외했다.
이 판단은 앞선 보고서의 S01-C2 후속 제안보다 우선한다. 구형 Unity 코드에 맞추기 위한 Core 변경·호환 계층을 추가하지 않는다.
현재 선정 범위의 완료는 모든 Core 경로·외부 제품·저사양 지원의 검증 완료를 뜻하지 않는다.

## 2 목적과 기대 효과

코드베이스가 크므로 전체를 한 번에 설계·수정하기보다 시스템별 책임과 연결 경계를 확인하며 진행한다.
현재 모든 시스템에 결함이 있다고 가정하지 않고, 조사 결과 유지가 적절한 영역과 개선할 영역을 구분한다.
조사는 동작 오류뿐 아니라 설계 품질도 포함한다. 정상 동작하더라도 책임·소유권·의존성·중복·복잡도·변경 및 검증 비용에
근거 있는 문제가 있으면 개선 후보로 평가한다. 결과에는 동작 오류, 설계 개선 후보, 설명 불일치를 구분해 기록한다.

기대하는 개선은 다음과 같다.

- 같은 상태·규칙의 원본과 변경 책임을 명확하게 한다.
- 하나의 변경을 위해 여러 곳을 수동으로 맞춰야 하는 부담과 누락 위험을 줄인다.
- 생성·취소·종료·실패·복원 흐름을 책임 경계 안에서 이해할 수 있게 한다.
- 실제 계약을 검증하기 쉽게 하고, 구현 세부사항에 불필요하게 결합된 테스트를 줄인다.
- 시스템 사이의 데이터·상태·결과 전달을 추적할 수 있게 한다.
- 이후 작업자가 필요한 코드와 기록부터 읽고 안전하게 작업을 이어갈 수 있게 한다.

성공은 파일 수·줄 수·추상화 수·테스트 수로 판단하지 않는다. 각 개선 작업에서 대표 변경이나 실행 흐름을 정하고,
전후의 소유자·수동 동기화·의존 관계·검증 부담과 필요한 성능 측정으로 효과를 확인한다.

## 3 대상 범위와 보존 조건

### 조사 대상

주 대상은 현재 작업 트리의 `core_enhanced`다.

- `src/**`의 공개 실행 경계, 게임 도메인, 데이터 처리, 제작·검증 도구와 공통 기반.
- 관련 단위·통합 테스트와 실제 fixture·실행 경로.
- manifest·feature·설정 중 실제 구현 선택과 검증에 영향을 주는 부분.
- 현재 정책·기술 계약 중 조사한 동작의 의미를 판단하는 데 필요한 절.

데이터·서버·Unity 등 외부 영역은 실제 생산자·소비자와 계약 영향을 확인하는 데 필요한 범위만 연결한다.
해당 영역의 독립적인 리팩토링이나 제품 수정은 선택 작업의 승인 범위로 포함됐을 때 수행한다.
`docs/goals/**`의 과거 계획·완료 선언을 현재 구조의 근거로 삼지 않는다. 기존 정식 작업과 직접 겹칠 때는
그 작업의 유효한 계약·필수 절차를 확인하되, 과거 finding을 현재 결함으로 자동 계승하지 않는다.

### 보존할 의미

최신 사용자 합의와 유효한 gameplay·runtime·data·외부 계약을 기준으로 다음 중 관련 항목을 보존한다.

- 입력의 허용·거절, 결과와 오류 의미, 상태 변화와 이벤트 순서.
- 상태·사본의 정체성, 소유·수명, 결정론과 저장 후 계속 실행.
- 실제 소비자가 사용하는 공개 인터페이스와 데이터·저장·통신 계약.
- 관련 성능·자원 예산과 기존 사용자 작업.

현재 동작이 확정 계약과 다르면 오류 교정과 동작 보존 리팩토링을 구분한다. 오류를 영구 보존하거나,
리팩토링에 새 정책·기능·밸런스·호환성 변경을 섞지 않는다. 필요한 변경은 기존 승인과 해당 owner 절차에 따른다.

전면 재작성, 모든 폴더·crate의 물리적 분리, 미래 기능용 추상화 구축은 미리 정한 목표가 아니다.
그 필요성이 실제 근거로 확인되면 별도 대안·범위 판단을 거친다.
검증에는 [현재 로드맵의 지원 경로 중심 범위](../roadmaps/core_first/ROADMAP.ko.md#19-검증-범위-제한--외부-임의-변조-방어-제외)를 적용한다.

## 4 진행 방식과 전체 완료 조건

진행 순서는 다음과 같다. 단계별 구체적인 수행·중지·감사 조건은 실행 지침을 따른다.

1. 전체 경계 지도를 작성하고 상세 조사 범위를 정한다.
2. 선택 시스템의 실제 흐름을 조사하여 유지·개선 후보·오류·미확인·후속을 구분한다.
3. 필요한 후보를 책임·의존성·유효한 중간 상태에 맞는 구현 작업으로 설계한다.
4. 승인된 작업을 구현·검증하고, 분리된 완료 검토로 결과를 확인한다.
5. 결과와 변경 영향을 지도에 반영하고 승인 범위의 다음 시스템을 진행한다.
6. 선택된 전체 범위의 시스템 간 연결과 최종 결과를 통합 검토한다.

기본 진행은 단독 순차 방식이다. 시스템 분할은 조사·수정의 경계이며 자동 병렬 위임의 근거가 아니다.
이미 승인된 범위의 내부 판단·일반 교정은 반복 승인 없이 수행하고, 사용자 checkpoint와 필수 독립 검토 조건은 유지한다.

전체 완료는 다음 조건으로 판단한다.

- 조사 대상 시스템과 공유 경계가 지도에 연결되고, 빠진 영역·범위 제외가 설명된다.
- 합의한 조사 범위의 흐름별 결과와 근거가 있고 핵심 경로의 미확인을 조사 완료로 숨기지 않는다.
- 확정 후보마다 유지·구현·기각·보류·후속의 처리와 이유가 있다.
- 선택한 필수 개선 작업은 동작 보존·구조 개선·관련 검증과 완료 검토를 충족한다.
- 후속 변경에 영향받은 선행 결과와 시스템 간 통합 조건이 최종 상태에서 유효하다.
- 남은 비필수 후보·제한과 완료를 막는 미해결을 구분한다. 필수 미완료를 후속으로 옮겨 완료 처리하지 않는다.

조사 완료, 구현·자체 검증 종료, 완료 검토 통과, 전체 범위 완료는 서로 구분한다.
일부 시스템만 끝났다면 그 범위만 완료로 보고하며, 프로젝트에 더 이상 개선 가능성이 없다는 선언을 목표로 삼지 않는다.

## 6 메모와 재개 규칙

중요한 근거·기술 선택·미확인·실패·범위 변화는 확인한 시점에 해당 상세 기록에 짧게 남긴다.
작업 끝에 기억으로 복원하지 않는다. 기록에는 결론뿐 아니라 코드·입력·실행 결과의 위치와 판단 이유를 연결한다.
실패와 이전 판단은 후속 교정·변경 이유와 함께 보존한다.

이 문서의 §1은 선택 작업, 단계 종료, 중지·인계 또는 다음 행동이 바뀔 때 갱신한다.
명령마다 전체 현황을 다시 쓰지 않는다. 상세 기록은 근거를 소유하고, §1은 그 위치와 현재 결론을 안내한다.

재개할 때는 다음 순서로 확인한다.

1. 최신 사용자 요청과 §1의 현재 범위·종료점·다음 행동을 대조한다.
2. 연결된 현재 작업 기록에서 마지막 유효 결과, 실패·미실행·미확인을 확인한다.
3. 관련 소스·데이터·설정·환경과 기존 사용자 변경의 차이를 필요한 범위에서 확인한다.
4. 유효한 조사·검증을 재사용하고, 바뀌거나 부족한 부분만 확인한다.
5. 현재 권한에 맞는 다음 작업을 수행하고 의미 있는 변화와 재개 위치를 기록한다.

진행이 끊길 때는 선택 시스템·작업, 마지막 유효 기준선·결과, 실행 중인 명령의 상태, 미해결 문제,
다음 행동·필요한 판단을 남긴다. 끝나지 않은 실행이나 필수 검토를 완료로 표시하지 않는다.
