# 리팩토링 판단과 실행 기준

작성일: 2026-10-16

리팩토링은 관측 가능한 동작과 유효한 계약을 보존하면서 코드의 책임, 상태 소유권, 의존 관계를 개선하는 작업이다.
이 프로젝트에서는 **현재 코드에서 확인한 구조 문제를, 그 문제를 해결하는 데 필요한 범위에서 고치고,
동작 보존과 구조 개선을 각각 검증한다.** 기능을 당장 추가할 수 있다는 이유로 필요한 개선을 미루지 않으며,
파일 수·줄 수·추상화 수를 맞추기 위한 변경은 하지 않는다.

큰 코드베이스를 시스템별로 조사·개선하는 순서와 인계 방법은
[시스템별 리팩토링 실행 지침](system_refactoring_execution_guide.ko.md)을 따른다.

## 1 적용 범위와 문서 책임

이 문서는 `core_enhanced`의 리팩토링 후보 선정, 우선순위, 변경 범위, 검증과 완료 판단의 공통 기준이다.
관련 데이터·서버·클라이언트는 변경 영향을 확인하는 경계로 다루며, 이 문서만으로 해당 영역의 구현 범위를 확대하지 않는다.
개별 작업의 시작·중지·승인 범위와 정식 구현·감사 절차는 현재 사용자 지시와 해당 실행 절차를 따른다.
기준 문서 작성이나 구조 조사 요청 자체는 제품 리팩토링 실행 승인이 아니다.

| 판단할 내용 | 우선 확인할 근거 |
| --- | --- |
| 의도된 게임 동작 | 최신 사용자 합의, [룰북](game_rulebook.md)과 연결된 상세 규칙 |
| 상태·실행·저장 계약 | [Runtime 계약](core_runtime_contract.md)의 관련 절 |
| 데이터 작성·로딩·검증 계약 | [Data 계약](data_loading_contract.md)의 관련 절 |
| 스킬·타겟팅 계약 | [타겟팅 계약](skill_target_contract.md)의 관련 절 |
| 현재 구현 사실 | 현재 소스, 실제 생산·소비 경로, 사용되는 데이터와 재현 가능한 실행 결과 |
| 검증 범위와 실행 방식 | 현재 승인 범위, [로드맵 검증 범위](roadmaps/core_first/ROADMAP.ko.md#19-검증-범위-제한--외부-임의-변조-방어-제외), [연속 실행 지침](roadmaps/core_first/execution/CONTINUOUS_EXECUTION_INSTRUCTIONS_REVISED.ko.md) |

코드는 현재 동작의 근거이며 정책을 덮어쓰는 근거가 아니다. 문서와 코드가 다르면 정책 미반영, 구현 오류,
문서의 오래된 설명, 미결정 정책 중 무엇인지 확인한다. 과거 감사 결론이나 테스트 통과만으로 현재 구조를 판정하지 않는다.
현재 동작을 기록하는 것과 그 동작을 영구 요구사항으로 승인하는 것도 구분한다.

본 문서는 일반 리팩토링에 아래 감사 기준의 판단 원칙을 적용한다. 전면 감사의 모든 산출물·검사를 작은 변경에
자동 적용하지 않는다. 별도로 승인된 심층 감사의 필수 조건은 해당 감사 기준을 따른다.

## 2 작업 유형을 먼저 구분한다

| 유형 | 판별 기준 | 다루는 방식 |
| --- | --- | --- |
| 동작 보존 리팩토링 | 입력의 허용·거절, 결과, 상태 변화, 순서, 실패 의미와 공개 계약을 유지하며 내부 구조를 바꿈 | 보존할 계약과 구조 개선 목표를 함께 정함 |
| 오류 교정 | 확정된 정책·계약을 위반한 현재 동작을 올바르게 바꿈 | 현재 실패와 올바른 기대값을 증명하고 회귀 검증을 수행함 |
| 불필요한 코드·테스트 정리 | 실제로 사용하지 않거나 다른 경로가 책임을 완전히 대체한 요소를 제거함 | 사용·소비 경로와 제거 후 남는 보장을 확인함 |
| 정책·기능·공개 계약 변경 | 허용 기능, 결과 의미, 저장·통신 형식, 외부 사용법을 바꿈 | 기존 승인에 포함되는지 확인하고 해당 정책·계약 절차로 처리함 |
| 성능 개선 | 관측 동작을 유지하며 실행 시간·메모리·작업량 등을 개선함 | 같은 작업 부하의 전후 측정을 근거로 판단함 |

한 작업에 여러 유형이 필요하면 각각의 목적과 기대 동작을 구분한다. 예를 들어 원자성 오류를 고치면서
commit 책임을 모으는 작업은 오류 교정과 리팩토링을 함께 포함한다. 현재 오류까지 보존하도록 요구하거나,
리팩토링이라는 이름으로 별도 동작 변경을 숨기지 않는다.

정책·계약과 충돌하는 동작은 알려진 차이로 기록하고 승인 범위에 맞게 교정하거나 후속으로 분리한다.
기존 테스트의 기대값이나 snapshot을 현재 구현에 맞춰 자동 갱신하지 않는다.

## 3 리팩토링이 필요한지 판단한다

### 3.1 후보를 확정하는 조건

다음 네 가지를 설명할 수 있으면 구현 후보로 삼는다.

1. **문제:** 어떤 책임·상태·의존·규칙이 잘못 배치되거나 중복되어 있는가?
2. **영향:** 실제 호출 경로나 구체적인 변경 시나리오에서 정확성·변경 용이성·검증 가능성·비용이 어떻게 나빠지는가?
3. **개선:** 어떤 책임을 어디로 옮기거나 통합·제거하면 그 영향이 줄어드는가?
4. **검증:** 기존 동작 보존과 목표 구조의 달성을 무엇으로 확인할 수 있는가?

실제 오류가 발생해야만 리팩토링할 수 있는 것은 아니다. 한 규칙을 바꾸기 위해 여러 소유자에게 같은 수정을
반복해야 하거나, 누락을 compiler와 테스트가 잡지 못하는 상황도 근거가 된다. 이때 막연한 미래 확장 대신
현재 지원 기능이나 승인된 다음 기능의 구체적인 변경 예를 사용한다.

파일·함수 길이, `pub` 필드 수, `clone`·`unwrap`·`match` 수, 중복된 텍스트, 테스트 수, AI 작성 여부는
조사 신호일 뿐이다. 이들만으로 후보를 확정하거나 임의의 숫자를 합격선으로 정하지 않는다.

### 3.2 구조 평가 항목

각 작업에 관련된 항목을 선택한다. 전면 구조 조사는 적용 여부를 전체 항목에서 확인하되,
국소 변경에 모든 항목의 조사를 강제하지 않는다.

| 항목 | 확인할 질문과 문제 근거 | 개선 후 확인할 결과 |
| --- | --- | --- |
| 책임과 도메인 경계 | 하나의 모듈이 독립된 변경 이유를 여러 개 가지는가? 다른 도메인의 내부 사정을 알아야 수정할 수 있는가? | 책임별 변경 경계가 분명하고 불필요한 동시 수정이 줄어듦 |
| 상태 소유권 | 같은 사실을 둘 이상이 독립적으로 변경하는가? 조회용 값이나 캐시가 원본처럼 판정에 사용되는가? | 원본과 변경 주체가 명확하고 파생값의 생성·갱신 규칙이 일관됨 |
| 상태 전이와 수명 | 생성·활성·취소·종료·복원마다 불변조건을 따로 맞추는가? 정상 경로가 모순 상태나 오래된 참조를 남기는가? | 관련 전이가 같은 책임 경계를 거치며 객체 정체성과 정리 의무가 보존됨 |
| 실패와 commit | 검증·변경·이벤트·저장 순서가 분산되어 부분 성공이나 중복 적용을 만드는가? | 계약이 요구하는 원자성·재시도·중복 처리 의미가 한 흐름에서 확인됨 |
| 규칙 중복 | 같은 정책을 여러 validator·handler·mapper가 독립적으로 해석하는가? 한쪽 수정이 다른 쪽에 자동 반영되는가? | 같은 의미의 규칙은 한 곳에서 결정하고 나머지는 결과를 소비함 |
| 의존 방향과 공개 범위 | 도메인이 전송·파일 I/O·상위 orchestration에 불필요하게 의존하는가? 공개 변경 경로가 검증을 우회하는가? | 필요한 경계만 노출하고 금지된 의존·우회를 타입과 가시성으로 줄임 |
| 변경 용이성과 확장성 | 대표 변경이 무관한 계층까지 전파되는가? 새 기능마다 별도 병렬 모델이나 분산 분기가 늘어나는가? | 변경할 표현·수동 동기화 지점·회귀 범위가 줄고 누락을 발견하기 쉬워짐 |
| 데이터와 외부 계약 | 작성 데이터·검증 결과·실행 타입·DTO·저장 상태가 불필요하게 결합되는가? 소비자가 핵심 규칙을 재추론하는가? | 의미를 결정하는 경계와 변환 책임이 분명하며 유효 데이터만 게시됨 |
| 결정론과 저장 후 계속 실행 | 순회·동시 시각·RNG·identity·복원 순서가 관련 없는 변경이나 관측에 흔들리는가? | 동일 입력의 결과·이벤트 순서와 계약상 복원 후 동등성이 유지됨 |
| 오류와 관측 | 로그·진단·export 실패가 게임 상태나 명령 결과를 바꾸는가? 오류 변환이 원인과 복구 의미를 숨기는가? | 권위 있는 처리와 관측이 구분되고 호출자가 실패 의미를 판별할 수 있음 |
| 검증 가능성 | 내부 상태를 비현실적으로 조립해야만 테스트할 수 있는가? 테스트가 구현을 복제하거나 private 구조만 고정하는가? | 실제 계약을 독립적인 기대값으로 검증하고 준비 비용·불필요한 결합을 줄임 |
| 성능과 자원 수명 | hot path의 전체 복사·반복 탐색·직렬화나 장기 실행의 queue·cache 증가가 비용을 키우는가? | 대표 규모와 지원 최대 규모에서 비용·성장·회수 특성을 설명하고 측정할 수 있음 |

도메인 타입과 DTO를 항상 별도 타입으로 만들거나, 모든 상태를 전용 wrapper로 감싸야 한다는 뜻은 아니다.
현재 결합이 실제 변경 위험을 만드는지, 분리 후 변환·동기화 비용이 더 커지는지 함께 비교한다.
읽기 전용 사본·캐시·인덱스도 원본과 갱신 규칙이 명확하면 중복 소유권으로 단정하지 않는다.

### 3.3 유지하거나 보류할 경우

- 겉모양은 비슷하지만 정책·수명·실패 의미가 다른 코드는 억지로 통합하지 않는다.
- 현재 변형이나 승인된 변경 요구가 없는 trait·registry·plugin 체계는 미래 가능성만으로 추가하지 않는다.
- 기존 도메인 연산의 조합으로 표현할 수 있는지 먼저 확인한다. 조합이 실행 순서나 수명을 왜곡하면 별도 책임을 유지한다.
- 파일 분할로 책임·가시성·의존 관계가 개선되지 않고 탐색만 늘어나면 분할하지 않는다.
- 근거가 부족하면 확인할 질문을 남긴다. 낮은 확신을 높은 우선순위나 큰 변경 범위로 보상하지 않는다.
- 조사 결과 현재 구조가 적절하면 유지 판단과 이유를 남긴다. 모든 영역에서 개선 후보를 만들어낼 필요는 없다.

## 4 근거와 우선순위를 분리한다

### 4.1 근거의 수준

| 상태 | 의미 | 처리 |
| --- | --- | --- |
| 확인됨 | 현재 기준선에서 실행 재현 또는 명확한 호출·상태·의존 분석으로 문제와 영향을 증명함 | 범위와 검증을 정해 구현 후보로 평가 |
| 미확인 | 위험 신호는 있지만 실제 발생·변경 영향을 설명할 근거가 부족함 | 필요한 좁은 조사나 보류 사유를 기록 |
| 기각·비적용 | 문제가 성립하지 않거나 현재 지원·승인 범위 밖임 | 이유를 기록하고 구현 목록에서 제외 |

확인된 후보도 실행으로 재현했는지 정적 분석으로 증명했는지 구분한다. 문제를 찾지 못했다는 사실은
전체 구조의 합격 증거가 아니다. 같은 원인이 여러 경로에 나타나면 공통 원인과 영향 경로를 묶고,
소유권·수정 방법이 다르면 겉으로 비슷해도 별도 후보로 둔다.

### 4.2 우선순위를 결정하는 요소

다음 요소에 실제 근거를 붙여 상대 순서를 정한다. 점수의 합계나 평균으로 실행 여부를 자동 결정하지 않는다.

| 요소 | 판단 내용 |
| --- | --- |
| 정확성과 복구 위험 | 정상 경로의 상태 손상·진행 불능·잘못된 결과·저장 실패에 연결되는가? |
| 노출과 확산 범위 | 자주 실행되는가? 여러 기능이 공유하는가? 오류가 조용히 누적되는가? |
| 현재 변경의 필요성 | 승인된 기능이나 교정이 이 구조 때문에 막히거나 우회 구현을 요구하는가? |
| 반복되는 변경 부담 | 같은 의미를 여러 곳에서 수정·검증해야 하는가? 실제 누락이나 회귀 근거가 있는가? |
| 개선 효과 | 권위 중복·수동 동기화·의존·검증 부담·측정 비용 중 무엇이 줄어드는가? |
| 변경 위험과 비용 | 외부 소비자·저장·데이터·전환 비용이 얼마만큼 관련되는가? 작은 단계로 검증하고 되돌릴 수 있는가? |
| 증거와 안전망 | 정책과 현재 경로가 확인됐는가? 필요한 기대값·기존 테스트·측정이 준비됐는가? |

기본 순서는 지원 경로의 중대한 정확성 문제, 현재 작업을 막는 구조 문제, 반복 비용이 확인된 공유 기반,
국소 유지보수 개선 순으로 잡는다. 실제 의존성이 있으면 선행 작업을 먼저 수행한다.
정확성 문제의 우선순위가 높아도 무관한 대규모 재설계까지 함께 승인된 것으로 보지 않는다.

**우선순위와 착수 가능성은 다르다.** 급한 후보라도 계약이나 소비자가 미확인이면 필요한 선행 확인부터 한다.
반대로 쉽다는 이유로 낮은 가치의 정리 작업을 중요한 문제보다 앞세우지 않는다.

## 5 변경 범위와 목표 구조를 정한다

최소 변경 범위는 가장 적은 줄을 고치는 범위가 아니라 **원인을 해결하고 정상 경로를 완결할 수 있는 가장 작은 책임 경계**다.
호출부·검증·파생 상태·정리 경로가 함께 바뀌어야 불변조건이 유지된다면 같은 작업에 포함한다.
인접한 스타일 정리나 독립 기능은 분리한다.

설계 전에 다음을 짧게 적는다.

- 현재 원본 상태·규칙의 소유자, 생산자와 소비자, 변경·실패·종료 경로.
- 목표 소유자와 허용 의존 방향, 없애거나 옮길 경로.
- 보존할 입력·출력·실패·순서·identity·저장·외부 계약 중 이번 변경에 관련된 항목.
- 대표 변경 하나의 전후 비교: 수정할 표현, 수동 동기화, 누락 검출, 회귀 범위.
- 동작 보존의 증거와 구조 개선의 증거, 변경 실패 시 안전하게 중단·복구할 단위.

새 공통 계층은 실제로 같은 정책을 공유하는 호출자가 있거나 승인된 변경에서 필요할 때 도입한다.
계층을 추가하는 대안과 기존 연산 재사용·책임 이동·삭제만으로 해결하는 대안을 비교한다.
단순 변경에는 장문의 대안 보고서 대신 선택 이유 한두 문장이면 충분하다.

### 5.1 제거와 호환성

미사용 판정은 이름 검색만으로 끝내지 않는다. 관련 호출부, 데이터 참조, feature 조합, 생성 코드,
등록 방식과 외부 소비자 중 해당되는 경로를 확인한다. 저장·통신·공개 API는 저장소 내부 검색 결과만으로 제거하지 않는다.

호환성은 현재 유효한 계약과 승인된 변경 범위를 따른다. 출시 전이라는 이유로 형식을 임의 변경하지 않으며,
옛 코드가 있다는 이유만으로 fallback·alias·이중 읽기/쓰기를 새로 추가하지 않는다.
전환 경로가 실제로 필요하면 대상 소비자, 한 시점의 권위 상태, 전환·종료 조건과 검증을 정한다.
관련 정책이 이미 승인됐다면 다시 승인을 요구하지 않는다.

### 5.2 부분 재작성과 전면 재작성

국소 개선으로 문제가 해결되지 않는 경우에만 기존 구조 유지·책임 재배치·부분 재작성을 비교한다.
보존할 동작·알고리즘·데이터·테스트, 전환 경계, 동등성 검증, 중간 상태의 안정성과 복구 가능성을 함께 평가한다.
실패한 대안을 설명하지 않은 채 큰 파일이나 누적 부채를 이유로 전면 재작성을 선택하지 않는다.

전면 재작성은 별도 설계 판단이다. [아키텍처 심층 검토 기준](audit/current_runtime_architecture_deep_review_criteria.ko.md)의
재작성 판단 절차를 적용해 단계적 개선으로 해결하기 어려운 이유와 의미 재발견·전환 위험을 비교한다.
일반 리팩토링 승인에서 전면 재작성으로 자동 확대하지 않는다.

## 6 작업 규모에 맞는 실행 절차

| 작업 규모 | 필요한 준비와 기록 | 검증 범위 |
| --- | --- | --- |
| 국소 변경 | 문제·목표·보존 계약·변경 위치·검증 결과를 기존 작업 기록에 간결하게 작성 | 관련 build·기존 집중 테스트·diff 검토. 필요 없는 새 테스트나 별도 계획 문서를 만들지 않음 |
| 여러 모듈의 소유권·공유 경계 변경 | 생산자→소유자→소비자 흐름, 상태 수명, 영향 경계, 전후 구조와 단계별 완료 조건 | 관련 실패·수명·통합 경로, 영향받는 feature·소비자 및 필요한 성능 검증 |
| subsystem 재설계·공개 계약 전환 | 대안, 보존 자산, 전환·복구 계획, 정책·계약 결정과 통합 수용 조건 | 승인된 전환 범위의 통합 검증 및 해당 공식 실행·감사 절차 |

### 6.1 조사와 착수

1. 요청과 승인 범위, 관련 계약과 현재 코드 상태를 확인한다. 사용자 변경을 보존하고 필요한 경로만 읽는다.
2. 진입점에서 입력 검증→규칙 판단→상태 변경→결과·이벤트→정리·복원까지 해당 흐름을 추적한다.
3. 문제 근거와 작업 유형을 정하고, 유지·국소 개선·더 큰 변경 중 필요한 선택을 한다.
4. 영향 범위, 목표 구조, 보존 조건과 검증을 확정한다. 정책 판단이 필요하면 그 부분과 독립 작업을 구분한다.
5. 변경 전 기준선을 남긴다. commit만으로 dirty 상태를 설명할 수 없으면 관련 diff·입력·필요한 파일 식별 정보를 함께 남긴다.
   기존 실패와 검증 미실행을 구분하고, 유효한 결과는 동일성 또는 비영향 근거로 재사용한다.

조사만 요청받았다면 후보·근거·추천 범위를 정리하고 끝낸다. 구현이 승인됐다면 위 준비 뒤 필요한 변경을 진행한다.
일반 내부 구현 선택·오류 교정·관련 검증마다 새 승인을 요구하지 않는다.

### 6.2 구현과 교정

1. 기존 테스트가 보존 조건을 보호하는지 확인한다. 중요한 공백만 변경 전에 관측 테스트나 재현으로 보강한다.
2. 빌드·검증 가능한 책임 단위로 이동·통합·제거한다. 전환 중 어느 경로가 상태를 결정하는지 명확하게 유지한다.
3. 관련 호출부·테스트·계약 설명을 함께 갱신하고, 변경 영향에 맞는 검사를 실행한다.
4. 예상 밖 차이가 나오면 제품·테스트·fixture·기대값·환경 원인을 구분한다. 실패를 숨기도록 기대값이나 입력 규모를 완화하지 않는다.
5. 원래 문제의 해소와 남은 중복·우회 경로를 검토한다. 범위 밖 문제는 근거와 함께 후속으로 남긴다.

실행 중인 검사의 입력은 고정한다. 관련 변경이 필요하면 자신이 소유한 실행을 종료·정리한 뒤 수정하고 영향받은 검증을 다시 한다.
사용자 변경을 되돌리는 전체 reset·clean이나 무관한 포맷 변경을 수행하지 않는다.

## 7 동작 보존과 개선 효과의 검증

### 7.1 동작 보존

관측 가능한 동작에는 반환값뿐 아니라 상태 변화, 허용·거절 조건, 오류 의미, 이벤트 순서, RNG·identity,
저장·복원 후 계속 실행과 실제 소비자가 받는 형식이 포함된다. 이 중 변경이 영향을 줄 수 있는 항목을 골라 검증한다.

- 가능한 한 실제 생산·소비 경로나 공개 진입점에서 결과를 확인한다. 작은 단위 테스트는 핵심 규칙을 빠르게 검증하는 데 사용한다.
- 기대값은 확정 계약·수작업 예·독립 계산에서 도출한다. 제품 알고리즘을 테스트 안에 복제하지 않는다.
- 현재 동작을 기록하는 테스트는 전후 동등성에 유용하지만, 그 동작의 정책 적합성까지 자동 증명하지 않는다.
- 실패 검증은 해당 거절 지점까지 실제로 도달했는지, 오류 종류와 실패 후 상태가 계약을 만족하는지 확인한다.
- 저장 관련 변경은 직렬화 왕복뿐 아니라 복원 후 다음 행동을 확인한다. 순서 관련 변경은 비교 전에 정렬해서 차이를 숨기지 않는다.
- 내부 fixture는 지원 경로로 도달 가능한 상태를 효율적으로 준비할 때 사용한다. private 상태 조립만 통과한 것을 공개 경로 검증으로 표기하지 않는다.

현재 로드맵의 외부 임의 변조 제외 원칙을 적용한다. 정상 플레이·지원 제작 입력·지원 명령·실제 저장 및 장애 경로에서
발생 가능한 오류는 확인하되, 비공개 상태나 저장 파일을 임의 변조해야만 생기는 사례를 새 방어 코드·필수 시험·완료 차단으로 만들지 않는다.
발생 경로가 미확인이면 실제 결함이나 변조 전용으로 단정하지 않는다. 기존 필수 수용 조건의 미검증을 이 이유로 면제하지 않는다.

### 7.2 테스트 정리와 실행 범위

기존 테스트를 제거·병합할 때는 그 테스트의 고유한 보장과 대체 검증을 확인한다.
성공 경로 테스트도 고유 계약을 보호하면 유지하며, 내부 구조를 고정하거나 더 강한 테스트와 중복된다면 정리할 수 있다.
테스트 수 감소나 전체 통과 수 자체를 개선 지표로 삼지 않는다.

국소 변경은 집중 검사부터 수행한다. 공유 기반·공개 계약·저장 경계를 바꾸거나 예상 밖 회귀가 생겨 영향이 불확실하면
관련 통합·전체 검사로 넓힌다. 필수 검사는 수행하되 동일 입력에 대한 전체 검사를 문서 정리·단계 전환만으로 반복하지 않는다.
실행한 검사, 재사용한 결과, 필수 미실행과 제외 사유를 구분하고 0시험·skip·환경 실패를 기능 통과로 기록하지 않는다.

### 7.3 구조 개선

테스트 통과와 별도로 최초 문제를 다시 대입한다.

- 목표 소유자만 해당 상태·규칙을 결정하며 우회·중복 경로가 제거됐는가?
- 대표 변경에서 수동 동기화·불필요한 의존·회귀 범위가 줄었는가?
- 잘못된 호출·누락을 타입·가시성·검증 경계가 이전보다 잘 드러내는가?
- 추가한 추상화·변환·캐시의 비용을 감안해도 이해·수정·검증이 쉬워졌는가?

전후 호출 경로, 상태 소유자 표, 실제 수정 지점이나 간단한 변경 예로 확인한다.
줄 수가 줄거나 파일이 작아진 것만으로 구조 개선 완료를 주장하지 않는다.

### 7.4 성능과 자원

hot path·자료구조·복사·캐시·직렬화·장기 수명을 바꾸면 대표 작업 부하와 관련 최대 규모를 정해 전후를 비교한다.
입력·seed·build profile·도구·환경·관측 지점을 맞추고 시간, 필요한 지연 분포, 메모리, 작업량, 유지 상태·payload 중 관련 항목을 측정한다.
내부 카운터를 실제 CPU 시간이나 메모리 사용량으로 대신하지 않는다.

기본 목표는 실제 사용에서 의미 있는 성능 부담과 퇴행을 방지하는 것이다. **수치 기준 초과만으로 제품 결함이나 필수 최적화로 판정하지 않는다.**
기준의 설정 근거와 실제 요구를 확인하고, 목표 PC·실제 호출 빈도·동시 실행 수·대표/최대 규모에서의 절대 시간과 메모리,
전체 처리 비용에서의 비중, 사용자 응답·프레임·처리량·장기 자원 증가에 미치는 영향을 함께 판단한다.
묶음 벤치마크의 wall time을 한 프레임 지연으로, 내부 비용 비중을 그 자체로 심각성으로 해석하지 않는다.

측정값·기준 초과 여부와 제품 영향·개선 우선순위를 구분해 기록한다. 영향이 작으면 유지 또는 낮은 우선순위로 종료할 수 있으며,
영향이 미확인이면 결함으로 확정하지 않고 판단에 필요한 최소 근거만 확인한다. 예상 절감량과 구현 복잡도·회귀 위험을 비교해
개선 가치가 있는 후보를 선택한다. 기준 통과만을 위한 세부 계측·최적화·반복 검증을 이어가지 않는다.
실제 소비자 제한이나 명시된 응답 요구 위반은 별도로 확인한다. 기존 guard 결과와 측정 이력은 보존하며,
기준 변경이 필요하면 요구 근거와 변경 이유를 남기고 과거 실패를 통과로 바꾸지 않는다.

측정 변동과 비교 조건을 먼저 확인하고 단일 측정이나 근거 없는 일률적 비율로 개선·비퇴행을 주장하지 않는다.
성능 영향이 없는 변경에 벤치마크를 의무화하지 않으며, 성능 개선을 주장할 때는 실제 비교 결과를 제시한다.

## 8 착수와 완료 체크리스트

### 착수 전

- [ ] 현재 코드의 문제와 영향이 근거로 확인됐다.
- [ ] 리팩토링·오류 교정·정리·정책 변경의 구분과 승인 범위가 명확하다.
- [ ] 목표 소유권·책임 경계와 보존할 계약을 설명할 수 있다.
- [ ] 실제 소비자·상태 수명·실패 경로 중 영향받는 부분을 확인했다.
- [ ] 현재 기준선, 필요한 검증과 기존 실패·미확인을 식별했다.

### 완료 전

- [ ] 최초 문제의 원인이 해소됐고 구조 개선의 전후 근거가 있다.
- [ ] 보존 대상 동작·공개 계약과 승인된 교정 사항을 각각 확인했다.
- [ ] 관련 검증이 최종 변경에 유효하며 필수 미실행·실패가 숨겨져 있지 않다.
- [ ] 관련 소비자·데이터·저장·feature 경계와 필요한 성능 검증을 확인했다.
- [ ] 불필요한 이중 경로·임시 adapter·이전 책임이 남지 않았거나, 승인된 전환 종료 조건이 있다.
- [ ] 관련 설명이 실제 구현과 일치하고 무관한 변경·사용자 작업 손실이 없다.
- [ ] 후속 문제와 남은 제한을 구분했으며 해당 작업의 필수 검토·감사 조건을 충족했다.

비적용 항목은 이유를 짧게 적는다. 완료 조건 자체가 미검증인 경우에는 후속 작업으로 옮겨 완료 처리하지 않는다.
반대로 이번 작업과 독립적인 새 개선 후보를 발견했다는 이유만으로 완료 범위를 계속 늘리지 않는다.

## 9 작업 기록 양식

다음 내용을 기존 작업 기록에 포함한다. 단순 변경은 몇 문장으로 합쳐도 되며, 항목마다 새 파일을 만들지 않는다.

```text
대상과 기준선:
문제·근거·발생/변경 시나리오:
작업 유형과 승인 범위:
현재 소유자·생산자·소비자 → 목표 구조:
보존할 동작·계약 / 승인된 동작 변경:
우선순위 근거와 선행 확인:
변경 범위·순서 / 제외·후속 항목:
검증 계획과 구조 개선의 판정 방법:
실제 변경·검증 결과·재사용 근거:
완료 판단과 남은 제한:
```

예를 들어 “큰 모듈을 여러 파일로 나눈다”만으로는 부족하다. “같은 자격 규칙을 세 경로가 별도로 판단해
변경 누락이 가능하다. 기존 결과·오류·순서를 보존하면서 한 도메인 연산으로 모으고, 세 소비 경로의 대조 입력과
호출 관계로 확인한다”처럼 문제·개선·검증이 연결되어야 한다. 이 예시는 판단 방식이며 현재 코드의 확정 finding은 아니다.
