1. ### Proposed minimal scenario/session surface

A finite recipe can use only `Command`, `Snapshot`, `Clock`, and finite `Assert` operations, with bounded JSON-pointer copies from earlier public response/snapshot documents into a command/context template. Explicit scalar/object/array literals and explicitly enumerated binding entries suffice. A scenario can choose candidate indices or explicitly named authored IDs itself. No loops, arbitrary script evaluator, filesystem expressions, content-name switch, hidden selecting-first behavior, or auto-play decision policy is needed. Exact type names are proposals.

Each step has a unique recipe-local step ID, a bounded prior-step source pointer and destination pointer, and an expected result/state assertion where necessary. Reject missing pointer, wrong type, future/cyclic reference, duplicate binding conflict, unexpected state/result, unknown operation, oversized expansion, and budget excess before publishing candidate success. Retain both recipe and resolved commands/contexts. Generic recipe bindings do not grant authority; CoreApplication still validates each result-derived value.

Alternative: one shared library public candidate-session owner driven by bounded JSONL CLI requests. The caller sees snapshots/results and submits ordinary explicit commands using observed values, and the host records the transcript. The same transcript can then be replayed as a finite batch. This avoids a selector DSL but requires explicit candidate lifetime, cumulative quotas, and final preparation assertion. A one-shot CLI with a finite binding recipe is easier for repeatable acceptance. Both are technically feasible; neither must automatically navigate arbitrary content successfully. Changed B that does not fit the requested recipe returns a real preparation failure while preserving A.

The actual prepare boundary should require a returned/setup-identified live battle under B after ConfirmEnterNode, checked through public reconnect/snapshot, rather than merely command Ok or NodeConfirm. Already-terminal time-zero scenarios need an explicit supported outcome classification if allowed; do not let a battle that never existed count as preparation. Nonzero execution is a separate required test: observed battle time/event/effect execution after public clock advancement, not merely N clock-call attempts.

## 2. Clock, transaction, result, readonly observation

`world/application.rs:172–216` validates live context, clones the entire GameCore, performs the operation on draft, validates draft, then infallibly installs state/run_seed/game_data and publishes. Thus normal application errors roll back draft state, token, UuidManager/RNG-owned state, and battle state together. `ActiveBattleSession` owns execution, BattleCore, revision, employee attempt, deployment/resource/playback remainder/focus (state.rs:507–527). The general root clone applies to active battle too; do not confuse it with cfg(test) non-battle rollback helpers (state.rs:163–190).

Clock modes have different semantics:

- Direct elapsed `advance_active_battle_by(delta,cursor)` → combat.rs:1420–1568 → kernel `step_battle_execution_by` uses saturating time addition (sim.rs:87–89,1655–1661). It directly advances simulation and does not pass through playback pause/speed or the host blocking-VN guard.
- Host tick `advance_active_battle_for_host_tick(raw,cursor)` → combat.rs:1585–1616 suppresses progress for blocking VN; state.rs:816–829 applies pause, speed ratio, and accumulated fractional remainder, returning None for no simulation delta.
- Next-event-bucket clock advances to the next scheduled bucket (combat.rs:1619–1638); its cursor is chosen internally from the history floor. It can jump arbitrarily far in simulation time and is not equivalent to a fixed host tick.

For the minimum authoring host, explicitly select a clock mode in the receipt. Host tick most closely exercises ordinary pause/speed behavior. Direct elapsed is legitimate explicit simulation input but must be described as such. Count actual time/events and distinguish attempted tick, None/no progress, Running, Finished, and Err. Repeated empty/paused ticks can exhaust a finite input budget without any battle execution.

`combat.rs:1460–1568` advances, finalizes real result, builds BattleAdvanced, then transitions finished battle. `combat.rs:1347–1406` retains result stats/outcome/policies and drops active_battle. The event_log copy into CombatBattleState is **test/debug/test-fixtures only** (1380–1381); debug JSON trace export is likewise gated (1398–1402), non-authoritative, and serde-skips skill source. Neither is an R03 default-release semantic trace solution.

### Required additive readonly seam

Introduce an authoring-owned readonly projection of the existing in-memory source-bearing outcomes plus cast/occurrence/source metadata. Capture the final advance's observation before `active_battle=None`, within the same draft/commit boundary, or carry a bounded owned authoring observation out with the operation. A bounded last-completed observation is an alternative only if its lifetime/eviction are explicit. Returning private BattleCore/GameCore, enabling fixture cfg, removing existing `serde(skip)` and changing gameplay wire/save DTOs, or relying on post-finish reconnect are unsuitable shortcuts.

The observer is `&self` when queried; it must not call mutating gameplay commands, consume UUID/RNG, increment battle revision, or rebuild a trial behind Explain. API/CLI export the same authored address/source data and semantic fields from this projection. Separate private Arc source metadata from owned public DTOs so retained user receipts do not pin a whole ContentGeneration.

Output commit detail: `execute_application` treats publication after commit as infallible (application.rs:152–161). If R03 serializes an oversized receipt only after CoreApplication has committed, it cannot retroactively report that gameplay was rejected. Either build/validate the bounded operation envelope in the draft before commit, or report committed gameplay plus a separate explicit observation/output error. A must remain unaffected for B preparation failures. Avoid returning Err that implies rollback after a commit.

Trace collection must be observational. Prefer always-maintained bounded provenance/window with the trace flag controlling projection/export, and explicit completeness/gap metadata. Trace-buffer exhaustion or export I/O failure must not silently alter gameplay or RNG. If a full trace is unavailable, return an explicit observation limitation/error and never label it complete; do not silently truncate or pretend a missing parent/event was observed. Root must express this consistent with E03/E06 in its proposed contract.

## 3. Existing source semantics and actual occurrence identity

`ability/authoring.rs:10–55` supplies ActionSite(definition_id,action_id), EffectSite(action,effect_id), EffectSource(file/site/field/origin-definition/origin), and source Arc reconstructed during compilation. Tags are attribution, not execution authority. The narrow editable support currently shown by 157–180 is Damage/Heal Instant; do not treat that descriptor as proof that all existing runtime effect kinds are unimplemented.

`skill_source.rs:8–29` supplies cast source skill_id/caster_instance_id/cast_seq plus ability_event_seq, cause, proc-origin(event_seq,activation_source,binding_index); effect source pairs authored Arc with cast Arc. `sim.rs:437–493` allocates cast_seq from a battle-local counter (wrapping_add), records AbilityCast, installs ActiveSkillCast, and schedules SkillStep with cast sequence. `sim.rs:1985–2079` lowers authored effects to per-target SkillCommands. `commands.rs:477–501` temporarily records a paired source around each lowered command; `recording.rs:13–35` clones that source into each resulting event and updates result statistics before bounded log retention.

The source context is real; log rows are outcomes, not a complete list of authored evaluations. Damage amount 0 emits no command (sim.rs:2024–2026); no target can emit no per-target effect; some operations have other paths (ModifyTacticalResource at 2093). Multiple log outcomes may arise from one command. A trace built from retained events must call itself observed outcomes and cannot infer skipped/rejected/no-op evaluations from absence. To explain all attempted applications, instrument actual evaluation/application boundaries separately and explicitly; do not manufacture them by parsing text logs.

Delayed ownership is also real: projectile and area snapshots retain cast-source Arc (projectile.rs:730–733,area.rs:486–489) and use it when processing commands on impact/tick (projectile.rs:881–905,area.rs:670–689). Active casts are cleaned only once deferred steps/areas are empty and steps terminal (cast.rs:61–76). Delivery objects and retained log rows can outlive removal of active cast state. A projection must follow these retained sources rather than looking up only current active casts or the newest loaded generation.

**What is already semantic:** DamageSourceSnapshot has CombatRollIdentity(roll kind, source unit, target unit, source_instance UUID,hit_index), and ProcRollIdentity has occurrence UUID/index plus trigger/binding/caster/target (damage.rs:38–138). damage_runtime.rs:358–423 derives source identity independently of log order and uses it to derive critical rolls. commands.rs:136–162 derives proc occurrences independently of event-log ordering; sim.rs:300–361 uses occurrence identity plus actual proc gate state. These identities affect gameplay RNG; project them unchanged if retained, never replace them with a new trace counter. Current SkillProcOrigin drops the richer ProcRollIdentity; retaining it is an additive observation delta.

**What is missing:** `cast_seq + EffectSite + target + timestamp` is not unique per application. `sim.rs:2291–2333` can repeat the same instant action against the same target at the same timestamp. Current SkillEffectExecutionSource carries no repeat/delivery/tick/application discriminator. HpChanged does not contain the damage roll identity (event_log.rs:1052–1073), and Heal has no equivalent damage roll identity. CastSeq and damage-source counters wrap; they are battle-local implementation identities, not durable global IDs.

Proposed identity shape: battle identity + actual cast identity + authored site + actual application qualification. Retain existing damage/proc occurrence fields as correlation when applicable. For instant effects, pass repeat index and lowered effect/target application position from the actual executor; for delayed effects retain delivery UUID or area UUID plus actual impact/tick/application qualification. Alternatively add a checked, battle-local observation-only effect-application ordinal allocated at `process_skill_commands`' actual command boundary, independently of log writes and even when trace export is off; record its precise meaning as a lowered command application, not an authored action, hit-chain node, or future R06 event. One application may own multiple outcome rows. Exhaustion must be explicit, never wrap into a duplicate identity. This is an internal source/observation design choice for root to assess; it must not enter RNG keys, target selection, execution order, cooldown, gameplay trigger chains, or persistent save semantics.

For minimum R03 correctness it is preferable to name exactly which semantic occurrence the DTO identifies rather than claim an all-effects causal graph. Real causes currently include log parent references; keep those separately as log correlation with explicit retained/missing-parent state. R06 chain/event gameplay should not be invented here.

## 4. Candidate reload, lifetime, cancellation and saving

`execute_with_generation` (application.rs:836–848/world.rs:291–303) only swaps validated generation through an eligible StartNewGame draft. That is the correct R02 atomicity and must remain intact. It commits after pre-run briefing succeeds; later starter/map/actual combat setup may fail. Therefore using this on A and then trying preparation cannot meet E05.

Proposed aggregate owner: one committed TrialSession A, at most one candidate B, each containing its own opaque token, explicit seed/player/initial-authority input, CoreApplication, finite recipe/transcript, observation cursor/window, and receipt/result. Build B from fresh explicit initial authority and loaded B token; execute all required public preparation; validate actual B battle assertion; complete bounded initial receipt; atomically replace the entire A aggregate with B. All attempts, diagnostic buffers, errors, and cancellation state before that swap belong to B/attempt output. In particular, do not append failed B attempts into A's receipt when E05 requires that receipt unchanged.

On bad B load, valid load followed by failed VN/starter/battle setup, missing binding, exhaustion, explicit cancel, or stale candidate handle: drop candidate/attempt-owned memory and retain A exactly. Repeated failed attempts must preserve A continuation semantics, not only A's visible snapshot. Candidate preparation is synchronous in the minimum design; cancel can be observed before/after finite calls unless new cooperative checks exist. Do not claim interruption inside a synchronous call without an implementation. If interactive candidates are supported, use one pending candidate and explicit candidate identity so a late result cannot replace a different A; no background tasks are needed for the minimal batch design.

Live battle lifetime is already process-local: combat.rs:1686–1688 says so. Durable active-run export (active_run.rs:207–222) exports the existing completed RunCheckpointPayload, not live battle execution. V6 contains checkpoint+hash (27–47); continue validates and restores it via a draft (229–277). RunCheckpointPayload binds content identity and selected run/roster/inventory/UUID state (state.rs:381–437), not SkillEffectExecutionSource or the active battle. The new authoring trial is likewise disposable process-local execution; store/replay input and receipt as an explicit artifact, not as a new midbattle gameplay save or token persistence mechanism. Replaying reconstructs B through public commands under exact content identity. No personal profile/store file is read, reset, migrated or written by this minimal design. If root instead plans imported private profiles, resume-after-process-loss or durable active battle, those are additional observable lifetime/compatibility choices that require separate source/policy assessment.

Reclamation: dropping B/A frees owned runtime collections; Arc refs delay freeing database/source objects until remaining owners drop. Token holds ContentGeneration; BattleCore holds a database Arc; effect source retains only authored/cast metadata Arcs. Bound host-held generations and receipts, avoid an unbounded generation cache/history. Returning owned DTO values avoids handing arbitrary long-lived internal generation pins to receipt consumers. Prove reclamation using narrow test-only Weak probes inside owning data/runtime modules and/or meaningful allocation observations; public ValidatedGameData intentionally exposes no strong-count or underlying Arc capability.

## 5. Bounds, retention, measurement and known limits

Current external input limits exist: schema.rs:157–176 defaults to 128 packs,4096 files,8 MiB/file,64 MiB total,4096 dependency edges, nesting128. Snapshot validates limit shape and checks reads/nesting (snapshot.rs:69–74,221,336,363–397). These are loader bounds, not a bound on generated gameplay work, a command JSON request, or an accumulated session transcript.

Current event retention is 8192 events,4 MiB compact serialized entries,180000 ms span (event_log.rs:41–44). Caps evict old rows and advance floor cursor (616–643). Arc-backed entries are copy-on-write on draft mutation (76–102). Cursor validation distinguishes future versus evicted-history gap (485–500). A reconnect request can report SnapshotResyncRequired and a current window (state.rs:1170–1208); ordinary command/clock validation can Err on old cursor (1211–1231). Polling after each call can still miss more than one window's events produced within a single call. A correct trace exposes requested/floor/latest range and completeness; event-log sequence closure is also not a gameplay budget.

The serialized history cap **explicitly excludes** skill_effect_source allocations (event_log.rs:751–756). New encoded public source rows, strings, application qualification, source tables, receipt arrays, and host generations need independent byte/count accounting. Retained rows are count-bounded but do not establish a measured whole-process heap bound. GameCore draft cloning also allocates runtime state; a raw event-log byte counter alone misses this workload.

The critical runtime gap: `BattleExecutionState` has no fuel field (sim.rs:60–89). `step_battle_execution_with_post_spawn_setup` drains/sorts/processes a whole same-time bucket then repeatedly drains newly queued same-time events (1820–1897). `step_until` repeatedly calls buckets until time target (1906–1948). Neither includes an event/command/work-budget or cancellation check. Large finite delta plus nested effects/procs can cost arbitrarily more than one host step; a same-time generated cycle can prevent return. Proc cooldown/count gates are optional per authored binding (sim.rs:316–361), not a general operation budget. Shell timeout only protects a spawned CLI process and does not give the library a safe in-process cancellation contract or preserve that process's A. Detached worker threads are not safe interruption.

Proposed scoped safety work: explicit validated authoring request/session limits for input bytes/nesting/string lengths/step count/binding count+expanded document size, per-call and cumulative clock requests, actual executed work, observation rows/source bytes/receipt bytes, and one committed+one pending generation. Checked arithmetic; reject zero/unbounded malformed limit values. Apply operation fuel/cancel checks inside the **existing application draft**, starting with event dequeue/same-time requeue, command/effect/target dispatch and setup work that the selected public preparation calls can expand; exhaustion returns a typed authoring failure before root commit. Meter allocations/enqueue/expansion before unbounded collection growth where practical, not solely after a huge bucket is built. Do not just insert a check between host steps and label it safe. Leave existing ordinary gameplay behavior unchanged unless an existing approved policy explicitly owns the change.

Precise fuel coverage and numeric defaults are **not measured by this helper** and must be settled in implementation/readiness with source-backed workload runs; no R03 host limit should be advertised as complete R23 safety. A cooperative budget still does not prove protection against allocator abort, stack overflow in unmetered recursion, arbitrary OS I/O delay or every future opcode. These are bounded implementation/measurement obligations, not a claim that all future safety work must be done now. If existing public preparation necessarily hits unmetered loops, fix/cover that direct route before claiming the bounded authoring host is safe; do not route around it through a private fixture.

Measurement seams: public_guards.rs uses Instant per public call, state snapshots around rejection, and optional global allocator tracking with baseline/peak/end/live and alloc/dealloc/realloc counts (1–55,124–167,388–442). Existing input setup there uses embedded fixture and named starters (280–288), so reuse the **measurement method**, not that workload as independent external-RON acceptance. final_performance.rs has event count/serialized bytes/ability-step/projectile/effect counts plus environment/source/workload identity receipt fields (228–238,255–267), but those are previous fixture tooling, not new measured R03 limits.

Useful R03 measurements are load; candidate public preparation including time-zero bucket; actual nonzero clock+effects; readonly Explain/query; late/invalid command rejection with dense retained history; B failed preparation; successful A→B replacement; cancellation/drop; serialization with and without trace. Report actual sample counts, elapsed values, positive executed work, source/feature/toolchain/workload hashes, retained source/receipt bytes, and peak/end allocation delta while observer is enabled. Keep allocation-disabled zeros explicitly N/A. Do not gate gameplay on nondeterministic wall-clock timing; use deterministic work fuel and report time as observational evidence.
