## Recommendation and technical limit

A request-local, crate-private execution scope installed by the authoring owner before generated validation is the smallest plausible delivery path in the current synchronous source. Its fuel, first failure, cancellation flag, and attempt counters must live outside `GameCore`/`BattleCore` value snapshots. A scoped thread-local implementation can reach existing infallible and `&self` helpers without threading arguments through every preview/runtime type. Explicitly shared operation handles are also sound if all clones share the same live operation accounting; a copied value budget is unsound at observed rollback sites.

This is a recommendation, not an implementation or a completeness claim. Sticky failure alone is insufficient: leaf loops must stop promptly, variable allocations must be admitted before growth, mandatory fallible boundaries must poll after void helpers and before every success/commit, and callers which rely on complete identities or `expect` invariants require fallible propagation or an admitted bounded indivisible block. Returning arbitrary fake IDs or partially constructed objects is not a valid general cancellation technique.

Neither fuel nor bounded input counts by themselves establish a measured wall-time or allocator-byte limit. The actual movement backend includes external Rapier calls with no local cancellation hook. Source-sized preflight plus pre/post-call polls and measurement are needed for these indivisible calls. This scoped R03 design does not claim broad R23 safety.

## TLS versus fields

**Scoped TLS option.** A crate-private authoring `run_with_control` owns a fresh attempt state and an RAII installation guard. Ordinary calls outside a scope see no active control and retain present semantics. A small `charge(kind, count)`/`poll()` helper borrows the TLS state only for the accounting operation, uses checked arithmetic, latches the first failure, and returns immediately. Cancellation can be represented by an externally signallable atomic flag; checking it is cooperative. TLS guard destruction restores previous state on normal return, `?`, and unwinding. Do not use panics as budget cancellation or promise restoration under process abort.

Nested internal operations must join the existing scope. A nested top-level authoring scope must either be rejected before candidate mutation or explicitly share it; it must never reset fuel, clear poison, or install an independent budget inside an ongoing request. A single `RefCell` borrow must not span a runtime callback or recursively invoked helper. The operation owner must unconditionally inspect sticky failure even when the underlying function returns a domain error, a default, or `Ok(Rejected)`. This is what prevents cancellation from being reported as an authored-content error.

The TLS option does not put control into saves, validated generations, `BattleExecutionState`, event ordering, RNG identity, or observer authority. Future async suspension/thread migration would require explicit propagation or a revised owner; an OS-thread TLS scope cannot transparently follow a future. Ambient same-thread reentry is a real tradeoff: the entry API should prevent unrelated public reentry while the authoring operation runs, or document shared-scope semantics. Merely accepting nested independent guards would bypass a request limit.

**Explicit field/argument option.** Pass a shared handle from authoring load/setup through validation and preview generation, into the constructor before startup, and attach/join it on every operation on an existing battle. An `Arc`/interior-state handle shared by clones avoids refund, whereas copied `remaining_fuel`/`failed` fields do not. Every early error/drop must detach the operation lifetime, and successful outer installation must not retain a finished attempt's handle. A new GameCore field would also need explicit lifecycle because prepared commit currently enumerates only state/run_seed/game_data/output. Storing the handle only in BattleCore misses preview generation and initial constructor work. Storing it only in BattleExecutionState misses direct commands and constructor work. Fields make ownership/thread propagation explicit but require many signatures/constructors and careful clone/save/debug treatment. This is larger than TLS for the currently synchronous route.

**Observed rollback evidence that selects shared accounting.** `execute_spawn_request` (S20:465–522) clones the complete BattleCore after reservation; mutation `Err(GameError)` becomes a `SpawnRejection::MutationFailed`, `*self = before` restores the core, and the method returns `Ok(Rejected)`. `run_boss_runtime_boundary` (S21:1762–1798) builds a staged clone and installs it only at success. `commit_summon_batch` (S22:270–470) also clones and restores at several failure paths. Operation fuel is attempted work and must remain consumed through all these rollbacks. Failure must stay latched through their error conversion and success exits. The existing boss microstep limit is domain-local per boundary; it is not a complete operation limit and need not be replaced.

### Queue interception alternative

All observed production heap push families are in sim, commands, basic_attack, basic_attack_projectile, boss_runtime, field_work, skill_runtime/{area,cast,projectile}, summon_runtime, tactical_stance, wave_runtime, plus core/mod auto scheduling. A private guarded heap wrapper can intercept `push` while preserving `peek/pop/iter/clear/clone` and debug `into_vec` behavior. Do not expose `DerefMut` or an unguarded mutable inner heap, or the bound is bypassable. This can be smaller than changing every push signature, but does not charge event payload construction or target/command lowering before the push. A rejected infallible push must latch failure, refuse growth, and be followed promptly by a poll; it must not merely drop an event and allow a successful candidate.

A pending-heap limit, a bounded bucket transfer, and cumulative work limit cover different resources. Draining the heap into an unbounded Vec before checking the bucket defeats a queue-only cap. A full queue that admits another identical-time event after each pop can run forever without a cumulative limit. A dequeue counter also misses a single large expansion. These are actual loop structures, not hypothetical new gameplay.

## Sticky failure: safe and unsafe boundaries

1. **Safe pattern in existing void/summary helpers:** charge before growth/work; on failure stop that local loop; restore any temporarily replaced recording context; return a structurally harmless disposable partial result; caller immediately polls before using that result to run another loop, allocate, finalize, or return success. The outer `process_event` wrapper is an especially small choke point: check before field-work settlement, after it, after the inner result, and after successful reconcile. A final unconditional operation check still remains necessary.
2. **Unsafe pattern:** infallible helper silently returns an arbitrary fake entity/sequence/complete constructor result and relies on the authoring facade to notice later. Callers can dereference missing records, make dependent allocations or hit invariants before reaching that facade. Entity-producing helpers already returning Result should propagate a controlled error. For `record_event_log -> u64`, preflight the log admission within an already fallible/event context or ensure an immediate abort boundary; do not advertise `u64::MAX` as a new successful occurrence ID. Existing sequence exhaustion behavior is separate.
3. **Actual `expect` hazard:** `generate_current_floor_map` returns a tuple (S06:286–324) and calls fallible certified power and `FacilityMapGenerator::generate_with_requirements` using `expect`. It is traversed by starter selection at S04:818 and next-floor transitions at S06:732/947. If new inner helpers return control errors, these `expect`s become panics before an outer sticky check. Either make the traversed wrappers return Result and update their real callers, or keep the entire admitted bounded block internally invariant-preserving and poll immediately after it. Merely inserting `?` deep inside a helper is not enough. The infallible CombatPreview convenience wrappers also contain expects; the actual loader path observed uses the try-generation API, so those convenience wrappers are not claimed as traversed here.
4. **Observed hidden success/normalization:** spawn rejection returns Ok; loader maps domain errors to content diagnostics; command/movement/area/projectile helpers return default/void; empty queue and target-time branches return Running/Finished; boss staged success installs a clone. All must preserve and check the same sticky state. Domain failure before cancellation should retain its own error unless the adopted operation error precedence explicitly chooses first observed scope failure; do not accidentally turn resource rejection into invalid authored data.
5. **Context restoration:** recording cause and source-command wrappers run a closure, then truncate/pop (S28:48–93). Returning from inside that closure preserves normal cleanup. New early exits inside manual `take/replace` sections (`process_skill_commands` S16:477–509; proc origin S16:535–576) must restore the prior value before returning. Panic cancellation would skip these manual restores and is unsuitable.
6. **Commit and cancellation race:** check failure/cancel after bounded trace/output serialization and immediately before the infallible session installation. Define that acceptance point as the operation completion linearization. A flag set after acceptance cannot retrospectively turn an installed result into Err. If the public cancellation contract requires stronger race semantics, it needs an owner handshake; a lone final atomic load cannot guarantee that. This is a concrete synchronization detail for GEX, not a request for new policy.

## Candidate/session lifetime

For create/new trial, the owner holds A unchanged while acquiring/validating B, creating B's seed/player state, running finite generic public steps, actually preparing B including time zero, and building B's observer/receipt. All B substeps join one attempt budget, or an explicit cumulative parent budget if sublimits exist. On any failure/cancel/trace overflow, discard B. A's generation, application, active battle, revision/RNG, input bindings and receipt remain untouched; failed B diagnostics may be returned separately but must not be appended to A's successful receipt.

For an operation on an existing session, perform public command/clock work on a disposable candidate of that session. World-level command atomicity is necessary but not sufficient, because receipt/provenance/output construction can fail after the current core facade has committed. Candidate serialization and all bounds checks occur before the outer swap. The execution scope is attempt-local, not session-local, saved, replayed, or shared with a read-only observer. A completed scope must never survive into an idle session. Any observer projection remains read-only and receives no BattleCore injection authority.

## Concrete validation oracles (proposed; no execution claimed)

- Budget absent and permissive-budget executions use the same external pack, seed/player and resolved public scenario; compare canonical command outcomes, battle/event/result state, RNG-sensitive outcomes and semantic source identities. No new fixture/private authority is required for positive default-release parity.
- Tiny injected allowance at generated-case expansion, constructor admission, startup enqueue and first time-zero drain causes a controlled bounded failure before B acceptance. An already running A must remain equal in full owner state/token/input/receipt and continue identically after the failure.
- Fail during one SkillStep's many repeats/effects/targets with a permissive event count: the inner work counter must stop it. Zero-result repeats and stale/no-op events must still consume work.
- Fail with heap count below the cap but with large same-time bucket or repeated refill; verify the bucket/cumulative controls close those distinct paths. Admission rejection must not publish a battle with silently missing events.
- Fail/cancel in spawn mutation after the first member, in summon staged execution, and in boss staged iteration; outer attempt failure survives rollback/Ok(Rejected), consumed fuel does not increase, and no successful tool session is installed.
- Fail inside an infallible area/projectile/movement/command helper; verify immediate caller detection and restored source/proc/cause contexts. Exercise `generate_current_floor_map` control failure without panic, including starter and next-floor callers actually reachable by the chosen generic scenario.
- A failed operation followed by a normal operation on the same thread must see no stale TLS failure. Nested operation attempts cannot reset or bypass fuel. A second independent thread cannot inherit the first thread's scope; thread-moving execution is unsupported until propagation exists.
- Terminal battle capture and bounded serialization fail before swap, including deliberate trace-count/byte overflow; A remains complete. This specifically tests the failure-after-inner-core-commit gap.
- Measure accepted work at loader cases, generated scenarios, zero-time events, per-event effects/targets/commands, deferred/queue/entity retention, movement unit/obstacle counts, and pre/post external calls. Record elapsed time and peak retained sizes for real workload cases. Fuel units/weights and numerical maxima need those measurements; do not infer CPU deadlines, memory-byte guarantees, or comprehensive R23 safety from count instrumentation.

## Remaining implementation-owned work and limits of this read

The inspected families establish the required delivery/atomicity model and concrete pitfalls. They do not constitute an exhaustive new formal source review of every gameplay opcode or an implementation-ready proof of work bounds. GEX must close the call/charge inventory across all currently enabled opcodes, generation internals, target/path/geometry helpers, retained-history collections, and serialization before claiming acceptance. Queue-family matches outside the deeper reads are explicitly marked as search-only in the JSON. No third-party Rapier internals, allocator/OOM behavior, or numerical interruption latency were audited. Where a helper cannot stop without violating invariants, use fallible propagation or measured bounded admission; do not treat a sticky flag as magic interruption.

No material policy ambiguity is asserted here. The concrete choice still owned by root/GEX is how to encode the same existing bounded-request requirement: scoped TLS with controlled reentry versus explicit shared handle plumbing, and the measured weights/limits plus narrow Result changes needed by the selected approach.
