# Experiment Notes

- This master goal is for confirmed follow-up policies only. Do not reopen settled policy choices unless runtime code or data reveals a new required decision.
- The first subgoal is intentionally small so easy contract cleanup can land before large battle runtime changes.
- `BattlefieldLayout` extraction should happen before lifecycle work because it removes the competing dynamic tile-position source.
- Lifecycle, redeploy, inactive effect resolution, and event/snapshot contracts are separate goals because each can change gameplay-visible behavior and test scope.
- If a subgoal finishes by producing a policy-decision report, record that in this master goal and stop the master run for user discussion.
- A subgoal being "complete" is not enough for the master to proceed. The master must run a review pass using `docs/goal_completion_review_guide.md` immediately after each subgoal and fix in-scope gaps before continuing.
- The review pass must check whether the implementation follows the long-term direction and whether code inspection reveals a better source-of-truth design than the one originally planned.
- `core_snapshot_error_contract_cleanup` review verdict: complete / high fit. Snapshot root shape is core-owned through generic `RunSnapshotDto`; server only enriches selected event. Static obstacle blocking now uses `StaticObstacleBlocked` / `static_obstacle_blocked`, while `PositionOccupied` remains for actual occupied board slots.
- Policy coverage is not assumed complete just because a policy is recorded. If code inspection reveals missing edge cases or an ambiguous gameplay/contract boundary, the master goal must complete with a policy-decision report instead of stretching the existing policy or burying the issue as an ordinary follow-up.
- `core_battlefield_layout_extraction` review verdict: complete / high fit. `BattlefieldLayout` is static-only, dynamic tile position APIs were removed without wrappers, and live deployment/checkpoint/event tile positions now derive from `RuntimeUnit.body`. Lifecycle work must revisit active/inactive filtering for retained units.
- Master run stops at `core_runtime_unit_lifecycle` with a policy-decision report. The issue is not whether lifecycle is desired; it is how official event-log contracts should represent withdrawal-caused buff expiration and cast cancellation.
- Withdrawal cleanup event policy is now confirmed: add explicit withdrawn buff-expire reasons and a `SkillCastCancelled` event with `SkillCastCancelReason::Withdrawn`; do not overload `SkillCastInterrupted`.
- `core_runtime_unit_lifecycle` review verdict: complete / high fit. `RuntimeUnitLifecycle` is the active/dead/withdrawn source of truth, withdrawal keeps old runtime units in the registry while excluding them from gameplay, active/pending withdrawal cast cleanup is represented by `SkillCastCancelled`, and official checkpoint `units` filters Active only.
- `core_runtime_unit_lifecycle` remaining work is intentionally deferred to later subgoals: redeploy HP/new instance policy, inactive projectile/delayed-effect resolution, `UnitWithdrawn`/`UnitDied` position fields, and debug/admin inactive visibility.
- Master run stopped at `core_redeploy_lifecycle_policy` with a policy-decision report. The issue was not new instance identity or withdraw HP; it was the old updated-trauma death HP wording. That wording is superseded by the fixed 60% death redeploy HP policy below.
- User resolved the `core_redeploy_lifecycle_policy` death HP question by simplifying death redeploy HP to 60% of the new runtime unit's max HP. Persistent trauma/injury remains post-battle-only, so implementation can resume without live consequence timing changes.
- `core_redeploy_lifecycle_policy` review verdict: complete / high fit. Redeploy HP policy is stored in live redeploy locks and applied by BattleCore after the new runtime unit's final max HP is known, before spawn/deploy event logging. Old inactive units remain in `BattleCore.units`; active deployment state points to the new instance.
- Master run stops at `core_inactive_unit_effect_resolution` with a policy-decision report. The issue is how already locked/scheduled effects should resolve against withdrawn targets across damage, non-damage effects, redeploy HP lock updates, and post-withdraw old-runtime death.
- User resolved the `core_inactive_unit_effect_resolution` policy by choosing strong withdrawal evasion for incoming hostile projectiles. Because the attacker is the opponent, projectiles flying toward the withdrawing unit should cancel/miss instead of damaging old runtime HP or reducing redeploy HP.
- Follow-up clarification: withdrawal should be understood primarily as an evasion/escape action. A hostile projectile already flying toward the unit being withdrawn is cancelled/missed by the target becoming `Withdrawn`; this is not a generic projectile-registry cleanup.
- `core_inactive_unit_effect_resolution` implementation keeps projectile cleanup local to normal advance/impact resolution. This preserves projectile/event ordering and avoids making withdrawal mutate the whole projectile registry as a hidden source of truth.
- `core_lifecycle_event_snapshot_contract` review verdict: complete / high fit for lifecycle event and checkpoint contracts. `UnitWithdrawn`/`UnitDied` carry body-derived positions, checkpoint units remain Active-only, and inactive retained runtime units are exposed only through a debug/replay query.
- Parallel full `cargo test` can race on battle record/debug JSON artifacts; serial full validation passed. Treat this as a test artifact isolation follow-up, not a gameplay contract blocker.
- Final cross-subgoal audit verdict: complete. No competing source of truth was found across static layout, runtime body position, lifecycle, redeploy HP policy, inactive projectile resolution, and lifecycle event/checkpoint contracts.
- Final code evidence: battle layout is static-only; lifecycle gates active participation; withdraw/death event positions derive from retained runtime body; checkpoint units are Active-only; hostile projectiles against withdrawn targets resolve as miss/no-hit without global projectile cleanup.
- Final remaining risks are follow-up-only: optional typed server/admin inactive-unit transport, parallel debug artifact isolation, and external Unity/event-log schema adoption for version 27.
