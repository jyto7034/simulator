## Current Structure

- `src/game/ability.rs:113` defines `SkillTarget` as `SelfUnit`, `EnemySingle`, and `CastTarget`. The `CastTarget` comment explicitly says range filtering belongs to `SkillStepDef.defense_tile_range` plus delivery hit filter (`src/game/ability.rs:119`).
- `DeliveryDef` supports `Instant`, `Projectile`, and `TileArea` (`src/game/ability.rs:153`). Projectile delivery has two policies: target-locked homing and directional collision (`src/game/ability.rs:128`, `src/game/ability.rs:157`).
- `SkillTileAreaDeliveryDef` documents `SkillStepDef.defense_tile_range` as the single source of truth for presentation, cast range, target candidates, and actual hit tiles in DefenseRoute (`src/game/ability.rs:328`).
- `SkillCastTargetingDef::FirstStepTarget` is the default backward-compatible cast target mode (`src/game/ability.rs:492`). `SkillDef::cast_target_definition` derives the cast target from the first step unless an explicit cast target is provided (`src/game/ability.rs:599`).
- Live RON uses `SkillDatabase.range_presets` and `defense_tile_range_preset`; the loader resolves presets into concrete `TileRangePattern` before runtime (`src/game/data/skill_data.rs:182`, `src/game/data/skill_data.rs:268`, `src/game/data/skill_data.rs:299`).
- Loader validation rejects invalid range patterns, `WholeFieldValidTiles` combined with `defense_tile_range`, target-locked projectile directional stop fields, invalid directional projectile endpoint policies, `TileArea` without range source, and dangling impact-context anchors (`src/game/data/skill_data.rs:350`, `src/game/data/skill_data.rs:432`).
- Runtime target selection for `EnemySingle` flows through `resolve_skill_cast_target`, `resolve_skill_target_definition`, and `choose_skill_target_by_rule` (`src/game/battle/core/sim.rs:631`, `src/game/battle/core/sim.rs:654`, `src/game/battle/core/skill_runtime/cast.rs:277`).
- Tile-based target membership is centralized in `is_target_in_tile_range_policy` (`src/game/battle/core/targeting.rs:88`). For `WholeFieldValidTiles`, it uses `Battlefield::in_bounds`, which includes `valid_tiles` filtering and therefore excludes void tiles (`src/game/battle/battlefield/field.rs:44`).
- Range preview DTOs are generated by `src/game/range_preview.rs`. `WholeFieldValidTiles` previews use `battlefield.valid_positions()` and pattern previews filter through `battlefield.in_bounds` (`src/game/range_preview.rs:112`, `src/game/range_preview.rs:273`, `src/game/range_preview.rs:298`).
- Manual active skill preview separates self-target effect cells, manual tile cast cells, and auto unit skills that require runtime target (`src/game/range_preview.rs:180`).
- Manual skill activation revalidates explicit targets in runtime before starting focus/cast (`src/game/battle/core/sim.rs:332`, `src/game/battle/core/sim.rs:552`).
- `TileArea` runtime computes affected tiles from `TileRangePattern.affected_tiles` and then filters units by hit target policy, not by a geometric shape (`src/game/battle/core/skill_runtime/area.rs:231`, `src/game/battle/core/skill_runtime/area.rs:382`, `src/game/battle/core/skill_runtime/area.rs:544`).
- Directional skill projectiles compute a fixed endpoint from facing plus `max_range_tiles`/`max_lifetime_ms` (`src/game/battle/core/skill_runtime/projectile.rs:95`, `src/game/battle/core/skill_runtime/projectile.rs:715`).
- `skill_catalog` exposes static skill metadata but sets `range_source_of_truth` to `range_previews.final_cells` (`src/game/world/snapshot.rs:231`, `src/game/world/snapshot.rs:304`).

## Source Of Truth Judgment

- Internal DefenseRoute skill range source of truth is the resolved `TileRangePattern` on `SkillStepDef.defense_tile_range`, or `TileRangePolicy::WholeFieldValidTiles` when explicitly set.
- RON preset ids are authoring convenience only. Runtime code, preview DTOs, and Unity-facing contracts consume the resolved pattern, not the preset id.
- Unity-facing overlay source of truth is final `range_previews` cells and runtime `SkillAreaDeclared.affected_tiles`, not `skill_catalog.defense_tile_range`, `range_units`, or local Unity reconstruction.
- `SkillTarget` is target/anchor policy, not range policy.
- `DeliveryDef::TileArea` is delivery/hit filter/persistence policy, not a second area shape source.
- `range_units` is no longer official DefenseRoute basic attack or skill target eligibility. It remains serialized for catalog/static display and future explicit continuous-space mechanics.
- `Battlefield::in_bounds` currently means "valid playable tile inside the battlefield", not only rectangular bounds. This is semantically correct for range filtering but easy to misread.
- Directional skill projectile endpoint source is currently `max_range_tiles`/`max_lifetime_ms`, not `TileRangePolicy` or `defense_tile_range`.

## Refactor Candidates

### 1. `SkillCastTargetingDef::FirstStepTarget` backward-compatible default를 명시 정책으로 정리

근거:

- `FirstStepTarget` is documented as a backward-compatible default (`src/game/ability.rs:494`).
- `SkillDef.cast_targeting` defaults to that mode (`src/game/ability.rs:552`), and `cast_target_definition` derives cast-level target data from the first step (`src/game/ability.rs:608`).
- `RawSkillCastTargetingDef` preserves the same default in live RON loading (`src/game/data/skill_data.rs:236`).
- `docs/skill_target_contract.md` now separates `cast_targeting`, `target`, `targeting`, and `defense_tile_range`.

판단:

- This is a real compatibility/default layer, but live RON still heavily relies on omitted `cast_targeting`.
- Immediate removal would be a live RON schema migration and content rewrite, not a small refactor.
- Refactor candidate: add an audit/migration step that makes official live skills with non-trivial multi-step or manual targeting use explicit `cast_targeting`, then decide whether `FirstStepTarget` remains only for tests/simple skills or is removed.

정책 영향:

- Making `cast_targeting` explicit/required in live RON and removing the backward-compatible default: `사용자와 정책 논의 필요`.

필요 검증:

- Live RON load succeeds with explicit cast target definitions.
- Manual skill activation, auto target selection, `RetargetOnStep`, and Unity skill catalog output remain behaviorally identical after migration.

### 2. `range_units`를 DefenseRoute 스킬 eligibility에서 더 강하게 격리

근거:

- `range_units` is still serialized on cast target and steps (`src/game/ability.rs:499`, `src/game/ability.rs:517`) and exposed in `skill_catalog` (`src/game/world/snapshot.rs:239`, `src/game/world/snapshot.rs:278`).
- `resolve_skill_target_definition` passes `range_units` to `choose_skill_target_by_rule` (`src/game/battle/core/sim.rs:638`), but the parameter is currently `_range_units` and ignored by the target chooser (`src/game/battle/core/skill_runtime/cast.rs:277`).
- Policy docs say official DefenseRoute `RetargetOnStep` uses `target`, `defense_tile_range`, and `air_capable`, while `range_units` is for future contagion/contact/aura/continuous mechanics.

판단:

- This is not a current gameplay source-of-truth bug; tests already prove skill and basic attack target eligibility do not fall back to large `range_units`.
- It is still a naming/API clarity risk because static catalog and RON carry a value that official DefenseRoute range logic ignores.
- Refactor candidate: rename internal parameters to `legacy_or_continuous_range_units` or split catalog/display data from eligibility data; add comments near `choose_skill_target_by_rule` that DefenseRoute tile eligibility must not use it.
- Do not delete `range_units` globally; movement/approach and future continuous mechanics still have legitimate uses.

정책 영향:

- Removing `range_units` from skill RON or Unity skill catalog would change schema/DTO shape: `사용자와 정책 논의 필요`.

필요 검증:

- `skill_enemy_single_uses_tile_range_not_range_units`.
- Skill catalog tests ensure `range_source_of_truth` remains `range_previews.final_cells`.

### 3. Range preview와 runtime tile range 해석의 공용 helper 추출

근거:

- `range_preview.rs` has its own `resolved_valid_cells_for_policy` and `resolved_valid_cells` helpers (`src/game/range_preview.rs:273`, `src/game/range_preview.rs:298`).
- Runtime single-target membership uses `is_target_in_tile_range_policy` (`src/game/battle/core/targeting.rs:88`).
- Manual explicit tile target validation checks `battlefield.in_bounds(position)` directly (`src/game/battle/core/sim.rs:364`).
- `Battlefield::in_bounds` excludes void tiles, but the name makes it easy to confuse with rectangular bounds only (`src/game/battle/battlefield/field.rs:44`).

판단:

- Current behavior appears aligned: preview and runtime both exclude void/invalid tiles and include obstacle/blocked tiles.
- Refactor candidate: introduce a small shared helper or clearer method name such as `is_valid_tile_for_range`/`contains_valid_tile`, and have preview, explicit cast tile validation, and single-target policy call it.
- Keep obstacle exclusion out of this helper; docs explicitly say range overlay is not walkability.

필요 검증:

- Pattern preview clips out-of-field and void tiles.
- `WholeFieldValidTiles` preview returns `valid_positions()`.
- Manual `CastTarget` tile activation rejects void/out-of-field tiles and accepts obstacle tiles if they are valid tiles.

### 4. `TileArea` affected tile filtering should explicitly document valid-tile assumptions

근거:

- `TileArea` runtime calls `tile_range.affected_tiles` and records/uses the result directly (`src/game/battle/core/skill_runtime/area.rs:231`, `src/game/battle/core/skill_runtime/area.rs:382`, `src/game/battle/core/skill_runtime/area.rs:544`).
- Cast target and preview paths already constrain manual tile targets and preview cells to valid battlefield tiles.
- `docs/skill_target_contract.md` says range preview excludes invalid/void tiles, and runtime `SkillAreaDeclared.affected_tiles` is the Unity effect tile source.

판단:

- For `tile_origin: Caster` and normal cast target flows, affected tiles are anchored from valid caster/target tiles and presentation preview is clipped.
- However the runtime `SkillAreaDeclared` event can include affected tiles outside valid battlefield if the authored pattern projects beyond the battlefield. That may be intended for visual shape continuity or may violate the "actual affected tiles" wording.
- Refactor candidate: decide whether `TileArea` runtime affected tiles should be clipped to `battlefield.in_bounds` before event/target collection, matching preview final cells, or whether out-of-field affected tiles are allowed only as presentation shape.

정책 영향:

- Clipping or preserving out-of-field/void `SkillAreaDeclared.affected_tiles` can change Unity telegraph/effect visuals: `사용자와 정책 논의 필요`.

필요 검증:

- TileArea near map edge has deterministic affected tile event shape.
- Targets on void/out-of-field tiles cannot be hit.
- Unity-facing `SkillAreaDeclared.shape.affected_tiles` expectation is fixed in tests.

### 5. Directional skill projectile endpoint policy vs existing tile range composition

근거:

- Directional projectiles have independent endpoint fields: `max_range_tiles`, `max_lifetime_ms`, `max_kills`, `max_pierces`, collision max hits (`src/game/ability.rs:157`, `src/game/data/skill_data.rs:463`).
- Runtime endpoint is facing vector times distance from `max_range_tiles`/`max_lifetime_ms` (`src/game/battle/core/skill_runtime/projectile.rs:95`, `src/game/battle/core/skill_runtime/projectile.rs:778`).
- Current live skill RON mainly uses target-locked projectiles and `TileArea`; directional projectile examples are mostly test contracts in `tests/skill_refactor_validation.rs`.
- The user specifically called out simplifying "map-end piercing projectile" by using existing range/void clipping rather than special void-tile death logic.

판단:

- Directional projectile is not safe to delete now because tests cover conditional projectile follow-up, fixed collision, and targetless line-shot behavior.
- It is a composition review candidate: if future official "line projectile until map/void end" can be expressed as `TileRangePolicy::WholeFieldValidTiles` or a long `TileRangePattern` plus existing valid-tile clipping, then `max_range_tiles` should not become a second source of map reach.
- Refactor candidate: classify directional projectile as explicit continuous collision mechanic. For tile-based DefenseRoute line skills, prefer `TileArea`/`TileRangePattern` unless continuous projectile collision is truly needed.

정책 영향:

- Whether official long line/piercing skills should use directional projectile collision or tile-range-driven `TileArea`: `사용자와 정책 논의 필요`.

필요 검증:

- Existing directional projectile tests continue to pass if kept.
- New official line skill should have one source of reach: either tile pattern/valid tile clipping or continuous projectile endpoint, not both.

### 6. Skill catalog metadata와 live range preview 계약 고정

근거:

- `SkillCatalogDto` includes `range_source_of_truth` and static authoring metadata (`src/game/behavior.rs:756`, `src/game/world/snapshot.rs:304`).
- Unity docs say skill catalog can be used for names/focus/target policy, but overlay source is `battle_update.checkpoint.units[*].range_previews` (`/mnt/f/unity projects/ark/docs/unity_core_contract.md:1996`).
- `tests/live_skill_catalog_audit.rs` is strict about live skill coverage but does not directly assert that catalog metadata is not used as overlay source by clients.

판단:

- Core side is already well aligned: final cells are produced in range preview DTOs and catalog marks the source.
- Refactor candidate: keep `range_source_of_truth` as a stable DTO guard, and in component 15 verify server/Unity readers never recompute overlay from catalog metadata.
- Do not remove catalog `defense_tile_range` only to prevent misuse; it is useful static metadata. Misuse should be prevented by client read model/tests.

필요 검증:

- `tests/live_skill_catalog_audit.rs`.
- Unity/client contract tests should parse checkpoint/pending `range_previews` final cells and avoid fallback reconstruction.

## Existing Composition Simplification Candidates

- Repeated live skill ranges are already composed through `SkillDatabase.range_presets` and resolved at load time. Keep this authoring convenience; runtime should not see preset ids.
- `WholeFieldValidTiles` is the right existing composition for boss/special whole-field target candidates. Do not add "sniper route-less" or "boss full range" special cases.
- Official DefenseRoute AoE is already `TileArea` plus `defense_tile_range`, not geometric AoE. Keep this composition and avoid reintroducing circle/line/box shape variants.
- Range preview already returns final cells. Unity should not combine skill catalog, weapon profile, effective basic attack, and local fallback to recalculate overlays.
- Target usefulness filtering is shared across auto hostile target selection and TileArea usefulness gates; keep it as a target eligibility layer, not a range layer.

## Legacy, Fallback, Compatibility Removal Candidates

- `SkillCastTargetingDef::FirstStepTarget` is explicitly backward-compatible. It is the main compatibility removal candidate, but removing it requires live RON migration.
- `range_units` on official DefenseRoute skills is a legacy-looking field for eligibility. It should remain only where a real continuous mechanic needs it; otherwise it should not influence target/range behavior.
- `DeliveryDef::Instant` live skills with spatial-looking names are guarded by `tests/live_skill_catalog_audit.rs`; newly added live skills should not silently remain instant if they need projectile/TileArea behavior.
- Geometric `DeliveryDef::Area` style is already removed per `docs/skill_target_contract.md`; do not add adapter/fallback tests for it.
- Basic attack fallback range is valid only for missing employee weapon/profile range. It is not a live corroded employee profile fallback and should not be reimplemented in Unity.

## Deferred Or Not Doing

- Do not refactor basic attack target profiles here; component 8 covers basic attack/projectile/judgement.
- Do not refactor damage/effect command application here; component 9 covers damage/stats and component 10 covers buffs/status effects.
- Do not change Unity DTO shape in this audit; component 15 covers server/Unity-facing contract surface.
- Do not delete directional projectile runtime in this audit because tests cover it and policy has not decided its official live scope.
- Do not remove `range_units` globally; existing docs already preserve it for movement/approach and future continuous mechanisms.
