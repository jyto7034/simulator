## Objective

Make the production gameplay RON bundle an exact-version, canonical, all-or-nothing input validated
before play. Remove permissive aliases, first-match duplicates, unsupported/runtime-panic variants,
late cross-reference failures, and partial bundle acceptance. Establish one reusable bundle-validation
authority that later domain goals extend instead of adding independent lenient loaders.

## User-Visible Problem

Current strictness documentation promises stronger guarantees than the runtime has proven. Invalid
or ambiguous generated content may be accepted until a later lookup, may select the first duplicate,
may retain an old alias, or may reach an unsupported Event reward/map/stage branch during gameplay.
That can turn an authoring error into a nondeterministic or crashing player flow instead of rejecting
the bundle before the run starts.

## Accepted Contract

- Gameplay RON is generated by a dedicated authoring program; human-edit convenience does not
  justify permissive runtime parsing.
- A bundle declares one exact supported schema version and uses only canonical field names and enum
  variants.
- Unknown, removed, aliased, duplicate, missing-required, unsupported, out-of-range, inconsistent,
  and cross-reference-invalid data is rejected before play.
- Duplicate canonical IDs are errors. No first-match or last-match winner is allowed.
- Defaults exist only for intentionally optional gameplay meaning and never conceal missing
  generator output.
- The entire production bundle validates before publication/use. A failed domain or reference does
  not leave a partially usable bundle.
- The authoring program validates before export and Core independently validates again. Prefer a
  shared schema/validator authority where the current repository structure permits it without
  inventing an unrequested external tool.
- Diagnostics identify source file, domain, object ID when available, field/reference path, and
  cause.
- Save-data migration is separate and does not authorize lenient gameplay-RON parsing.

## Source Of Truth And Ownership

- Core's production loader and typed validators own runtime acceptance.
- Typed gameplay schema owns the canonical serialized RON shape.
- One completed immutable bundle/index publication boundary owns all-or-nothing availability.
- The future authoring program consumes or reproduces the same canonical schema/validation contract;
  G12 must not create a second drifting policy table merely to simulate that program.
- game_server consumes a successfully constructed Core bundle and does not reinterpret content
  validity.
- Later domain goals add their new schema and semantic validators to this shared boundary.

## Invariants

- No gameplay command can observe a bundle that failed any schema, domain, or cross-reference check.
- Every accepted ID is unique in its canonical domain and every required reference resolves to the
  correct target kind.
- Every supported run mode has the required RunStart definition/trigger cardinality and policy before
  a run begins.
- Unsupported or runtime-panic Event reward/effect variants are rejected at load time unless current
  source review proves they are live-supported and fully implemented.
- Extra-wave, stage, mission, and map-event references are validated through the final production
  bundle, not only inside isolated fixtures.
- Diagnostics are deterministic and carry enough source context to repair generated output.
- No alias, fallback, silent default, duplicate winner, or partial-bundle publication remains after
  cutover.

## First Revalidated Production Boundary

Revalidated on 2026-07-13:

- game_server startup calls only `GameDataBase::load_live_embedded()`. Core documents and runtime
  agree that this compile-time embedded loader is the single production live-data entry point.
- `load_live_embedded()` independently deserializes 18 embedded domain files with
  `ron::de::from_str(...).expect(...)`, builds through `GameDataBuilder`, then runs one generated
  combat-preview validation after construction.
- `GameDataBase::new()` already centralizes domain index validation, cross-domain reference checks,
  cross-item UUID validation, Shop item validation, starter loadout validation, and final immutable
  database construction. This is the strongest existing all-or-nothing seam and should be evolved,
  not bypassed with a second loader.
- No bundle or per-file schema version is visible at the production entry point. Parse errors name
  the file only through a panic `expect`; semantic validators predominantly panic/assert and do not
  carry a typed file/domain/object/path diagnostic.
- Database/index construction already rejects many duplicate IDs by panic. G12 must inventory every
  domain before concluding duplicate coverage is complete and must replace first-match gaps without
  adding a parallel registry.
- The worktree has extensive user/G01/G06/G07/Event edits, including `src/game/data/mod.rs`,
  `event_data.rs`, `validation.rs`, and live Event RON. Preserve all unrelated semantics and use
  scoped patches/diffs.
- There are 23 production gameplay RON files under `game_resources/data`. Nineteen are reached by
  `GameDataBase::load_live_embedded()` including `RunPolicyData::builtin()`. Four map/battlefield
  files are loaded independently and lazily by `MapGenerationPolicyData::builtin()`,
  `MapNodeDefinitionDatabase::builtin()`, and two combat-preview `OnceLock` databases. Their domain
  ownership may remain separate, but the final startup validation seam must initialize and
  cross-check the exact same objects before returning production data.
- The only explicit serde aliases found in current gameplay source are legacy `DamageType` spellings
  (`physical/ad/Ad`, `magic/ap/Ap`, `true`). Live RON uses canonical variants, so removal requires no
  live content compatibility.
- Shop pools and general reward pools are linear first-match lookups and their validators do not
  reject duplicate pool IDs. Equipment reward pools do reject duplicates separately. This is a
  confirmed first-match gap.
- Event scene/immediate/staged `RewardEffect` values are not passed through the existing reward
  reference validator. `ApplyBossOmenStepResult` is accepted in both Event effect enums and panics at
  execution; live Event RON contains neither variant. The accepted master policy already directs
  removal unless concrete live policy exists.
- RunStart validation rejects duplicate modes but does not require exactly one trigger for each
  supported `GameMode::{Standard, Endless}` or validate its required repeat/checkpoint/blocking
  policy.
- The production main loader now parses all 23 sources through the versioned source set and runs the
  four domain-owned map/battlefield local validators before constructing `GameDataBase`. The old 18
  independent `from_str(...).expect` assembly and separate production `RunPolicyData::builtin()`
  call are removed.
- Map generation and combat preview now consume the exact parsed `GameplayMapCatalogs` stored in
  `GameDataBase`. The four old production `builtin()` readers and all map/combat-preview
  `include_str!` calls are removed. Fixture builders use the same four-source parser through one
  test-only cached catalog, not an alternate schema or runtime loader.
- Final catalog validation now requires exactly one `RunStart` trigger for both supported modes,
  `Standard` and `Endless`, and requires each trigger to be blocking, `OncePerRun`, and
  `PersistAcrossCheckpointLoad`. Missing or policy-mismatched generated data is rejected before
  publication with source/object/path context.
- Shop general pools, Reward general pools, and equipment reward pools now share duplicate/empty-ID
  validation before their existing first-match lookup APIs can be observed. Focused negative tests
  prove duplicate Shop and Reward pool IDs reject rather than selecting a winner.
- Reward records and Event scene/immediate/staged grants now call one fallible `RewardEffect`
  reference/value validator before publication. Invalid embedded Event rewards identify the Event
  source, Event ID, exact nested effect path, and cause instead of reaching a later gameplay lookup.
- Every explicitly authored map payload reference now resolves before publication: Event,
  encounter, Headquarters/regular Shop pool, concrete Shop, and Reward pool. Existing `None` values
  retain their authored random-selection meaning and are not replaced with fallback IDs.
- Run-policy stage `extra_waves` now share the encounter-wave authoring and reference validators.
  Empty/duplicate/colliding IDs, zero counts/budgets, invalid route requirements, unsupported
  FacilityEntity entries, and missing abnormality/corroded-preset/profile references reject before
  publication with the exact stage/wave path.
- Startup generated-combat validation now covers every encounter at the representative first floor
  of every scaling stage across five deterministic seeds. Later-stage wave/template route,
  spawn-zone, mission, and briefing-warning combinations can no longer hide behind floor-0-only
  validation.
- The official production loader now returns `Result<Arc<GameDataBase>, LiveRonError>` for strict
  parse and final catalog failures. game_server maps this to an `InvalidData` startup error and does
  not bind the HTTP server; no fallback bundle is published. Existing domain/index assertions still
  require conversion before the typed boundary is complete.
- Every top-level authored catalog ID and indexed UUID is now checked for emptiness/uniqueness before
  index construction, and Equipment/Artifact/Consumable item UUIDs are checked across registries.
  Duplicate keys report their exact source/object/path instead of invoking first/last-winner or
  `ItemRegistry` panic behavior.
- Strict generated-field migration has begun with Consumable `rarity` and `live_pool`: both are now
  required authored fields, current live data is already canonical, and omission rejects rather than
  silently selecting ZAYIN/not-live defaults. Remaining serde defaults still require classification.
- Core-only generated Shop stock/pools, Reward pools/filter/entries, run-policy extra waves, and
  BossOmen optional references are also presence-required. A shared required-Option deserializer
  forces generated data to emit `Some` or `None`, because plain Serde Option fields otherwise accept
  omission implicitly.
- Domain semantic validation now has a reusable structured error shape. Consumable bounds/tier/
