# S2 accounting and storage contract

The existing native budget is the safety authority. Observation reads accepted work/clone/admission totals at the existing budget teardown and takes accounted retained extent from the already-required reconciliation calculation. It adds no retained-owner walk. Extent is an accounting model, cumulative admission is accepted reservation traffic (including the initial retained seed), and neither is a per-battle RSS measurement. An attempted operation can consume work and reach peaks before returning an error or discarding its draft. The outer observer retains those values outside rollback; the actual public return determines one outcome/reason. The current usage and commit counter advance only when the original live GameCore root is published. Nested draft publication cannot publish observation gauges. A prepared operation detaches thread-local capture before returning and reports once on consuming commit or drop. Its duration ends at detachment, so time spent by the host holding the prepared object or performing persistence I/O is not counted as Core execution time.

`runtime-observation` is optional and non-default in Core and host. With the feature disabled all observation hooks compile away; with no attached observer no wall clock or channel operation is performed. An observed CoreApplication owns one non-cloneable lease. Forks start without an observer. Registration uses `try_lock`; contention skips attachment and counts a registration drop. Core operations use atomics and a bounded channel `try_send`, with no wait for collector/export/scrape. The channel implementation may briefly synchronize internally; this is not a hard-real-time or lock-free claim.

## Finite metric vocabulary

69 operation labels (59 command variants and 10 explicit public mutation routes);4 outcome labels (accepted, rejected, read_only, discarded);63 reason labels (30 native fault codes,29 reviewed domain codes,4 public-boundary errors). These labels are generated/registered before collection. No UUID, player/session ID, skill ID, reason text, input path or content field becomes a metric label. Unknown errors use the finite public fallback; errors themselves retain their existing public details.

| core_runtime_rejections_total{reason} | Returned public rejection exactly once, including discarded draft work only if an actual public error was returned |
| core_runtime_commits_total | Actual observed root publication |
| core_runtime_operation_seconds{operation} | Monotonic wall duration histogram of collected attempts |
| core_runtime_work / core_runtime_clone_slots / core_runtime_admitted_bytes{operation} | Accepted cumulative native quantities per collected attempt; classic histograms |
| core_runtime_usage{quantity,statistic} | Active battle committed usage sum/max and interval_peak_sum/interval_peak_max |
| core_runtime_selected_usage{slot="0",quantity,statistic} | Selected committed current usage and captured interval peak |
| core_runtime_active_battles | Currently live observed battles |
| core_runtime_selected_active / core_runtime_selection_generation{slot="0"} | Selected slot liveness and selection-switch generation |
| core_runtime_observation_dropped_total / core_runtime_registration_dropped_total / core_runtime_observation_expired_total | Queue loss / attachment contention / stale or duplicate queued summary |
| core_runtime_collector_up / core_runtime_last_snapshot_unix_seconds | Collector state and wall clock freshness |

Nine finite quantities: accounted_extent_bytes, pending_events, active_actions, projectiles, units, history_events, history_accounted_encoded_bytes, history_span_ms, simulation_time_ms. Interval peaks are maxima captured at existing insertion/admission/history seams and already-required reconciliation; interval_peak_sum sums each live battle's peak and does not claim all peaks occurred simultaneously. History encoded-byte accounting includes cached encoded entries and the unaccounted upper bound, so it is deliberately conservative between reconciliations. Simulation time is the current battle event clock, distinct from wall sampling time. A short-lived draft peak can exceed the committed value. Queue drops do not erase atomically published committed state or lifetime operation/rejection/commit/drop counters. Histograms can omit dropped/expired summaries and must be interpreted with loss counters.

## Storage and lifecycle

Core queue has1024 fixed OperationSummary slots; collector handles at most128 per batch. Each live observed application has fixed atomics for current usage/peaks/identity and commit sequence. Host holds weak leases, finite state per live application, and a300-row selected detail ring; ring overwrite is intentional. Dropped applications and ended battles are removed independently of queued summaries, even if the queue is full. A bounded three-attempt sequence read can defer polling a writer; cached state is kept on contention, avoiding false battle termination. Registry and owner maps are pruned and excess capacity shrunk; this is O(live sessions), not constant memory independent of the number of actual sessions.

Metrics use one owned recorder, no process-global installation. All histogram bounds are explicit classic buckets. Only the collector records samples. Every nonempty batch is followed immediately by synchronous standard `run_upkeep`, even with no scrape. This drains raw samples into fixed bucket/count/sum distributions. Crossbeam deferred frees are not assumed to happen on drain: a retirement fence, deferred after the histogram blocks and flushed, gates the next batch until reclaimable. A pinned reader can stop new histogram writes while Core continues and eventually drops observation summaries. Idle polling advances reclamation without an unbounded retry loop. The standard exporter runtime has one worker thread and at most one blocking render thread. A concurrently popped retirement callback may be in flight; the bound includes one such batch per participating thread in addition to the gated batch. Source-based byte counts and an isolated actual exporter allocator test are recorded separately; allocator/RSS fragmentation is not the retained logical byte model.

Selection metadata is only at loopback `/state`: session ID, battle UUID, wall selection time, generation and ring rows (wall time plus simulation time). `/selection` accepts `{"session":number}` or `{"session":null}`. Selection changes increment generation and append a boundary; end appends an ended boundary and clears selected_active. The Grafana XY view uses points, so it does not draw a connecting line across different sessions; consult the boundary panel and detail metadata to choose the relevant wall interval. Old Prometheus samples remain under its24h retention; removing a live gauge is not erasing historical samples.


The current exporter has678 registered handles:343 counters (69×4 attempts+63 reasons+4 scalar counters),59 gauges (9×4 aggregate+9×2 selected+5 scalar gauges), and276 histograms (69×4). Duration has13 explicit buckets; the other three histograms have10 each. Including +Inf/count/sum, a scrape therefore has4197 sample lines:402 scalar series+69×16 duration series+69×3×13 native quantity series. Actual live005/metrics.prom matches these counts. A batch emits at most512 raw values. On64-bit each AtomicBucket block holds64 `(f64,Instant)` values; using an upper1088bytes per block and a loose partial-block allowance of276+512 gives857344bytes per raw retirement batch. The isolated allocator experiment conservatively allows four such batches (3429376bytes), while the general concurrency argument is `(in-flight participating collectors + gated batch) ×857344` plus finite recorder/distribution/queue/session storage. Four is a bound for that isolated experiment, not a claim that arbitrary external threads are limited to four. A thread paused inside one detached callback cannot also pop unlimited new callbacks. Thread/session counts are process configuration/liveness quantities, not observation history.

Allocator-test scope: it invokes the actual host Worker/Handles/RetirementGate and standard owned recorder with all276 histogram handles, using4 explicit test buckets and `build_recorder` without HTTP/background runtime. Its baseline is therefore not the production service footprint. The production10/13 bucket arrays are fixed and add only fixed distribution storage; raw sample block allocation/drain/deferred retirement use the same dependency code and host batch path. Actual HTTP, scraper absence, exporter binding failure, concurrent collection and browser consumption are covered by the separate release-driver/service runs. The heap test is a growth/reclamation experiment, not a measurement of the complete production process RSS.

For this pinned production graph specifically, metadata's reverse dependencies show only game_server and metrics-util0.20.4 depend on crossbeam-epoch0.9.21; metrics-util uses it only in storage/bucket.rs. Native Core/Rapier does not link that epoch collector in this graph. The actual production users are the one collector runtime thread (worker and automatic upkeep) and the at-most-one standard HTTP blocking render thread (`http_listener.rs:157`). Thus the gated batch plus at most two popped in-flight callback batches fits inside the conservative four-batch allowance above for this host. The parameterized participating-thread statement covers an embedding that deliberately introduces additional users of the same default collector; it is not an unbounded-history loophole in the supplied host.
