## Assessment

The live-data pipeline is one of the strongest current boundaries: authored sources are parsed, validated, compiled and only
then published once. Protocol evolution is the weakest: many purpose-built DTOs exist, but they are centralized in one broad
module and version/strictness policy is local rather than envelope-wide. Checkpoint V4 is strict and independently validated,
which is excellent for correctness but is not yet a migration strategy.

Provisional A08 verdict: `PARTIAL`.

## Live Data Findings

- Code's single generated inventory contains 24 gameplay RON sources (`live_ron.rs:137-162`); with `bundle.ron`, current
  physical inventory is 25. SRC-03 lines 28-34 saying 23 is a minor documentation drift. The macro and exact inventory test are
  operational authority for the current baseline.
- Parsing and validation construct private type states. Generated combat preview/setup reaches `BattleCore` construction before
  the candidate `Arc<GameDataBase>` is returned, preventing partial publication.
- `GameDataBase` is a broad published catalog and `BattleCore` stores the whole `Arc<GameDataBase>`. Publication correctness is
  strong, but consumer scoping is weak. A `CompiledBattleCatalog`/`BattleContext` should contain only immutable runtime inputs.
- New Relic and fragment forms should use stable IDs and a compiler into battle/run effects. They should not mutate shared
  equipment/skill definitions at runtime.

## Protocol Findings

Purpose-built DTOs prevent accidental direct serialization of every internal type, but protocol ownership is still colocated
with domain/application errors and behaviors. Some nested contracts are strictly versioned while others accept unknown fields
or have no explicit version. This makes a current client shape hard to reason about as one capability contract.

Recommended target:

1. Version a root command/result envelope and capability-specific payload schemas.
2. Keep domain commands/results independent of serde and map them at an adapter boundary.
3. Generate or exhaustively register command classification, capability and version tables.
4. Use explicit compatibility adapters only for versions intentionally supported; current Unity compatibility is not a Goal
   constraint.

## Persistence Strategy

Strict V4 is safe for the current pre-release baseline because it fails closed and validates before mutation. It cannot be the
only long-term strategy once released or once new required systems persist state. The recommended migration sequence is:

1. Freeze current V4 decoder and canonical semantic projection as an import oracle.
2. Define the target checkpoint as application-owned aggregate documents with stable domain IDs, not serialized internal
   module layout.
3. Implement `V4 → target` as a one-shot validated conversion; never dual-write two mutable authorities.
4. Run old/converted state through the same continuation command tape and compare observable results.
5. Publish only the target writer; retire the importer when product compatibility policy permits.

The pre-release freedom should be spent on a clean target schema and adapters, not on a full domain rewrite.
