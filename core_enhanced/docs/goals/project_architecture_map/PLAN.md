# 신규 정책 설계 검토를 위한 프로젝트 지도 제작 Goal

Status: `complete`

문서 준비: 완료 / 지도 조사·작성: 완료 / 완료 감사: 완료

작성일: 2026-09-06 (Asia/Seoul)

## 1. 목적과 단일 Goal 경계

유물 시스템과 관련 성장 체계, 침식 정책을 구현하기 전에 고성능 AI가 현재 프로젝트의 설계를
검토할 수 있도록 **현재 구조와 승인된 변경 목표를 연결하는 프로젝트 지도**를 만든다.
검토자가 전체 코드를 처음부터 읽지 않아도 책임·의존 관계·상태 수명·주요 실행 흐름을 이해하고,
추가 판단에 필요한 원문을 선택해서 찾을 수 있어야 한다.

사용자는 검토 AI가 프로젝트 코드를 직접 읽을 수 있도록 **압축된 프로젝트 코드 또는 GitHub 링크와
지도를 함께 전달**할 계획이다. 지도는 전체 구조를 설명하고 어떤 원문을 왜, 어떤 순서로 읽을지
안내한다. 코드 접근이 불가능한 검토자를 전제로 대량의 코드 발췌본을 만들지 않는다.

콘텐츠 상태는 2026-09-06 사용자 확인 기준 **장비·스킬 파편 설계 완료, 유물 설계 진행 중**이다.
설계 완료를 코드 구현이나 live data 적용 완료로 해석하지 않는다.

이 Goal의 완결된 결과는 설계 검토용 지도 한 묶음이다. 여러 도메인을 조사하더라도 각 도메인의
구현을 변경하는 작업이 아니므로, 책임 경계를 여러 개 발견했다는 이유만으로 Goal을 분리하지 않는다.
조사 결과는 후속 설계 검토의 입력이며, 아키텍처의 적합성 최종 판정이나 리팩토링·전면 재작성 실행 계획을
대신하지 않는다.

### 후속 검토의 변경 폭

2026-09-06 사용자는 필요에 따라 **프로젝트의 전면 재작성도 검토할 의향**을 밝혔다.
후속 고성능 AI는 기존 코드 구조 유지를 필수 조건으로 두지 않고, 현재 구조 유지·부분 재설계·전면
재작성을 선택지로 비교할 수 있다. 승인된 목표 정책과 데이터 기반 콘텐츠 제작 목표를 기준으로,
각 선택의 근거·기대 효과·전환 비용과 위험·재사용 가능한 부분을 평가하도록 전달한다.

전면 재작성을 미리 권장안으로 정하거나 새 구현을 실행하도록 승인한 것은 아니다.
지도는 특정 선택으로 유도하지 않고 현재 책임·데이터·상태 수명·실행 흐름과 근거를 설명한다.
선택지의 비교 평가와 새 구조 설계는 후속 검토가 담당하며 지도 제작의 필수 산출물로 추가하지 않는다.

### 후속 설계 검토에 전달할 콘텐츠 제작 목표

2026-09-06 사용자는 커뮤니티 제작자가 전용 제작 프로그램을 통해 RON 데이터를 작성하고,
**엔진이 지원하는 명령·행동·조건·효과를 조합해 보스·장비(무기 포함)·스킬 파편·유물을 만들 수 있는
구조**를 목표로 확인했다. 지원 범위 안의 새 콘텐츠마다 코어에 전용 코드를 추가하지 않는 방향이다.
제작 가능한 콘텐츠의 폭을 넓히기 위해 엔진의 공통 기능을 확장할 수 있으며, 엔진 업데이트 없이
모든 미래 기믹을 표현해야 한다는 요구는 아니다.

지도는 현재의 정의·조합·실행·확장 위치와 데이터/코드의 경계를 설명한다. 고성능 AI의 후속 검토는
그 구조가 목표 콘텐츠를 표현하기에 충분한지, 공통 기능을 추가하기 쉬운지, 어떤 기능이나 구조
변경이 필요한지를 판단한다. 이 역할 구분도 사용자와 확인했다.

현재 모든 콘텐츠를 RON만으로 제작할 수 있다는 완료 주장이나 새 엔진 기능의 승인으로 해석하지 않는다.
관리 프로그램의 기능, 외부 콘텐츠의 직접 불러오기·무재빌드 적용·배포·리소스 제작 범위는 이 대화로
확정하지 않는다. 지도에 기록한 목표와 관련 근거 위치를 후속 설계 검토 지침에도 전달한다.

## 2. 실행 입력과 이번 요청의 권한

| 항목 | 값 |
| --- | --- |
| goal_name | `project_architecture_map` |

| 해결할 문제 | 원문 코드에 접근 가능한 검토 AI가 현재 설계와 신규 정책의 영향 범위를 효율적으로 파악할 안내 자료가 필요함 |

| 실행 승인 | 2026-09-06 사용자 첨부 지시로 실제 지도 제작·별도 문서 검토까지 승인 |
| production_change_authorized | `no` |
| 현재 승인된 쓰기 범위 | `docs/goals/project_architecture_map/`의 아래 네 문서와 `docs/project_map.ko.md` |
| 테스트 실행 | 사용자 지시로 제외. 아래 검증 규칙 참조 |

이번 요청은 실제 지도 제작 실행이다. 기존 준비 기록을 보존하고 `investigation_only` 범위에서
조사·지도 작성·별도 문서 검토까지 진행한다. 코드 수정이나 테스트 실행 권한으로 확대 해석하지 않는다.

## 3. 참조 지침의 적용 범위

참고 원문: [단일 Goal 조사·구현·검증 실행 프롬프트](</mnt/f/unity projects/ark/docs/single_goal_execution_prompt.ko.md>).
이 링크는 작업 절차의 출처이며 Unity 계약이나 Unity 구현을 조사하기 위한 입구가 아니다.
필요한 규칙을 아래에 반영했으므로 실행마다 외부 원문을 다시 읽을 필요는 없다.

| 적용하는 원칙 | 이 Goal에서의 적용 |
| --- | --- |
| 실행 입력과 변경 권한 구분 | 문서 준비와 실제 지도 조사를 구분하고, 코드·데이터 변경을 허용하지 않음 |
| 단일 Goal 범위 통제 | 설계 검토용 지도에 필요한 조사만 수행하고 발견한 문제는 근거와 질문으로 기록 |
| 초기화·재개 기록 | 현재 revision·dirty 상태·기록을 확인하고 유효한 조사를 불필요하게 반복하지 않음 |
| 현재 코드·기존 계약·목표 정책 구분 | 서로 다른 사실을 각각 기록하며 임의로 하나에 맞춰 수정하지 않음 |

| 완료 조건과 근거 연결 | 지도 주장과 코드·데이터·정책 출처를 다시 대조하는 별도 문서 검토 수행 |

저장소의 [문서 색인](../../README.md), [작업 가이드](../../engineering_workflow.md),
[P2G Reader Contract](../../policy_to_goal_pipeline.md),

P2G는 정책을 동결하고 구현 Goal로 변환하는 절차이며 GEX는 그 구현·감사 절차다.
이번 요청은 기존 조사 Goal에 따른 지도 조사·작성·문서 검토다. 새 정책 동결이나 구현 Goal Set 생성은 포함하지 않는다.
P2G Freeze·Handoff·Phase를 새로 만들거나 그 부재를 이 지도 제작의 선행 blocker로 삼지 않는다.

범용 지침의 구현 baseline, 정책 질문 전부 해결, producer-consumer의 실제 일치 달성,
canonical 수정, migration, rollout, 테스트 통과 조항은 이 Goal의 완료 조건으로 가져오지 않는다.
불일치와 미결 사항을 정확히 설명하는 것은 정상적인 조사 결과다.

## 4. 조사 범위

| 대상 | 조사 깊이와 경계 |
| --- | --- |
| `core_enhanced` | 주 조사 대상. 공개 진입점, 주요 도메인, 상태 소유·변경, 전투 실행, 성장·장비·보상·진행·저장 경계를 추적 |
| `../game_server/src` | 코어 호출, command 전달, tick·Pause, 결과·snapshot 전달, 재접속과 저장 연결에 필요한 경계만 읽음 |
| `../game_resources/data` | 코어가 실제로 읽는 데이터와 loader·validation·runtime 소비 관계를 확인. 콘텐츠 전체를 전수 평가하지 않음 |
| 코어의 기존 계약 문서 | 현재 명세와 코드의 관계를 확인. 변경 목표가 이미 구현된 것으로 간주하지 않음 |
| 신규 정책·콘텐츠 문서 | 승인된 변경 목표, 보류 사항, 후속 콘텐츠와 과거 참고안을 구분 |
| 기존 테스트 소스 | 핵심 책임이나 계약을 설명하는 데 필요할 때 관련 위치만 읽음. 테스트 전수 조사·실행·coverage 감사는 하지 않음 |

명시적 비범위:

- Unity 계약 문서와 Unity 클라이언트 구현. 사용자에 따르면 오래되어 이번 검토 근거로 부적절하다.
  서버 쪽에 있는 Unity 계약 문서도 읽기 경로에 포함하지 않는다.
- Unity 소비·화면·연출의 실제 일치 검증. 서버의 출력 경계까지만 확인하고 그 이후는 제외 범위로 표시한다.
- production 코드·live data·schema·저장 형식·기존 canonical 정책의 수정.
- 대표 유물 창작, 태그 vocabulary·수치 확정, 파편 재설계, 유물 획득·일반 보스 재조우 정책 결정.
- 리팩토링·전면 재작성의 설계와 구현, 버그 수정, 미래 기능의 선행 추상화, 새 Goal·Master·Phase 자동 생성.
- 엔진 명령·행동·효과의 추가 설계와 구현, 제작 도구 조사·구현, 커뮤니티 배포 체계 설계.
  전체 콘텐츠의 데이터 표현 가능성 평가와 필요한 엔진 확장안 결정은 후속 설계 검토에서 다룬다.
- 테스트·빌드·probe·benchmark·fixture 생성·서버 실행·패키지 설치·배포.
- 과거 지도 복원, 기존 Goal 재작성, 관련 없는 문서 정리.

Unity의 미조사는 승인된 비범위이므로 접근 실패나 완료 blocker로 취급하지 않는다.
서버·코어 연결이 코드상 일치하지 않으면 각 경계의 실제 확인 내용을 기록하고 가상의 연결을 그리지 않는다.
현재 작업 트리를 배포된 버전이나 실행 검증된 동작과 동일시하지 않는다.

정책 전문은 원문에 두고 지도에는 구조 검토에 필요한 요약과 출처를 기록한다.
유물·침식 문서는 사용자가 승인한 **변경 목표의 기록**으로 사용하며 현재 canonical이나 구현 완료로
승격하지 않는다. 원문의 `대화 결정`, `보류`, `기존 참고`, `구현 검토`를 서로 섞지 않는다.
콘텐츠 문서의 과거 공통 시스템 설명과 최신 목표 기록의 충돌도 구분해서 기록한다.
유물 콘텐츠는 별도 작업에서 설계 중이다. 일부 항목이나 파일의 존재만으로 전체 설계 완료를 선언하지
않으며, 지도 실행 시 최신 문서의 설계 상태를 확인한다.

지도에서는 각 중요한 주장에 다음 분류를 붙인다.

- **코드 확인:** 현재 작업 트리의 호출·구현·상태 변경·소비 경로를 읽어 확인한 사실. 실행 검증과 구분.
- **현재 명세:** 기존 계약 문서에 정의된 의미. 구현 일치를 자동 보증하지 않음.
- **승인된 변경 목표:** 사용자 결정 기록이 뒷받침하는 미래 정책.
- **추론:** 직접 확인한 근거에서 도출한 해석. 확인한 사실과 남은 가정을 함께 적음.
- **미확인 / 미결정 / 비범위:** 아직 조사하지 못한 사실, 사용자가 정하지 않은 정책, 의도적으로 제외한 범위를 구분.

삭제된 `normal_boss_egg_design_notes_2026-08-19.ko.md`와
`handoff_skill_fragment_design_2026-08-20.ko.md`는 입력으로 사용하지 않는다.
과거 감사의 인용·hash·이전 지도에 나타나더라도 승인 정책이나 현재 구현의 증거로 복원하지 않는다.
일반 보스 재조우의 장비·재화 파밍 목적만 확인됐으며 방식·빈도·보상은 미정이다.
개별 보스 연출에서 일반적인 알 획득·보관·부화 정책을 도출하지 않는다.

지도 본문은 다음 순서로 읽을 수 있게 작성한다. 분량 상한을 채우기 위한 나열은 하지 않는다.

1. **읽기 안내와 기준 상태:** 목적, 조사 날짜·revision·dirty 범위, 코드와 변경 목표의 구분, 제외 범위.
2. **전체 구조:** 주요 책임과 의존 방향. C4의 계층 구분을 참고하되 프로젝트 설명에 필요한 수준만 사용.
   호출 의존·데이터 흐름·상태 소유 관계를 같은 의미의 화살표로 섞지 않는다.
   콘텐츠 데이터, 이를 조합·실행하는 공통 코드, 개별 콘텐츠에 고정된 코드의 경계를 설명한다.
3. **상태 소유와 수명:** 물리적인 소유 타입과 개념적인 수명을 구분한 표.
4. **대표 실행 흐름:** 아래 필수 흐름의 진입점·상태 변경·commit·실패·복원 경계.
5. **신규 정책 연결 표:** 승인된 목표 → 현재 관련 구조 → 연결 가능 지점 또는 부재 → 후속 검토 질문.
6. **불일치·미확인·검토 질문:** 관찰과 추론을 구분하고 후속 검토자가 확인할 근거 위치를 제시.
7. **코드 읽기 순서와 근거 색인:** 전체 이해, 유물 검토, 침식 검토, 데이터 기반 콘텐츠 제작 구조
   검토 등 목적별 최소 읽기 경로. 1절의 콘텐츠 제작 목표를 후속 검토자가 함께 읽을 수 있게 한다.

Markdown 표와 작은 Mermaid 구조·흐름도를 필요한 곳에 사용한다. 그림의 주요 항목에는 일반 Markdown
파일 링크와 심볼을 함께 제공한다. 모든 파일·함수를 열거하거나 하나의 거대한 그래프를 만들지 않는다.
라인 번호는 보조 정보이며 파일 경로와 타입·함수명이 기본 탐색 기준이다.
지도에서 주요 관계를 이해한 뒤 직접 원문으로 이동할 수 있도록, 중요한 판단마다 관련 경로·심볼과
읽을 이유를 적는다. 꼭 필요한 작은 선언·분기만 발췌하며 긴 코드·로그는 복사하지 않는다.

### 전달할 코드와 지도의 기준

- GitHub로 전달할 때 확인할 기준 commit을 지도에 기록한다. 조사에 포함한 미커밋 변경이 있다면
  그 상태도 명시하고, 해당 변경이 빠진 GitHub 코드와 지도가 일치한다고 표현하지 않는다.
- 압축본으로 전달할 때에도 지도가 설명하는 코드·데이터·정책 문서의 상태와 맞춰야 한다.
  기본 원문 경로는 저장소 상대 경로와 심볼로 안내해 다른 환경에서도 찾을 수 있게 한다.
- 실제 전달 시 참조한 서버·데이터 등 조사 범위도 함께 접근 가능하게 하거나 누락 범위를 표시한다.
- 이 Goal은 기준 상태와 원문 탐색 정보를 기록한다. 압축본 생성·업로드·GitHub 공개나 실제 전달은
  이번 문서 작성 및 지도 제작의 완료 조건에 추가하지 않는다.

## 7. 필수 조사 관점

### 상태 소유와 수명

최소한 run, roster 직원, 전투 runtime instance, attempt, inventory·장착, 효과·스택·횟수,
checkpoint·영구 profile을 조사한다. 각 상태는 소유 타입, 생성·변경 주체, 초기화·제거 시점,
저장 여부, 실패·재시도·재배치·재접속 시 보존 범위를 연결한다.
이 목록은 조사 질문이며 해당 상태나 필드가 이미 존재한다는 주장이 아니다.

### 대표 실행 흐름

| 흐름 | 확인할 연결과 경계 |
| --- | --- |
| 데이터에서 실행 정의까지 | authored data → loading·validation → publication → runtime 소비 |
| 외부 요청에서 결과까지 | 서버 입력 → 실제 코어 진입점 → dispatch·허용 조건 → 상태 변경·commit → 응답·snapshot |
| 장비·파편에서 전투 구성까지 | 보유·장착·형태 선택 → 전투 진입 → 능력치·효과 구성 → 실제 사용 |
| 파편 시전과 효과 연쇄 | 입력 접수 → Pause·tick → cast 상태·공명 소비 → 실제 효과 처리 → 적중·피해·처치·후속 효과 |
| 직원과 attempt 수명 | 배치 → 철수·전투불능 → 재배치 자격·초기화 → 결과 반영 또는 실패·재시도·rollback |
| 전투 종료와 진행 | 적 사망 → wave·승리 판정 → 결과 commit → 보상·직원 상태·조우/런 진행 |
| 저장과 재접속 | 저장 대상 선택 → serialize·서버 저장 → 복원·checkpoint·현재 snapshot/resync의 관계 |

각 흐름은 호출 이름만 검색해서 완성하지 않는다. 실제 호출자·구현·변경 대상·소비자를 연결하고,
중요한 실패·거부·재시도 분기와 상태가 확정되는 지점을 함께 기록한다.

### 데이터로 콘텐츠를 구성하는 현재 경계

기존 데이터·보스·장비·스킬 흐름 조사와 유물 목표의 연결에서 다음 정보를 함께 요약한다. 명령·효과·콘텐츠 전체의
별도 전수 조사나 새 기능 목록 설계로 범위를 넓히지 않는다.

| 관점 | 지도에 준비할 사실과 근거 |
| --- | --- |
| 정의와 실행 | 현재 행동·조건·효과의 주요 종류, 데이터 정의 위치와 이를 해석·실행하는 코드 위치 |
| 조합 방식 | 보스 행동·단계 전이, 스킬 단계·효과, 장비 발동 조건의 대표 경로와 유물의 태그·효과 조합 목표가 연결될 위치 |
| 공유와 전용 처리 | 보스·장비·파편·유물 관점에서 기존 공통 기능과 도메인별 처리. 개별 콘텐츠 ID에 고정된 분기가 확인되면 위치·역할·근거 |
| 확장 위치 | 콘텐츠 데이터 추가와 공통 명령·행동·효과 추가가 각각 어떤 정의·검증·실행 경계를 통과하는지 |
| 데이터 적용 | 현재 loading·validation·publication 경로와 적용 조건. 스키마에 이름이 있는 것과 실제 실행 지원을 구분 |

특정 ID 참조 자체를 전용 로직이나 결함으로 판단하지 않는다. 자료 조회·등록과 ID별 행동 분기를
구분한다. 기능의 부재와 데이터만으로 작성할 수 있는 범위는 직접 확인한 정도에 맞게 기술한다.
유물은 승인된 변경 목표와 현재 구현 상태를 구분하여 연결 후보·부재를 기록한다.
어떤 기능을 더 구현해야 하는지, 전체 보스·장비·파편·유물 설계를 얼마나 표현하는지에 대한 최종 평가는
후속 AI 검토 질문으로 남긴다. 현재 구현이 목표에 충분하지 않더라도 근거를 갖춰 지도에 설명하면 된다.

### 신규 정책과의 연결

다음 요약은 원문을 찾기 위한 조사 목록이다. 상세 의미는 5절의 정책 기록을 따른다.

표현만으로 일시정지 중 침식 연출이 즉시 시작한다고 결론 내리지 않는다. 반대로 모든 command를
Resume 이후로 미루는 큐가 존재한다고 추정하지도 않는다. 정확한 현재 코드 지점과 목표의 차이를 적는다.

정책의 연결 지점은 후보이며 신설 타입·모듈·schema·event bus·구현 방식의 확정안이 아니다.
부재는 관련 정의·호출·데이터·소비 범위를 확인한 정도에 맞춰 표현한다.

## 8. 작업 방식과 검증 제한

지도 실행을 요청받으면 먼저 이 PLAN과 두 실행 기록의 현재 요약을 읽고 현재 작업 트리·대상 경로를
확인한다. 기존 유효한 조사는 재사용하되 다른 revision이나 대화 기억을 이번 직접 근거로 옮기지 않는다.
큰 책임을 파악한 뒤 필요한 흐름을 추적하고, 정책 연결과 근거를 보완한다. 세부 순서와 읽기 단위는
작업자가 결정하며, 서로 무관한 과거 감사·콘텐츠·테스트 전체를 필수 입력으로 삼지 않는다.

사용자는 2026-09-06에 본인이 `all test`를 실행했을 때 모두 통과했다고 알렸으며,
이 Goal에서 테스트에 토큰을 소비하지 말라고 명시했다.

- 테스트를 새로 작성하거나 실행하지 않는다. 기존 전체 테스트의 명령·수량·로그 제출도 요구하지 않는다.
- `cargo test`, `cargo check`, `cargo clippy`, probe, benchmark 등으로 검증 범위를 우회 확대하지 않는다.
- 사용자 보고는 **사용자 확인**으로 기록한다. AI가 재실행했거나 현재 서버 통합·개별 새 정책을 검증한 근거로 쓰지 않는다.
- 테스트 수와 pass/fail/skip 수는 해당 없음이다. 실행하지 않은 것을 테스트 성공·실패·runner skip으로 집계하지 않는다.
- 허용된 검증은 작성 문서의 diff·경로·링크·심볼·내용 대조와 Markdown 구조 확인이다.
  문서 확인을 위해 패키지나 다이어그램 도구를 설치하지 않는다.

실제 조사 명령·읽은 경로·핵심 결과·미확인 지점만 EXPERIMENTS에 기록한다. 전체 console 출력은
복사하지 않는다. 최종 문서 검토는 작성 후 별도 읽기 pass로 수행하며 별도 에이전트나 새 Goal이 필수는 아니다.

모든 콘텐츠의 RON 표현 가능성 입증이나 엔진 확장안의 완성도 지도 완료 조건이 아니다.
이번 Goal 문서 작성 완료만으로 이 표를 충족했다고 표시하지 않는다.

## 10. 진행 상태와 중단 조건

- `active`: 승인된 현재 작업 안에서 문서 준비 또는 조사·작성을 진행할 수 있음. 단계와 잔여 작업을 별도 명시.
- `scope_decision_required`: 요청의 조사·산출물 범위 자체가 모호하여 선택에 따라 필수 결과가 달라짐.
- `policy_decision_required`: 지도 결과의 필수 의미를 정하려면 새 정책 결정이 꼭 필요한 예외 상황.
  발견한 미결 정책을 기록하는 것만으로 진행 가능하면 이 상태로 전환하지 않음.
- `externally_blocked`: 필수 코어·데이터 등 근거에 접근할 수 없어 지도 완료 조건을 충족할 수 없음.
- `complete`: M01~M10의 필수 근거와 문서 감사가 모두 충족됨.

기존 파일과 충돌해 안전하게 작성할 수 없거나 필수 근거가 없으면, 해당 부분을 추측해 채우지 않는다.
독립적인 조사는 계속하고 완료할 수 없는 정확한 항목과 필요한 입력을 보고한다.
범위 밖 문제를 고치거나 미결 gameplay 정책을 대신 결정하는 방식으로 막힌 부분을 해소하지 않는다.
