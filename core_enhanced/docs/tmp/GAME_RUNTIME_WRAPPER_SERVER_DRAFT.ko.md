# Game Wrapper / Game Server 실행 구조 검토 초안

작성일: 2026-09-26 KST  
상태: **임시 논의 기록 / 설계 제안 / 구현·로드맵 변경 미승인**

## 1. 문서의 목적과 지위

Unity 프론트엔드와 Rust 백엔드를 PC·모바일에서 사용하는 방법, 클로즈 베타의 원격 실행, wrapper/server의 중복 유지보수 방지 방향을 기록한다.

- 사용자에게 확인된 요구와 검토 중인 제안을 구분한다.
- 이 문서는 정식 P2G/GEX 계획, 아키텍처 결정 기록, 구현 지시서 또는 플랫폼 지원 완료 선언이 아니다.
- 기존 R02 완료 기록, R06 동결 target·baseline·감사 증거를 소급 변경하지 않는다.
- 문서 작성만으로 server 제거, Runtime 추출, 의존성 추가, Unity 변경 또는 배포를 시작하지 않는다.

## 2. 사용자가 설명한 구조와 목적

### 현재 책임 분리

- **Game Core — Rust:** 모든 게임 시스템 처리와 게임 상태 변경을 담당한다.
- **Game Server — Rust:** Core를 라이브러리로 사용하며 플레이어와의 상호작용을 연결한다.
- **Frontend — Unity:** 백엔드와 실시간 통신하여 정보·상태를 표시하고, 플레이어 입력을 백엔드로 전달한다. 게임 규칙을 독립적으로 재구현하지 않는다.

### 배포 및 운영 요구

- PC는 프론트엔드와 백엔드를 함께 배포할 계획이다. 이것만으로 단일 프로세스 방식까지 확정된 것은 아니다.
- Windows와 일반적으로 사용하는 Linux 환경을 지원하고 싶다는 요구가 있다. 정확한 OS 버전·CPU·파일시스템 지원 범위는 미정이다.
- macOS 지원 여부는 미정이다. Android/iOS는 실행 가능성과 구조를 검토 중이며 정식 지원 범위는 아직 확정하지 않았다.
- 클로즈 베타는 EC2에서 백엔드를 실행하고 플레이어에게 프론트엔드만 배포하는 방식을 고려한다. 기간 종료 뒤에는 플레이를 중단시킬 수 있어야 한다.
- 원격 실행과 네이티브 내장을 모두 지원하되, 게임 실행 로직을 두 벌로 유지하는 구조는 피하고자 한다.

## 3. 제안: 공통 Game Runtime과 두 개의 연결 방식

사용자가 제안한 `game wrapper`를 **공통 게임 실행 관리 계층**으로 정의한다. 역할을 명확히 하는 이름으로 `game_runtime`을 후보로 사용하며, 실제 crate명·디렉터리 분할은 미확정이다.

```text
원격 배포 / 클로즈 베타
  Unity → Remote 연결부 → 네트워크 → Game Server → Game Runtime → Game Core
                                        └──────── EC2 등 서버 측 ────────┘

로컬 배포 / 네이티브 내장
  Unity → Local 연결부 → Native/FFI 연결부 → Game Runtime → Game Core
  └──────────────── 플레이어 앱 프로세스 내부 ────────────────────────┘
```

두 실행 경로가 같은 Runtime과 Core 구현을 사용한다. 서버 기능을 복사해서 별도의 로컬 wrapper를 만드는 방식은 피한다.

네이티브 내장이란 Rust 소스를 C#으로 변환하는 것이 아니라, 대상 플랫폼용으로 컴파일한 라이브러리를 Unity에 연결하는 것이다. 연결부·Runtime·Core는 논리적으로 구분하되 하나의 네이티브 라이브러리로 묶어 배포할 수 있다.

| 계층 | 책임 | 포함하지 않을 책임 |
| --- | --- | --- |
| Unity 표현 계층 | 화면·소리·애니메이션, 입력 수집, 앱 상태 전달 | 게임 규칙·보상·피해 등의 별도 판정 |
| Unity backend 접근 창구 | 명령 제출, 결과·이벤트 수신, 연결/실행 상태 표현 | 원격·로컬별 게임 로직 복제 |
| Game Server | 네트워크 연결, 인증·이용 권한, 세션·재접속, 원격 메시지 전달 | Core와 중복된 규칙, 별도 게임 실행 알고리즘 |
| Native/FFI 연결부 | C#↔Rust 호출, 버퍼·메모리 소유권, 오류 변환 | 게임 규칙, 저장·게임 진행 정책의 중복 구현 |
| Game Runtime | Core 인스턴스 수명, 명령 직렬화, 게임 진행 호출, 결과 전달, 콘텐츠 로딩 및 저장·복원 조율 | Unity·WebSocket에 대한 직접 의존, Core 내부 규칙 재구현 |
| Game Core | 명령 유효성, 게임 상태, 시뮬레이션, 체크포인트의 게임 의미 | 접속 인증, 베타 운영 일정, OS 앱 수명주기 |

저장 데이터의 유효성은 Core가 판단하고, 저장 시점·안전한 파일 기록·실패 전달은 Runtime과 저장 어댑터의 책임으로 나누는 방향을 검토한다. 필요한 파일 접근 차이는 호스트 어댑터에 한정한다.

## 4. 공통화할 계약과 남겨야 할 차이

### 공통화 후보

- 명령·응답·이벤트·스냅샷의 의미와 버전.
- 게임 인스턴스 생성·종료, 콘텐츠 세대 선택, 저장·복원 흐름.
- 하나의 Core를 변경하는 명령·시간 진행·저장의 순서.
- 오류 발생 시 상태 보존, 요청 중복·재시도 처리의 책임 경계.
- UI 스레드에서 무거운 게임 계산을 수행하지 않도록 하는 실행 모델.

Unity에 `IGameBackend` 같은 공통 접근 창구를 두고 Remote/Local 구현을 교체하는 방안을 검토한다. 이름과 실제 메서드는 확정하지 않는다. 초기에는 공통 직렬화 메시지를 로컬 연결에서도 재사용할 수 있으나, JSON 채택 및 복사·메모리 예산은 측정 후 결정한다.

### 동일하게 취급하면 안 되는 차이

- 원격에는 지연·연결 끊김·인증 실패가 있다. 로컬과 같다고 숨기지 않고 명시적인 상태·실패로 표현한다.
- 서버의 세션 종료와 모바일 앱의 일시정지는 원인이 다르다. 공통 실행 제어에 연결하되 같은 정책으로 강제하지 않는다.
- 벽시계·Unity 프레임률·네트워크 도착 시각을 게임 시간의 의미와 혼동하지 않는다. 시간 공급 및 Core 진행 규칙은 별도로 설계한다.
- 연결 timeout이 곧 명령 미실행을 뜻하지 않는다. 재시도에 따른 중복 실행을 막는 계약이 필요하다.
- 네이티브 호출에서 Rust 내부 가변 객체나 임의 메모리를 Unity에 직접 노출하지 않는다. 핸들 수명, 버퍼 해제 주체, panic/오류 경계, 동시 호출 규칙을 정한다.
- 같은 프로세스로 내장하면 네이티브 크래시가 앱 전체에 영향을 줄 수 있다. 오류 처리와 프로세스 격리를 같은 보장으로 취급하지 않는다.

## 5. 클로즈 베타 종료 통제

강한 종료 통제가 필요하면 베타는 **원격 실행 전용 배포**를 유지하는 방향을 추천한다.

- 베타 클라이언트에 로컬 Runtime/Core 실행 라이브러리와 오프라인 대체 실행 경로를 포함하지 않는다. UI에서 숨기기만 하는 방식과 구분한다.
- 이용 권한·베타 기간은 서버 측에서 검사한다. 로그인 성공만으로 무기한 게임 실행 권한을 주지 않는다.
- 종료 시 신규 접속뿐 아니라 기존 세션의 명령, 대기 요청 및 자동 게임 진행도 정책에 따라 중단한다.
- 종료 안내, 저장·진행 중 전투 처리, 유예 시간, 로그 보존 후 서버 중단의 순서를 정한다. 개인 파일·서버 데이터를 자동 삭제한다는 뜻은 아니다.
- 현재 인증·세션 구현이 실제 베타 운영에 충분한지는 별도 감사한다.

로컬 실행 코드와 데이터를 배포한 뒤 날짜 검사나 온라인 이용권만으로 변조된 클라이언트의 실행까지 완전히 회수할 수 있다고 보장하지 않는다.

원격 베타는 로컬 내장의 성능·파일 접근·모바일 중단/복원을 대신 검증하지 않는다.

## 6. 플랫폼과 외부 콘텐츠 팩

현재 확인한 외부 팩 파일시스템 구현은 Unix/WSL 중심이며 비 Unix 구현은 명시적 오류를 반환한다. 이는 기존 R02의 구현·검증 범위이며, 최종 제품에서 Windows를 제외하기로 사용자가 승인했다는 뜻은 아니다.

- Windows 네이티브 외부 팩 로딩·생성은 별도 구현·검증이 필요하다.
- Unix 조건에 Android/iOS/macOS 코드가 포함될 수 있다는 사실만으로 해당 플랫폼 지원을 주장하지 않는다.
- 공통 라이브러리를 우선 검토하고, 프로젝트 요구를 담당하는 작은 어댑터를 둔다. `cap-std`/`cap-fs-ext`는 후보이지 채택 완료가 아니다.
- 루트 밖 접근 차단, 링크 거부, 파일 identity·변경 검사, 중복 거부, 입력 한도, 새 출력의 독점 생성 등 기존 조건의 충족 여부를 확인한다.
- 라이브러리의 루트 내부 링크 허용과 기존 계약의 링크 자체 거부는 다른 정책이다. 변경이 필요하면 명시적으로 검토한다.
- 호스트의 실제 경로와 팩 내부 논리 경로를 구분한다. 플랫폼별 경로·파일 식별자를 콘텐츠 의미 지문에 섞지 않는다.
- 모바일의 앱 동봉 asset, 앱 전용 저장소, 다운로드/가져오기 경로를 일반 PC 폴더와 동일시하지 않는다.
- 플랫폼별 OS·CPU·파일시스템·도구체인과 실제 테스트 범위를 정한다. WSL 실행 또는 교차 컴파일만으로 Windows 네이티브 검증을 대신하지 않는다.

`resource_lifetimes`의 Unix 조건 추가는 기존 테스트 도우미의 가용 조건에 맞춘 컴파일 수정일 뿐이다. Windows 로더가 지원되면 공통 회귀 테스트도 Windows에서 실행하도록 전환해야 한다.

## 7. 현재 코드에서 재사용할 출발점

- [CoreApplication](../../src/application.rs): 명령 실행, 상태 조회, 전투 진행, 체크포인트 내보내기·복원 등의 공개 Rust API. FFI API가 이미 구현됐다는 뜻은 아니다.
- [서버 진입점](../../../game_server/src/main.rs): HTTP/WebSocket 서버와 데이터·저장 초기화.
- [PlayerGameActor](../../../game_server/src/game/player_game_actor/mod.rs): 게임 인스턴스, 전투 tick, 이벤트 전달 위치, 저장 관련 책임.
- [세션](../../../game_server/src/game/player_game_actor/session.rs): 연결·heartbeat·인증 및 메시지 전달.
- [파일 저장 처리](../../../game_server/src/persistence/mod.rs): 기존 플랫폼별 저장 처리를 조사할 출발점.
- [외부 팩 snapshot](../../src/game/data/content_pack/snapshot.rs) 및 [데이터 로딩 계약](../data_loading_contract.md): 파일시스템 경계와 현재 제한.

전체 서버→공개 CoreApplication 전환의 누락·호환성은 아직 조사하지 않았다. 현재 서버가 Core 내부 타입을 직접 사용하는 경로도 있으므로, 공개 API가 있다는 사실만으로 즉시 교체 가능하다고 판단하지 않는다.

## 8. 로드맵과 도입 순서 제안

기존 [콘텐츠 제작 기반 로드맵](../roadmaps/content_authoring/roadmap/ROADMAP.ko.md)은 game_server/Unity 전환을 비범위로 둔다. R24 완료를 최종 게임의 다중 플랫폼 배포 완료로 해석하지 않는다. 별도의 실행·플랫폼 통합 계획을 만들고 필요한 의존 관계만 연결하는 것을 제안한다.

1. **요구·경계 정리:** 지원 플랫폼, Runtime 책임, 원격 베타/로컬 배포, 저장·일시정지 정책을 정한다.
2. **서버 책임 조사:** 각 기능을 제거 / 공통 Runtime 이전 / 서버 전용 보존으로 분류한다. 타이머·저장·이벤트·재시도 의미를 먼저 확인한다.
3. **작은 기술 검증:** 기존 R06의 안정된 경계를 보존한 별도 작업에서 Unity→Rust 생성·명령·결과·종료와 Windows 팩 접근의 가능성을 검증한다. 폐기 가능한 검증 코드와 제품 구현을 구분한다.
4. **공통 Runtime 추출:** 기존 원격 경로가 Runtime을 사용하도록 바꾸고 기존 동작을 검증한다. 서버 기능 복사본을 만들지 않는다.
5. **네이티브 연결 추가:** 동일 Runtime에 Unity 연결부를 붙이고 저장·복원·중단·오류까지 검증한다.
6. **양쪽 인수·플랫폼 확대:** 동일 시나리오의 원격/로컬 결과를 비교하고 Windows/Linux 실제 배포를 검증한다. 모바일·macOS는 승인된 지원 범위에 따라 추가한다.

작은 검증을 R24 이후까지 미루지는 않되, 새 통합 작업 전체를 모든 후속 R의 필수 선행으로 만들지도 않는다. R20 저장·재접속 및 R23 결정론·성능 시나리오는 새 통합 검증에서 재사용할 수 있지만 각 감사의 범위·판정은 구분한다. 베타가 가까우면 기존 원격 배포를 먼저 유지할 수 있다.

고성능 모델의 검토·계획 수립 후 구현 담당에게 인계하는 기존 방식을 유지한다. 단계검토는 사용자가 명시적으로 활성화한 경우에만 적용하고, 새 작업의 before/after를 별도 고정한다. 이 문서는 현재 동결 구간을 재개하거나 변경하는 권한이 아니다.

## 9. 향후 수용 기준 후보

- Core·Runtime의 게임 실행 코드가 원격/로컬에서 하나이며, 통신 계층에 게임 규칙 복제본이 없다.
- 동일 콘텐츠·초기 상태·seed·명시적 게임 시간·명령 순서에서 도메인 결과와 이벤트 순서가 일치한다. 세션 ID·벽시계 등 호스트 정보는 비교 범위를 구분한다.
- 명령 중복·동시 호출·실패·중단·복원에서 상태 보존과 저장 계약이 유지된다.
- Windows/Linux의 실제 release 실행에서 외부 팩 입력부터 게임 진행·체크포인트 복원까지 연결된다.
- 원격 베타 종료가 신규 접속과 기존 세션 모두에 적용되고, 베타 배포물에 로컬 실행 경로가 없다.
- 모바일을 포함한다면 화면 전환·백그라운드·프로세스 종료·재실행과 성능·메모리 사용을 별도 검증한다.
- 기존 체크포인트 지원 범위를 넘어 임의 전투 순간의 영구 저장·복원을 자동으로 약속하지 않는다. 필요한 경우 별도 요구로 설계한다.
- 기존 동결 target·실패 기록을 덮어쓰지 않고 새 변경·검증·감사 범위를 식별한다.

## 10. 미결정 사항

- Windows 최소 버전, Linux 대표 배포판·최소 실행 환경, CPU 아키텍처, 파일시스템 지원 범위.
- Android/iOS 및 macOS의 필수 지원 여부와 우선순위.
- Runtime의 실제 crate 경계, worker thread/큐와 시간 공급 방식.
- 공통 명령·이벤트 형식, 데이터 복사 예산, FFI 메모리·오류 계약.
- 로컬 저장 모듈 재사용 범위와 앱 중단 시 허용되는 저장 단위.
- 베타 종료 시 진행 중인 게임의 처리와 유예 여부, 인증·이용 권한 운영 방식.
- 파일시스템 라이브러리 선정 및 기존 보안 계약과의 차이 처리.
- 기존 R06 이후 정확한 삽입 시점과 정식 계획·감사 owner.
