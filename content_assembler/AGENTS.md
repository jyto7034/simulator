# 콘텐츠 조립기 작업 규칙

이 규칙은 `content_assembler/` 아래에 적용한다. 제품은 Windows 데스크톱 앱이며,
주 개발 환경은 WSL이다. React/TypeScript/Vite/Tauri와 기존 Radix 기반 shadcn/ui를 사용한다.

기능을 설계하거나 범위를 판단할 때는 [프로젝트 목적과 범위](docs/project-purpose.md)를 확인한다.

코드 작성·수정 시 [개발 지침](docs/development-guidelines.md)의 관련 항목을 읽고 적용한다.
상태 소유권, 책임 분리, 편집 이력·저장·검증의 일관성을 기준으로 구현하고 검토한다.
문서 상태 변경에는 개발 지침 4절의 트랜잭션 원칙을 적용한다. 임시 변경 준비·검증 후
관련 데이터와 이력을 한 번에 확정하고, 확정된 결과만 외부에 알린다.

## 스킬 그래프의 외부 설계 참고

스킬 그래프 작업을 처음 맡으면 [Forge 참고 기준](docs/forge-statescript-reference.md)의 읽기 순서와
실행 구조 안내를 확인한다. `../references/`의 사본을 둔 이유와 보관 범위는
[참고 자료 안내](../references/README.md)에 있다. 세부 구현은 현재 스킬에 필요한 부분부터 읽고,
우리 계약에 채택한 의미와 차이·검증 사례를 기록한다.

## UI 구현

- 먼저 변경할 화면, 사용자 동작, 확인할 상태를 정한다. 기존 공통 컴포넌트와
  `src/index.css`의 색상·간격·테마를 사용한다.
- 편집기에 맞는 정보 밀도를 유지한다. 임의의 장식, 과도한 카드·그라데이션,
  요청하지 않은 기능을 추가하지 않는다. 라이브러리로 해결되는 위젯을 다시 만들지 않는다.
- 클릭할 수 있는 요소는 실제 동작을 구현한다. 버튼·입력에 접근 가능한 이름을 부여하고,
  키보드 탐색, 포커스 표시, 메뉴/대화상자의 Escape 닫기와 포커스 복귀를 유지한다.
- 최소 지원 창 크기는 960×640이다. 기본 크기 1280×800, 큰 화면 1920×1080과
  밝은/어두운 테마를 확인한다. 도킹·분할 패널을 추가하면 패널 최소 폭도 확인한다.
- 새 데이터 화면은 긴 한글 이름, 빈 목록, 많은 항목, 로딩, 오류 등 관련 상태를
  재현할 고정 fixture를 함께 준비한다. 아직 없는 기능의 가짜 동작을 제품에 넣지 않는다.

## 변경 후 검증

1. `npm run check`와 변경에 맞는 빌드/테스트를 수행한다.
2. UI 변경에는 `npm run ui:inspect`를 사용한다. 새 화면/상태를 추가하면
   `tests/ui/`의 촬영·동작 시나리오도 해당 변경에 맞게 확장한다.
3. 생성된 PNG를 이미지 보기 도구로 직접 연다. 명령 성공이나 PNG 존재만으로
   화면 검토를 완료했다고 판단하지 않는다. 겹침, 잘림, 한글 글리프, 줄바꿈,
   정보 밀도, 정렬, 포커스 표시, 메뉴 위치를 의도한 화면과 대조한다.
4. `artifacts/ui/report.json`과 첨부 진단을 확인한다. 오류를 고치고 관련 검사를 다시 한다.
   axe의 `incomplete` 항목은 수동 확인 대상으로 취급한다.
5. 검토한 기준 이미지가 있으면 `npm run ui:compare`로 회귀를 검사한다.
   차이를 없애려고 기준 이미지를 자동 재생성하거나 허용 오차를 늘리지 않는다.
   의도한 변경임을 이미지로 확인한 경우에만 `ui:baseline`을 사용하고 변경 이유를 남긴다.
6. 결과 보고에는 확인한 화면/상태, 검사 결과, 이미지 경로와 미검증 범위를 명시한다.
   새 의존성이나 도구 자체를 설명하는 작업에서는 불필요하게 앱을 실행하지 않는다.

사용자가 실행을 금지한 작업에서는 `ui:inspect`, `ui:compare`, `ui:baseline`,
개발 서버, 브라우저, Tauri 앱을 실행하지 않는다. `npm run check`, `npm run build`,
`npm run ui:list` 같은 실행 없는 준비 검사를 하고 실제 화면 검증이 남았음을 알린다.
사용자의 기존 실행 허용 범위는 유지하며 매 단계마다 재확인을 요구하지 않는다.

## 플랫폼과 재현성

- WSL의 Chromium 검사는 브라우저 UI 검증이다. Windows WebView2, Tauri IPC,
  파일 대화상자, 권한, 설치 프로그램, 한글 IME 검증까지 완료했다고 표현하지 않는다.
- 브라우저용 모의 데이터/IPC가 필요하면 테스트 경계에 명시적으로 주입한다.
  네이티브 API 실패를 제품 코드에서 숨기거나 가짜 성공으로 바꾸지 않는다.
- 경로는 Tauri 경로 API와 Rust `Path`/`PathBuf`로 처리한다.
  로컬 절대 경로, OS별 경로 구분자, Bash 전용 명령을 제품에 하드코딩하지 않는다.
- Windows와 WSL의 `node_modules`와 빌드 산출물은 별도 작업 폴더에서 관리한다.
  소스와 잠금 파일은 공통으로 관리한다.
- 시각 비교는 같은 OS·브라우저 버전·폰트·배율에서 수행한다.
  기준 이미지는 플랫폼별로 분리하고 환경 변경으로 생긴 차이도 검토한다.
- UI 검사는 전용 포트 1422를 사용한다. 포트가 점유되어 있으면 원인을 확인한다.
  기존 프로세스를 임의로 종료하거나 알 수 없는 서버를 재사용하지 않는다.
- 실제 사용자 데이터나 자격 증명을 캡처 fixture에 사용하지 않는다.

명령과 결과물은 [UI 검증 안내](docs/ui-validation.md)를 따른다.
