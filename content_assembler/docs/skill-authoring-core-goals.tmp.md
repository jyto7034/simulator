# 스킬 기능 정의·조합을 위한 Core 개선 목표 — 구체화 초안

작성일: 2026-10-23  
상태: **목적 확장·구체화 작업 중**. 목표와 판단 기준의 초안이며, 실행 모델·라이브러리·구현 범위는 아직 확정하지 않았다.

작업을 맡기고 이어갈 때는 [자율 작업 하네스](skill-authoring-autonomy-harness.tmp.md)에서
목표·계획·실행 지침과 증거 기록의 위치를 확인한다. 하네스 준비가 Core 구현의 시작이나 완료를 뜻하지 않는다.

## 1. 확장한 목적

사용자는 Core를 개선하여 **스킬 작성자가 새 기능을 정의하고 조합할 수 있게 하는 것**을 목표로 삼고,
작성 포맷 선택보다 기능 정의·실행 기반 검토를 앞세우는 순서로 목적을 구체화하기로 했다.
사용자 정의 타입은 그 기반의 한 후보이며, 저장 방식 하나를 고르는 것으로 목표를 한정하지 않는다.

작성자가 지원되는 기본 동작을 이용해 값·조건·순서·상태·수명과 재사용 관계를 정의하고,
Core가 이를 검증된 의미로 실행할 수 있어야 한다. 새로운 조합마다 스킬 이름을 분기하는
Rust 코드를 추가해야 하는 구조를 줄이는 것이 목표다.

Core는 피해·회복·공간 조회·시간 진행 등 게임의 기본 동작과 판정 권한을 책임진다.
기본 동작 자체가 새로 필요한 경우에는 공통 계약과 Core를 확장할 수 있다.
어떤 게임 기능이든 Core 수정 없이 표현한다는 목표로 해석하지 않는다.

기존의 AI 텍스트 작성, 사람이 그래프·속성으로 확인·편집, 한 작성 원본,
작성 중 컴파일·진단, Rust Core와 Unity 연출 연결 목표는 [전제](ai-skill-authoring-premises.tmp.md)를 유지한다.
현재 요청은 그 목적과 범위의 구체화다. 이 문서를 작성한 사실은 Core 수정이나 실행 검증 완료를 뜻하지 않는다.

## 2. 작성자가 수행할 작업과 후보 정의 단위

아래 행은 검토할 능력이다. 각각을 독립 문법·노드·Rust 타입으로 채택한 것은 아니다.
기존 M01~M12는 표현해야 할 정보의 분류이며 실행기의 최종 명령 목록으로 간주하지 않는다.

| 작성자가 할 일                                 | 후보 정의 단위             | 구체화할 계약                                                     |
| ---------------------------------------------- | -------------------------- | ----------------------------------------------------------------- |
| 같은 계산을 정의하고 여러 동작에서 사용        | 이름 있는 순수 식·함수     | 입력·출력 타입과 단위, 값의 관측 시점, 의존 참조, 실패와 반올림   |
| 조회·판정·효과 적용을 묶어 새 동작을 구성      | 매개변수 있는 복합 동작    | 호출·반환, 순서, 직접 결과와 후속 결과, 부분 실패·비용 확정 경계  |
| 실행 사이에 필요한 정보를 기억하고 상태를 전환 | 상태 정의와 인스턴스       | 필드·초기값, 소유자·생성 시점, 읽기·쓰기 권한, 진입·이탈·종료     |
| 피해·사망·시간 경과 등에 반응                  | 사건 필터·구독과 후속 흐름 | 사건 발생 단계·출처, 중복·재진입, 활성 범위와 구독 해제           |
| 기다리거나 반복하고 여러 흐름의 완료를 처리    | 지속 흐름과 실행 범위      | 순서·시간, 결과 합류, 취소 전파, 종속·분리 수명, 오래된 실행 거부 |
| 다른 스킬에서 기능을 불러오고 일부만 구성      | 재사용 정의와 명시적 연결  | 공개 입력·출력, 내부 상태의 격리, 정의 버전, 변경 영향·원본 추적  |

후보마다 실제 스킬의 요구 ID, 작성 예시, 호출자·소비자, 기대 결과를 연결한다.
필요한 경우 함께 표현하고, 분리할 이유가 없는 개념을 일대일로 별도 시스템화하지 않는다.
사용자 정의 사건·재귀·임의 컬렉션·외부 코드 호출 등의 지원 여부도 사용 사례와 실행 계약으로 판단한다.

## 3. 성공을 판단할 기준 초안

| ID                   | 판단할 결과                                                           | 필요한 근거                                                             |
| -------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| G01 의미 보존        | 선택한 스킬의 조건·대상·순서·수치식·상태·수명이 기존 합의와 일치      | 기존 요구·전체 예시와 원문 대조, 기대값이 독립적으로 정해진 실행 사례   |
| G02 작성 가능한 조합 | 지원되는 기본 동작 안에서 새 기능과 사용처를 작성 데이터로 정의       | 변경 전후 데이터와 실행 결과, 해당 조합을 위해 추가한 제품 코드의 검토  |
| G03 재사용과 격리    | 같은 정의를 서로 다른 스킬에서 사용하고 각 실행의 상태가 섞이지 않음  | 서로 다른 의미를 가진 둘 이상의 사용처, 다중 소유자·동시 활성 사례      |
| G04 검증과 추적      | 잘못된 타입·단위·참조·미정·미지원을 구분하고 정의와 호출 위치를 찾음  | 각 거절 경계에 도달하는 부정 사례, 원본 위치·호출 맥락과 실행 결과 대응 |
| G05 수명과 종료      | 정상 완료·취소·퇴장·재배치 시 상태·구독·예약 실행이 계약대로 정리됨   | 종료 사유별 기대 결과, 오래된 핸들·타이머의 후속 접근 사례              |
| G06 기존 기반과 연결 | 상태·자원·결과의 원본 권한이 중복되지 않고 기존 소비자와 연결됨       | 생산자→검증→산출물→로드→실행 경로, 영향받는 기존 동작의 회귀 확인       |
| G07 작성·편집 가능성 | 사람이 고칠 값과 공유 영향이 드러나고 AI가 정의를 찾아 수정할 수 있음 | 초기에는 작성·진단 예시, 후속 포맷 단계에서는 실제 편집·AI 과제         |

‘서로 다른 사용처’는 계수만 바꾼 복사본으로 일반성을 증명하는 것을 피하기 위한 기준이다.
첫 검증 범위에서 어떤 공통 기능을 공유하고 어떤 차이를 표현할지는 사례 선정 때 명시한다.
한 사례의 성공을 67개 요구 묶음 전체의 실행 지원으로 확대하지 않는다.
콘텐츠 미정은 유지하며 시험 값은 명시된 fixture로만 사용한다.

## 4. 기존 문서의 역할과 읽는 순서

문서 이동·이름 변경·전면 재작성 없이 역할과 현재 진입점을 정리한다.
기존 1~3단계와 감사 기록의 당시 완료 범위는 유지한다. 구조 초안은 재검토 가능한 설계이고,
스킬 예시는 게임 의미의 대조 자료이며 두 문서 모두 확정된 실행 명세로 승격하지 않는다.

완료 보고의 과거 문장을 모두 현재형으로 고쳐 이력을 훼손하지 않는다.

## 5. 이번 구체화에서 남은 결정

1. 후보 정의 단위가 실제로 필요한 요구 ID와 사용 사례, 합치거나 분리할 이유.
2. 작성 데이터가 정의할 책임과 Core 기본 동작의 책임, 기존 공통 계약의 유지·개선 범위.
3. 첫 실행 검증 범위와 서로 다른 두 번째 사용처, 제외한 요구와 후속 확인 경로.
4. 상태 소유·필드 접근·호출·사건·취소의 최소 계약과 수명 경계.
5. 기존 원본·실행 산출물·저장 상태의 전환 범위와 유효한 중간 상태.
6. 실행 결과·진단에서 관측할 지점과 G01~G07의 구체적인 통과 조건.

구체적인 저장 표현, IR 명령, 인터프리터·VM·코드 생성, DLL 확장, 라이브러리,
텍스트 문법은 위 의미와 필요한 범위를 근거로 비교한다. 어느 후보도 이 문서에서 채택하지 않는다.
전체 Core 재작성, 모든 콘텐츠의 일괄 전환, 미리보기 UI·Unity 실제 연출 완성을 현재 구체화의 완료 조건으로 넣지 않는다.

바로 다음 작업은 기존 요구·예시에서 **정의할 기능, 사용처, 필요한 상태·수명, Core와의 경계**를 뽑아
후보와 연결하는 것이다. 그 결과로 첫 구현 범위와 기대 결과를 고를 수 있을 때 C0를 완료한다.
현재는 목적·문서 역할·후속 순서를 정리한 초안이며 C0 전체가 완료된 것은 아니다.
