# 스킬의 동적 타입·상태 저장·노드 데이터 흐름 참고

조사·기록일: 2026-10-23

사용자 요청으로, **Core가 컴파일 시점에 모르는 스킬별 필드 구성을 작성 데이터에서 선언하고,
실행 중 인스턴스를 생성·조회·갱신하는 문제**의 기존 구현을 기록한다.
공식 문서·예제와 공개 소스를 읽은 조사 결과이며, 라이브러리 선정이나 우리 Core의 구현·실행 검증 결과는 아니다.

[작성 데이터 구조 초안](ai-skill-authoring-data-model.tmp.md)의 M01 값·타입, M05 상태,
M09 인스턴스 수명, M10 참조를 구체화할 때 참고한다.
수명·취소·재실행은 기존 [Forge 참고 기준](forge-statescript-reference.md)과 함께 대조한다.
단계별 작업 상태는 [작성 형식 설계 계획](ai-skill-authoring-plan.tmp.md)에서 관리한다.

## 1. 확인한 자료와 적용 경계

### R01. Flecs — 실행 중 타입 정의와 인스턴스 생성

- [공식 Runtime Component 예제](https://www.flecs.dev/flecs/examples-reflection-runtime_component.html)
- [공식 Meta API](https://www.flecs.dev/flecs/group__c__addons__meta.html)

공식 예제는 컴파일 시점에 알려지지 않은 `Position` 타입을 `x`, `y` 필드와 기본 수치 타입으로 정의한다.
그 타입의 크기를 조회해 엔티티에 데이터를 만들고, 메타 커서로 필드 값을 기록한 뒤 문자열로 출력한다.
Meta API에는 구조체 타입 생성과 이름·인덱스에 의한 멤버 조회가 있다.

우리 문제와 가장 직접적으로 대응하는 선례다. 작성 데이터의 타입 선언을 런타임 타입 정보로 등록하고,
그 정보로 상태를 생성·접근하는 경로를 검토할 수 있다. 예제의 C/C++ API를 읽었으며,
Rust 바인딩에서 같은 기능을 사용할 수 있는 범위와 비용은 확인하지 않았다.
Flecs의 ECS를 도입하거나 현재 Core의 저장 구조를 교체하기로 결정한 것은 아니다.

### R02. Bevy — Rust의 DynamicStruct

- [공식 bevy_reflect의 structs.rs 소스](https://docs.rs/bevy_reflect/latest/src/bevy_reflect/structs.rs.html)
- [Bevy 리플렉션 개요](https://docs.rs/bevy/latest/bevy/reflect/index.html)

`DynamicStruct`는 실행 중 필드를 추가하고 이름·인덱스로 접근할 수 있는 동적 구조체다.
확인한 소스에는 필드 값 배열, 필드 이름 배열, 이름을 인덱스로 연결하는 맵이 있다.
`insert`와 `insert_boxed`는 필드를 추가하거나 같은 이름의 값을 교체하며,
`field`와 `field_mut`는 공통 리플렉션 인터페이스로 값에 접근한다.

Rust에서 스킬별 레코드를 범용 저장 구조로 표현하는 구현 참고이자 재사용 검토 후보다.
새 네이티브 Rust 타입을 실행 중 생성하는 기능과 구분한다.
동적 필드를 담을 수 있다는 사실만으로 작성 스키마의 필수 필드·타입·단위·수명 검사가 확보되지는 않는다.
`bevy_reflect`의 도입 범위, 의존성, 직렬화, 성능과 우리 Core의 결정적 실행 요구에 대한 적합성은 미검증이다.

### R03. Unreal Engine — FInstancedPropertyBag

- [공식 FInstancedPropertyBag API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/CoreUObject/FInstancedPropertyBag)
- [AddProperties 설명](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/CoreUObject/FInstancedPropertyBag/AddProperties)

이름과 타입을 지정해 속성을 추가하고, 타입별 API로 값을 조회·수정하는 속성 저장소다.
속성 설명자 조회, 이름·ID가 대응하는 값의 복사, 배열·맵 등의 접근 API도 제공한다.
`AddProperties`는 속성 타입 변경 시 가능한 수치 변환을 설명한다.

게임 엔진에서 범용 속성 저장과 타입 정보를 함께 다루는 설계 참고다.
Unreal의 객체·타입 체계에 속한 API이므로 현재 Rust Core에 곧바로 연결할 부품으로 간주하지 않는다.
수치 자동 변환 정책도 우리 HP량·개수·기간 등의 단위 검사에 그대로 적용하지 않는다.

### R04. BehaviorTree.CPP — Blackboard와 타입 있는 입출력 포트

- [공식 Blackboard and ports 튜토리얼](https://www.behaviortree.dev/docs/tutorial-basics/tutorial_02_basic_ports/)
- [Ports VS Blackboard 설계 설명](https://www.behaviortree.dev/docs/guides/ports_vs_blackboard/)

Blackboard는 노드가 공유하는 키·값 저장소이며, 입력 포트는 값을 읽고 출력 포트는 값을 쓴다.
포트와 저장 항목의 연결은 작성 파일에서 지정한다. 튜토리얼은 타입이 다른 포트를 연결하면
트리 생성 시 오류가 발생한다고 설명한다. 설계 설명은 포트 선언을 통해 읽기·쓰기 관계를 드러내고,
이름 재연결과 하위 트리 범위를 다루는 이유를 제시한다.

우리에게는 저장된 상태를 그래프 노드에 연결하고 그 연결을 검사하는 방식이 참고 대상이다.
이 자료는 작성 데이터만으로 새로운 네이티브 타입을 만드는 근거가 아니다.
행동 트리의 실행 의미나 Blackboard의 공유 범위를 스킬 그래프 전체에 그대로 적용하지 않는다.

## 2. 우리 설계에서 검토할 연결

다음은 자료에서 도출한 검토 방향이며 확정된 Core API나 작성 문법이 아니다.

| 단계          | 검토할 내용                                                          | 참고                           |
| ------------- | -------------------------------------------------------------------- | ------------------------------ |
| 작성·로딩     | 상태 타입의 필드·타입·기본값을 선언하고 검증한 정의를 등록           | R01, R03                       |
| 인스턴스 생성 | 등록한 정의에 따라 소유자별 필드 값을 생성하고 정의와 실제 값을 분리 | R01, R02                       |
| 노드 연결     | 필드 읽기·쓰기와 입출력 타입을 명시하고 잘못된 연결을 진단           | R04                            |
| 실행          | 검증한 필드 참조로 값을 읽고 갱신하며 기존 게임 동작 계약과 연결     | R01, R02와 우리 M01/M05/M07    |
| 종료·복원     | 시전·배치·런 수명, 취소, 재배치, 저장·복원의 경계를 적용             | 기존 Forge 기준과 우리 M09/M10 |

기술적 선례가 확인된 부분은 동적 필드 정의·저장·접근과 노드 간 타입 있는 데이터 전달이다.
우리에게 남는 일은 다음 계약을 현재 Core에 맞게 설계하고 검증하는 것이다.

- 시전별·파편 복사본별·배치별·런별 상태의 소유자와 초기화·종료 시점.
- 필드 참조의 타입·단위, 미정 값, 누락·잘못된 참조와 런타임 실패 진단.
- 취소·퇴장·재배치 뒤 예약된 실행이 이전 상태를 읽거나 수정하지 못하게 하는 세대 검사.
- 동일 시점의 상태 변경 순서, 스냅샷과 현재값, 저장·복원 시 정의 버전의 일치.
- 기존 자원·결과·효과 상태와 값의 권한이 중복되지 않는 연결 방식.

조사 후의 우선 검토 후보는 **R01의 타입 등록·인스턴스 생성 예제와 R02의 Rust 구현**이다.
실제 라이브러리 재사용과 필요한 범위의 전용 구현을 비교할 때 의존성·성능·직렬화·검증 비용을 확인한다.
이 기록만으로 DLL 기반 확장, 코드 생성, 특정 저장 방식이나 라이브러리를 채택하지 않는다.

## 3. 조사 범위와 다시 확인할 때의 기준

이 문서의 링크는 2026-10-23에 읽은 온라인 자료다. `latest`와 기본 버전 문서 URL은 내용이 바뀔 수 있으며,
이번에는 릴리스·커밋 고정이나 로컬 소스 사본 보관을 수행하지 않았다.
구현 근거로 채택할 때는 사용 버전·커밋과 해당 코드·테스트를 확인하고 기록을 보완한다.
이번 조사에서 외부 예제를 실행하거나 빌드·성능·우리 Core와의 통합을 시험하지 않았다.

외부 자료의 타입 저장 기능을 우리 스킬의 표현·실행 완료 근거로 사용하지 않는다.
게임 의미와 기대 결과는 현행 콘텐츠·공통 계약·사용자 합의를 기준으로 유지한다.
