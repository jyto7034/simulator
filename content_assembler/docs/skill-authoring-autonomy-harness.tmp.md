# 스킬 작성·Core 개선 자율 작업 하네스 — 준비 초안

작성일: 2026-10-23  
상태: **자율 위임 전 준비**. 기존 목표·계획·실행 지침을 연결하는 운영 기준이다.
자동 실행 서비스나 완성된 시험 도구를 구현한 문서가 아니며, 이 문서 자체로 작업 범위를 확대하지 않는다.

## 1. 목표와 근거의 위치

중심 목적은 **작성자가 지원되는 기본 동작으로 새 기능을 정의·조합하고, Core가 검증한 의미로 실행하게 하는 것**이다.
기존 스킬 의미를 보존하면서 스킬마다 전용 Rust 실행 코드를 추가해야 하는 구조를 줄인다.
사용자 정의 타입이나 특정 포맷의 도입만으로 이 목적을 달성했다고 판단하지 않는다.

| 찾을 내용                                    | 관리 위치                                                                                                               |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 사용자 합의·콘텐츠·편집·연출의 지속 기준     | [전제](ai-skill-authoring-premises.tmp.md)와 최신 사용자 요청                                                           |
| 확장한 목적·G01~G07 성공 기준·미결정         | [목표 초안](skill-authoring-core-goals.tmp.md)                                                                          |
| 현재 단계·진행 순서·다음 작업                | [계획](ai-skill-authoring-plan.tmp.md)                                                                                  |
| 조사·구현·검증·감사·교정 방법                | [실행 지침](ai-skill-authoring-execution-guide.tmp.md)                                                                  |
| 기대 동작과 출처                             | [요구사항](ai-skill-authoring-requirements.tmp.md), [대표 예시](ai-skill-authoring-examples.tmp.md), 연결된 현행 콘텐츠 |
| 실제 위임 범위·선택 근거·시도·결함·검증 증거 | [작업 기록](skill-authoring-worklog.tmp.md)                                                                             |

최신 명시적 사용자 요청이 문서보다 우선한다. 이전 완료 기록과 제안은 새 지시로 읽지 않는다.
게임 의미는 현행 콘텐츠·합의로, 구현 사실은 관련 코드와 실행 근거로 판단한다.
각 사실은 위 관리 위치에서 갱신하고 다른 문서에는 링크한다.
Core 로드맵과 연속 실행 지시서에서 채택한 원리·적용 범위는 [작업 기록 H01](skill-authoring-worklog.tmp.md#h01-기존-로드맵실행-문서의-유용한-지침-반영--2026-10-23)에 남긴다.
이후 세부 지침의 통합 위치와 교정은 [H02](skill-authoring-worklog.tmp.md#h02-독립-검토에-따른-정합성-교정과-축약--2026-10-23)를 따른다.
원문 전체를 이번 작업의 실행 명령이나 승인 조건으로 가져오지 않는다.

## 2. 작업을 시작할 때

1. 사용자에게 실제로 위임받은 목표·포함 범위·종료점·제약을 작업 기록에 적는다.
   현재 단계와 직접 의존하는 결과를 계획에서 확인한다. 사용자 부재나 무응답은 범위 확장이 아니다.
2. 선택한 작업을 목표 G 항목과 실제 요구 ID·스킬 사용처에 연결한다.
   어떤 판단이나 관찰 가능한 결과를 얻을지 설명되지 않으면 작업을 재정의한다.
3. 변경할 하위 프로젝트의 `AGENTS.md`와 관련 계약을 읽고 현재 코드·사용자 변경·실행 중인 검사를 확인한다.
   문서만 보고 기존 기능을 다시 만들거나 무관한 변경을 되돌리지 않는다.
4. 기대 결과와 실패·종료 사례를 먼저 적고 필요한 코드·자료만 조사한다.
   전체 외부 프로젝트 분석이나 전면 문서 재작성은 선행 조건이 아니다.

첫 자율 위임 구간으로 **C0~C3**을 권장한다. 목적 구체화부터 실제 Core 경로와 서로 다른 스킬의
조합·재사용 검증까지 연결해 구현 방향을 평가할 수 있는 지점이다. 이는 아직 채택되지 않은 제안이다.
사용자가 더 좁거나 넓은 범위를 위임하면 그 범위를 따른다. 매 단계별 재승인 절차를 추가하지 않는다.

## 3. 한 작업 단위의 진행

```text
목표·요구·기대 결과 확인
  → 관련 경로 조사와 선택 근거 기록
  → 관찰 가능한 결과 하나를 구현 또는 구체화
  → 해당 수용 조건과 영향받는 기존 동작 검증
  → 수정과 분리한 자체 재검토
  → 발견 기록 → 교정 → 영향받는 조건 재검증·재검토
  → 증거·잔여 항목·현재 위치 기록
  → 위임 범위 안의 다음 작업
```

설계 단계의 결과는 실제 사례에 연결된 정의·책임·기대 결과여야 한다.
구현 단계는 저장소·파서·노드 하나의 존재가 아니라 필요한 생산자에서 최종 소비자까지 연결한다.
문서·추상화·테스트 수의 증가를 진행률로 사용하지 않는다.
판단·증거·동작의 변화 없이 같은 조사·시험을 반복하면 원인 가설과 작업 단위를 다시 정한다.

계약·범위·수용 조건에 영향을 주는 주요 선택은 대안·채택 이유·영향·확인할 사례를 작업 규모에 맞게 기록한다.
같은 요구를 충족하는 기술 선택·리팩토링·결함 교정은 위임 범위 안에서 진행한다.
새 근거로 설계를 바꿀 때는 이전 선택과 무효화되는 증거를 남기고 관련 판정을 다시 확인한다.

조사·설계는 [실행 지침 §4](ai-skill-authoring-execution-guide.tmp.md#4-설계-검토와-요구사항-추적)에 따라
현재 사실·합의·제안을 구분하고 실제 계약과 의존성을 확인한다.
작업 분할·기반 개선은 [§5](ai-skill-authoring-execution-guide.tmp.md#5-구현-원칙)에 따라 유효한 중간 상태와 확인된 문제를 기준으로 한다.

## 4. 목표가 달라지는 것을 막는 확인

- 상태를 담을 수 있다는 사실과 새 동작을 정의·조합해 실행할 수 있다는 사실을 구분한다.
- 스킬 이름이나 fixture 식별자로 기존 전용 구현을 선택하는 포장만으로 G02/G03을 통과시키지 않는다.
- 데이터만 바꿔 새 조합이 실행된다는 주장은 공통 실행 기반을 식별한 뒤 작성 입력만 변경한 사례로 확인한다.
  새 기본 동작을 구현했다면 그 변경과 이후 데이터 조합 검증을 구분한다.
- 실패를 없애기 위해 요구를 제외하거나, 미정 값을 임의 확정하거나, 시험 기대값을 제품 코드에 맞추지 않는다.
  실제 전제 오류는 출처·영향을 기록해 교정하며 기존 실패를 지우지 않는다.
- 선택하지 않은 요구도 남긴다. 현재 작업 단위의 제외와 전체 목표에서의 제외를 구분한다.
- 신규 범용 기능은 사용처와 필요한 계약을 제시한다. 후보 라이브러리·VM·문법의 채택을 목적 자체로 바꾸지 않는다.
- 포맷 후보 조사는 C0~C3과 병행할 수 있다. 최종 선택은 실행·편집 요구와 비교 근거를 따른다.
- G01~G07을 세부화할 수 있지만 통과하기 쉽게 필수 의미를 약화하지 않는다. 바뀐 목표는 사용자 합의와 연결한다.

## 5. 단계 전환에 필요한 증거

완료 조건의 원본은 계획과 목표 문서다. 아래는 완료 판정 때 찾을 최소 근거이며 단계별 승인 요청이 아니다.

| 단계 | 완료를 뒷받침할 근거                                                                   | 완료로 세지 않는 것                                       |
| ---- | -------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| C0   | 요구·사용처·후보 능력의 대응, 첫 검증 범위와 둘째 사용처 선정 근거, 기대 결과·미정     | 후보 기능 목록이나 목표 문서만 작성                       |
| C1   | 선택 범위의 입출력·상태·수명·실패 계약, 실제 Core 생산자·소비자와 차이, 구현·검증 경로 | 타입 선언이나 일반적인 실행기 구조도만 제시               |
| C2   | 실제 입력→컴파일→산출물→로드→Core 실행, 성공·진단·종료 결과와 회귀 근거                | helper 호출·저장소 단위 시험·빌드 성공만 확인             |
| C3   | 서로 다른 스킬의 공유 정의·조합 차이, 데이터 변경 사례, 상태 격리·취소와 원본 추적     | 계수만 다른 복사본이나 스킬별 제품 분기로 성공            |
| 4    | 같은 의미·편집 과제의 포맷 비교, 원문·주석 보존·진단, 지정한 AI 과제의 실제 결과       | 짧은 문법이나 조사자의 선호를 AI 사용성 결과로 표시       |
| 5    | 선택한 작성·속성 편집·저장·컴파일·실행 경로의 의미 일치와 범위별 검증                  | 앞선 headless 시험을 편집기·Unity 실제 동작 검증으로 확대 |

선정 사례의 검증 조건을 실행 가능한 시험으로 연결하는 것이 후속 구현의 일부다.
아직 모델과 사례가 정해지지 않았으므로 이 준비 단계에서 내용 없는 시험이나 성공 플래그를 만들지 않는다.
명령·환경·입력 기준·실제 시험 수·종료 코드·원시 결과를 보존하고,
`PASS / FAIL / PARTIAL / UNKNOWN / N/A`는 실행 지침의 의미로 사용한다.
필수 조건의 실패·미확인을 남긴 채 다음 완료 판정으로 덮지 않는다. 승인 범위 안의 원인 교정은 계속한다.

검증은 지원 경로의 목표 동작·거절 지점까지 실제로 도달했는지 확인한다.
범위·시험 준비·성능·증거 재사용은 [실행 지침 §6](ai-skill-authoring-execution-guide.tmp.md#6-검증-설계와-실행)을 따른다.
검토는 수정과 분리하고 발견·교정·재검증을 연결한다.
자체·독립 검토 구분과 필수 조건은 [§7](ai-skill-authoring-execution-guide.tmp.md#7-완료-검토와-감사),
원인 분류와 교정은 [§8](ai-skill-authoring-execution-guide.tmp.md#8-결함-교정과-재감사)을 따른다.

## 6. 사용자 판단·중단·재개

일반 기술 선택은 근거를 남기고 진행한다. 게임 의미 변경·상충하는 합의 등 실제 사용자 판단이 필요한 경우에는
선택지와 영향, 제안, 막힌 작업을 기록하고 해당 결정에 의존하지 않는 위임 작업을 계속한다.
이미 승인된 선택을 반복해서 질문하지 않으며 문서에 있다는 이유만으로 새 승인 단계를 만들지 않는다.

진행 중인 검사는 [실행 지침 §6.3](ai-skill-authoring-execution-guide.tmp.md#63-실행과-증거-관리)에 따라 입력을 고정하고 소유 세션을 관리한다.

외부 도구·환경 때문에 검증할 수 없으면 제품 결함과 구분하고, 가능한 대체 근거의 범위와 남은 검증을 명시한다.
필수 검증을 수행하지 못한 결과는 완료가 아니다. 새 근거 없이 같은 실패 명령을 반복하지 않는다.
사용자가 중지하면 정리·기록하고 멈춘다. 위임한 종료점에 도달하면 그 범위의 결과를 보고한다.

작업이 중단되거나 담당자가 바뀌면 계획의 현재 위치와 작업 기록의 마지막 유효 근거부터 재개한다.
관련 파일·설정이 달라졌는지, 진행 중인 검사 세션이 있는지 확인하고 이전 작업을 중복 실행하지 않는다.
이 하네스는 상태를 복구하는 기준이며 프로세스의 무중단 실행을 보장하는 장치가 아니다.

## 7. 인계와 보고

의미 있는 시도·주요 선택·실패·설계 변경·검증 완료를 작업 규모에 맞게 기록한다. 원시 결과는 기존 로그를 연결한다.
전체 단계 상태와 다음 행동은 계획에만 유지하고, 작업 기록에는 해당 시점의 이력과 증거를 둔다.
최종 보고는 달성한 범위, 바뀐 동작, 검증 근거, 남은 필수 미검증·판단 사항과 읽을 문서를 간결하게 제시한다.

첫 자율 위임을 할 때 사용할 수 있는 요청 예시는 다음과 같다. 아직 실행 지시로 적용하지 않는다.

> 목표 문서와 이 하네스를 기준으로 C0부터 C3까지 자율적으로 진행한다.
> 필요한 조사·Core 수정·검증·교정·자체 재검토를 포함한다.
> 기존 게임 의미와 사용자 변경을 보존하고, 기술 선택은 근거를 남겨 결정한다.
> 포맷 후보 검토는 병행하되 최종 포맷 선정·편집기 구현은 이번 종료점 이후다.
> 새 사용자 판단이 필요한 작업은 구분하고, 답변에 의존하지 않는 범위는 계속한다.
> C3의 수용 조건 충족 여부와 근거, 남은 요구와 다음 선택을 보고한다.
