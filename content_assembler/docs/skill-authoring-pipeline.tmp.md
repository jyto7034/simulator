# 스킬 조립기 임시 작업 파이프라인

작성: 2026-10-22 / 후속 작업 안내 갱신: 2026-10-23  
현재 개선 작업: [기능 정의·조합을 위한 Core 목표 구체화](skill-authoring-core-goals.tmp.md). 단계와 다음 행동은 [개선 계획](ai-skill-authoring-plan.tmp.md)에서 관리한다.  
기존 그래프 경로의 완료 이력: **P5~P8 구현·필수 검증·독립 검토 1회·개선 후 재검증 완료**  
일반 보스 10계열·엘리트 11계열의 포함 동작을 작성·컴파일·IR/RON·실제 전투 경로에 연결했다.
미정 수치와 명시적으로 보류한 형태는 유지한다. 아래 기록은 단계별 당시 결과이며, 최신 통합 근거는
[통합 검증](#p5-p8-integrated-verification)과 [독립 검토·개선 결과](#p5-p8-independent-review-complete)에 모았다. 신규 비참여 검토자 한 명의 지적 두 건을 근거 확인 후 수용하고 수정·재검증했다.

## 목적과 범위

확정된 스킬 파편을 공통 기능의 조합으로 작성하고 실제 게임에서 같은 의미로 실행한다.

**노드 그래프 작성 → Core 검증·컴파일 → 실행용 IR → RON 저장 → 게임 로드·실행**

- 현재 제작 기준은 일반 보스의 직원용 파편 10계열이다. 엘리트 11계열도 작성·대조 대상이며,
  후속 검토에 따른 변경은 해당 콘텐츠와 영향을 받는 공통 기능에 반영한다.
- 최종보스 파편은 설계 완료 뒤 별도 단계에서 추가한다. 최종보스용 전장 전환·고유 연출을
  현재 작업의 선행 조건으로 만들지 않는다.
- 합의된 기본형·개화형과 파편 동작에 필요한 장비·유물 연결을 대조한다.
  원문에서 명시적으로 보류한 형태는 보류로 표시하고 새 동작을 만들지 않는다.
- 적 보스 조우 전체, 장비 제작기 전체, 연출 제작기 전체를 함께 구현하는 작업은 아니다.
- 2026-10-22 사용자가 P5~P8 구현·검증과 최종 독립 검토·개선을 명시적으로 요청했다.
  P5 작성과 편의 개선, P6 대조, Core 컴파일·IR/RON·실제 전투 실행 및 필수 검증, 한 차례 독립 검토와 개선·재검증을 완료했다.
  앞선 문서 생성 한정 설명과 후속 단계 표기는 이번 실행 승인을 제한하지 않는다.

범위 원본은 [프로젝트 목적](project-purpose.md), 콘텐츠 기준은
[일반 보스 요구사항](normal-boss-skill-requirements.md)과
[현행 환상체 목록](../../core_enhanced/docs/content/abnormalities/README.md)이다.
판정·수치·합의를 이 문서에 별도 복제하지 않고 해당 원문을 참조한다.

## 작업에 필요한 기준 문서 읽기

단계 착수·설계·테스트 준비 때 해당 작업의 기대 동작을 결정하는 문서를 읽는다.
아래 문서를 매번 전부 읽는 것은 아니며, 관련 절부터 확인하고 근거가 부족할 때 범위를 넓힌다.

- [게임 룰북](../../core_enhanced/docs/game_rulebook.md)에서 공통 정책과 관련 세부 규칙의 위치를 확인한다.
- 정확한 판정은 연결된 `game_rules/`의 관련 페이지에서 확인한다. 공명·스킬 사용·시간·배치·제어는
  [전투 규칙](../../core_enhanced/docs/game_rules/combat.md), 유물 연결은
  [유물 규칙](../../core_enhanced/docs/game_rules/relics.md), 전투 종료·원정 상태·복원은
  [결과와 저장 규칙](../../core_enhanced/docs/game_rules/results-and-save.md)을 필요에 따라 읽는다.
- 해당 파편의 현행 상세 문서와 관련 장비·유물·연결 문서를 읽어 고유 동작과 명시된 예외를 확인한다.
  요구사항 요약만으로 원문의 조건을 대신하지 않는다.
- [공통 스킬 그래프 계약](common-skill-graph-contract.md)과 실제 코드·사용 예를 대조해
  합의된 의미, 현재 지원, 추가 구현이 필요한 부분을 구분한다.
- 상태·수명·취소·재실행을 설계할 때 [Forge Statescript 적용 기준](forge-statescript-reference.md)의
  관련 원리와 고정 버전 소스·테스트를 대조한다. P1~P6에서는 작성 계약과 진단에, P7~P8에서는
  컴파일·실행 의미와 검증에 반영한다. 외부 구현을 현행 게임 규칙이나 우리 검증 결과로 대체하지 않는다.
- 최신 명시적 사용자 합의를 우선하며, 공통 규칙과 개별 콘텐츠 문서가 충돌하면 근거를 확인한다.
  현재 구현·파일 수정 시각·과거 아카이브를 이유로 새 규칙을 확정하지 않는다.
- 이미 읽은 자료가 유효하면 재사용한다. 관련 내용이나 전제가 바뀌었거나 기억한 근거가 불명확할 때
  해당 부분을 다시 읽고, 구현·검증 판단에 사용한 문서와 절을 작업 기록에 연결한다.

## 작업 원칙

1. 실제 파편 하나를 작성하며 필요한 기능을 찾는다. 사용처 없는 범용 기능을 먼저 만들지 않는다.
2. 기존 동작·콘텐츠 정의를 조합하고 참조한다. 스킬별로 같은 공격·효과·검증을 복제하지 않는다.
3. 공통 규칙은 해당 동작이 책임진다. 제작자가 매번 엔진 내부 절차를 모두 연결하게 하지 않는다.
   묶인 동작의 의미와 내부 구성은 확인할 수 있어야 한다.
4. 게임 판정과 연출을 분리한다. 보여주기 위한 눈·검·입자를 실제 전투 유닛으로 추론하지 않는다.
5. 합의된 동작은 그대로 구현하고 수치는 조정 가능한 매개변수로 둔다. 미기입 값을 임의로 채우지 않는다.
6. 필요한 의미가 빠졌으면 기존 합의부터 확인한다. 2026-10-21 사용자 위임에 따라 통상적인 게임 규칙으로
   정할 수 있는 정책은 작업자가 판단하고 해당 원문에 결정·근거를 남긴다. 미정 표기만으로 중단하지 않는다.
   기존 합의의 변경·충돌이나 플레이 방식에 큰 영향을 주어 사용자 판단이 필요한 문제에서만
   작업을 멈추고 일반 채팅으로 질문한다. 질문 카드를 사용하지 않는다.
7. 설명문에 동작을 적어둔 것, 편집 검사 통과, 실제 전투 실행 성공을 서로 다른 상태로 기록한다.

금지·수동 인계 규칙을 이 요청에 적용해 검토를 생략하거나 다시 승인을 요청하지 않는다.

### 단계 착수와 구현

1. 이 문서의 현재 위치·최근 기록·다음 작업부터 확인한다. 관련 소스와 기존 변경, 마지막 유효 검사,
   남은 문제, 실행 중인 세션을 대조한다. 과거 기록에 실행 중이라고 적혔다는 이유로 중복 실행하지 않는다.
   위 기준 문서 읽기에 따라 해당 파편과 공통 게임 규칙의 관련 절을 확인한다.
2. 현재 요구에 필요한 코드·직접 호출자·소비자를 읽고 기존 기능과의 차이를 확인한다.
   권장 구조나 검색 결과만으로 실제 지원 여부를 확정하지 않는다.
3. 이번 결과물·보존할 동작·변경할 동작·중요한 상태와 수명·검증 방법을 기존 진행 기록에 짧게 적는다.
   단순 변경에 별도 설계서나 승인 양식을 추가하지 않는다.
4. 단계 번호를 필수 선행으로 간주하지 않는다. 실제 기능·저장 계약·검증에 필요한 선행과 권장 순서를
   구분한다. 모델·편집 연산·검증·저장·소비자가 함께 바뀌어야 한다면 같은 작업에서 맞춘다.
   후속 단계가 시작되지 않아도 현재 편집기의 지원 범위가 일관된 상태여야 한다.
5. 정확성이나 검증을 막는 상태 소유권 혼재·규칙 중복은 해당 기능과 함께 해결한다.
   외형이 비슷한 동작을 억지로 합치거나 무관한 정리·미래용 계층을 추가하지 않는다.
6. 승인된 구현 요청에서는 관련 검증과 일반 오류 교정까지 이어간다. 내부 구현 선택·테스트 실패·단계 번호
   변경을 반복 승인 사유로 만들지 않는다. 게임 정책은 작업 원칙 6에 따라 자율 판단 범위와 사용자 결정 범위를 구분한다.
7. 검사가 실행 중인 동안 그 검사의 소스·테스트·fixture·설정·판정 입력을 고정한다.
   수정이 필요하면 해당 실행을 종료·정리한 뒤 변경하고 필요한 검사를 다시 한다.

### 검증과 실패 교정

- 기대값은 합의한 규칙·작은 수작업 예제·외부 관찰에서 도출한다. 제품 계산이나 helper를 복제한 시험으로
  정확성을 주장하지 않는다. 초기 상태 → 행동 → 관측 → 기대 결과를 먼저 정하고, 거절 사례도 의도한
  거절 지점까지 도달하는지 확인한다.
- 편집기의 작성 오류·지원 JSON 가져오기·저장/재열기·실제 IO 실패 등 지원 경로를 검증한다.
  지원 경로에서 발생할 수 없는 내부 상태 위조를 새 필수 시험으로 만들지 않는다.
  도달 근거가 미확인인 사례는 곧바로 결함이나 범위 밖으로 단정하지 않으며, 기존 입력 검증을 약화하지 않는다.
- 변경 위험에 맞는 검사를 먼저 수행하고 필요한 통합 회귀를 마친다. 기존 `AGENTS.md`의 필수 검사는 유지한다.
  관련 소스·입력·시험·설정·의존성·환경이 같거나 비영향 근거가 있는 결과는 재사용할 수 있다.
  변경된 경로는 다시 검증하며, 영향 분리가 어려우면 관련 범위를 넓힌다.
- 실행·재사용·미실행을 구분한다. 종료 코드와 실제 실행/통과/실패/skip 수를 확인하고,
  0개 실행·skip·중단·빌드 성공만을 기능 테스트 통과로 기록하지 않는다.
- 실패는 제품·시험·fixture·기대값·판정 도구·환경으로 원인을 구분한다. 예상과 실제의 차이,
  깨진 가정, 교정 근거와 영향 범위를 남긴다. 새 가설이나 교정 없이 같은 실행을 반복하지 않는다.
- 실패를 숨기기 위해 기대값·입력 규모를 바꾸거나 한도·허용 오차를 완화하거나 테스트를 끄지 않는다.
  특정 시험에서만 동작하는 제품 분기, 조용한 성공 대체, 임의 대기시간 증가로 결함을 우회하지 않는다.
- 장시간 검사는 기존 근거로 예상 시간과 진단 시점을 정한다. 기존 세션에서 결과를 수집하고 짧은 주기 조회나
  중복 실행을 피한다. 자기 실행만 필요한 근거를 보존해 중단하고 정리한다. UI 검사에서 기존 서버를 임의 종료하지 않는다.
- 성능 문제가 실제로 생기면 같은 대표 입력의 시간·메모리·작업량을 대조한다. 한도 완화를 최적화 성과로
  기록하거나 매 작업에 별도 성능 측정을 강제하지 않는다.

### 작업 중 피드백과 자기 개선 — 2026-10-22 사용자 요청

**구현과 테스트 통과에 더해, 실제 제작자의 관점으로 결과물을 비판하고 개선 효과까지 확인한다.**
사용자가 문제를 먼저 지적하거나 전체 작업이 끝날 때까지 기다리지 않는다. 단계별 실제 그래프를 작성·수정할 때
주 실행자가 이 과정을 수행한다. 전체 완료 후 독립 검토 한 차례는 이 일상적인 자기 검토를 대체하지 않는다.

1. **실제 과제로 관찰:** 대표 그래프를 열어 시작·분기·비용·효과·종료를 따라가고, 수치 하나와 조건 하나를
   찾아 수정한 뒤 실행 취소·저장·재열기를 확인한다. 변경과 관련된 과제를 선택하며, 구현 지식을 이용한
   추측이나 우측 패널의 설명만으로 그래프 자체의 이해 가능성을 대신하지 않는다.
2. **문제와 원인 구분:** 어디서 흐름을 놓치는지, 어떤 값의 위치나 출처가 불명확한지, 어떤 조작이 불필요하게
   반복되는지 화면·행동·코드에 근거해 적는다. 가독성·작성 편의성·불필요한 복잡성을 정확성과 함께 검토한다.
   화면 잘림·글리프·자동 접근성 검사 통과만으로 사용성이 확인됐다고 판단하지 않는다.
3. **레퍼런스와 비교:** Forge 등의 실제 화면·작성 방식·관련 구현에서 문제를 줄이는 원리를 찾는다.
   작은 예제와 큰 그래프의 차이를 고려하고, 외형 모방이나 기능 수 비교만으로 결론을 내리지 않는다.
   우리 게임의 의미와 상태·참조 계약을 보존하는 개선안을 선택한다.
4. **타당한 개선 반영:** 원인을 확인한 문제는 승인된 구현 범위에서 배치·표현·편집 방식 또는 구조를 고친다.
   통상적인 개선마다 재승인을 요구하지 않는다. 기존 합의 변경과 게임 정책 판단은 작업 원칙 6을 따른다.
   사용자 피드백도 근거와 영향 범위를 확인해 반영하고, 보류·비수용이면 이유와 남은 영향을 기록한다.
5. **효과와 회귀 확인:** 같은 대표 그래프·창 크기·배율·테마와 같은 작성 과제로 개선 전후를 비교한다.
   핵심 흐름을 따라갈 수 있는지, 값과 출처를 찾고 수정할 수 있는지, 불필요한 화면 이동·패널 왕복·연결 추적이
   줄었는지 구체적인 관찰을 남긴다. 노드나 선의 수 감소만으로 성공을 선언하지 않는다.
   의미 보존과 영향을 받는 편집·저장·검증 경로도 재검사한다. 효과가 없으면 원인과 접근을 재검토한다.
6. **완료 근거:** 문제 → 원인과 비교 근거 → 변경 → 같은 과제의 전후 관찰 → 회귀 결과·남은 한계를
   기존 진행 기록에 짧게 남긴다. 확인하지 않은 사용성을 완료로 표시하지 않으며, 실질적인 문제가 없으면
   개선 실적을 만들기 위한 변경이나 반복 검토를 강제하지 않는다.

**이번 대화에서 확인된 후속 과제 — 아래 P5 실행에서 1차 개선:** 사용자가 현재 그래프를 읽기 어렵다고 지적했다.
기존 P4 화면 검사는 잘림·글리프·편집 동작 확인에 치우쳐 그래프 전체의 이해 가능성을 충분히 검증하지 못했다.
생성 순서 중심 배치, 실행 흐름과 값/참조 연결의 구분, 작은 글자·긴 이름, 별도 값 노드와 연결의 필요성을
후속 구현에서 우선 검토한다. 노드 내부 값 저장은 이미 가능하지만 현재 캔버스는 주로 표시용이고 편집은
우측 패널에 있으며, 입력마다 직접값·참조·계산을 선택하는 공통 방식은 별도 설계가 필요하다.
고정값의 노드 내부 편집과 필요한 입력의 연결 전환은 개선 후보이며, 이번 문서 기록만으로 구현됐다고 보지 않는다.
P1~P4의 기존 기능 검사 결과는 보존하되 가독성 개선 완료의 근거로 확대하지 않는다.

### 완료 검토와 재개 기록

완료 전에는 현재 코드·주요 상태 경계·시험 기대값·원시 결과와 단계 완료 조건을 직접 대조한다.
검사 통과나 자신이 작성한 요약만으로 동작 누락 여부를 판단하지 않는다.
위 작업 중 피드백 절차에 따른 실제 작성 과제와 개선 전후 관찰도 확인한다.
자체 검토를 독립 감사로 표시하지 않는다.

기존 사용자 변경과 실패 원본을 보존하며 전체 저장소 reset/clean/stash로 정리하지 않는다.
문서 갱신·시간 경과·단계 이동만을 이유로 전체 테스트·전수 해시·압축 보관을 반복하지 않는다.
현재 변경을 검증하는 데 필요한 기록만 남기고 기존 유효 증거의 재사용 이유를 표시한다.
사용자 중지나 질문 대기 때는 현재 위치와 재개 조건을 이 문서에 남긴다. 무응답이나 시간 경과로 재개하지 않는다.

### 전체 완료 후 독립 검토와 한 차례 개선 — 2026-10-22 사용자 요청

**현재 상태: 대기.** P1~P8의 구현·필수 검증을 마친 뒤, 최종 완료 보고 전에 다음 절차를 한 차례 수행한다.
P4 자체 검토나 같은 실행자의 역할 전환으로 이 독립 검토를 대신하지 않는다. 이번 문서 반영은 실행 절차의
기록이다. 이후 P5~P8 실행 요청에 따라 구현을 시작했으며, 최종 독립 검토는 구현·필수 검증 완료 뒤에 착수한다.

1. **검토 입력 준비:** 현재 요구사항·완료 조건, 최종 코드·그래프·산출물, 관련 계약, 실행 명령과 원시 검사 결과,
   재사용 근거·알려진 한계를 제공한다. 검토 중 대상 입력을 수정하지 않는다. 변경이 생기면 어떤 입력에 대한
   검토인지 다시 구분한다. 이를 위해 정식 Goal 동결·전체 압축·전수 해시 절차를 새로 만들지는 않는다.
2. **독립 서브에이전트 호출:** 이번 구현에 참여하지 않은 새 서브에이전트 한 명에게 검토를 맡긴다.
   구현 대화 전체를 상속시키지 않는 새 문맥으로 시작하고, 필요한 자료의 위치와 검토 범위를 중립적으로 전달한다.
   작성자의 완료 주장이나 권장 결론에 동의하도록 유도하지 않는다. 검토자는 제품을 직접 수정하지 않고
   요구사항 충족·설계/코드 결함·검증 누락·기존 기능 회귀를 실제 코드와 결과에서 확인한다.
   가독성·작성 편의성·불필요한 복잡성도 대표 그래프의 실제 과제로 평가하고, 작업 중 자기 검토의
   전후 근거를 대조한다. 자동 검사 통과나 작성자의 사용성 주장만으로 충분하다고 보지 않는다.
3. **근거 있는 지적 수집:** 각 지적에 중요도, 대상 파일/위치, 위반한 계약 또는 방해받는 작성 과제, 지원 경로에서의 발생 조건,
   재현 방법 또는 구체적인 근거, 영향과 수정 방향을 기록한다. 임의 내부 상태 변조만 가능한 사례와
   발생 근거 미확인은 지원 입력·저장·실행 경로에서 재현되는 결함과 구분한다. 실제 필수 검증 누락을
   범위 밖으로 돌려 완료 처리하지 않는다. 근거 없는 가설을 확정 결함으로 보고하지 않는다.
4. **주 실행자의 타당성 판단:** 모든 지적을 원문 계약·코드·재현 결과와 다시 대조해 수용·비수용·추가 확인으로
   분류하고 이유를 남긴다. 검토자의 권위만으로 수정하거나, 기존 구현과 다르다는 이유만으로 기각하지 않는다.
   추가 확인 항목은 가능한 조사로 판단하고, 해결할 수 없는 사항은 구체적인 장애·미검증으로 남긴다.
5. **개선과 재검증:** 타당한 지적은 검토 기록을 보존한 별도 수정 작업에서 코드·설계·문서·테스트에 반영한다.
   실패 재현과 변경 영향 범위를 검사하고 필요한 회귀를 수행한다. 기대 동작·입력 규모·허용 오차를 약화하거나
   테스트를 끄지 않는다. 바뀌지 않은 경로의 유효 증거는 근거와 함께 재사용한다. 타당한 지적이 없으면
   그 결과를 기록하며 개선 횟수를 채우기 위한 불필요한 변경은 하지 않는다.
6. **종료 기록:** 검토 대상과 결과 위치, 지적별 판단·근거·반영 내용 또는 비수용 이유, 재검증 결과와 남은 한계를
   이 진행 기록에서 연결한다. 독립 검토 → 타당성 판단 → 개선·재검증은 한 차례이며, 수정 검증에 실패하면
   원인을 해결할 때까지 필요한 교정은 계속한다. 독립 검토를 반복하는 무한 절차로 만들지 않는다.
   미해결 필수 결함이나 검증 누락이 있으면 전체 완료로 표시하지 않는다.

여기서 자기 개선은 이번 결과물의 품질 개선이며 모델 자체의 학습·수정을 뜻하지 않는다.
[연속 실행 지시서](../../core_enhanced/docs/roadmaps/core_first/execution/CONTINUOUS_EXECUTION_INSTRUCTIONS_REVISED.ko.md)의
§4~5에서 지원 경로·기대값·실패 원인 판정을, §7에서 실제 코드/원시 결과 대조와 유효 증거 재사용을,
§8에서 검토 입력 고정과 검토/교정 분리를, §9에서 사실에 근거한 종료 기록을 채택한다.
그 문서의 단독 실행·서브에이전트 금지보다 이번 사용자의 명시적 독립 검토 요청을 우선한다.
Core 우선 로드맵의 U29/U33/U31 독립 제작·정식 감사나 특정 모델 지정까지 수행했다고 주장하지 않는다.

**확정한 사용자 결정:** 도발 유지 중에는 시전자 이외 아군의 새 저지를 막는다. 아래 질문에 사용자가 제안 A를 수락했다.
파편 원문의 ‘이미 저지된 적도 빼앗기’는 기존 저지 해제만 확정하고 새 저지 관계의 우선순위는 후속 세칙으로 남겼다.
공통 저지 규칙을 그대로 적용하면 해제 직후 같은 아군이 다시 저지할 수 있어 집결 효과가 막힐 수 있다.
반대로 다른 아군의 새 저지를 막는 것은 도발에 저지 예외를 추가하는 플레이 방식 결정이다.

- 제안 A: 도발 중 시전자 이외 아군의 새 저지를 막는다. 시전자에게 접근하면 시전자의 기존 저지 수·조건을 적용한다.
  벽 통과·순간이동·무제한 저지는 허용하지 않는다. 집결 역할을 유지하는 안으로 추천했고 사용자가 채택했다.
- 대안 B: 시작 시 기존 저지만 해제하고, 이후에는 다른 아군도 정상적으로 다시 저지할 수 있다.

새 서브에이전트 한 명에게 독립 검토를 맡긴다. 앞서 읽은 기준 문서와 P4의 유효한 기능 검증은 재사용한다.
기존 P4 보고서의 모델 167개·UI 24개·화면 48장 검토는 당시 작성 기능의 근거이며 사용성 개선이나
Core 실행의 근거가 아니다. 현재 저장소에 광범위한 기존 변경이 있으므로 관련 파일만 편집한다.

- **첫 작업:** P5 파편 원문·장비/유물 연결을 대조하면서 기존 기사 그래프의 가독성을 먼저 개선한다.
  생성 순서 격자 배치를 연결 방향 배치로 바꾸는 명시적 편집, 실행 연결 집중 보기, 연결값의 출처 표시,
  캔버스에서 설정값과 연결된 고정값 수정, 제목 줄바꿈과 글자 크기를 구현 중이다.
  문서의 의미·참조 ID는 보존하고 배치는 하나의 이동 이력으로 확정한다. 공유값은 공유임을 표시한다.
- **검증 과제:** 같은 기사 그래프에서 입력→자격→접수 흐름을 보고 단계 소비의 나눌 수와 보호막 유지 시간을
  수정한다. 배치/값 수정의 실행 취소와 저장·재열기, 같은 화면 조건의 전후 관찰을 대조한다.
  현재 배치 보존·겹침·한 번의 실행 취소·오래된 결과 거절 모델 2개와 빌드는 통과했고 UI 검증은 진행 중이다.
  첫 UI 실패는 미저장 빈 그래프 교체 확인을 테스트에서 누락한 준비 오류로 확인해 실제 교체 동작을 추가했다.
- **P5 표현 경계:** 녹아내리는 사랑은 출처별 숙주 감염과 연속 위력 자원, 무기 피격/사망 전파,

  수치 공백을 임의 밸런스로 채우지 않고, 실행 검증에 필요한 수치는 명시적인 시험 입력에서만 지정한다.

## 파편별 공통 작성 완료 기준

1. 합의된 동작이 노드·설정·연결·참조로 표현되고, 핵심 동작이 메모에만 남지 않는다.
2. 해당 파편 그래프가 실제 파일로 존재하며 저장·재열기와 편집 이력에서 의미가 유지된다.
3. 미정 수치, 의미 누락, 잘못된 연결과 현재 미지원 기능을 구분해 진단한다.
   미정 값이 남은 작성 완료는 실행 준비 완료와 구분한다.
4. 기존 기능 재사용 여부와 새 공통 기능의 실제 사용처를 확인한다. 특정 스킬 이름으로 숨은 실행 분기를 만들지 않는다.
5. `npm run check`와 변경에 필요한 빌드·테스트를 통과한다. UI 변경은
   [AGENTS.md](../AGENTS.md)와 [UI 검증 안내](ui-validation.md)에 따라 화면을 직접 검토한다.
6. 대표 그래프에서 흐름 파악·값 찾기·수정 과제를 직접 수행해 가독성·작성 편의성·불필요한 복잡성을 검토한다.
   발견한 문제의 타당성을 판단해 개선하고 같은 과제에서 효과와 회귀를 확인한다. 남은 사용성 한계를 명시한다.
7. 원문·그래프 파일·변경 기능·검증 기록·미검증 범위를 연결한다. Core 실행과 Windows 네이티브 검증 여부를 구분한다.

P7·P8에서는 위 작성 기준에 더해 컴파일 진단, RON 재로드, 실제 전투 결과를 각각 확인한다.
대표 파편 하나의 통과를 모든 파편의 실행 완료로 확대하지 않는다.

## 진행 기록과 갱신

한 작업을 마칠 때 현재 위치, 단계 상태, 관련 체크리스트와 아래 기록을 함께 갱신한다.
단계를 완료로 표시하려면 완료 조건에 대응하는 결과물과 검증 근거가 있어야 한다.
수행 중 결정한 게임 규칙은 콘텐츠 원문에, 공통 의미는 공통 계약에 반영하고 여기에는 링크만 남긴다.
새 문서나 검증 절차를 단계마다 반복 생성할 필요는 없다.

- 요청 범위와 끝점, 현재 상태, 다음 행동
- 변경 파일·기능과 실제 선행 근거, 기존 변경과 이번 변경의 구분
- 실행 명령·입력·환경·결과 위치와 필요한 시험 수, 재사용한 검증과 비영향 근거
- 실패가 있었다면 원인·교정·재검증, 남은 미검증과 사용자 질문
