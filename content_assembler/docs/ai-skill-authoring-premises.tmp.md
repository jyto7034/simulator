# AI 스킬 작성 방식 개선의 전제 — 임시

작성일: 2026-10-23

저성능 AI도 스킬의 의미를 이해하고 작성·수정할 수 있도록 제작 방식을 개선하기 위한
논의 기준이다. 사용자가 제시한 네 가지 전제, 추가로 제안한 기준과 후속 합의한
작성·편집 방향을 기록한다. 구현 완료 보고나 구체적인 작성 형식의 명세가 아니다.

현재 구현의 제작 방식은 노드 그래프다. 개선 방향은 AI가 구조화된 텍스트로 작성하고,
그 데이터를 그래프로 변환하여 사람이 확인하고 편집하는 방식으로 합의했다.
구체적인 문법과 데이터 구조는 후속 설계에서 정한다.

## 기능 정의·조합으로 목적 확장 — 2026-10-23 후속

사용자는 Core를 개선하여 스킬 작성자가 새 기능을 정의하고 조합할 수 있게 하는 방향으로
목적을 확장·구체화하기로 했다. 사용자 정의 타입의 저장뿐 아니라 계산·동작·상태·사건·수명과
재사용 관계 중 무엇을 작성자가 정의할 수 있어야 하는지 검토한다.
[확장 목표 초안](skill-authoring-core-goals.tmp.md)에 후보 능력·성공 기준·문서 역할·미결정을 둔다.
이 목록은 검토 범위이며 각 기능이나 특정 언어·라이브러리의 채택을 뜻하지 않는다.

기존 1~3단계 결과를 의미 대조 자료로 유지하고, 포맷 선택보다 Core 실행 모델의 설계·작은 실행 검증을
앞세운다. 현재 단계와 작업 순서는 [계획](ai-skill-authoring-plan.tmp.md)을 따른다.
아래 콘텐츠·편집·연출·진단에 관한 합의는 계속 적용한다.

## Rust Core와 Unity 연출의 연결 기반 — 2026-10-23

게임은 **Rust로 작성된 Core 백엔드를 Unity에 네이티브 방식으로 연결하여 사용**할 계획이다.
스킬 작성 데이터는 게임 판정뿐 아니라, Unity에서 이펙트·사운드·애니메이션 등을
재생하기 위해 필요한 정보를 표현할 수 있어야 한다.

**연출의 세부 명세는 아직 확정되지 않았지만, 스킬 실행과 연출을 연결할 기반은 마련한다.**
작성 데이터 구조 초안과 대표 스킬 예시에도 이 요구를 포함한다.
현재 단계에서 개별 스킬의 연출이나 구체적인 연동 API까지 확정하는 것은 아니다.

기반 설계에서 다룰 정보의 범위는 다음과 같다. 아래 항목은 검토할 정보 범위이며,
확정된 필드명이나 데이터 스키마는 아니다.

- 재생할 이펙트·사운드·애니메이션 자원의 참조.
- 시전·명중·상태 진입 등 연출을 시작하거나 갱신하는 스킬 실행 사건과 시점.
- 재생 대상·위치·방향과 부착·추적 관계.
- 연출의 수명과 종료 조건, 취소·사망·상태 종료 시의 처리.
- 크기·속도 등 필요한 재생 매개변수.
- 원본의 동작, Core의 개별 스킬 실행과 Unity의 연출 재생을 연결하여 식별·추적할 정보.

Core의 판정과 Unity의 연출 재생을 연결하는 전달 데이터와 책임 경계를 후속 설계에서 구체화한다.
연출 자원이나 세부 값이 정해지지 않았어도 연결 의도와 미정 상태를 원본에 보존할 수 있어야 한다.
미정 연출을 임의로 확정하거나 구현 완료로 표시하지 않는다.
연출 미정이 컴파일·미리보기의 어느 단계에 어떤 진단을 발생시키는지는 별도로 정한다.

## 합의한 작성·편집 방향 — 2026-10-23

**AI가 주로 작성하되 사람도 편집할 수 있고, 사람의 편집 범위를 속성 수정부터
구조 변경까지 단계적으로 넓힌다.** 단순 수치 변경을 위해 AI에게 요청할 필요는 없어야 한다.

### 초기 범위

- AI는 구조화된 텍스트 원본에서 스킬의 구조와 동작을 작성·수정한다.
  자연어 설명을 추측하여 실행하는 방식이 아니라, 타입·참조·실행 의미가 명시된 데이터를 작성한다.
- 작성된 데이터를 노드 그래프로 변환하여 흐름과 관계를 보여준다.
  그래프의 동작이나 진단을 선택하면 관련 원본 위치를 확인할 수 있게 한다.
- 사람은 그래프에서 동작을 선택하고 속성 패널에서 피해량·지속 시간·주기 등 수치와
  대상·피해 유형·조건 등 제공된 편집 항목을 직접 변경할 수 있다.
- 노드 추가·삭제와 연결 변경 같은 구조 편집은 초기에는 AI 또는 텍스트 편집으로 처리한다.
  그래프에서 직접 구조를 편집하는 기능은 후속 단계로 미룬다.

그래프는 처음부터 속성 편집의 진입점으로 사용한다. 따라서 초기 범위를
모든 수정이 금지된 조회 전용 화면으로 해석하지 않는다.

### 하나의 작성 원본과 공통 변경 경로

AI, 텍스트 편집, 속성 패널은 동일한 작성 원본을 수정한다.
속성 변경을 원본에 반영하면 그래프에 표시하고 컴파일 결과나 진단을 갱신한다.
각 수정 경로는 같은 검증·변경 이력·실행 취소 체계를 사용하며,
독립적인 텍스트 원본과 그래프 원본을 각각 관리하지 않는다.
노드 위치 같은 화면 배치 정보는 스킬의 실행 의미와 분리하여 보관한다.

공유 값을 편집할 때는 공유 여부와 영향을 받는 동작을 보여준다.
계산식으로 정해지는 값은 계산 결과를 직접 덮어쓰기보다 식과 수정 가능한 입력값을 보여준다.
사람이 수정한 결과도 AI가 다시 읽고 이어서 작업할 수 있어야 한다.

### 후속 그래프 구조 편집

그래프에서 노드를 추가·삭제하거나 연결을 변경하는 기능을 영구적으로 금지하지 않는다.
그래프 조작이 원본의 어떤 변경에 해당하는지 명확히 정의한 뒤 단계적으로 지원한다.
예를 들어 연결 삭제가 실행 순서 제거인지 값 참조 해제인지 구분할 수 있어야 한다.
이 기능 역시 동일한 작성 원본과 검증·변경 이력 체계를 사용한다.
구체적인 지원 순서와 범위는 후속 설계에서 정한다.

## 사용자가 제시한 전제

1. **작성된 스킬을 미리보기로 볼 수 있어야 한다.**
   미리보기는 아직 미구현이며, 추가할 계획이다.
2. **Core 시스템은 아직 완성되지 않았으며, 명세도 확정되지 않았다.**
   현재 구현은 재사용할 기반이지만, 작성 모델의 표현 범위를 제한하는 최종 기준은 아니다.
3. **작성 중인 스킬은 컴파일이 되어야 한다.**
   완성된 콘텐츠만 마지막에 변환하는 방식이 아니라, 작성 과정에서 컴파일 결과를
   확인하며 작업할 수 있어야 한다.
4. **컴파일이 거부된다면 추적할 수 있어야 한다.**
   거부 원인과 관련된 작성 위치를 찾아, 무엇을 고치거나 결정해야 하는지 알 수 있어야 한다.

### 작성 중 컴파일과 실행 산출물의 구분

3번을 구체화하기 위해 다음 구분을 제안했다.

- 작성 중 언제든 컴파일을 요청하고 결과나 진단을 확인할 수 있어야 한다.
- 실행에 필요한 조건을 갖추면 실행 산출물을 생성한다.
- 미정 수치, 미완성 동작, 끊어진 참조가 있는 원본도 저장하고 이어서 편집할 수 있어야 한다.
- 실행에 필요한 정보가 부족하면 원본을 보존하고 해당 이유를 진단한다.
  임의 값을 채우거나 동작을 생략하여 성공시키지 않는다.

따라서 원본 저장 가능 여부, 컴파일 요청 가능 여부, 실행 산출물 생성 가능 여부를 구분한다.
이 구분은 [기존 제작·실행 흐름](project-purpose.md)의 미완성 원본 보존과도 연결된다.

## 추가로 제안한 기준

### 1. 현재 Core의 한계 때문에 작성 의도가 달라지면 안 된다

합의된 게임 규칙과 스킬 동작을 기준으로 작성 모델과 Core를 함께 발전시킨다.
필요한 동작을 현재 Core가 지원하지 못하면 미지원으로 드러내고, 지원에 필요한 차이를 기록한다.
비슷한 다른 동작으로 바꾸거나 일부 의미를 생략하여 컴파일에 성공시키지 않는다.
작성 오류, 미정 정보, Core 미지원은 원인과 후속 작업이 다르므로 진단에서 구분할 수 있어야 한다.

### 2. 실행 의미는 작성 데이터와 명시적인 공통 규칙으로 결정한다

조건, 순서, 대상, 값을 읽는 시점, 소유자, 수명, 종료 사유 등 필요한 의미를
AI나 구현자가 설명문에서 추측하게 두지 않는다. 타입과 참조 관계도 확인할 수 있어야 한다.
공통 기반 기능의 모든 내부 절차를 스킬마다 다시 작성할 필요는 없지만,
생략한 부분에 적용되는 공통 계약은 찾아볼 수 있어야 한다.

### 3. 미리보기와 실제 게임 실행은 같은 의미를 사용한다

가능한 한 같은 컴파일 결과와 Core 실행 경로를 사용한다.
미리보기용 편성, 적, 시험 수치 등은 별도 시험 조건으로 관리하고 원본의 확정값과 구분한다.
실제 판정과 화면 연출이 어떻게 연결되는지도 확인할 수 있어야 한다.
이 항목은 향후 미리보기의 설계 기준이며, 현재 구현되었다는 뜻은 아니다.

### 4. 추적은 컴파일 오류부터 실행 결과까지 이어진다

컴파일 거부 사유뿐 아니라, 실행 중 발생한 피해·비용·상태 변화가 원본의 어느 동작에서
비롯되었는지도 찾을 수 있어야 한다. 컴파일 과정에서 동작이 합쳐지거나 여러 실행 단계로
나뉘어도 원본 위치와의 연결을 유지하여, 미리보기에서 발견한 문제를 작성 데이터에서 고칠 수 있게 한다.

### 5. Core와 작성 형식의 변경이 기존 콘텐츠를 조용히 재해석하지 않는다

변경된 규칙과 영향을 받는 콘텐츠를 식별할 수 있어야 한다.
버전과 변경 영향을 드러내고, 변환 가능한 것은 변환하되 작성자의 판단이 필요한 것은 진단으로 남긴다.
모든 과거 형식을 영구 지원해야 한다는 뜻은 아니다.

### 6. AI가 필요한 범위만 읽고 수정할 수 있어야 한다

주기나 동작 하나를 바꾸기 위해 스킬 전체와 Core 구현을 모두 이해해야 하는 구조를 피한다.
관련 동작, 의존하는 참조, 공통 규칙을 찾아 읽고, 수정 영향과 실제 변경 내용을 확인할 수 있어야 한다.
여러 동작이 공유하는 값을 수정할 때도 영향을 받는 범위가 드러나야 한다.

### 7. 저성능 AI의 사용 가능성은 실제 작성 과제로 검증한다

노드 수나 문서 길이가 줄었다는 사실만으로 목표를 달성했다고 판단하지 않는다.
다음과 같은 과제로 기존 방식과 후보 방식을 비교한다.

- 기존 스킬을 읽고 동작을 설명한다.
- 수치를 조정하고 기존 동작을 수정한다.
- 동작을 추가하거나 지원되는 기능을 새롭게 조합한다.
- 컴파일 진단을 따라 오류를 찾아 고친다.

의미의 정확성, 의도하지 않은 변경, 필요한 재시도와 입력 부담을 함께 확인한다.
대상 모델과 성공 기준은 아직 정하지 않았다.

## 아직 결정하지 않은 사항

- 구조화된 텍스트의 구체적인 문법과 그래프 변환 규칙.
- 편집 원본과 실행 의미를 담는 데이터의 구조, 공통 계약과 컴파일러의 구체적인 연결 방식.
- 초기 속성 패널의 세부 편집 항목과 후속 그래프 구조 편집의 지원 순서·범위.
- 미리보기의 화면, 시험 조건 설정 방법, 진단·실행 추적을 보여주는 방식.
- 연출의 세부 명세·자원·매개변수, Core와 Unity 사이의 전달 데이터·네이티브 연동 API와 책임 경계.
- 연출 미정 상태의 컴파일·미리보기 처리와 진단 기준.
- AI 비교 과제의 대상 스킬, 모델, 측정 방법과 통과 기준.

작성·편집의 큰 방향과 Rust Core·Unity의 네이티브 연결 계획은 위 합의를 따른다.
작성 데이터의 구체적인 문법, 컴파일 구조, 연동 API와 기존 편집기의 전환 절차는 아직 결정하지 않았다.
후속 설계에서는 위 전제를 충족하는지 확인하고, 세부 선택과 근거를 별도로 기록한다.
