# 스킬 작성·Core 개선 작업 기록 — 임시

작성일: 2026-10-23

실제 위임 범위·설계 선택·시도·발견·검증 근거를 기록한다.
현재 단계와 다음 행동의 원본은 [계획](ai-skill-authoring-plan.tmp.md)이며,
진행 방법은 [자율 작업 하네스](skill-authoring-autonomy-harness.tmp.md)와 [실행 지침](ai-skill-authoring-execution-guide.tmp.md)을 따른다.
과거 기록은 해당 시점의 사실이며 뒤의 변경으로 소급 덮어쓰지 않는다.

## H00. 자율 위임을 위한 준비 — 2026-10-23

### 요청과 범위

사용자는 자율 작업을 맡기기 전에 목표·지침 등 기본 하네스를 갖추고 더 나은 진행 방법을 검토하고자 했다.
이번 작업은 기존 문서를 연결한 하네스와 기록 방식의 준비다.
C0~C3 전체 구현·검증의 위임은 제안 상태이며 이 준비 기록을 실행 지시로 사용하지 않는다.

### 준비한 기반

- 목표·계획·실행 지침·요구·예시의 원본 위치를 하네스에 연결했다.
- 목표에서 벗어나는 선택을 점검하고 실제 증거로 단계 완료를 판단하도록 정리했다.
- 작업→검증→별도 자체 재검토→결함 기록·교정→재검증→인계의 순환을 기존 지침과 연결했다.
- 첫 자율 구간은 C0~C3을 권장하되 사용자 위임 범위가 정해지면 그 범위를 기록하도록 했다.
- 모델·사례가 미정인 현재 단계에서는 제품 코드·시험 프레임워크·빈 검증 스크립트를 추가하지 않았다.

### 작성 포맷의 1차 조사 인계

2026-10-23 대화에서 공식 자료를 조사했다. 아래 우선순위는 조사자의 비교 제안이며 실제 AI 과제 결과나 채택 결정이 아니다.
포맷 후보 조사·소규모 표현 실험은 C0~C3과 병행하고 최종 선정은 의미·편집·실행 근거를 따른다.

| 후보                               | 확인한 공식 근거와 후속 확인                                                                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| JSONC — 우선 비교                  | [jsonc-parser](https://github.com/microsoft/node-jsonc-parser): 위치 정보·편집 API. 주석 부착·부분 수정 보존은 실제 과제로 검증                              |
| YAML 1.2의 제한된 문법 — 우선 비교 | [yaml 도구](https://eemeli.org/yaml/): Document·CST·주석·위치 정보. 값 해석·문법 범위·공유 정의와 앵커의 구분 필요                                           |
| KDL — 우선 비교                    | [언어](https://kdl.dev/)·[Rust 도구](https://docs.rs/kdl/latest/kdl/): 항목·속성·블록, 형식 보존·span. 스킬 의미 매핑과 AI 작성 능력은 미검증                |
| RON·TOML — 보조 비교               | [RON](https://github.com/ron-rs/ron)·[toml_edit](https://docs.rs/toml_edit/latest/toml_edit/): Rust 연결·편집 지원의 장점과 복잡한 작성 흐름의 적합성을 대조 |
| 전용 문법 — 필요성 검토            | 표현 이득과 파서·진단·편집 유지 비용을 기존 포맷과 비교. 아직 문법 설계·채택하지 않음                                                                        |

동일한 의미의 정의·상태·사건·대기·취소 예시로 읽기·부분 수정·참조 교정·진단·원문 보존을 비교한다.
숫자·문자열의 타입 해석, 큰 정수의 보존, 중복 키, 미완성 입력도 검증 조건에 포함한다.
온라인 기본 버전·`latest` 링크는 변경될 수 있으므로 실제 실험에는 버전과 입력을 기록한다.

### 준비 검토

현재 문서 묶음은 목표·근거 위치, 위임 경계, 실행 순환, 단계별 증거, 재개·보고 방법을 갖춘 초안이다.
아직 첫 사례·실행 계약·자동화된 기능 검증은 정하지 않았다. 하네스 준비의 완료와 C0~C3의 완료를 구분한다.
문서·링크·서식 검사 결과는 이번 준비 작업의 최종 보고로 남기고, 후속 실행의 근거로 재사용하지 않는다.

## H01. 기존 로드맵·실행 문서의 유용한 지침 반영 — 2026-10-23

### 요청과 범위

사용자는 Core Enhanced 로드맵과 연속 실행 지시서가 언급하는 문서를 읽고 유용한 지침을 하네스에 넣는 방안을 요청했다.
관련 운영·설계·검증 절을 읽어 기존 실행 지침과 대조하고, 빠진 기준을 하네스에 보완했다.
전체 로드맵 구현이나 정식 P2G/GEX 실행의 착수를 뜻하지 않는다. 현재 단계와 위임 상태는 기존 계획을 유지한다.

공통 원리는 하네스에 적용하고, 상세한 입력 보존·증거 재사용·감사·교정 절차는 기존 실행 지침에 연결한다.

### 그대로 가져오지 않은 것

- 과거 모델·담당자 지정, U/CA 단계 번호, 옛 HANDOFF·상태 파일을 이번 작업의 진행 원본으로 삼는 규칙.
- 과거 작성 범위의 RON 전제·UI 제외. 현재 포맷은 미선정이며 편집기·Unity는 현행 계획의 범위와 순서를 따른다.
- 모든 작업에 P2G/GEX 산출물·별도 승인·독립 에이전트를 일률적으로 요구하는 운영 방식.
  실제 적용되는 정식 계약의 필수 감사·독립성·보존 조건을 면제한 것은 아니다.
- 현행 목표의 요구 여부를 확인하지 않은 외부 변조 방어 시험, 기능과 무관한 전체 기반 재작성,
  매 단계 전체 재검사·전수 해시·증거 복제. 이미 필요한 검증을 줄이는 근거로 사용하지 않는다.

### 이번 변경의 검증 범위

하네스와 이 기록의 문구·출처·상호 링크·기존 지침과의 정합성을 검토하고 저장소가 요구하는 검사를 수행한다.
검토 방식은 같은 실행자의 별도 읽기 전용 자체 재검토다. 제품·실행 모델·게임 동작의 검증 결과로 확대하지 않는다.
명령 결과와 검토 근거는 최종 보고에 남긴다.

## H02. 독립 검토에 따른 정합성 교정과 축약 — 2026-10-23

사용자가 요청한 독립 서브에이전트 검토에서 정합성 결함 F01과 편집 개선 E01·E02가 나왔고,
후속 요청에 따라 세 항목을 교정했다. 이번 범위는 문서 정리이며 C0~C3 구현 위임으로 확대하지 않는다.

- **F01:** 실행 지침의 옛 1~5단계 표를 현행 계획의 C0~C3·4·5단계 링크와 공통 검토 원칙으로 바꿨다.
  5단계 완료 설명도 선택 범위의 작성·편집·실행 통합 검증으로 맞췄다.
- **E01:** 하네스의 상세 절차를 짧은 확인 문장과 실행 지침 링크로 축약했다.
  H01 당시 하네스 §3.1의 고유한 의존성·준비 기준은 실행 지침 §4.3·5로,
  §5.1의 지원 경로·시험 준비 기준은 §6·6.1로, §5.2의 성능 기준과 §6의 검사 관리는 §6.2·6.3으로 통합했다.
  기존 증거 재사용·실패 분류·검토 분리는 실행 지침 §6.3·7·8을 사용한다. H01의 당시 기록은 보존한다.
- **E02:** 하네스의 기록 기준을 주요 선택·의미 있는 시도와 작업 규모에 맞게 한정하고 기존 원시 로그를 연결하도록 했다.

위임 범위, 진행 순환, G02/G03의 실제 조합·재사용 증거, 단계별 핵심 근거, 필수 실패·미확인과 재개 기준은 유지했다.
수정 후 문서·링크·서식을 재검토하고 `npm run check`로 확인한다. 교정 후 검토와 검사 결과는 최종 보고에 남긴다.

## 후속 작업 기록 형식

작업 규모에 맞춰 기존 절이나 별도 결과물에 기록하고 여기서 연결한다. 각 항목마다 새 파일을 만들 필요는 없다.

```text
기록 ID·날짜 / 실제 사용자 위임과 종료점:
목표 G 항목·요구 ID·선택 사례 / 관찰할 결과:
대상 파일·입력 기준 / 보존할 기존 변경:
선택·대안·근거 / 영향받는 계약·소비자:
기대 결과 / 실행 명령·환경·원시 결과·종료 코드:
수용 조건별 판정 / 실행·재사용·미실행·N/A의 구분:
발견·실패·교정 / 이전 판정에 대한 영향:
별도 검토의 대상과 결과 / 남은 필수 작업·다음 행동:
```

새 근거가 앞선 판단을 바꾸면 새 기록에서 앞선 ID와 변경 이유를 연결한다.
완료를 가로막는 발견은 별도 ID로 추적하고 교정·재검증 근거가 생긴 뒤 닫는다.
