# 전투 맵 조립기 프로토타입 구현 프롬프트

아래 「구현 요청」부터 끝까지 다른 AI에게 전달한다. 이 저장소에 접근할 수 있는 AI를
대상으로 하며, 경로는 별도 표시가 없으면 저장소 루트 기준이다.

## 구현 요청

`content_assembler/`에 전투 맵 조립기의 첫 번째 동작 가능한 프로토타입을 구현해줘.
계획이나 정적인 화면 시안만 제시하고 끝내지 말고, 사용자가 맵을 만들고 수정하고 저장한
뒤 다시 열어 작업할 수 있는 흐름을 완성해줘.

### 1. 배경과 먼저 읽을 문서

콘텐츠 조립기는 장기적으로 맵·스킬·장비·아이템·유물·보스를 제작하는 도구다.
이번 대상은 **전투가 일어나는 전장 편집기**다. 시설 배치도나 방 사이를 연결하는
진행 노드 맵을 만드는 작업이 아니다.

먼저 아래 문서와 현재 소스를 읽고 기존 구조를 활용해줘.

- [프로젝트 목적과 범위](project-purpose.md)
- [콘텐츠 조립기 작업 규칙](../AGENTS.md)
- [개발 지침](development-guidelines.md)
- [README](../README.md)
- [UI 검증 안내](ui-validation.md)
- `content_assembler/src/`, `content_assembler/tests/ui/`, `content_assembler/package.json`

작성 시점에는 React·TypeScript·Vite·Tauri, Radix 기반 shadcn/ui, 테마와 UI 검사 도구가
준비되어 있다. 편집 기능의 실제 구현 여부는 작업 시작 시 소스로 다시 확인해줘.
기존 사용자 변경을 보존하고, 수정 범위는 원칙적으로 `content_assembler/` 안으로 제한해줘.

게임 코어는 미완성이며 명세가 바뀔 수 있다. **웨이브는 편집기용 임시 데이터 구조로
작성하고, 현재 코어 스키마와의 일치를 강제하지 않는다.** 코어 코드는 조건의 의미를
확인할 때 참고하되, 이번 작업 때문에 코어를 수정하거나 연결을 기다리지 마.

### 2. 이번 프로토타입의 완료 목표

다음 흐름이 실제로 동작해야 한다.

1. 새 전투 맵을 만들고 기본 정보를 입력한다.
2. 유효 영역을 칠하거나 지워 비정형 외곽과 내부 구멍을 만든다.
3. 지형·장애물·배치 가능 구역·적 등장 구역을 편집한다.
4. 이동 경로의 시작점·경유점·도착점을 작성하고 수정한다.
5. 웨이브 구성과 등장 조건을 설정하고 구역·경로를 연결한다.
6. 진단에서 누락·잘못된 참조를 확인하고 해당 대상으로 이동해 수정한다.
7. 편집을 실행 취소/다시 실행하고, 파일로 저장한 내용을 다시 열어 이어서 편집한다.

전투 시뮬레이션, 적 이동 재생, 길 찾기 엔진, 코어용 최종 내보내기, 시설 노드 맵,
다른 콘텐츠 편집기, 협업·계정·클라우드 기능은 이번 범위에 넣지 마.
범용 노드 시스템, 복잡한 타임라인, 플러그인 시스템, 완전한 도킹·다중 창도 필수 기능이 아니다.

### 3. 화면 구성

포토샵처럼 캔버스를 중심으로 도구와 속성을 함께 다루는 밀도 있는 데스크톱 편집 화면을
구성해줘. 한국어 UI와 기존 밝은/어두운 테마를 유지하고, 큰 카드가 반복되는 대시보드로
만들지 마. 다음은 배치 기준이며 정확한 패널 폭과 세부 정렬은 구현자가 조정해도 된다.

| 영역   | 내용                                                                       |
| ------ | -------------------------------------------------------------------------- |
| 상단   | 문서 이름·미저장 표시, 새로 만들기·열기·저장, 실행 취소·다시 실행, 테마    |
| 왼쪽   | 선택, 유효 영역 추가/제거, 지형·장애물, 구역, 경로·지점 도구와 관련 팔레트 |
| 중앙   | 격자 캔버스, 줌·이동, 선택·호버·편집 미리보기, 경로와 구역 오버레이        |
| 오른쪽 | 선택 대상 속성, 맵 기본 정보, 레이어의 표시·잠금                           |
| 하단   | 웨이브 목록·조건 편집과 진단을 전환하는 패널                               |
| 상태줄 | 현재 도구, 맵 좌표, 확대율, 간단한 조작 안내                               |

- 캔버스 선택과 속성·목록 선택이 연결되어야 한다. 선택이 없으면 맵 기본 정보를 보여줘.
- 지형·구역·경로 등 표시 레이어를 구분하고, 숨김과 잠금의 의미를 다르게 처리해줘.
  잠긴 레이어가 다른 입력 경로를 통해 수정되지 않게 해줘.
- 작은 창에서는 패널 내부 스크롤·접기·탭을 활용해 캔버스와 주요 조작을 유지해줘.
- 버튼과 메뉴는 실제 기능에 연결해줘. 아직 없는 기능의 가짜 성공 동작은 넣지 마.
- 기본 편집 도구에는 단축키와 툴팁을 제공하되, 텍스트 입력 중에는 편집기 단축키가
  입력 필드의 삭제·실행 취소 등을 가로채지 않게 해줘.

### 4. 맵·지형·구역

- 기본 정보: 안정적인 문서 ID, 표시 이름, 설명, 가로·세로 크기.
  분류 값이 필요하면 현재 확인 가능한 값만 쓰고 미정 값을 게임 정책으로 확정하지 마.
- 맵 크기는 사각 좌표 범위이고, 실제 맵은 별도의 유효 셀 집합으로 표현해줘.
  비정형 외곽, 떨어진 영역, 내부 구멍을 표현할 수 있어야 한다.
- 최소 지형은 일반 바닥·고지대/플랫폼·장애물을 구분해줘. 배치 가능 여부는 구역 정보로
  다뤄서 모든 고지대를 자동으로 배치 구역으로 간주하지 마.
- 유효 영역 편집과 지형 지우기를 구분해줘. 지형을 지워도 해당 셀 자체가 없어지지 않으며,
  유효 영역을 제거한 자리는 바닥과 다르게 보여야 한다.
- 구역은 ID·이름·종류·셀 집합을 가진 편집 대상으로 다뤄줘. 최소한 아군 배치 가능 구역과
  적 등장 구역을 생성·수정·삭제할 수 있어야 한다.
- 브러시와 사각형 범위 편집을 제공해줘. 영역 복사·붙여넣기나 채우기 도구는 핵심 흐름이
  완성된 뒤 필요에 따라 추가할 수 있지만 완료 목표를 대체하지는 않는다.
- 크기 축소나 영역 제거가 지형·구역·경로에 미치는 영향을 알려줘. 참조를 다른 대상으로
  자동 변경하거나 경로를 재작성하지 마.

### 5. 경로와 좌표

- 경로마다 안정적인 ID와 이름을 두고, 순서 있는 점을 생성·선택·이동·삽입·삭제할 수 있게 해줘.
  시작과 도착, 진행 방향을 구별해서 표시해줘.
- 기본 모드는 타일 중심을 선택하여 경로를 작성한다. 고급 모드를 켜면 타일 내부를
  N×N 격자로 나누어 더 세밀하게 경유점을 찍을 수 있게 해줘.
- N과 기본/고급 모드는 입력 스냅 규칙이다. 값을 바꾸는 것만으로 기존 경유점 좌표를
  이동시키지 마. 고급 모드에서도 타일 중심을 선택할 수 있어야 한다.
- 셀 인덱스, 연속 맵 좌표, 화면 픽셀을 구분해줘. 원점·축·경계 포함 규칙과 스냅 위치를
  한 곳에 정의하고 렌더링·입력·저장·검증에서 함께 사용해줘.
- 경로 연결은 편집자가 지정한 점을 잇는 선으로 표현하면 된다. 경로 탐색이나 적의
  실제 이동 규칙을 임의로 구현하지 마. 영역 밖·장애물 통과 등은 근거에 맞춰 진단하고,
  코어의 이동 가능성 검증을 완료했다고 표시하지 마.
- 조건 웨이브의 지점 참조를 위해 이름 있는 지점을 최소한의 기능으로 작성할 수 있게 해줘.
  경로 점과 조건용 지점의 참조 의미를 구분하고 ID로 연결해줘.

### 6. 웨이브와 조건 웨이브

복잡한 타임라인 대신 목록과 속성 폼으로 시작해줘. 웨이브를 추가·선택·복제·삭제하고
순서를 정리할 수 있게 하되, 목록 순서와 발동 조건을 혼동하지 않게 해줘.

최소 편집 항목은 ID·이름, 적 구성 항목, 수량, 등장 간격, 등장 구역, 경로,
발동 조건, 우선순위, 승리 판정에 필요한 웨이브 여부다.
적 콘텐츠 카탈로그가 아직 없으면 참조 ID를 입력하는 방식으로 작성할 수 있게 하고,
코어에서 존재를 검증한 선택지처럼 꾸미지 마.

조건은 기존 코드와 문서에서 확인한 다음 다섯 종류를 기준으로 구성해줘.

| 종류                  | 필요한 입력과 의미                                                                  |
| --------------------- | ----------------------------------------------------------------------------------- |
| 전투 시간             | 전투 시작부터의 절대 시각                                                           |
| 선행 웨이브 정리      | 참조 웨이브. 구성원이 등장한 뒤 모두 비활성 상태가 된 경우이며, 사망 외 제거도 포함 |
| 지정 개체 HP          | 개체 참조와 HP 비율 임계값 이하                                                     |
| 지정 개체 사망        | 개체 참조. 단순 퇴장과 사망을 구분                                                  |
| 지정 개체의 지점 도달 | 개체 참조, 이름 있는 지점, 셀 단위 도달 반경                                        |

- 기본 조건 하나와 선택적인 **대체 발동 시각**을 편집하게 해줘. 예를 들어
  “선행 웨이브 정리 또는 전투 시작 45초에 발동”이다. 이 시각은 만료·취소 시간이 아니다.
- 시간 조건에는 중복된 대체 시각을 요구하지 마. 같은 시각에 기본 조건과 대체 시각이
  충족되면 기본 조건을 우선한다는 의미를 도움말에 반영해줘. 각 웨이브는 한 번 발동한다.
- 임의의 AND/OR 조건 트리나 “출현 완료”를 여섯 번째 조건으로 추가하지 마.
- 개체 참조는 현재 코어에서 보스 개체 슬롯을 가리킨다. 이번에는 편집 문서 안의
  임시 슬롯 선언(ID·이름)을 선택하거나 미지정으로 남길 수 있게 해줘. 웨이브의 적 종류나
  수량 항목을 런타임의 특정 개체와 동일시하지 마. 실제 코어 바인딩은 후속 작업이다.
- 참조 누락, 자기 참조와 웨이브 의존 순환, 수량·시간·비율·반경의 잘못된 값을 진단해줘.
- 조건 폼을 편집·저장하는 기능까지만 구현한다. 실제 조건 평가나 전투 실행을 구현하지 마.

의미 확인에 필요한 경우 아래 범위만 읽어줘. 이 타입을 그대로 편집기 저장 형식으로
복사하거나 코어 전체 개발 절차를 이번 작업에 도입할 필요는 없다.

- [웨이브 데이터 타입](../../core_enhanced/src/game/data/pve_data.rs): `PveWaveActivationData`, `PveWavePrimaryTriggerData`, `PveWaveData`
- [전투 규칙](../../core_enhanced/docs/game_rules/combat.md): 「웨이브와 적」
- [조건 평가 코드](../../core_enhanced/src/game/battle/core/wave_runtime.rs): `wave_activation_cause`, `wave_primary_is_true`, `scenario_group_is_clear`

### 7. 편집 문서·실행 취소·파일

- 편집기용 버전 있는 문서 형식을 정해줘. 맵·지형·구역·경로·지점·임시 개체 슬롯·웨이브와
  관련 참조를 보존하고, 줌·호버·선택·테마는 별도 화면 상태로 관리해줘.
- 문서 원본은 하나로 유지하되 모든 로직을 하나의 컴포넌트나 저장소 파일에 몰지 마.
  순수 편집 규칙, 이력 처리, 화면, 외부 입출력의 책임을 나눠줘.
- 모든 문서 변경은 같은 편집 경로를 거쳐 실행 취소/다시 실행되게 해줘.
  브러시 한 획과 드래그 한 번은 한 번의 실행 취소로 복원되어야 한다.
- 미리보기 취소, 변경 없는 연산, 실행 취소 뒤 새 편집, 삭제된 대상의 선택 정리와
  폼 입력 버퍼 처리까지 개발 지침에 맞춰 구현해줘.
- 미완성 경로·참조·조건은 진단과 함께 저장할 수 있어야 한다. 구조적으로 잘못된 입력,
  중복 ID, 지원하지 않는 형식 버전은 안전하게 거부하고 현재 작업을 보존해줘.
- 프로토타입 저장 형식은 JSON을 기본안으로 삼아도 된다. 실제 파일로 내보내고 다시
  읽을 수 있어야 하며, 브라우저 저장소만으로 파일 기능을 대신하지 마.
- 브라우저에서는 파일 선택·다운로드를 명시적인 입출력 방식으로 제공할 수 있다.
  다운로드 요청만 가능한 환경에서는 디스크 저장 완료를 확인했다고 표시하지 마.
  Tauri 저장을 구현한다면 성공·실패·취소를 구분하고 같은 편집 규칙에 연결해줘.
- 네이티브 환경 준비가 부족하다고 브라우저의 실제 편집 흐름까지 중단하지 마.
  구현한 입출력 방식과 네이티브에서 미검증인 부분을 보고서에 구분해줘.
- 저장 실패나 취소 시 현재 작업을 유지해줘. 새로 만들기·열기 등 문서 교체는
  미저장 내용 처리와 새 파일 검사를 끝낸 뒤 수행해줘.
- 비동기 저장 중 추가 편집, 문서 전환 후 늦게 도착한 결과, 저장 중첩이 현재 문서나
  파일을 오래된 내용으로 덮어쓰지 않게 해줘.

### 8. 진단과 프로토타입 기본값

진단은 코드·심각도·대상 ID·필드·설명을 가지고, 클릭하면 해당 대상과 속성으로 이동하게 해줘.
오류를 수정하면 원본 문서를 기준으로 갱신하고, 대상이 삭제된 경우에도 안전하게 처리해줘.
작성 중 누락과 파일 구조 오류, 코어 미연동으로 확인할 수 없는 사항을 구분해줘.

아래는 미결정 사항 때문에 구현이 멈추지 않도록 둔 **프로토타입용 제안**이다.
게임 규칙이나 확정된 기존 합의로 취급하지 말고, 선택한 값을 짧게 기록해줘.

- 새 맵은 예를 들어 16×12, 좌측 상단 원점, 오른쪽 +X·아래쪽 +Y로 시작할 수 있다.
- 고급 격자는 N=4를 기본으로 두고 2·4·8을 선택하게 해도 된다.
  분할선 교점/하위 셀 중심 중 실제 스냅 위치는 정해서 표시하고 테스트해줘.
- 화면의 시간 입력은 초, 문서 내부는 정수 밀리초로 통일할 수 있다.
- 참조 대상 삭제는 영향을 알린 뒤 수행하고, 끊어진 참조는 진단으로 남겨 수정하게 할 수 있다.
  이를 선택했다면 삭제와 실행 취소에서 일관되게 적용해줘.
- 경로·구역의 색, 패널 폭, 파일명 규칙 등 내부 UI 선택은 기존 테마에 맞춰 판단해줘.

새 게임 규칙이 필요한 결정과 내부 구현 선택을 구분해줘. 내부 선택마다 승인을 요구하지 말고
진행하되, 실제로 사용자 결정이 필요한 의미를 임의로 확정하지 마.

### 9. 구현 방식과 진행

- 현재 설치된 라이브러리와 공통 UI를 먼저 활용해줘. 캔버스 라이브러리가 필요하면
  React Konva 등을 검토할 수 있지만, 채택 시 실제 호환성·유지보수·라이선스를 확인해줘.
  화면을 만들기 위해 노드·도킹·표 라이브러리를 한꺼번에 추가하지 마.
- 필요한 패키지를 도입하면 잠금 파일과 고지를 갱신해줘. 이미 제공되는 기본 위젯은
  재사용하고 게임 고유의 편집 규칙에 구현을 집중해줘.
- 먼저 실제 소스를 확인하고 작업 순서·문서 모델·검증 계획을 짧게 정리한 뒤 구현해줘.
  계획 제출만으로 작업을 끝내거나 불필요한 승인 대기로 전환하지 마.
- 권장 순서는 문서/편집 연산 → 캔버스/영역/지형 → 구역/경로 → 웨이브/진단 →
  저장·열기 통합 → 화면·회귀 검증이다. 각 단계부터 이력과 저장 가능성을 고려해줘.
- 형식 버전, 좌표/스냅 규칙, 참조·삭제 정책, 선택한 기본값과 알려진 제한을
  `content_assembler/docs/`에 간결하게 기록해줘. 현재 구현 상태에 맞게 README도 갱신해줘.

### 10. 검증과 완료 보고

현재 세션의 사용자 실행 제한을 우선해줘. 이 프롬프트는 이전에 내려진 앱·서버·브라우저
실행 금지를 자동으로 해제하지 않는다. 금지가 유지되면 정적 검사와 시나리오 준비를
진행하고 실제 화면 검증을 미실행으로 보고해줘. 별도 금지가 없는 구현 세션에서는
AGENTS.md와 UI 검증 안내에 따라 관련 동작과 실제 화면을 확인해줘.

- `npm run check`, `npm run build`와 편집 규칙·이력·직렬화에 맞는 테스트를 수행해줘.
  테스트 도구가 필요하면 현재 구조에 맞는 최소 구성을 추가해줘.
- 기존 `tests/ui/`에 편집 동작과 상태를 추가하고, 구현으로 바뀐 기존 화면의 기대값은
  새 동작에 맞춰 갱신해줘. 테스트를 삭제하거나 검사를 약화해서 통과시키지 마.
- 작은 일반 맵, 비정형 맵과 구멍, 여러 경로·웨이브, 긴 한글 이름, 빈 문서,
  미완성 참조·잘못된 파일·저장 실패를 재현하는 고정 데이터를 준비해줘.
- 실행이 허용되면 세 창 크기와 두 테마를 검사하고 PNG를 직접 열어 검토해줘.
  캔버스·패널의 잘림, 한글, 입력·메뉴 포커스와 axe 진단까지 확인해줘.
- 브라우저 검사와 Windows WebView2·네이티브 파일·IME 검사 결과를 구분해줘.

최소한 다음 결과를 확인해줘.

1. 비정형 맵과 내부 구멍을 만들 수 있고, 지형 지우기와 영역 제거가 구별된다.
2. 구역·경로·지점을 생성·수정하고 목록과 캔버스에서 같은 대상을 편집한다.
3. 기본/고급 스냅과 N을 바꿔도 기존 좌표가 유지되며 줌·이동 후 입력도 정확하다.
4. 다섯 조건 폼과 웨이브 구성의 값·참조가 편집되고 저장 후 다시 열어도 보존된다.
5. 드래그 취소, 한 획 실행 취소, 다시 실행, 복제 ID와 참조 처리에 일관성이 있다.
6. 미완성 문서를 저장할 수 있고, 잘못된 파일 열기·저장 실패는 현재 작업을 훼손하지 않는다.
7. 미저장 표시, 입력 버퍼, 문서 교체와 비동기 결과가 실제 편집 내용과 일치한다.
8. 오류 진단에서 해당 대상으로 이동해 수정할 수 있다.

완료 보고에는 구현한 사용자 흐름, 실행·사용 방법, 주요 파일, 선택한 기본값,
검사 명령과 실제 결과, 검토한 스크린샷 경로, 남은 제한을 적어줘.
동작하는 프로토타입과 코어 연동 완료를 혼동하지 말고, 미실행 검사는 분명하게 남겨줘.
