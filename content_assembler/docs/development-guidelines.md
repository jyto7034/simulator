# 콘텐츠 조립기 개발 지침

기능을 추가할 때마다 중복 상태, 임시 예외, 거대한 컴포넌트가 누적되지 않도록 하는
코드 작성·검토 기준이다. `content_assembler/`의 프런트엔드와 데스크톱 연동에 적용한다.
기존 프로젝트의 품질 원칙을 제작기 작업에 맞게 정리했으며, 맵 편집기 사례는 앞으로
구현할 기능의 적용 예시다. 구현 완료를 뜻하지 않는다.

사용자가 합의한 기능과 동작을 우선한다. 이 문서가 새로운 기능이나 필수 승인 절차를
추가하지는 않는다. 작업 규칙은 [AGENTS.md](../AGENTS.md), 실행 명령은
[README](../README.md), 화면 검사 절차는 [UI 검증 안내](ui-validation.md)를 함께 따른다.

## 1. 변경 전에 책임과 동작을 정한다

- 바꿀 사용자 동작, 데이터를 소유하는 곳, 실패 시 결과, 확인 방법을 먼저 정한다.
  작은 변경은 짧은 작업 메모로 충분하다. 매번 별도 설계 문서나 프레임워크를 만들지 않는다.
- 현재 호출 경로와 타입을 읽고 기존 책임에 기능을 붙인다. 비슷한 모델·검증기·저장소를
  새로 만들기 전에 기존 경로를 확장할 수 있는지 확인한다.
- 새 필드나 편집 도구를 추가할 때 UI, 문서 모델, 검증, 실행 취소, 저장 중 어디가
  바뀌는지 확인한다. 같은 의미를 여러 곳에서 수동으로 맞춰야 한다면 소유권부터 고친다.
- 폴더와 파일은 변경 이유와 책임에 따라 나눈다. 행 수 제한을 맞추기 위한 분할이나
  단순 전달만 하는 래퍼를 늘리지 않는다.

## 2. 사실 하나에는 원본 하나만 둔다

| 상태 종류         | 예시                            | 관리 기준                                         |
| ----------------- | ------------------------------- | ------------------------------------------------- |
| 편집 문서         | 맵 영역, 지형, 경로, 웨이브     | 저장·검증·실행 취소가 바라보는 원본               |
| 편집 중 임시 상태 | 드래그 미리보기, 폼 입력 버퍼   | 확정·취소 시점과 원본 반영 경계가 명확해야 함     |
| 화면 상태         | 선택, 호버, 줌, 열린 패널       | 문서 데이터와 분리하고 저장·이력 포함 여부를 명시 |
| 사용자 설정       | 테마, 패널 배치 선호            | 콘텐츠 파일과 분리                                |
| 파생 상태         | 선택 개수, 참조 목록, 검증 결과 | 원본에서 계산하며 독립적으로 수정하지 않음        |

- 캔버스, 속성 패널, 레이어 목록이 각자 문서 사본을 소유하지 않는다. 화면 간 갱신은
  같은 원본과 편집 연산을 통해 이루어진다.
- 단일 원본은 같은 사실의 수정 권한과 기준 데이터가 하나라는 뜻이다. 모든 상태와
  연산을 하나의 파일이나 저장소에 모으라는 뜻은 아니다.
- React Hook Form 등의 입력 버퍼는 허용한다. 입력 중 값과 확정된 문서를 구분하고,
  선택 대상 변경·취소·실행 취소·저장 시 버퍼 처리 규칙을 정한다. 화면에 보이는 입력이
  저장에서 빠지거나 다른 대상에 뒤늦게 반영되지 않게 한다.
- 삭제·실행 취소·문서 교체 후 선택과 입력 버퍼가 유효한 대상을 가리키는지 확인한다.
  화면 상태를 이력에서 제외하더라도 없어진 대상을 계속 편집할 수 있게 두지 않는다.
- 캐시가 필요하면 원본과 무효화 조건을 명시한다. 성능을 이유로 두 번째 원본을 만들지 않는다.
- 객체 참조에는 안정적인 ID를 쓴다. 목록 인덱스나 표시 이름으로 경로·웨이브 대상을 연결하지 않는다.
- 동시에 성립할 수 없는 상태는 판별 가능한 유니온 등으로 표현한다. 독립적인 boolean을
  늘려 불가능한 조합을 만들지 않는다.

## 3. UI, 편집 규칙, 외부 입출력을 분리한다

- UI는 입력을 해석하고 결과를 표시한다. 좌표 변환, 스냅, 영역 판정, 참조 검증과 같은
  규칙은 React·캔버스·Tauri 없이 호출할 수 있는 함수로 둔다.
- 편집 연산은 문서를 어떻게 바꾸는지 정의한다. 패널과 단축키가 각자 같은 변경 규칙을
  복제하거나 저장소 내부 필드를 제각각 수정하지 않게 한다.
- 파일 선택, 읽기·쓰기, 네이티브 호출은 외부 입출력 경계에 둔다. 편집 규칙이 Tauri API,
  브라우저 전역 객체, 파일시스템에 직접 의존하지 않게 한다.
- 여러 기능을 함께 바꾸는 동작은 이를 조정하는 명시적인 경로를 둔다. 하위 모듈끼리
  서로의 저장소를 호출하는 순환 의존으로 해결하지 않는다.
- `App`, 단일 Zustand 저장소, 공용 `utils` 파일에 서로 무관한 책임을 계속 추가하지 않는다.
  공유 코드는 실제로 같은 의미를 쓰는 소비자가 있을 때 추출한다.

## 4. 문서 변경은 트랜잭션으로 확정하고 실행 취소도 같은 단위를 따른다

문서 상태 관리의 기본 원칙은 **트랜잭션 기반 설계**다. 하나의 편집 동작에 필요한 변경은
모두 적용하거나 모두 취소하며, 관찰자가 일부만 적용된 상태를 보지 않게 한다.
기존 `EditorSession.commit`과 편집 연산을 중심으로 아래 계약을 유지·보강한다.
새 트랜잭션 프레임워크나 라이브러리 도입을 요구하는 것은 아니다.

| 단계            | 책임                                                                                               |
| --------------- | -------------------------------------------------------------------------------------------------- |
| Stage — 준비    | 현재 문서와 분리된 초안 또는 패치에 관련 변경 전체를 준비한다. 원본과 과거 이력은 수정하지 않는다. |
| Validate — 검증 | 변경 결과의 구조, 연산의 필수 조건, 참조 정책, 잠금 조건을 검사한다.                               |
| Commit — 확정   | 문서·변경 이력·리비전과 필요한 선택 유효성 보정을 하나의 상태 전환으로 확정한다.                   |
| Publish — 알림  | 확정된 상태를 UI와 구독자에 알린다. 준비 중인 상태를 확정 결과로 노출하지 않는다.                  |

- 문서 변경은 검증과 이력 기록이 이루어지는 일관된 경로를 거친다. 클릭, 속성 입력,
  단축키 중 어느 곳에서 시작해도 같은 규칙을 적용한다.
- UI와 외부 호출자는 현재 문서나 이력의 객체를 직접 수정하지 않는다. 같은 사용자 동작에
  속하는 하위 연산은 하나의 초안을 함께 수정하며, 각자 별도 commit을 호출해 부분 확정하지 않는다.
  예를 들어 맵 확장의 크기 변경과 새 유효 셀 추가, 구역 추가와 반대 종류 구역의 겹침 제거는
  각각 하나의 트랜잭션이다.
- 확정 전 오류·취소·잠금 거부가 발생하면 초안을 버린다. 문서·Undo/Redo 이력·리비전·
  미저장 판정은 유지하며, 실패 메시지와 미리보기 정리는 별도의 화면 상태로 처리한다.
- 변경 준비와 확정 사이에 비동기 작업이 있다면 대상 문서와 기준 리비전을 다시 확인한다.
  기준이 달라졌으면 오래된 초안을 거부하거나 최신 상태에서 다시 준비·검증한다.
  확정 구간에는 `await`나 외부 입출력을 두지 않고, 구독자의 후속 편집은 별도 트랜잭션으로 다룬다.
- 편집 확정 시 문서 구조와 연산의 필수 조건을 검사한다. 허용된 미완성 상태의 진단은
  편집·저장을 차단하지 않는다. 전체 진단을 매 입력마다 동기 실행할 필요는 없으며,
  계산 중이거나 이전 문서를 기준으로 한 진단을 최신 결과처럼 표시하지 않는다.
- 사용자가 한 번의 동작으로 인식하는 변경을 한 번에 실행 취소할 수 있게 한다.
  브러시 한 획이나 드래그 한 번을 포인터 이동 횟수만큼 이력에 쌓지 않는다.
- 미리보기와 확정을 구분한다. Escape, 포인터 취소, 처리 실패 시 미확정 변경을 되돌리고
  문서·참조·이력에 일부 변경만 남기지 않는다.
- 실행 취소/다시 실행은 객체 값뿐 아니라 ID와 관련 참조까지 일관되게 복원한다.
  여러 대상을 함께 바꾼 연산은 하나의 변경 단위로 복원한다.
- 실제 변경이 없는 연산은 이력과 미저장 상태를 바꾸거나 다시 실행 기록을 지우지 않는다.
  실행 취소 후 새 변경을 확정하면 이전 분기의 다시 실행 기록은 제거한다.
- 이력이나 저장 작업에 넘긴 문서 상태가 이후 편집으로 바뀌지 않게 한다. 스냅샷·패치 등
  구현 방식은 필요에 맞게 고르되, 공유 객체의 직접 수정으로 과거 상태를 훼손하지 않는다.
- 호버·줌 등 화면 조작을 콘텐츠 변경 이력에 섞지 않는다. 별도 이력이 필요하면 그 의미를 정한다.
- 문서 변경 여부는 실제 저장한 문서 상태와 비교한다. 비동기 저장 중 새 편집이 발생해도
  이전 버전의 저장 완료가 최신 편집까지 저장된 것으로 표시하지 않게 한다.
  저장한 내용으로 실행 취소해 돌아온 경우에도 미저장 표시가 실제 내용과 일치해야 한다.

## 5. 작성 중인 문서와 잘못된 입력을 구분한다

- 작성 중에는 경로 미지정, 조건 미완성 등 합의된 미완성 상태를 표현하고 저장할 수 있다.
  이를 숨기기 위해 임의의 기본값을 채워 정상 문서처럼 만들지 않는다.
- 미완성 문서의 진단과 파일 구조·타입 자체가 잘못된 입력을 구분한다.
  외부 입력은 `unknown`에서 검사하고, 타입 단언이나 `any`로 검사를 우회하지 않는다.
- ID의 유일성과 참조 대상의 종류를 검사한다. 중복 ID처럼 대상을 모호하게 만드는 입력과
  정책상 허용하는 미지정·끊어진 참조를 구분한다. 가져오기·복제를 구현할 때는 새 ID와
  내부·외부 참조 처리 규칙을 함께 정한다.
- 진단은 식별 가능한 코드와 대상 ID·필드 정보를 갖게 한다. 사람이 읽는 문구를
  프로그램 분기의 기준으로 삼지 않는다. 화면에서는 관련 대상을 찾을 수 있게 한다.
- 삭제나 크기 축소로 참조가 끊길 때의 동작을 명시한다. 차단, 참조 제거, 진단 유지 중
  합의된 정책을 적용하며 다른 대상을 자동 지정하거나 경로를 몰래 보정하지 않는다.
- 숫자의 범위와 단위를 명시하고 경계에서 검사한다. 무한대·NaN·잘못된 좌표가 타입 검사만
  통과해 문서에 들어가지 않도록 한다.
- 예상 가능한 오류는 호출자가 구분할 수 있는 결과로 전달한다. 광범위한 `catch`로
  빈 문서나 성공 값을 반환하지 않는다. 사용자의 파일 대화상자 취소는 오류와 구분한다.

## 6. 저장 형식과 게임 코어의 책임을 분리한다

- 편집기 문서는 편집에 필요한 상태와 형식 버전을 명시한다. UI 컴포넌트 상태나
  실행 중인 게임 객체를 그대로 직렬화하지 않는다.
  지원하지 않는 버전은 명시적으로 알리고, 일부 필드를 버린 채 열고 덮어쓰지 않는다.
- 코어 계약이 확정되지 않은 기능은 합의한 편집기 형식으로 다룬다. 예를 들어 웨이브의
  임시 편집 형식을 현재 코어의 미완성 타입에 억지로 맞추지 않는다.
- 코어 연동이 실제 작업 범위에 들어오면 변환·검증 경계를 둔다. 아직 쓰이지 않는
  내보내기 어댑터, 호환 계층, 범용 플러그인 시스템을 미리 만들지 않는다.
- 파일 열기는 읽기·파싱·구조 검사가 끝난 뒤 현재 문서를 교체한다. 실패할 때 편집 중인
  문서와 이력을 먼저 지우지 않는다.
- 새 문서·열기·닫기처럼 작업을 떠나는 동작은 미저장 변경과 미확정 입력의 처리 정책을
  따른다. 저장을 선택했다면 저장 성공을 확인한 뒤 진행하고, 실패·취소 시 작업을 보존한다.
- 비동기 결과를 반영할 때 대상 문서와 요청의 유효성을 확인한다. 이전 문서나 이전 요청의
  결과가 현재 문서·선택·진단·저장 상태를 덮어쓰지 않게 한다.
- 저장 실패는 사용자에게 알리고 미저장 상태를 유지한다. 실제 파일 저장에서는 실패 시
  기존 파일 손상을 막는 쓰기 방식을 선택하고 해당 환경에서 검증한다.
- 메모리의 원자적 확정이 파일 저장이나 외부 전달의 원자성까지 보장한다고 가정하지 않는다.
  외부 작업에는 확정된 스냅샷을 전달하고 성공·실패를 별도로 추적한다. 파일 쓰기는 필요에 맞게
  임시 파일 작성 후 교체 등을 사용하되, 해당 플랫폼의 보장 범위와 실패 시 복구를 확인한다.
- 확정 후 구독자 알림·파일 저장·외부 전달이 실패해도 문서 변경 자체가 취소된 것으로 보고하지
  않는다. 확정 결과와 외부 작업 실패를 구분하며, 알림 실패가 다른 구독자 갱신을 막지 않게 한다.
  재시도를 지원할 때는 편집을 다시 실행하거나 외부 결과를 중복 생성하지 않게 한다.
- 같은 파일의 저장이 겹칠 때는 쓰기 순서를 보장하거나 중복 실행을 제한한다. 오래된 저장의
  완료 표시만 무시한 채 실제 파일이 이전 내용으로 덮어써지는 상황을 허용하지 않는다.
- 이전 형식을 지원할 필요가 생기면 지원 버전과 변환 정책을 명시한다. 이름이 비슷한
  필드를 추측해 읽는 암묵적 호환 처리나 미사용 레거시 경로를 남기지 않는다.

## 7. 맵 편집에는 좌표와 영역의 의미를 일관되게 적용한다

- 화면 픽셀과 맵 좌표를 구분한다. 확대·이동된 픽셀 값을 콘텐츠 좌표로 저장하지 않는다.
  그리기와 포인터 입력이 같은 좌표 변환 규칙을 사용하게 한다.
- 좌표 기능을 구현할 때 원점·축 방향·단위·셀 중심과 경계의 의미·정밀도를 정하고 공유한다.
  셀 인덱스와 연속 좌표를 구분하며, 반올림이나 경계 포함 여부를 화면마다 따로 정하지 않는다.
- 기본 중심점 스냅과 고급 N×N 세부 격자는 입력 규칙이다. 모드나 N 변경만으로 이미
  작성한 점의 좌표를 이동시키지 않는다. 좌표 보정이 필요하면 별도 편집 동작으로 다룬다.
- 맵의 사각 경계와 유효 영역을 구분한다. 비정형 외곽과 내부 구멍을 표현할 수 있게 하며,
  사각형 안의 모든 셀을 유효하다고 가정하지 않는다.
- 지형 지우기와 맵 영역 제거는 서로 다른 동작이다. 빈 지형과 존재하지 않는 셀의
  의미를 하나의 값에 섞지 않는다.
- 캔버스, 속성 패널, 저장 결과가 좌표·영역·참조를 동일하게 해석하는지 확인한다.
  렌더링에 맞추려고 문서 규칙을 화면마다 재구현하지 않는다.

## 8. UI와 라이브러리는 필요한 만큼 사용한다

- 기존 Radix 기반 shadcn/ui와 테마 토큰을 먼저 사용한다. 제공되는 메뉴·대화상자·입력을
  임의로 다시 만들거나 같은 역할의 라이브러리를 중복 도입하지 않는다.
- 라이브러리는 현재 필요한 기능에 도입하고, 문서 모델이 특정 렌더러나 도킹 도구의
  내부 객체에 종속되지 않게 한다. 불필요한 범용 래퍼도 만들지 않는다.
- 의존성과 가져온 코드는 필요한 동작·유지보수 상태·상업적 사용 및 배포 조건을 확인한다.
  잠금 파일과 필요한 고지를 함께 관리하고, 자동 생성·갱신된 코드도 변경 내용을 검토한다.
- Effect는 외부 환경 동기화에 사용한다. 계산 가능한 값을 상태로 복사하거나 Effect를
  연쇄 실행해 편집 순서를 조정하지 않는다.
- 이벤트 구독·타이머·포인터 처리에는 해제를 둔다. 전역 단축키는 입력 필드와 대화상자의
  키보드 동작을 존중한다.
- 버튼은 실제 동작과 연결하고, 아직 없는 기능을 가짜 성공으로 표시하지 않는다.
  접근성·창 크기·한글·테마 검사는 기존 UI 검증 규칙을 따른다.
- 포인터가 움직일 때마다 전체 문서를 직렬화하거나 불필요한 전체 화면 갱신을 만들지 않는다.
  성능 개선은 대표 데이터에서 확인하고, 근거 없이 캐시와 복잡한 구조를 추가하지 않는다.

## 9. 검증은 사용자 동작과 실패 결과를 확인한다

- 변경에 맞는 타입·정적 검사와 테스트를 수행한다. 단순 문서 수정에 앱 실행이나
  무관한 전체 테스트를 추가하지 않는다. 실행하지 않은 검사를 통과로 보고하지 않는다.
- 순수 규칙은 UI 없이 검사하고, 통합 검사는 실제 편집 경로에서 관측되는 문서·이력·저장
  결과를 확인한다. 내부 함수 호출 순서만 고정하는 테스트를 늘리지 않는다.
- 트랜잭션 경계를 변경할 때는 여러 대상 중 일부를 준비한 뒤 검증이 실패하는 사례를 포함한다.
  실패 전후 문서·Undo/Redo·리비전·미저장 판정이 같고, 성공 시 전체 변경이 한 번에 관찰되며
  한 번의 실행 취소로 복원되는지 확인한다. 관련 알림·입출력 경계를 변경했다면 확정 후 실패도
  재현해 확정된 문서 보존과 재시도의 중복 방지를 검사한다.
- 맵 기능을 추가할 때는 해당 변경과 관련된 아래 사례를 선택한다.
  - 비정형 영역과 내부 구멍, 경계 밖 입력, 지형 지우기와 영역 제거의 차이.
  - 스냅 모드/N 변경 후 기존 좌표 보존, 드래그 확정·취소, 실행 취소/다시 실행.
  - 참조 대상 삭제, 미완성 웨이브 진단, 저장 후 다시 열었을 때의 의미 보존.
  - 잘못된 파일 열기, 저장 실패, 저장 중 추가 편집 발생 시 현재 문서 보호.
  - 변경 없는 연산, 실행 취소 후 새 편집, 저장한 내용으로 돌아왔을 때의 미저장 표시.
  - 미확정 입력 중 선택·문서 전환, 삭제·복원 후 선택과 입력 버퍼의 유효성.
  - 요청 완료 순서 역전, 문서 교체 후 늦은 응답, 같은 파일에 대한 저장 중첩.
- 기대 결과는 요구 동작에서 정한다. 테스트 대상 함수를 다시 호출해 기대값을 만들거나,
  테스트 이름·fixture 값에 따라 제품 코드가 다르게 동작하게 하지 않는다.
- 비동기 순서와 실패 검사는 완료 시점·실패 지점을 제어해 재현한다. 실제 시간 지연에
  우연히 의존하지 않는다. 저장·열기 왕복 검사에서는 필드와 참조의 보존도 확인한다.
- 외부 입출력의 모의 구현은 명시적 테스트 경계에 둔다. 브라우저 검사가 네이티브
  파일 대화상자·Windows WebView2·IME까지 검증했다고 주장하지 않는다.
- UI를 변경했다면 재현 가능한 상태를 준비하고 실제 이미지를 열어 검토한다.
  테스트 성공이나 스크린샷 생성만으로 화면 품질 검토를 끝내지 않는다.
- 실패를 없애려고 단언 삭제, 테스트 비활성화, 무조건적인 기준 이미지 교체,
  임의의 대기 시간·재시도 증가를 하지 않는다. 계약과 실패 원인을 먼저 확인한다.

## 10. 변경을 마칠 때 확인한다

- [ ] 새 기능의 책임과 문서 원본이 한 곳에 있으며, 같은 규칙을 화면마다 복제하지 않았는가?
- [ ] 변경·취소·실패·실행 취소·저장이 같은 문서 의미를 유지하는가?
- [ ] 연관된 변경을 하나의 트랜잭션으로 확정하고, 확정 전 실패와 확정 후 알림·입출력 실패를 구분하는가?
- [ ] 문서 전환과 비동기 완료가 현재 편집·입력 버퍼·파일을 오래된 결과로 덮어쓰지 않는가?
- [ ] 미완성 상태와 잘못된 입력을 구분하며, 실패를 숨기거나 값을 몰래 보정하지 않는가?
- [ ] 아직 사용하지 않는 확장 계층, 임시 분기, 교체된 이전 경로를 남기지 않았는가?
- [ ] 관련 검사로 정상 동작과 중요한 실패 결과를 확인했는가?
- [ ] 변경 이유, 검사 결과, 남은 제한을 실제 확인한 범위대로 보고했는가?

체크리스트는 변경에 해당하는 항목에 적용한다. 사용자 결정이 필요한 기능 의미와
구현자가 판단할 수 있는 내부 기술 선택을 구분하고, 승인된 작업 범위의 기술 선택 때문에
매번 새 승인을 요구하지 않는다.

## 근거 문서와 적용 범위

- [Goal Execution Pipeline](<../../core_enhanced/docs/goal_execution_pipeline(1).md>)의
  **Implementation Quality Guardrails**: 중복 원본, 조용한 실패 은폐, 테스트 전용 제품 분기,
  미사용 추상화, 근거 없는 테스트·기준값 변경 금지 원칙을 가져왔다.
- [현재 런타임 아키텍처 심층 검토 기준](../../core_enhanced/docs/audit/current_runtime_architecture_deep_review_criteria.ko.md)의
  **A01~A03, A05~A08, A11**: 책임 경계, 단일 소유권, 의존 방향, 변경 용이성,
  테스트 가능성, 입출력과 저장 형식 분리 원칙을 제작기에 적용했다.
- [구현 단계 검토 요청 템플릿](../../core_enhanced/docs/templates/IMPLEMENTATION_CHECKPOINT_REQUEST.template.ko.md)의
  품질 가드레일과 내부 기술 선택 처리 원칙을 참고했다.

원문의 코어 전용 단계·감사 산출물·승인 절차 전체를 제작기에 도입하는 것은 아니다.
문서/화면 상태 분리, 편집 이력, 작성 중 진단, 좌표·영역 규칙은 위 원칙을 현재 제작기
요구사항에 적용해 구체화한 기준이다. 기능 범위가 바뀌면 관련 기준도 함께 갱신한다.
