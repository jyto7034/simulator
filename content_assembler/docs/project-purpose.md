# 콘텐츠 조립기의 목적과 범위

콘텐츠 조립기(`content_assembler`)는 우리 게임에 사용할 콘텐츠를 시각적으로 작성하고,
관련 데이터와 참조를 확인하며, 반복해서 수정·저장할 수 있게 하는 제작 도구다.
제작자가 콘텐츠의 구조와 의도를 화면에서 다루고, 그 결과를 게임에서 활용할 수 있는
데이터로 발전시키는 것이 목적이다.

이 문서는 프로젝트의 방향과 범위를 설명한다. 기능별 세부 명세나 구현 완료 목록은 아니다.
개발 기준은 [개발 지침](development-guidelines.md), 현재 구현 상태와 실행 방법은
[README](../README.md)를 따른다.

## 해결하려는 문제

게임 콘텐츠에는 수치뿐 아니라 공간 배치, 이동 경로, 등장 순서, 발동 조건과 대상 간
참조가 함께 들어간다. 이런 관계를 텍스트와 코드만으로 다루면 전체 모습을 파악하고
수정 결과를 확인하기 어렵다.

콘텐츠 조립기는 제작자가 다음 작업을 할 수 있게 하는 데 집중한다.

- 콘텐츠의 구조와 관계를 적합한 화면에서 보고 편집한다.
- 기본 속성과 세부 설정을 같은 작업 공간에서 확인한다.
- 수정 결과를 확인하고 실행 취소·다시 실행으로 여러 설계를 시도한다.
- 누락된 설정과 끊어진 참조를 찾아 고친다.
- 작성 중인 결과를 저장하고 다시 열어 작업을 이어간다.

화면을 보기 좋게 만드는 것과 함께, 작성한 데이터의 의미가 편집·검증·저장 과정에서
유지되는 것을 중요하게 본다.

## 전체 프로젝트의 대상

장기적으로 다룰 콘텐츠에는 맵, 스킬, 장비, 아이템, 유물, 보스가 포함된다.
맵 편집기는 이 제작 도구의 첫 기능이다. 다른 콘텐츠의 세부 편집 기능과 도입 순서는
실제 제작 요구에 맞춰 정한다.

콘텐츠마다 적합한 편집 방식을 선택한다. 공간 데이터에는 캔버스와 격자, 관계에는 노드,
시간에는 타임라인, 반복되는 수치에는 표, 세부 설정에는 속성 폼 등을 고려할 수 있다.
이들은 사용할 수 있는 수단이며, 모든 편집 방식을 반드시 구현한다는 뜻은 아니다.

공통 선택·속성 편집·저장 등의 경험은 일관되게 유지하되, 서로 다른 콘텐츠를 하나의
범용 편집 형식에 억지로 맞추지 않는다.

## 스킬 노드 그래프의 목표

### 현재 제작 범위 — 2026-10-21

일반 보스의 직원용 스킬 파편을 기준으로 조립기를 완성한다. 엘리트 파편도 작성 대상에 포함하되,
사용자의 후속 검토에 따른 조정을 수용한다. 현재 엘리트는 일반 보스의 공통 스킬 기능 범위에서
다루는 것을 기준으로 한다. 최종보스 파편은 사용자가 설계를 마친 뒤 별도 단계에서 추가한다.
최종보스용 전용 맵 전환이나 고유 연출 시스템을 현재 단계의 선행 구현으로 요구하지 않는다.

일반 보스와 엘리트의 합의된 스킬 동작을 제작 기준으로 사용하며, 콘텐츠 설계를 다시 시작하지 않는다.
기존 동작과 콘텐츠 정의의 조합·참조로 구현을 단순하게 유지한다. 연출의 복잡함을 그대로 게임 개체나
신규 시스템의 복잡함으로 옮기지 않는다. 실제 표현에 필요한 공통 기능부터 추가하며, 수치는
조정 가능한 매개변수로 둔다. 통상적인 게임 정책은 사용자의 2026-10-21 위임에 따라 작업자가 결정하고 근거를 원문에 남긴다.
기존 합의의 변경·충돌이나 플레이 방식에 큰 영향을 주어 사용자 판단이 필요한 부분만 확인한다.

### 표현과 실행의 목표

2026-10-20 사용자 합의: **우리 게임의 스킬을 노드 그래프로 완전히 표현하고,
그 의미를 지원하도록 Core를 수정한다.** 스킬 그래프는 합의된 게임 규칙을 구조화하고
Core 구현의 기준이 되는 콘텐츠 정의로 발전시킨다. 실제 실행 기능을 만들기 전에도
노드의 의미와 연결 계약은 명확하게 작성할 수 있어야 한다.

- 노드는 발생 사건, 입력·출력의 타입과 단위, 대상과 소유자, 조건, 효과, 수명,
  실패·취소·중복 처리 등 해당 동작에 필요한 의미를 명시한다.
- 실행 순서, 값 전달, 상태 정의에 대한 참조와 개별 활성에 대한 참조를 구분한다.
  스킬 이름이나 설명 문구를 읽어 구현자가 동작을 추측하게 두지 않는다.
- 스킬 고유 동작은 노드와 설정·연결로 표현한다. 복합 노드는 정의된 내부 구성이나
  계약을 확인할 수 있어야 하며, 이름 하나에 확인할 수 없는 규칙을 숨기지 않는다.
- 공통 피해 판정·대상 조회·시간 진행 등의 기반 기능은 명시된 계약을 가진 노드로
  사용한다. 완전한 표현은 기반 엔진의 모든 내부 처리를 각 스킬에 다시 펼친다는 뜻이 아니다.
- 기존 Core의 표현 한계는 차이와 변경 요구로 기록한다. 필요한 게임 규칙을 그래프에서
  생략하거나 다른 의미로 축소해 맞추지 않는다.
- 합의되지 않은 수치·정책은 미정으로 드러내고, 의미가 빠진 부분을 진단한다.
  현재 예제를 그릴 수 있다는 것만으로 스킬의 완전한 표현이나 Core 지원이 완료된 것으로 보지 않는다.

진행 순서는 콘텐츠 요구사항 확인 → 노드 의미 정의 → 스킬 그래프 작성과 정적 검증 →
Core 계약의 차이 확인과 수정 → 의미 일치 검증이다. Hello / Goodbye를 첫 상세 사례로 삼아
입력·상태·재입력·공격 교체·종료를 명확히 표현하고, 다른 스킬에도 적용해 표현 범위를 검토한다.
최종 제작·실행 흐름은 아래 합의를 따르며, 실행용 중간 표현의 구체적인 구조와 실행 방식은
이 과정에서 결정한다.
룰북·기존 작성 모델·로드맵을 노드 편집기에 연결한
[공통 스킬 그래프 계약](common-skill-graph-contract.md)을 따른다.
공통 정책과 개별 미정 사항을 구분하고, 최신 여러 파편으로 표현 범위를 대조한다.

2026-10-22의 P5–P8 실행 요청에 따라 그래프 의미·편집·컴파일·RON 로드와 Core 전투 실행을
연결했다. 작성 검사, 컴파일 성공, 실제 전투 검증은 구분하여 작업 파이프라인에 기록한다.
이 도구에 전투 플레이 화면이나 전체 장비 제작기를 추가했다는 뜻은 아니다.

### 최종 제작·실행 흐름

2026-10-20 후속 사용자 합의:
**스킬 노드 그래프 작성 → Core에서 그래프 탐색·의미 검증·컴파일 →
실행용 중간 표현(IR) 생성 → RON 저장 → 게임에서 로드·검증·실행**을 최종 목표로 한다.

- 편집 원본은 노드·연결·배치를 보존하여 다시 수정할 수 있게 저장한다.
  실행용 RON은 이 원본에서 생성하는 별도 산출물이다.
- 컴파일은 값 전달·실행 순서·조건·비용·효과·수명을 보존해야 한다.
  RON은 실행용 데이터를 저장하는 형식이며, 흐름의 의미는 IR과 Core가 정의한다.
- 미완성 그래프는 편집 원본으로 저장할 수 있다. 실행에 필요한 미정 값이나 미지원 동작은
  해당 노드·연결을 가리키는 컴파일 진단으로 알리고, 임의 값이나 다른 동작으로 대체하지 않는다.
- 지원하는 공통 노드를 조합한 스킬은 스킬별 Core 코드를 추가하지 않고 실행할 수 있게 한다.
  새로운 동작이 필요하면 공통 노드 계약과 Core 지원을 확장한다.

먼저 실행용 IR의 의미와 구조를 설계하고 이를 RON에 담는다. 그래프를 중첩된 트리로
억지로 바꾸지 않고, 값과 실행의 연결을 구분하여 표현한다.
세부 책임과 완료 기준은 [공통 스킬 그래프 계약](common-skill-graph-contract.md#그래프-컴파일과-ron-산출물)을 따른다.
현재 지원 범위의 노드 그래프는 Core 컴파일·IR·RON 출력·로드와 전투 실행에 연결되어 있다.
원본의 미정 값, 보류한 형태와 미지원 구성은 명시적으로 거절하며 임의의 실행값으로 채우지 않는다.

## 첫 작업 범위: 전투 맵 편집

먼저 구현할 대상은 전투가 일어나는 전장이다. 다음 요소를 함께 작성할 수 있게 한다.

| 대상        | 작성할 내용                                                         |
| ----------- | ------------------------------------------------------------------- |
| 기본 정보   | 맵 식별자, 이름, 설명, 크기 등                                      |
| 맵 형태     | 유효한 셀과 빈 공간, 비정형 외곽과 내부 구멍                        |
| 지형과 구역 | 지형·장애물, 배치 가능 구역과 적 등장 구역                          |
| 이동 경로   | 시작점·도착점·경유점, 기본 타일 중심 스냅과 고급 N×N 세부 격자 입력 |
| 웨이브      | 등장 구성, 수량·시점, 등장 구역과 경로 연결                         |
| 조건 웨이브 | 특정 조건에 따른 등장과 관련 설정                                   |
| 편집 지원   | 선택·수정, 실행 취소·다시 실행, 저장·열기, 작성 내용의 진단         |

화면은 캔버스를 중심으로 도구, 레이어, 속성, 웨이브와 진단을 함께 다루는 작업 공간을
지향한다. 맵을 보면서 관련 설정을 고칠 수 있고, 목록에서 선택한 대상과 캔버스의 대상이
서로 연결되어야 한다.

기본 경로 입력은 타일 중심을 기준으로 하고, 고급 모드에서는 타일 내부를 N×N 격자로
나누어 경유점을 지정한다. 구체적인 N 값과 입력 UI 등 세부 사항은 기능 설계에서 정한다.

현재 전투 맵 프로토타입은 구현되어 있다. 실제 완료 범위와 검증 상태는 README와 관련 검증 기록을 따른다.

## 게임 코어와의 관계

게임 코어는 아직 개발 중이며 명세가 달라질 수 있다. 코어의 완성을 기다리기보다
현재 결정할 수 있는 맵 조립, 경로, 배치 구역, 웨이브와 조건 웨이브의 작성부터 진행한다.

- 조립기는 콘텐츠 작성과 편집 상태를 담당하고, 코어는 게임 실행 규칙을 담당한다.
- 웨이브는 우선 편집기용 임시 데이터 구조로 작성한다. 현재 코어의 저장 형식과 즉시
  일치시키는 것을 초기 구현의 전제로 삼지 않는다.
- 기존 게임 문서와 코드는 기능 의미를 이해하는 근거로 활용한다. 편집기에서 참고한
  규칙과 실제로 코어에 연결되어 검증된 동작은 구분한다.
- 스킬은 위의 노드 그래프 목표에 따라 합의된 규칙을 먼저 충분히 표현하고, 그 의미를
  지원하도록 코어를 수정한다. 현재 코어의 문법과 기능이 스킬 표현 범위의 상한이 되지는 않는다.
- 코어 계약이 정리되고 연동이 작업 범위에 들어오면 변환과 검증을 구현한다.
  아직 필요한 계약이 없는 상태에서 미래 호환 계층을 미리 만들지 않는다.
- 편집기에서 저장할 수 있다는 것과 게임에서 실행할 수 있다는 것은 별도 상태다.
  미완성 콘텐츠는 진단을 남긴 채 작업을 이어갈 수 있어야 한다.

게임 실행·전투 시뮬레이션·최종 데이터 내보내기는 별도 연동 작업으로 다룬다.
전투 맵을 편집할 수 있다는 이유만으로 이러한 기능까지 구현된 것으로 취급하지 않는다.

## 제작 도구를 만드는 원칙

- **실제 제작 작업을 우선한다.** 콘텐츠를 작성하고 수정하는 데 필요한 기능부터 만든다.
  사용 목적이 없는 위젯이나 확장 구조를 채우는 것을 목표로 삼지 않는다.
- **검증된 도구를 활용한다.** 적합한 기존 UI·편집 라이브러리를 활용하고, 게임 고유의
  의미와 작업 방식에 필요한 부분을 직접 구현하거나 커스터마이징한다.
- **도입 근거를 확인한다.** 라이브러리는 유지보수, 실제 동작, 코드 품질과 사용 조건을
  확인한다. 소개나 외형만으로 검증되지 않은 프로젝트를 채택하지 않는다.
- **상업적 게임 제작에 사용할 수 있어야 한다.** 의존성과 가져온 코드의 라이선스,
  배포 조건과 필요한 고지를 도입 시 확인한다.
- **AI가 이어서 개발할 수 있는 구조를 유지한다.** 책임과 상태 소유권을 분명히 하고,
  변경 결과를 정적 검사·동작 검사·실제 화면 검토로 확인한다.
- **Windows 사용 환경을 기준으로 완성한다.** 배포 대상은 Windows 데스크톱이며,
  주 개발 환경은 WSL이다. 두 환경에서 확인한 범위를 구분한다.

현재 기술 기반은 Tauri, React, TypeScript, Vite와 Radix 기반 shadcn/ui다.
구체적인 코드 작성·상태 관리·실행 취소·저장·검증 규칙은
[개발 지침](development-guidelines.md)에 모은다.

## 목적을 달성했는지 판단하는 기준

첫 전투 맵 편집기의 가치는 제작자가 맵 형태와 구역을 구성하고, 경로와 웨이브를
연결한 뒤, 문제를 찾아 수정하고 저장한 결과를 다시 열어 작업할 수 있는지로 판단한다.

기능을 확장할 때도 같은 기준을 적용한다. 새 기능이 실제 콘텐츠 제작을 돕는지,
수정한 내용의 의미와 참조가 보존되는지, 오류와 미완성 상태를 이해할 수 있는지,
다른 기능을 불필요하게 복잡하게 만들지 않는지를 확인한다.

프로젝트의 목적이나 범위를 변경하면 이 문서도 함께 갱신한다. 개별 기능의 구현 상태는
목적과 구분하여 기록한다.
