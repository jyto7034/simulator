# AI 스킬 작성 형식의 검토 구현 검증 재감사 지침 — 임시

작성일: 2026-10-23

[설계 계획](ai-skill-authoring-plan.tmp.md)을 수행할 때 사용할 작업 지침이다.
요구사항과 현재 코드를 조사하고, 작성 모델을 설계·검토한 뒤 구현·검증하며,
결함이 발견되면 교정과 재감사로 닫는다. 각 단계의 완료는 해당 범위의 근거로 판단한다.
지침 작성 완료를 조사·제품 구현·실행 검증 완료로 해석하지 않는다.

2026-10-23 후속 목적 확장에 따라 [기능 정의·조합 목표](skill-authoring-core-goals.tmp.md)와
계획의 C0~C3에도 이 지침을 적용한다. 기존 1~3단계 결과는 재사용하고, 현재 요청은 C0의 목적·범위 구체화다.
단계 순서는 계획에서 관리하며 포맷 선택·Core 구현·전체 콘텐츠 전환의 완료를 미리 주장하지 않는다.

자율 작업의 시작·목표 점검·단계 전환·재개는 [하네스](skill-authoring-autonomy-harness.tmp.md)에서
이 지침과 연결한다. 실제 위임 범위와 시도·선택·발견·검증 근거는 [작업 기록](skill-authoring-worklog.tmp.md)에 둔다.
하네스는 별도 승인 절차를 추가하거나 이 지침의 검증·감사 요구를 대체하지 않는다.

## 1. 적용 기준과 요청 범위

### 1.1 이번 목표의 기준

[합의한 전제](ai-skill-authoring-premises.tmp.md)를 기준으로 다음을 유지한다.

- AI가 구조화된 텍스트로 작성하고, 사람이 생성된 그래프와 속성 패널에서 확인·수정한다.
  모든 수정 경로는 같은 작성 원본을 사용한다. 그래프 구조 편집은 후속 단계로 둔다.
- [현재 스킬 파편 목록](../../core_enhanced/docs/content/skills/README.md)에서 연결되는 최신 파편·장비·유물 문서를 읽는다.
  일반보스는 합의된 리워크, 엘리트는 현재 안대로 진행하되 추가 점검·변경 가능성이 있는 잠정안이다.
  이 구분은 2026-10-23 사용자 정정을 따른다. 최종보스는 확정 요구사항에서 제외하며 이관 전 보존 사본으로 최신 합의를 대체하지 않는다.
- Core는 미완성이다. 합의된 스킬 구조를 표현·실행하도록 개선하며,
  현재 구현에 맞추어 스킬 의미를 생략·축소하거나 기존 오류를 보존하지 않는다.
- Rust Core를 Unity에 네이티브 방식으로 연결한다. 연출의 세부 명세는 미정이지만,
  이펙트·사운드·애니메이션의 자원·사건·대상·수명을 연결할 기반을 마련한다.
- 미완성 원본 보존, 작성 중 컴파일 요청, 거부 원인 추적과 향후 미리보기를 함께 고려한다.
  실행 정보 부족을 임의 기본값이나 조용한 대체 동작으로 감추지 않는다.

게임의 기대 동작은 최신 사용자 합의와 지정된 콘텐츠·현행 게임 규칙에서 확인한다.
현재 소스와 실행 결과는 구현 사실의 근거다. 두 근거가 다르면 차이와 원인을 기록한다.
과거 계획·감사·테스트 기대값을 최신 합의보다 우선하거나, 미확인 코드 사실을 사용자 정책 질문으로 넘기지 않는다.

### 1.2 요청에 맞는 종료점

문서 작성 요청은 문서와 탐색 링크를 정리하는 작업이다. 조사·설계 요청에서는 해당 산출물을 만들고,
제품 구현은 그 범위가 요청되었을 때 수행한다. 구현·검증·재감사까지 위임받았다면 같은 범위에서
필요한 교정까지 이어간다. 단계가 바뀌었다는 이유만으로 재승인을 요구하지 않는다.

사용자가 지정한 검토 대기·중지 지점은 지킨다. 이미 정한 정책과 위임 범위로 해결할 수 있는 기술 선택은
실행자가 근거를 남겨 결정한다. 실제로 새 사용자 판단이 필요한 의미·범위 변경만 질문하고,
답변에 의존하지 않는 승인된 작업은 계속할 수 있다.

이 지침은 기존 지침의 원칙을 이번 목표에 맞게 선별한 것이다. 정식 P2G/GEX로 관리되는 작업에 적용할 때는
그 작업의 필수 인수·동결·감사 조건을 유지한다. 일반 문서·내부 변경에 전체 P2G/GEX 체계를 자동 추가하지 않는다.
특정 모델이나 서브에이전트 사용을 요구하지 않는다.

## 2. 시작과 재개 때 확인할 것

1. 현재 요청, 계획의 선택 단계, 대상 스킬·기능, 원하는 결과와 종료점을 확인한다.
2. 전제 문서와 현재 작업 기록에서 직접 선행 결과, 미정 사항, 미해결 결함과 다음 행동을 읽는다.
3. 관련 소스·데이터·테스트와 기존 사용자 변경을 대조한다. 이미 끝난 구현을 반복하거나
   무관한 dirty·untracked 파일을 되돌리지 않는다. 충돌 범위를 안전하게 구분할 수 없으면 해당 편집을 보류한다.
4. 검토·실행 대상의 상태를 식별한다. 관련 파일·버전·diff 또는 필요한 사본을 남기며,
   dirty 상태를 commit ID 하나로 표현하지 않는다. 복구 가능한 원본 보존과 해시 기록은 구분한다.
5. 이번 수용 조건과 확인 방법, 유효한 기존 증거, 필요한 새 검사·환경을 정한다.

전체 저장소와 모든 과거 로그를 매번 읽지 않는다. 마지막 유효 결과 이후의 변경과 판단 공백부터 확인한다.
조사할 코드에서는 입력 생산자 → 파싱·검증 → 컴파일 → 실행·상태 → 결과 소비자를 필요한 범위까지 추적한다.
그래프·속성 편집·저장·미리보기·Unity 전달이 관련되면 해당 소비자도 연결한다.
검색 결과나 타입 이름만으로 실제 사용 여부와 동작을 확정하지 않는다.

## 3. 계획 단계별 검토와 종료 기준

단계별 범위·산출물·완료 조건의 원본은 [설계 계획](ai-skill-authoring-plan.tmp.md)이다.
검토는 각 산출물의 준비 상태를 확인하는 활동이며, 단계마다 별도 승인 절차나 새 담당자를 요구하지 않는다.

기존 1~3단계 결과는 계획의 해당 절에서 확인한다. 이후 단계는
[C0](ai-skill-authoring-plan.tmp.md#c0-확장-목적범위성공-기준-구체화--진행-중)·
[C1](ai-skill-authoring-plan.tmp.md#c1-기능-정의-단위와-core-실행-계약)·
[C2](ai-skill-authoring-plan.tmp.md#c2-작은-범위의-컴파일core-실행-검증)·
[C3](ai-skill-authoring-plan.tmp.md#c3-서로-다른-스킬에서-정의조합재사용-검증)·
[4단계](ai-skill-authoring-plan.tmp.md#4-포맷과-편집-도구-비교선택--c3-이후)·
[5단계](ai-skill-authoring-plan.tmp.md#5-선택한-작성-포맷편집core-실행의-통합-검증)의 조건을 적용한다.

문서 단계는 의미 대조와 추적 근거로 검토할 수 있다. 아직 코드가 없는 구조 초안을 컴파일·실행 완료로 보고하지 않는다.
대표 사례에서 표현 불가능한 요구가 나오면 초안을 보완한다. 세 예시의 성공만으로 전체 스킬을 표현한다고 결론내리지 않고,
1단계의 전체 요구사항에 다시 대조하여 추가 사례와 남은 공백을 정한다.

단계 상태는 `미착수 / 진행 중 / 검토 준비 / 교정 필요 / 단계 완료 / 판단 대기`로 구분한다.
단계 완료, 컴파일 성공, Core 실행 검증, 사람의 UI 편집 검증, AI 사용성 검증,
Unity 실제 재생 검증과 전체 콘텐츠 전환은 별개의 완료 주장이다.

## 4. 설계 검토와 요구사항 추적

### 4.1 정책과 구현 선택을 구분한다

다음 세 가지를 구분해서 기록한다.

- 확정 의미: 합의된 스킬 동작과 제품 요구. 구현 편의로 바꾸지 않는다.
- 설계 선택: 작성 구조·포맷·변환 경계·데이터 전달 방식. 실제 근거와 대안을 비교하여 결정한다.
- 현재 구현 사실: 코드·데이터·실행에서 확인한 기능과 제약. 설계안이나 미완료 API를 실제 지원으로 표시하지 않는다.

미정 연출과 미확인 구현도 구분한다. 연출이 미정이라는 이유로 연결 기반을 빼지 않으며,
연결 기반이 필요하다는 이유로 개별 이펙트나 애니메이션을 임의 확정하지 않는다.

### 4.2 양방향으로 추적할 수 있게 한다

요구사항에는 안정적으로 구분할 수 있는 ID 또는 이름을 두고 다음 관계를 연결한다.

```text
스킬 원문·사용자 합의 → 요구사항 → 작성 데이터·공통 계약 → 컴파일·Core 경로 → 검증 근거
                                      ↕                         ↕
                              그래프·속성·진단 위치       실행 사건·연출 연결
```

요구사항에서 구현·검증을 찾을 수 있어야 하고, 실행 결과·진단·연출 연결에서도 원본 동작을 찾을 수 있어야 한다.
컴파일 중 동작이 합쳐지거나 분해되어도 이 관계를 잃지 않는다.
그래프 배치 변경이나 표시 이름 변경이 실행 의미·참조 정체성을 바꾸지 않도록 설계한다.

추적 정보는 요구사항 표와 설계·실행 기록의 해당 절에 둘 수 있다. 같은 사실을 여러 원본 문서에 복제하지 않는다.
아직 없는 구현·검증은 미구현·미검증으로 표시한다.

### 4.3 구현 준비 검토

제품 코드를 바꾸기 전에 선택 기능에 대해 다음을 설명할 수 있어야 한다.

- 실제 생산자·소비자와 입력·출력·오류, 적용 중인 타입·버전·단위.
- 원본 상태의 소유자·식별자·수명, 생성·변경·취소·종료와 오래된 참조의 처리.
- 조건·순서·값 평가 시점·원자성, 부분 실패 시 보존할 상태와 결과.
- 재사용·변경·제거할 경계, 함께 전환할 소비자와 유효한 중간 상태.
- 올바른 결과를 판단할 사례와 기대값, 필요한 조회·진단·시험 수단, 영향을 받는 기존 기능.
- 미정 사항과 그 결정 없이 진행할 수 있는 범위.

번호상 선행과 실제 의존성을 구분한다. 기능·스키마/저장·검증·함께 전환할 최소 범위·권장 순서 중
어떤 관계인지, 어느 소비자가 무엇을 요구하는지 확인한다. 같은 파일을 수정한다는 사실만으로 실행 의존성이 생기지 않는다.
선택 범위의 계약과 검증 수단을 기능 도입 때 준비하되 모든 후속 단계를 미리 상세 설계하지 않는다.
현재 경계의 필수 의미를 후속 단계로 미루지 않는다.

작은 변경에는 짧은 메모면 충분하다. 공유 계약·상태 수명·저장 형식 변경은 깊게 검토한다.
형식을 맞추기 위해 빈 인터페이스나 미래용 체계를 만들지 않는다. Unity 연출 기반처럼 이미 합의된 요구에는
최소 작성 예시와 실제 계약 검증 방법을 연결하되, 미래 소비자를 현재 구현으로 꾸미지 않는다.

## 5. 구현 원칙

하나의 관찰 가능한 기능이 입력에서 결과까지 완결되는 책임 단위로 구현한다.
파일 수나 코드 길이로 단계를 나누지 않는다. 다음 작업을 하지 않으면 현재 변경을 실행·검증할 수 없다면
최소 결합 범위를 함께 구현하거나, 실제로 유효한 중간 계약을 먼저 정한다.
미완성 전환을 통합 완료로 표시하지 않는다. 함께 바꿀 코드 범위와 실행 중 단일 트랜잭션 범위도 구분한다.

- 기존 동작·타입·검증·실행 기반이 의미에 맞으면 재사용한다. 현재 구조가 필요한 표현을 막으면
  문제·영향·개선 방향·검증 방법을 기록하고 해당 책임 경계를 개선한다.
  리팩토링은 확인한 결함·표현 제약·중복 책임·실측 비용에 연결하고 파일 길이나 분기 수만으로 착수하지 않는다.
  기능상 필수 개선·권장 개선·범위 밖 후속 작업을 구분하며, 문제 해소 뒤 무관한 정리를 계속하지 않는다.
  교체한 경로는 소비자를 확인해 정리하고 같은 상태의 최종 결정 주체를 중복해서 만들지 않는다.
- AI 편집과 속성 패널은 동일한 변경 경로를 사용한다. 변경 준비·검증·문서와 이력의 확정·알림 순서,
  Undo/Redo, 저장 상태와 비동기 결과의 기준 리비전을 일관되게 처리한다.
- 편집 원본, 그래프·진단 같은 파생값, 실행 데이터와 런타임 상태의 책임을 구분한다.
  Unity나 미리보기에서 스킬의 판정 규칙을 별도로 재추론하지 않는다.
- 미지원 동작·잘못된 참조·미정 정보를 조용히 생략·보정하거나 성공처럼 반환하지 않는다.
  허용된 미완성 원본의 저장과 실행 산출물 생성 조건을 구분한다.
- 생산자·소비자·스키마·설명·관련 테스트를 같은 의미로 맞춘다. 전환 중 경로가 필요하면
  원본의 소유자, 지원 범위, 전환·제거 조건과 검증을 기록한다.
- 테스트 이름·특정 fixture에 맞춘 제품 분기, 근거 없는 delay·재시도 증가,
  오류 무시, 실패 테스트 제거로 통과시키지 않는다.

구현 선택의 변경이 합의된 동작을 보존하면 근거를 남기고 진행한다.
게임 의미·호환성·데이터 손실·사용자 경험을 바꾸는 선택은 기존 결정과 위임 범위를 확인하고,
아직 정해지지 않은 사용자 판단을 기술 선택으로 숨기지 않는다.

## 6. 검증 설계와 실행

검증은 지원하는 작성·편집·컴파일·실행 경로와 그 경로에서 발생 가능한 오류를 중심으로 정한다.
작성자가 콘텐츠 파일을 직접 수정하는 행위도 지원 입력에 포함한다. 입력 오류·취소·수명 경계·I/O 실패 등
선택 계약의 필수 조건은 유지한다. 임의 메모리·저장 내부 변조에 대한 방어는 별도 요구가 없으면 자동 추가하지 않는다.
발견은 `지원 경로에서 발생 / 지원 경로 밖 변조에만 의존 / 발생 경로 미확인`으로 구분한다.
새로운 가능성만으로 무관한 필수 시험을 늘리지 않으며, 기존 필수 조건의 미확인이나 실제 실패는 제외하지 않는다.

### 6.1 기대값과 관측 지점을 먼저 정한다

요구사항·공통 계약·수작업 예제에서 기대값을 도출한다. 현재 구현의 알고리즘이나 helper를 테스트 안에 복제하지 않는다.
이전 실행과의 비교도 유효한 계약을 보존하는지 함께 확인한다. 기존 코드의 오류까지 정답으로 고정하지 않는다.

시나리오마다 초기 상태, 목표 동작까지의 입력 순서, 대상 자격·자원·시간 조건, 관측 지점과 기대 결과를 정한다.
부정 사례도 의도한 거절 지점에 도달해야 한다. 파싱 실패만 확인한 시험을 참조·수명 검증 성공으로 세지 않는다.
실행 준비 전략을 바꾸더라도 원래 확인하려던 경로와 성공 판정은 유지한다.
준비 fixture는 가능한 상태를 재현하는 수단이며 제품 정책의 근거가 아니다.
주요 행동 뒤에는 예상 상태·다음 행동의 자격을 확인하고, 진행기가 예상 밖 상태를 건너뛰어 실패를 숨기지 않게 한다.
반복·취소·복원 사례는 실제 계약별로 구분한다. 최초 실행으로 반복을, 자동 종료로 명시적 취소를,
같은 프로세스의 상태 재사용으로 새 프로세스 복원을 검증했다고 하지 않는다.

### 6.2 이번 목표의 검증 항목

각 작업은 아래 항목의 적용 여부와 이유를 기록한다. 단계에 맞는 깊이로 검증하며,
하나의 항목마다 별도 테스트 명령이나 새 문서를 만들 필요는 없다.

| 항목                 | 확인할 내용과 대표 사례                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------- |
| 스킬 의미 보존       | 원문의 조건·대상·순서·비용·계산·상태·종료를 빠짐없이 대조. 필요하면 대표 사례 추가                |
| 작성 중 보존과 진단  | 미정·미완성 원본 저장·재열기, 잘못된 타입·참조·미지원 동작의 구분, 원본 위치와 수정에 필요한 설명 |
| 그래프와 사람의 수정 | 원본→그래프 변환, 속성 변경→같은 원본 반영, 공유 값 영향, 계산식 보존, Undo/Redo·저장·재열기      |
| 오래된 비동기 결과   | 편집·문서 교체 후 이전 컴파일·진단·저장 결과가 최신 상태를 덮어쓰지 않음                          |
| 컴파일과 실행 연결   | 의미 보존, 산출물 로드, 실제 Core 경로 도달, 결과·진단에서 원본 동작 추적                         |
| 상태·수명·실패       | 재입력·반복·중복·같은 시각의 사건·취소·만료·사망·실패 후 상태를 관련 계약에 따라 확인             |
| 연출 기반            | 원본·실행 사건·개별 실행·연출 참조 연결, 대상·위치·수명과 종료 의미. 미정 값과 검증한 경계 명시   |
| 버전과 전환          | 원본·공통 계약·산출물의 버전 변화, 영향 진단·변환, 조용한 의미 변경이나 필드 유실 방지            |
| 실제 AI 작업         | 읽기·수치 수정·동작 추가·오류 수정의 의미 정확성, 무관한 변경, 재시도·입력 부담                   |
| 성능과 자원          | 필요한 경우 대표 규모에서 작성·컴파일·그래프 갱신·실행의 시간·메모리·증가·회수 특성 확인          |

연출 세부 명세·자원이 없는 단계에서는 확정된 연결 계약과 미정 상태 보존을 검증한다.
계약·headless 관측·모의 소비자 검증을 Unity 네이티브 연결이나 실제 연출 재생 완료로 보고하지 않는다.
미리보기 역시 계획, Core 실행 관측, 실제 화면 검증을 구분한다.

AI 비교 전에는 대상 모델, 제공할 문서·도구·입력, 과제·기대 결과, 허용 수정·재시도와 판정 기준을 정한다.
후보 포맷은 가능한 한 같은 조건으로 비교하고 차이를 기록한다. 모든 시도와 실패를 보존하며,
작성자의 자기 평가를 대상 AI의 실제 사용성 검증으로 대신하지 않는다.

성능·한도에 관련된 변경은 작업량 계수와 실제 경과 시간·메모리·회수 결과를 구분해 측정한다.
오프라인 컴파일과 실시간 실행, 개발 검사와 배포 환경의 한도를 혼동하지 않는다.
측정용 설정도 유한하게 두고 기록하며 실패를 통과시키려고 제품 한도를 자동으로 늘리지 않는다.

### 6.3 실행과 증거 관리

먼저 실제 package·target·feature·선택 조건과 fixture를 확인한다.
고비용 검사 전에는 작은 집중 검사나 유효한 기존 증거로 주요 가정과 목표 동작까지의 도달 가능성을 확인한다.
사전 실행 통과는 전체 시나리오 통과가 아니다. 입력·환경이 같은 검사는 공유 자원 충돌이 없는 범위에서 묶는다.
그 뒤 공유 계약과 소비자에 필요한 통합·회귀 검사로 넓힌다. 새 실패나 불확실한 영향이 있으면 범위를 확대한다.
합격한 입력을 아무 변화 없이 안심 목적으로 반복하지 않는다.

`content_assembler` 변경은 [AGENTS.md](../AGENTS.md)의 `npm run check`와 변경에 맞는 빌드·테스트를 따른다.
UI 변경은 [UI 검증 안내](ui-validation.md)에 따라 동작·스크린샷을 직접 확인한다.
Rust 변경은 현재 Cargo 구성과 실제 검증 대상을 확인하여 관련 테스트·필요한 빌드·정적 검사를 선택한다.
문서 작업에 제품 실행 검증을 했다고 표시하지 않으며, WSL 브라우저 검증을 Windows·Unity 검증으로 확대하지 않는다.

실행 중인 검사의 소스·데이터·테스트·fixture·설정은 고정한다. 관련 수정은 실행 종료·정리 후 수행한다.
장시간 검사는 예상 규모·시간·진행 확인 수단·한도를 정하고 기존 세션과 로그로 추적한다.
출력이 없다는 이유로 정지를 단정하거나 중복 실행하지 않는다. 이번 작업 소유의 프로세스만 관리한다.
중단·재실행 시 입력·명령·경과 시간·원시 결과·이유를 보존하고 종료·정리를 확인한 뒤 수정한다.
명령, 작업 경로, 입력·환경·도구 버전, 실제 실행 수, 종료 코드, 원시 결과와 실패·중단 이유를 남긴다.
0시험·skip·빌드만 성공·환경 실패·중단·결과 불명을 기능 통과로 기록하지 않는다.

기존 증거는 입력·관련 코드·설정·도구·환경이 같거나 변경이 해당 주장에 무영향임을 확인한 경우 재사용한다.
실행·재사용·비적용·미실행을 구분한다. 테스트 파일이 같아도 제품 코드·콘텐츠 입력이 바뀌면 영향받는 검증을 다시 한다.
문서 날짜나 검토 단계 변경만으로 전체 테스트·전체 해시·보관본 생성을 반복하지 않는다.
필수 검증을 재사용할 근거가 없으면 미검증으로 남기고 필요한 실행을 수행한다.

## 7. 완료 검토와 감사

구현·산출물 수정이 끝나면 대상과 증거를 식별하고, 별도 검토 활동으로 요구사항부터 다시 대조한다.
검토자는 구현자의 완료 요약을 결론으로 받아들이지 않는다.
문서 단계에서는 요구사항·표현·예시·미정 사항을, 구현 단계에서는 실제 경로·변경·실행 증거까지 확인한다.

감사 중에는 감사 대상을 수정하지 않는다. 읽기 전용 검사·격리된 관측·감사 기록 작성은 가능하다.
결함은 먼저 기록하고 교정 활동으로 분리한다. 감사 결과를 쓰는 문서와 감사 대상도 구분한다.
대상이 바뀌면 기존 판정의 범위와 새 변경을 기록하고 영향받는 항목을 다시 확인한다.

엘리트의 현재 안으로 수행한 검토는 최종 콘텐츠 합의의 완료를 뜻하지 않는다. 변경 시 해당 요구·예시·Core 경로의 영향을 다시 대조한다.

같은 실행자가 검토하면 자체 재검토라고 명시한다. 사용자나 적용 계약이 비참여 독립 감사를 요구하면
그 자격을 갖춘 별도 검토가 필요하며, 역할명만 바꾼 자기 검토로 대신하지 않는다.
이 지침은 단계마다 새 에이전트나 별도 승인 대기를 요구하지 않는다.

검토 항목은 다음 상태로 판정한다.

| 판정    | 의미                                                             |
| ------- | ---------------------------------------------------------------- |
| PASS    | 명시된 범위에 대해 현재 근거로 조건 충족을 확인함                |
| FAIL    | 요구 위반을 현재 입력·실행 또는 명확한 코드·데이터 경로로 증명함 |
| PARTIAL | 일부는 확인했지만 포함 범위의 경로·조건이 남음                   |
| UNKNOWN | 필요한 사실이나 증거가 부족함                                    |
| N/A     | 해당 단계·작업에 실제로 적용되지 않으며 이유가 있음              |

큰 파일, 많은 노드, 긴 문서, enum·분기 수 자체는 결함이 아니다.
실제 의미 누락·중복 소유·변경 부담·실패 결과를 제시해야 한다.
단순히 문제가 보이지 않았다는 이유로 PASS를 부여하거나 평균 점수로 필수 실패를 덮지 않는다.

전체 판정은 해당 범위의 `완료 / 미완료 / 판정 보류`와 근거로 기록한다.
모든 필수 조건이 충족되고 완료를 막는 미확인이 없어야 완료다.
요구사항·계획·예시 검토의 완료를 제품 전체의 완료로 표시하지 않는다.

## 8. 결함 교정과 재감사

### 8.1 발견 사항 기록

발견 사항은 ID, 대상 기준선, 관련 요구사항, 위치·경로, 기대 결과와 실제 결과,
재현·정적 증거, 영향과 확신도, 원인 또는 미확인 가정, 교정할 작업과 필요한 재검증을 남긴다.
같은 원인의 여러 증상은 묶고, 가설을 확정 결함 수에 넣지 않는다.

| 발견 유형                           | 처리                                                            |
| ----------------------------------- | --------------------------------------------------------------- |
| 원문·요구사항 누락 또는 충돌        | 요구사항 조사로 돌아가 적용 근거와 영향 범위를 보완             |
| 데이터 구조로 의미를 표현할 수 없음 | 구조 설계와 예시를 보완하고 관련 포맷·그래프·컴파일 가정 재검토 |
| 승인 의미 안의 구현 오류            | 책임 경계에서 교정하고 해당 실패·관련 회귀를 재검증             |
| fixture·기대값·검사 도구·환경 오류  | 제품 오류와 구분해 교정하고 원래 검증 목적을 유지한 채 재실행   |
| 후속 변경이 앞선 결과를 무효화      | 회귀를 만든 변경을 교정하고 영향받는 선행·후행 판정 복원        |
| 새 정책·범위 결정 필요              | 기존 결정·위임을 먼저 확인하고 남은 실제 사용자 판단만 요청     |
| 현재 목표와 무관한 개선 후보        | 근거와 후속 위치를 남기고 현재 완료 조건을 확대하지 않음        |

원인이 불명확하면 제품·시험·환경 중 하나로 성급히 확정하지 않는다.
실패 원본과 성공 판정의 의미를 보존하고, 새 가설·증거·교정 없이 같은 실행을 반복하지 않는다.
기대값·입력 규모·검증 강도를 낮춰 통과시키지 않는다. 전제 오류가 확인되면 같은 가정을 공유하는 사례도 점검한다.

### 8.2 교정에서 재감사까지

1. 실패한 판정과 원시 근거를 보존하고, 실제 원인과 수정 책임을 찾는다.
2. 바꿀 범위와 영향을 받는 요구사항·소비자·검증·기존 판정을 식별한다.
3. 승인 범위에서 교정한다. 범위나 의미가 달라져야 하면 필요한 설계·정책 판단부터 해결한다.
4. 원래 실패 사례와 영향을 받는 회귀를 실행한다. 무관한 유효 근거는 이유를 적고 재사용한다.
5. 수정이 끝난 대상을 다시 식별하고 별도 재감사에서 원래 결함의 해소와 새 회귀를 확인한다.
6. 현재 판정·잔여 항목·다음 행동을 갱신한다. 과거 실패·감사를 성공으로 덮어쓰지 않는다.

재감사는 모든 명령의 재실행과 같지 않다. 새 검토에서는 기존 증거가 현재 대상에도 유효한지 판단하고,
부족하거나 영향받은 부분을 다시 검증한다.

| 변경                          | 다시 확인할 범위                                                       |
| ----------------------------- | ---------------------------------------------------------------------- |
| 문구·탐색 링크만 변경         | 의미 변경 여부와 링크·서식. 제품 입력이 같으면 실행 근거 재사용        |
| 작성 의미·참조·타입 변경      | 영향받는 전체 스킬 요구, 예시·진단·그래프·컴파일·실행·연출 연결        |
| 파서·컴파일러·Core 변경       | 관련 실제 작성 입력, 거부 진단, 실행 결과·수명·추적과 공유 소비자 회귀 |
| 속성 패널·편집·저장 변경      | 같은 원본 반영, 공유 참조·Undo/Redo·저장·오래된 결과, 관련 UI          |
| 연출 전달 계약 변경           | 사건·실행 식별·대상·수명·미정 처리와 실제로 존재하는 소비자            |
| 테스트·fixture·판정 도구 변경 | 원래 검증 목적과 기대값 근거, 영향을 받는 실행·판정                    |
| 후보 포맷·AI 문서·도구 변경   | 관련 AI 과제와 부분 수정·진단 비교. 이전 결과의 적용 범위 재평가       |

공유 경계의 영향을 분리할 수 없으면 검증 범위를 넓힌다. 판정이 무효화된 선행 조건에 의존하는 작업을
완료로 처리하지 않되, 승인된 회귀 교정 자체를 실패한 선행 판정 때문에 막지 않는다.
교정 후 실제 의존 순서대로 필요한 판정을 복원한다. 무관한 후속 작업 전체를 자동 재감사하지 않는다.

## 9. 최소 기록과 인계

계획·현재 위치, 시도 이력, 현재 판단, 검토 결과의 역할을 구분한다.
작은 작업은 한 문서의 절로 모아도 된다. 기존 실행 기록이 있으면 연결하고,
같은 해시·로그·테스트 건수를 여러 문서에서 독립적으로 복제하지 않는다.
고정된 감사 대상과 그 감사 기록은 분리한다.

작업 시작·의미 있는 실패·설계 변경·검증 완료·인계 시점에 필요한 부분을 갱신한다.
모든 파일 읽기를 일기처럼 남기거나 종료 때 기억으로 실패 기록을 재구성하지 않는다.

```text
요청 범위와 종료점 / 선택 단계·스킬·기능:
적용 요구사항·사용자 결정 / 미정 사항:
현재 대상·관련 변경 / 보존한 사용자 변경:
설계 선택과 이유 / 실제 생산자·소비자:
수용 조건별 근거: 실행·재사용·N/A·미실행 구분
시도와 실패·교정: 명령·입력·환경·결과·원시 근거
검토 결과 / 미해결 발견과 영향받는 판정:
완료한 범위 / 남은 필수 작업 / 다음 행동:
```

최종 보고에는 바뀐 동작이나 산출물, 검증 결과, 남은 필수 미검증과 관련 경로를 간결히 남긴다.
설계 계획의 5단계 완료는 선택한 범위의 작성·편집·실행 통합 검증이며 전체 콘텐츠 지원을 뜻하지 않는다.
전체 목표 완료에는 전체 일반보스·엘리트 요구사항과 실제 작성·편집·실행·연출 기반의
선언된 수용 조건을 각각 연결해야 한다. 아직 범위가 확정되지 않은 후속 기능은 완료 주장에서 구분한다.
